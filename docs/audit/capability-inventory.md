# 能力清单（S1 · 能力考古）

> 镜头：**用户能做什么**。判断依据只有仓库代码（`packages/**` 的 src 与 test）——路由注册、action 实现、组件与页面、测试与调用点；一个概念只出现在文档里不算能力。
> 证据一律 `文件:行号`，可逐条复核。实现程度只有三档：**端到端可用** / **部分可用（写清缺口）** / **桩或不可达**。
> 分类标签写在能力名末尾：〔平台级·咨询内容类〕= 领域专家往里填咨询内容的能力；〔平台级·功能类〕= 产品/工程向的功能；〔引擎级〕= 引擎内核在会话中真实生效的机制。
> **⚠️ 2026-09-29 数字订正（独立验收发现）**：`SessionManager` 在 `CLAUDE.md` 的引用数是 **7 处**，本文件两处写作 9，已改。订正依据见 [`mess-disposition.md`](mess-disposition.md) E-04 行。

## 三、能力缺口（代码里明确没有的东西）

- **意识层 / 议程运行时 / 信息点**：代码里没有对应模块、没有数据表、没有端口，只在文档措辞中出现。
- **面向来访者的咨询界面**：只有编辑器里的调试对话面板（`DebugChatPanel`），没有最终用户产品页；`POST /api/chat` 只有接口没有客户端。
- **登录与权限**：没有 `users` 表、没有任何鉴权插件或钩子；`userId` 是请求体里的自由字符串（`api-server/src/routes/sessions.ts:14`）。
- **脚本的导入 / 导出 / AI 生成**：编辑器里没有入口（内置的 `POST /api/scripts/import` 只服务于调试启动流程）；"AI 帮我写脚本"不存在。
- **图形化流程画布**：`reactflow`、`zustand` 写在 `script-editor/package.json` 里，全仓零引用；编排只有树 + 表单。
- **文件的删除与重命名**：API 有（`script-editor/src/api/projects.ts:196`），界面没有入口。
- **脚本的删除**：`ScriptRepository` 只有 create / update / listAll，没有 delete（`api-server/src/services/script-repository.ts`）。
- **咨询产出物（报告、文书、量表结果）生成**：没有任何 action 类型或模板落点承载"这次咨询产出什么文件"。
- **`use_skill` / `show_form` 动作**：JSON Schema 已备（`core-engine/src/adapters/inbound/script-schema/actions/use-skill.schema.json`），实现类不存在。

### 4.3 在 CAP-16/CAP-10 上发现的两个缺陷（读码所得，未实跑复现）

> **⚠ 2026-09-28 缺陷① 的因果链已被 S1' 调试簇推翻并重写**（初审推错了机制，缺陷本身仍成立）。推翻有三条证据，已逐条复核：①回填守卫是 `snapshots[key].messageCount === undefined`（`session-repository.ts:461`）；②引擎在 `script-executor.ts:1006` **无条件**写该字段；③写入（commit `565c448`，2026-05-11）早于回填（`b38d9a0`，2026-05-17），且无任何代码删除该字段。⇒ **回填在正常路径永不触发**，`session-orchestrator.ts:600` 的 `??` 链永远取第一个分支。

**缺陷 ①（重写后）：错标消息。** 生效的 `messageCount` 就是 `script-executor.ts:1006` 写的 `executionState.conversationHistory.length`——**活跃消息数**（来源是 `loadConversationHistory` 里那层 superseded 过滤，`session-repository.ts:186-188`）。但它被 `flagSupersededMessages` 当作**全表排序行号**消费：查询不过滤 superseded（`session-repository.ts:413-417`），随后 `slice(fromMessageIndex)`（`:421`）。

**偏差量 = 快照创建时全表已有的 superseded 行数。** 所以触发条件比初审说的窄：首次重跑、以及"重跑同一个 action"都恰好正确；**只有「快照创建于已有 superseded 行之后、其后又被当作重跑目标」时才错**——最常见的一条链是「先回退到靠前的 action → 后续 action 的快照被 `session-orchestrator.ts:591-597` 丢弃后重建 → 再回退到那个 action」。

最坏后果：**全表 superseded、活跃对话历史归零**——AI 拿着空上下文重新开场，界面气泡消失，而默认日志级别下**完全无痕**（只有 `logger.debug`，`session-repository.ts:441`）。

**根因表述**：写值方（引擎）用活跃语义，前端消费者也用活跃语义（`DebugChatPanel:1463-1467`、`separatorUtils.ts:24-35`，这两处是**对的**）——只有后端消费者把它读成了全表语义。

**并且这与一份封板文档相矛盾**：`docs/design/memory/memory-framework.md:340`（`status: decision-recorded`）明写「`flagSupersededMessages(position)` 按 action 位置精确废弃消息」，而代码形参是 `fromMessageIndex`、传入的是消息计数。按 CLAUDE.md 约定 3，这属于"实现或新证据与封板文档矛盾"，需修订其一。

**缺陷 ②：分支只在调试记录上成立，执行状态不分支。** `rerunAction` 把 `actionSnapshots` 截断到分叉点（`session-orchestrator.ts:591-597`）后就地覆盖，`sessions.current_run_id` 只留最新一个（`db/schema.ts:65`）。所以 `debug_entries` 里旧分支的记录**留着**，但**回不去继续跑**——只能对照着看，不能切回去接着执行。这是能力的天花板，不一定是缺陷，但必须写进能力描述，否则"分支"一词会被误读成 git 式的分支。

### 4.4 本节未覆盖的面（留给 S1'）

- **组件面**：编辑器页面/组件清单未做"每个组件是否归属某能力"的自检。
- **测试面**：`core-engine/test/` 与各包 `__tests__/` 未做同样的归属自检——那里可能还藏着已实现但没被当能力的东西。
- 4.3 两条为**静态读码结论**，未经运行复现；S1' 深挖 CAP-10/16 时应以实跑确认或推翻。**→ 已由 `deep-dive-debugging.md` 处理：缺陷①因果链被推翻并重写（见 §4.3 更正块），缺陷②成立。约束②禁止实跑，故仍为静态结论。**

## 七、编排产物到运行时没有一级通路（本轮最要紧的一条）

> 由 `deep-dive-authoring.md` 发现（此前五份报告都没抓到）。**编者按：该报告的原始措辞"两表之间没有任何代码相连"说重了**——经复核确有一条通路，但它**按字符串名连接**（见下），且不承载主脚本。核心判断成立，措辞按本节为准。

**编辑器写 `script_files`，运行时读 `scripts`。** 运行时侧的入口是 `routes/sessions.ts:80` → `session-orchestrator.ts:112`（读 `script.scriptContent`，来源 `loadScriptById`）。

**两表之间确有一条通路，但它是隐式的**：`session-repository.ts:215-217` 用 `script_files.fileName == scripts.scriptName` 做**字符串等值连接**（无外键、无约束），取该 `projectId` 后读其 `global` 文件——**只用于 `global.yaml` 变量定义与用户级全局变量**（`:207-290`）。主脚本内容不经过它。

**唯一把编辑器内容送进 `scripts` 的通路是 `POST /api/scripts/import`**（`routes/scripts.ts:171-172`），而该路由**自述原文**是「导入YAML脚本内容到数据库（**用于调试**）」。项目 ↔ 会话的关联则靠脚本文本里的 tag（`tags:['debug','project:'+projectId]`，`:266,281` → `routes/sessions.ts:86-89`）。

**连带确认**：`sessions.version_id` 与 `version_snapshot` 两列（`db/schema.ts:72-73`，后者还带索引 `:83`）**零读者零写者**——`versionSnapshot` 全仓只有 `schema.ts:73` 这一处声明。⇒ **「发布版本」不产生可运行脚本。**

**为什么这条最要紧**：它决定了 CAP-01 的 story 怎么切。**「写脚本」（CAP-11/12）与「跑咨询」（CAP-01/03）目前不构成一条链**——中间只有一条调试专用、且靠字符串匹配的窄路。任何把 CAP-01 当作"已完成能力"来验收的做法都会撞在这里。

**附一条同源问题**：编辑器 `package.json:14-28`**未声明** `@heartrule/core-engine`，却有 4 处 import（含值导入 `validation-service.ts:11`），靠 pnpm 根提升解析——phantom dependency，即 3007 kB 前端包与 `__vite-browser-external` 告警的来源。文档说编辑器「仅依赖 shared-types + REST」（`strategic-design.md:329,334`），实际把上游实现打进了下游包。
