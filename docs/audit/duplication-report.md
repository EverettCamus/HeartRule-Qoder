# 重复与名实检测报告（Duplication & Name-vs-Reality）

> 审计波次 2 · S4。只读编目，未改动任何代码与既有文档。
> 主依赖：`docs/audit/domain-ledger.md`（领域设计分布）、`docs/audit/mess-map.md`（混乱地图）、`docs/audit/capability-inventory.md`（能力清单）。
> 口径：每条给出**两侧 `file:line`**；"活的是哪侧"以 `packages/*/src` 与 `packages/*/test` 的 grep 调用点为准（**不含 `dist/` 构建产物**）；差异性质二分为**抄错/抄漏**（同一份东西被复制后未同步）与**演化分叉**（同一职责先后长出两套，各自都对过当时的需求）。

## 总述

同一件事被定义两次以上的实例，本报告记 **27 对**，分布在五类：双实现 7、同概念多名 5、同名多实 5（其中 3 条是纯文档侧）、文档重复 5（另有一条实测为"无重复"，见四-5）、层级重复 5（其中 3 条与双实现/同名多实是同一对的两面，已交叉标注）。

**主因不是"抄错"，而是三次编号重构各留一半**：Phase 2（`ActionFactory`）、Phase 3（`MonitorTemplateService`）、Phase 5（`MonitorOrchestrator`）都是"新增一层、旧路径不动"。Phase 2 的旧路径注释里明白写着保留意图——`application/actions/action-factory.ts:62`（"回退到硬编码（向后兼容）"）与 `:78`（"Fallback to createAction"）——结果是新旧两条创建通道并存（见一-4）；Phase 3/5 抽出新层（`application/monitors/ai-ask-monitor-handler.ts:6,26` 与 `application/orchestrators/monitor-orchestrator.ts:4` 的"Extracted from ScriptExecutor"），但被抽取的模板解析逻辑在 `application/monitors/monitor-template-resolver.ts` 里又抄了一遍引擎版（见一-3）。第二个主因是**同一份契约有代码和文档两个作者**：DSL 字段名（`exit` / `exit_criteria` / `exit_condition`）、核心引擎清单、限界上下文成员表，都在代码与文档之间各写各的。第三个主因是**抽象先写、真需求后到**：`VariableExtractor`（`engines/variable-extraction/extractor.ts:25`）与 `topic-decision-v2`（`shared-types/src/domain/topic-decision-v2.ts:153`）都是在真实用法出现前写的抽象，后来真逻辑落在别处，抽象成死码但没删，文档却仍指向它们。

**最要紧的一条**：DSL 两套不只是"两份定义"，而是**引擎的 JSON Schema 会拒绝引擎自己能跑的脚本** —— `scripts/sessions/test_ai_say_basic.yaml:33-37` 用了 `require_acknowledgment` 与 `exit_criteria`，而 `ai-say.schema.json:30` 的 `additionalProperties: false` 不允许这两个字段，同一字段在编辑器里又叫 `exit_condition`（`YamlService.ts:341`）。这是名实不符 + 双实现叠加后的实际后果。
