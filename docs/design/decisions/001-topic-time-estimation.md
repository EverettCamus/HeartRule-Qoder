# 001 — 话题时间预估策略

## 背景

议程中的每个话题需要 `estimatedDuration`，供意识层在时间压力下做取舍决策（挑哪个话题、放弃哪个话题）。这个值从哪来？是强制咨询师为每个话题预估时间，还是交给系统？

经过心理咨询、法律顾问、战略咨询、营养咨询四个领域的交叉讨论，确认了一个事实：**咨询师对有些话题可以预估时间，对另一些话题不能。**

- 刚性话题（如法律"确认委托范围"、营养"评估饮食结构"）流程固定，时间可预估。
- 弹性话题（如心理咨询"收集主诉"）时间取决于来访者情绪状态、表达能力、话题敏感度——同一话题，不同来访者差四倍。
- 同一话题在初次会谈和第五次会谈的耗时也不同。
- 但意识层做取舍决策的时间精度要求不高——知道 A 话题比 B 话题长就够了，不要求精确到分钟。误差 30-50% 不影响决策。

## 决策

**咨询师只声明阶段级时间和刚性话题的可选预估。弹性话题的时间由系统从历史数据中学习。**

具体规则：

1. **阶段级时间由咨询师声明**。每个 Phase 的 `plannedDuration`（或占总时间的比例），以及关键阶段（如"结束收尾"）的 `minDuration`。

2. **话题分刚性/弹性**。脚本中可声明 `duration_type: rigid` 并填写 `estimatedDuration`，或声明 `duration_type: flexible` 并可选填写 `minDuration`（这个话题至少要多久）。未声明类型时，弹性为默认。

3. **系统学习补充**。引擎记录每次会谈每个话题的实际耗时。弹性话题在积累数据后自动生成 `estimatedDuration`。学习结果可按来访者维度存储——同一话题对不同来访者耗时不同。

4. **时间是相对排序工具，不是精确计时器**。意识层用 `estimatedDuration` 比较长短、判断"剩多少时间大约够跑几个"，不做分钟级精确调度。

5. **阶段的时间保障优先于话题级预估**。`minDuration` 是第一优先级——收尾阶段必须留够时间。所有话题级预估都必须让位于阶段级保障。

6. **总时长和阶段比例在脚本层声明**。引擎不内置"心理咨询是 50 分钟"这类假设。

## 考虑过的替代方案

- **方案 A**：强制咨询师为每个话题填写 `estimatedDuration`。  
  驳回理由：弹性话题的时间咨询师也无法预估。强制填写导致虚假精度——看起来有计划，实际上不准。

- **方案 B**：不提供时间管理能力，由意识层完全自由判断。  
  驳回理由：意识层需要数据输入做决策。没有时间预估，取舍就是盲猜。脚本声明的是咨询师的意图（"这个阶段大概占 30% 时间"），是意识层判断的重要参考。

- **方案 C**：AI 在首次会谈开始时实时预估每个话题的时间。  
  驳回理由：没有历史数据的首次预估和猜没有区别。不如给默认值，让系统在几场会谈后学到真实值。

## 后果

- 实现上需要在议程执行完成后回写每个话题的实际耗时（`actualDuration`），作为系统学习的训练数据。
- 学习模型不需要复杂——移动平均或加权平均即可，几场会谈后收敛到可用精度。
- `duration_type`、`minDuration` 等字段需要加入话题的 YAML Schema。
- 不同咨询领域的时间参数差异较大（心理咨询 50 分钟 vs 战略咨询 90-120 分钟），引擎不做假设，参数由脚本声明。
