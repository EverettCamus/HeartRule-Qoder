# 007 — 变量职责收缩：跨会话状态唯一权威为信息点文档，全局变量取消

## 背景

现行记忆框架（memory-framework.md §2.1/§2.3、variable-memory-bridge.md）给变量系统分配了跨会话职责，2026-09-09 设计讨论暴露四类问题：

1. **同一信息存三处**：跨会话事实同时存在于 `user_global_variables` 表、Hindsight 会谈记忆、临床文档。全局变量中过期的语义结论（如"核心信念"）与记忆中的动态判断（observation refine / mental model 重写）必然漂移——bridge 文档 §1 自己指认了这个问题。
2. **变量类型混杂**：全局变量既有操作参数（咨询师名、session_count），也有语义结论（核心信念、主要压力源）——后者本质是记忆/文档的衍生品，不该独立存储。
3. **双路径刷新复杂**：bridge 的"同步 piggyback + 异步 recall 择优覆盖"为变量刷新引入了最复杂的合并策略（比较 proofCount / 新鲜度 / is_stale），而它保护的正是一个不该存在的第三处存储。
4. **人类无修正面**：AI 对用户的跨会话理解错了（如核心信念），人类咨询师没有编辑 Hindsight 记忆的界面——错误只能靠下次对话自我纠正。

## 决策

### 决策 1：变量收缩为会话内操作参数，不做类型声明

**结论**：变量职责两条——(a) 将用户具体信息代入提示词模板（模板实例化），(b) 驱动脚本流程分支。变量在本会话内收集、本会话内演化，默认不跨会话。变量值以文本流入 LLM 与条件求值，**映射层不要求类型声明**（数值比较由条件求值器按操作符语义转换，咨询工程师无感；现有 ai_ask 提取时的类型转换机制保持不变）。

**理由**：变量是"脚本与具体个案之间的锚点"，生命周期与会话执行一致；跨会话职责移交信息点文档（决策 2）。无类型降低咨询工程师编写负担——变量的最终消费者是 LLM，文本即够用。

### 决策 2：信息点文档（Info-Point Document）是跨会话状态的唯一权威，全局变量取消

**结论**：取消变量 global 作用域与 `user_global_variables` 表。所有跨会话状态写入**信息点文档**：文档 = 格式区 + 数据区，数据区的每个命名信息点即一个跨会话值的唯一存放处。实例不限于临床文档——会谈笔记、用户表单、未来的引擎状态文档共用同一机制（"临床文档本质就是全局的"）。**文档具体形态不在本 ADR 封板**：笔记型候选 markdown+frontmatter、表单型候选 HTML 模板+JSON 实例，语法与渲染细节后续另行设计，此处只固定"数据区信息点可结构化解析"这一约束（决策 4 的前提）。

**全局层为何不留**：若保留 global 变量层，跨会话值同时可走全局变量与信息点文档两条路，使用者必然混淆；直接取消，只留文档一条路。

**待设计（备注）**：同一信息点可能需要被多份文档引用——一处权威、多处引用同步更新。引用关系与同步机制不在本 ADR 展开，以探索项挂账（见后果·遗留跟进）。

**理由**：人类可读、可编辑、版本化可审计——给人类咨询师一个修正 AI 理解的控制面（改文档 = 改下次会谈的理解）；与真实咨询实践同构（咨询师跨会话状态就是会谈笔记）；分支驱动的跨会话值走精确键读而非概率召回，符合三决策区（Must Determine 用确定性机制）。

### 决策 3：脚本声明映射，引擎统一管理读写时机

**结论**：脚本 variables 声明新增三个可选字段，最小映射写法：

```yaml
variables:
  - name: 治疗阶段 # 默认：读默认笔记文档的同名信息点，只读
  - name: 核心信念
    doc: 会谈笔记 # 信息点所在文档模板（默认文档时可省）
    info: 核心信念结论 # 信息点与变量不同名时声明（同名可省）
    write: true # 显式授权会话末写回（默认只读）
  - name: 情绪触发场景 # 无映射 → 纯会话内变量
```

有映射才存在装载与写回；无映射的变量纯会话内。**读写时机由引擎统一约定，脚本不写时序逻辑**：

```
会话启动（首个 action 前）:  同步装载全部映射变量（DB 直读，无 LLM）
用户提交表单（ai_fill）:     即时写回生成文档新版本 + retain 汇入会谈记忆（沿用双重存储）
                            表单文档写入者 = 用户；变量对表单文档只读
会话正常结束:                写回全部 write:true 映射变量 + 生成笔记正文（笔记文档写入者 = AI）
会话中 piggyback:            只刷新内存值，永不触文档
```

**理由**：默认同名只读 + 显式 write 把咨询工程师的负担压到最小（多数变量零声明开销）；读写时机是引擎机制而非领域知识，落在代码侧符合代码-vs-脚本边界；表单即时写回保护用户提交的数据不因会话异常中断而丢失。

### 决策 4：会话启动装载是机制，带 fallback 链

**结论**：装载（hydrate）是机制不是便利：必须在执行前同步完成、无 LLM 参与。信息点缺失时走固定 fallback 链：`文档信息点 → Hindsight recall 兜底 → 脚本声明默认值 → 变量未定义（分支走 default 路径）`。

**理由**：首个 action 的分支就可能依赖跨会话值（`condition: 治疗阶段 == '评估期'`）；若把装载当便利，缺失时的行为未定义——脚本要么出错要么静默走错分支。无 LLM 保证启动快速且结果确定。此决策倒逼信息点数据区结构化可解析，不可依赖 LLM 提取。

### 决策 5：版本与人类编辑规则

**结论**：文档版本化，每版本记 provenance（`ai` / `human` / `user`）。装载读最新版本；AI 写回基于最新版本生成新版本，不覆盖。写回前比对：本会话开始时读到的信息点值 ≠ 最新版本当前值（会话期间被人类改过）→ 该信息点跳过写回并提示。

**理由**："创建后不篡改"与写回以版本语义共存；人类编辑优先落实"人类咨询师掌控"；一条比对规则替代逐字段编辑锁。

### 决策 6：会谈记忆角色收缩——取消异步 recall 覆盖变量

**结论**：bridge 的"同步 piggyback + 异步 recall 择优覆盖"双路径取消异步侧。Hindsight 保留三个角色：(a) `{{memory_context}}` 语义上下文注入（不变）；(b) 装载 fallback 兜底（决策 4）；(c) 会话末生成笔记正文时的素材来源（以 recall/reflect 辅助笔记生成，降低漏写概率）。

**理由**：合并策略（比较 proofCount / 新鲜度 / is_stale）是 bridge 中最复杂的部分，其保护对象（全局变量副本）随决策 2 消失；recall 兜底防止笔记有损生成导致事实永久丢失；变量刷新只剩会话内 piggyback，机制显著简化。

## 后果

- **正面**：跨会话状态三处存储收敛为一处权威；变量作用域四层变三层（topic → phase → session）；bridge 双路径与合并策略删除；人类获得修正控制面；分支值确定性键读；派生值免存（session_count = 文档版本数）。
- **成本**：迁移成本——global.yaml、`user_global_variables` 表、四层解析器、存量脚本全局声明（独立 [feature] 故事）；会话异常中断丢失未写回值（AI 提取类可接受，表单类由即时写回保护）；装载机制要求信息点区结构化，约束了文档形态自由度（具体形态留扩展）。
- **红线修订**：architecture-constraints.md **B3 变量作用域四层**改为三层（删除 global 层）——已获人确认。
- **遗留跟进**：[design] 故事修订 memory-framework.md §2.1/§2.3/§7 与 variable-memory-bridge.md（autoRefresh 矩阵重画、双路径收缩、迁移策略替换）；[feature] 故事全局变量取消迁移；智能设计议题区探索项——咨询方案（§2.4）是否改为信息点文档形态替代 `treatment_plans` 表、文档形态语法细化、信息点跨文档引用关系（决策 2 备注）。
