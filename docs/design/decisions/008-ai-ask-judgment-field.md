# 008 — ai_ask 判定字段：判定并入生成，三档输出契约

## 背景

`ai-ask-memory-recall.md` 要回答「ai_ask 这一轮要不要查会谈记忆」，三处问题逼出这个决策：

1. **检索词只有主线模型写得出来**：「那件事」指什么、「你上次说的那句话」要引哪段既往——这些只有看得见最近对话的模型知道。规则路径只能拼出"原话 + 变量名"，写不出"这一轮缺什么"。
2. **单起一道判定会拖慢每一轮**：判定若单独起一次 LLM 调用，用户等回复的路上每轮都多压一次完整生成——而大多数轮根本不需要查记忆。
3. **分工没有契约**：判定结果要和模板那份输出 JSON 共存、还要能被引擎稳定读出来；判错了往哪边倒，也需要一句纪律。

2026-09-23 ~ 09-29 用 21 案例集 × 10 发（生产参数）迭代判定段提示词，v6b 读数：`none` + `block` 档 157/160 = 98.1%（线 ≥144）、漏查 0、误查 3。

## 决策

### 决策 1：判定并入生成，不新增 LLM 调用

**结论**：判断者是**主线 AI 自己**。它在生成这一轮回复的**同一次生成**里，输出的**开头**先给判定字段，其余字段照常跟在后面；引擎读到、摘掉，据此决定这一轮怎么走——判定字段不给用户看。不新增 LLM 调用、不新增往返。

**理由**：并进生成，判定只是主线这次生成开头多写的几十个 token——不需要查的轮（大多数）只有一次调用。真需要两次生成的只剩判 `block` 的少数轮（收笔 → 查一次 → 重新生成）。输入账同向：两次调用要把内容大半相同的 prompt（原话、最近对话、变量）预填两遍，并进只预填一遍。这笔账押在「大多数轮不需要查记忆」上，实证路径挂 backlog（见后果·未验证）。

### 决策 2：三档输出契约

**结论**：`recall` 三档——

| 档      | 这一轮怎么走                                             |
| ------- | -------------------------------------------------------- |
| `none`  | 不查，直接回复                                           |
| `defer` | 先回复（不含任何对未知信息的预设），同时查一次，下轮带上 |
| `block` | 这次生成到此收笔 → 查一次 → 记忆注入后重新生成           |

四字段按此顺序排在模板那份 JSON 的最前：`reason` → `recall` → `entities` → `query`。**字段名与三档取值由代码写死**——模板改了字段名即解析失败、按 `block` 兜底；解析**从宽**（空格、大小写、多余字段都算合法）。

**理由**：顺序是设计的一部分——串行生成里先写的 token 影响后面，`reason` 排最前是要它先把「缺什么」想清楚再落判定与检索词；`entities` 排在 `query` 前是先把专名交代出去，检索词才好写这一轮要问的那一面。两处判据（① 这一轮有没有钩子 ② 钩子不许猜——把这一轮想说的那句话试写出来、看它带不带那个东西）写在提示词里，全文见 [ai-ask-memory-recall.md](../memory/ai-ask-memory-recall.md) §2。

### 决策 3：档位只以「最近对话 + 已收集变量」为据（2026-09-27 裁定）

**结论**：档位**只以「最近对话 + 已收集变量」为据**。prompt 里另外那几段（背景记忆、收集前回顾的预取上下文、实体备忘、往年洞察）**改不了档位**——它们只用于判断这一轮缺什么、要向记忆要哪一面。一句话：**档位看窗口，面可以看全。** 模型把记忆段当依据用、据此把 `block` / `defer` 改成 `none` 的，记「依据越界」，与档位判错分开记。

**理由**：档位问的是「只靠已知够不够」，而已知就是主线看得见的那两份。把记忆段算进来，等于让"查过的东西"证明"不用查"——该查的轮会被判成 `none`，而漏查是三种错里唯一不自愈的。

### 决策 4：调用侧四条——宁可多查

**结论**：

1. **头部缓冲**：判定字段读出来之前，输出不发给用户。
2. **判 `block` 就收笔**：提示词要求「判 `block` 时写完这四个字段就停」，这次生成自然结束——引擎不必去学"掐断流"；模型不听、继续往下写也照旧丢弃，第 1 条保证用户看不到。
3. **只重新生成一次**：第二次生成时提示词注明「记忆已注入，直接作答，判定字段给 `none`」；**每个用户输入最多查一次**（硬限，防打转）。
4. **判不出来就按 `block` 兜底**：仍读不出判定字段，弃掉这次生成，按固定拼法查一次、重新生成。不为此再起一次 LLM 调用。

拿不准时倾向查：多查的代价是慢一轮，猜错的代价是不实的回复，两个方向不对等。

**理由**：这套判法的失败倾向只有一条——模型会顺着往下写、不会停下来；猜错了没有回头路（写到一半才需要「李光是谁」，开头的 `none` 已经写出去了）。收笔由模型自己执行、由头部缓冲兜底，就不必去碰各家中止语义不一的"掐断流"。

### 决策 5：收集前回顾不进判定段——代码拼词、零 LLM

**结论**：进话题时（该话题第一个动作执行前），静态解析本话题内全部 ai_ask 的 `output` 变量、取当前值为空的，**代码直接拼检索词 → recall → 注入本话题首问**，每话题最多 1 次。这一处没有用户原话，**不判三档**。

**理由**：判定字段存在的理由是「信息不对称」——有些判断只有模型做得来（所指在最近对话里还是不在）。这一处不存在不对称：变量名和话题名都在代码手里，代码不比模型少知道什么；让它判一次等于白花一次生成。

**与 006 的关系**：本决策保留 006 决策 3 在**无原话场景**下的原样（查询构造走规则、零 LLM）。006 决策 3 中「快通道查询构造全程走规则」的措辞，指有原话可挖的两处（指代 / 反问）时，由**决策 1** 局部取代——其本意「不新增 LLM 调用、不占 ≤200ms 往返」在决策 1 下依然成立：判定并入主线那次生成，不新增调用。006 决策 2（单路查询默认、三路扩展待实证默认关闭）不受本 ADR 影响。

## 后果

- **正面**：ai_ask 快通道从「会话启动查一次、查询硬编码」变成「该查的轮才查、检索词来自这一轮缺什么」；判定不新增 LLM 调用，兑现 Sprint 目标「不额外调用 AI」；三档给出可执行的失败纪律（宁可多查）；与 006（检索层范围）、007（变量权威在信息点文档）无冲突。
- **红线修订**：`architecture-constraints.md` **D6** 由「快通道检索零 LLM：查询构造走规则」改为「**快通道不新增 LLM 调用**」（检索词由并进生成的判定字段产出；收集前回顾由代码拼词）——已获人确认（2026-09-29）。
- **未验证**（押在这上面的账，尚无读数）：①「大多数轮不需要查记忆」——决策 1 的性能账全押在它上；② `reason` 前置是否真提升检索词质量（是推断，不是实测）；③ `§3.4` / `§3.5` 的 `defer` 行与 `§3.6` 无三档结论系按判据推出，随实现观测；④ 实体备忘的数据地基（附 C.6 四处待实证）。
- **遗留跟进**：**实现未开工**——判定四字段与三档在代码、shared-types、模板、测试里零落脚（`ai-ask-memory-recall.md` 附 C.7 十一行差距），判定段文本也尚未装进 Default 层模板。实现故事：backlog [intelligence] ai_ask 快通道实现 · [feature] recall 取回接线与实证。
