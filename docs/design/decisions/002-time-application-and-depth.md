# 002 — 时间预估的用途与深度切换

## 背景

在确定了话题时间预估策略（见 [001](./001-topic-time-estimation.md)）之后，需要明确这些时间数据在系统中具体用在什么地方，以及深度切换（quick / standard / deep）与时间压力之间的关系。

经过了心理咨询、法律顾问、战略咨询、营养咨询四个领域的交叉讨论。

## 决策

### 一、时间预估的五个用途

| 场景             | 机制                                                                             | 触发条件                                 |
| ---------------- | -------------------------------------------------------------------------------- | ---------------------------------------- |
| **取舍**         | 剩余时间 vs 后续话题预估总和 → 选择执行哪些、取消哪些                            | 阶段剩余时间不足以覆盖所有 pending 话题  |
| **节奏微调**     | 当前话题实际耗时 vs 预估 → 轻量提示词注入，提醒 AI 收束                          | 实际超预估 50% 以上                      |
| **异常检测**     | 当前话题实际耗时 vs 该来访者历史均值 → 若显著偏离，向上报告信号                  | 偏差超过来访者常规波动范围               |
| **跨会谈学习**   | 历史耗时按来访者×话题维度存储 → 下次会谈准备时自动调整预估                       | 每次会谈结束后更新                       |
| **阶段边界决策** | 阶段剩余时间 vs 后续阶段 `minDuration` → 触发结构干预（取消/深度切换/carryover） | 阶段剩余时间无法覆盖后续阶段最低时间保障 |

**不用的地方**：不做分钟级精确调度、不做硬截断（到点就停）、不做前台实时计时显示。时间是参谋，不是军令。

### 二、两级压力，分级响应

时间判断分两个层级，互不混淆，按更严重的那个行动：

| 层级       | 判断什么                              | 触发动作                                |
| ---------- | ------------------------------------- | --------------------------------------- |
| **话题级** | 当前话题实际耗时 vs 预估              | 提示词注入（"请收束"），属于节奏微调    |
| **阶段级** | 当前阶段实际耗时 vs `plannedDuration` | 深度切换、取消、carryover，属于结构干预 |

话题级管"当前这个怎么收"，阶段级管"整个阶段还能塞多少"。例：

```
阶段"咨询评估" plannedDuration=20min, 当前第 18 分钟
话题 A(active): 预估 8min, 实际已 14min → 话题级压力：超 75%
阶段 pending: B(预估 6min), C(预估 5min)

阶段剩余 2min → B 和 C 都跑不完
→ 话题级：A 注入"1-2 轮内收束"
→ 阶段级：B cancel(carryover), C cancel(时间不够)
```

### 三、深度切换的作用范围

深度切换（`setDepth`）对不同类型的条目行为一致（减轮数、跳过 Think、加速提示词、调整预估时长），但**作用范围不同**：

| 作用范围            | 适用场景                                  | 影响                                                                     |
| ------------------- | ----------------------------------------- | ------------------------------------------------------------------------ |
| `current_remaining` | 当前 active 话题已超时，需要加速剩余部分  | 只影响剩余动作。已执行的不重跑。剩余 Ask 减 `max_rounds`，跳过剩余 Think |
| `all_pending`       | 阶段时间不够，后续话题整体降速            | 所有 pending 条目从开始就按 quick 执行                                   |
| `full`              | 脚本预设——咨询师声明某话题默认为 quick 版 | 同 all_pending，但意图来自脚本而非意识层                                 |

**触发优先级**：先阶段级判断 → 若阶段级压力触发 `setDepth('quick', all_pending)` → 当前话题若也超时，叠加 `setDepth('quick', current_remaining)`。两种范围可以同时生效。

### 四、异常检测

话题耗时不仅是执行参数，也是**信号源**。同一来访者、同一话题的历史耗时是稳定的基线。当本次实际耗时显著偏离历史均值时，这不是时间管理问题，是来访者状态问题——可能发生了重要的事，可能情绪状态不同，可能阻抗或回避。这个信号上报意识层，由意识层判断是否需要干预，而非由时间管理模块直接行动。

## 后果

- `setDepth` 的实现需要接受 `scope` 参数（`current_remaining` / `all_pending` / `full`）。
- 阶段级和话题级的时间压力需要独立计算，由意识层汇总后选择更严重的行动。
- 异常检测需要按来访者×话题维度维护历史耗时基线，初始几场会谈数据不足时不触发。
- 跨会谈学习需要每次会谈结束后回写话题的实际耗时，用于下次会谈准备的预估调整。
