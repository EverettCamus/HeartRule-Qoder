## 1. 设计目标与原则

### 1.1 两方涉众与 AI 的双重角色

AI 咨询引擎的记忆系统服务于两类**人**，而 AI 在其中扮演**双重角色**:

```
┌──────────────────────────────────────────────────────────────┐
│                 两类涉众 (人)                                  │
│                                                              │
│  ┌─────────────────────────┐    ┌─────────────────────────┐  │
│  │  人类咨询师 (老师傅)       │    │  来访者                  │  │
│  │  "把我的咨询之道传给AI，   │    │  "我需要被理解、         │  │
│  │   让徒弟按套路走"          │    │   被记住、被认真对待"     │  │
│  │                          │    │                         │  │
│  │  通过脚本 + 知识库         │    │  通过 AI 咨询师          │  │
│  │  传承咨询之道              │    │  获得服务                │  │
│  └────────────┬─────────────┘    └────────────┬────────────┘  │
│               │                               │               │
│               │  传承经验 (脚本/知识库)          │  咨询互动      │
│               ▼                               ▼               │
│  ┌──────────────────────────────────────────────────────────┐ │
│  │                   AI 咨询师 (徒弟/数字分身)                │ │
│  │                                                         │ │
│  │   · 应用咨询经验技术 — 循师傅之道 (人类咨询师可掌控)      │ │
│  │    话题选择与控制    · 节奏与流程分支                      │ │
│  │    变量收集与使用    · 知识引用的准确性                    │ │
│  │                                                         │ │
│  │   · 理解来访者个案 — 现场应变 (AI 自主构建)                │ │
│  │    记住来访者说过什么  · 理解经历脉络                      │ │
│  │    觉察变化与矛盾      · 调整治疗策略  · 形成临床文档      │ │
│  └──────────────────────────────────────────────────────────┘ │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

---

**涉众 1: 人类咨询师 (老师傅) —— 用脚本和知识库传承咨询之道**

人类咨询师将咨询经验、三观和专业判断沉淀为脚本和知识库，AI 作为徒弟/数字分身继承这套"道":

- **变量 (操作锚点)**: 脚本是抽象经验套路，变量是脚本与具体个案之间的"锚点" —— `{情绪问题} = "焦虑"` 决定了走 CBT 焦虑分支还是抑郁分支；`{session_count}` 控制着第几次会谈启用哪种技术。
- **领域知识库 (专业表达边界)**: 当 AI 向来访者解释概念时（"什么是自动化思维"、"为什么要做暴露练习"），引用的必须是师傅所在流派的专业定义，而非 LLM 训练数据中混杂的任意解释。

人类咨询师对 AI 的掌控是**间接的** —— 他们不直接操作每次对话，而是通过 YAML 脚本和知识库为 AI 划定行为边界。随着 AI 引擎变得更简单易用，人类咨询师能更直接地将经验以脚本形式沉淀下来。

**对应记忆类型**: 1. 脚本变量 + 5. 领域知识库

---

**涉众 2: 来访者 —— 需要被理解、被记住**

来访者的诉求很简单：AI 应该像一个真正的咨询师那样对待自己。这要求 AI 拥有:

- **记住** 来访者说过什么 —— 不是回放原始对话，而是有组织地记忆和按需检索
- **理解** 来访者的经历脉络 —— 不同会谈中提到的碎片拼成连贯的叙事
- **觉察** 来访者讲述中的变化与矛盾 —— 不是为了"揭穿"，而是作为临床洞察的线索
- **规划** 基于不断加深的理解调整治疗策略 —— 同一个 CBT 脚本，在不同来访者身上产生不同的干预重点
- **记录** 形成可读、可存档的临床文档 —— 让来访者感知"被认真对待"

这些能力不由人类咨询师直接指定，而是 **AI 自主构建**的 —— 人类咨询师只能通过调整提取提示词间接影响记忆的维度，但记忆的内容、组织、演化由 AI 自行完成。

**对应记忆类型**: 2. 会谈记忆 + 4. 咨询方案 + 3. 临床文档

---

**AI 的双重角色与掌控边界:**

```
角色                              谁掌控                    靠什么记忆实现
───────────────────────────────────────────────────────────────────────────────
角色 A: 应用咨询经验技术             人类咨询师 (师傅) 可掌控    1. 脚本变量 + 5. 领域知识库
                                                            3. 临床文档 (模板)
                                                              ↑ 格式由人类咨询师预设

角色 B: 理解来访者个案               AI 咨询师 (徒弟) 现场应变  2. 会谈记忆 + 4. 咨询方案
                                                            3. 临床文档 (内容)
                                                              ↑ 内容由 AI 根据模板填充
```

注意 **3. 临床文档** 横跨两个角色：人类咨询师定义**文档格式**（模板、字段、量表结构）—— 这是应用咨询经验技术的一部分；AI 自主生成**文档内容**（会谈总结、进展评估、临床判断）—— 这依赖 AI 理解个案和现场应变的能力。复杂场景下，AI 也可以根据实际需要自行设计文档结构，但默认由人类咨询师预设模板。人类咨询师对 AI 的掌控是**间接的** —— 通过 YAML 变量声明和知识库条目划定边界，通过文档模板规范产出格式；但边界内的内容、组织、判断由 AI 自行完成。

两者的关系: 应用咨询经验技术为理解来访者个案提供了**流程框架**（当前话题、当前阶段、该收集什么）和**产出格式**（会谈笔记模板、量表模板），AI 在此基础上运用**自主记忆能力**完成对来访者的深度理解并填充内容。师傅的经验告诉 AI "做什么、输出什么格式"，AI 现场应变决定 "怎么理解这个人、具体写什么"。

### 1.2 设计原则

1. **存储时保留认知类别** —— 一条信息在 retain 时就要标记它属于哪类认知产物：用户以事实声明方式给出的（诊断、用药、人口学信息）、用户以叙事方式讲述的（经历、事件）、AI 推断出的判断、以及跨信息综合形成的观察。不在存储环节把不同类别的信息合并——合并意味着丢失认知来源，无法在 recall 时区分"这是用户说过的事实"和"这是 AI 据此做出的推断"。

2. **保真度与时间距离成反比** —— 越靠近当前的对话，保留越高的原文保真度；越远，越可压缩为结构化摘要。不是"全部保留或全部压缩"的二元选择，而是 round → action → topic 逐级衰减：同一 action 最近 N 轮保留原话，同 topic 前面 action 压缩为摘要，更早 topic 只剩关键结论。当信息的时间距离远到压缩保真度不够用时，recall() 的语义检索比低质量压缩更有效。

3. **推论与证据可互查** —— AI 基于记忆做出的任何判断（Opinion、DeepInsight、从记忆派生的变量值），都能反向追溯到支撑它的原始记忆片段。反过来，从任意一条原始记忆，能查到它参与了哪些推论的生成。不出现"这个判断从哪来的"回答不了的情况。

## 2. 五种记忆类型

> **"记忆"在此处是广义用法**。这五种"记忆"本质上是对 AI 咨询引擎需要持有、累积和调用的不同类别信息的完整枚举。这里应澄清各自的职责定位，建立一套协作的规范，人类咨询师避免混乱，其中：
>
> - **会谈记忆** 最接近狭义的"记忆"——跨会话积累的、动态演化的认知
> - **临床文档**和**咨询方案**是记忆的延伸产物——前者是记忆的显式投射（制品快照），后者是基于记忆形成的意图
> - **领域知识库**是"需要时翻书查阅"的外部参考，而非 AI 自己的记忆，但它同样是系统必须持有并检索的信息
> - **脚本变量**比较特殊——它是被持久化的关键信息片段，但其用途是驱动咨询流程控制而非理解来访者
>
> 将它们统称为"记忆"是因为它们共享一个核心特征：**跨会话持久化，并在适当的时机被检索和使用**。

```
┌──────────────────────────────────────────────────────────────────┐
│                    HeartRule 记忆体系                              │
│                                                                  │
│  ┌──────────────┐ ┌──────────────┐ ┌─────────────────────────┐   │
│  │ 1.脚本变量    │ │ 2.会谈记忆   │ │ 3.临床文档              │   │
│  │ 流程控制      │ │ 认知血肉     │ │ 制品快照                │   │
│  │              │ │              │ │                        │   │
│  │ 消费者:      │ │ 消费者:      │ │ 消费者:                │   │
│  │  脚本引擎    │ │  LLM上下文   │ │  用户 + 人类咨询师     │   │
│  │ 作用:        │ │ 作用:        │ │ 作用:                  │   │
│  │  分支/跳转   │ │  理解/策略   │ │  展示/存档/临床记录    │   │
│  └──────────────┘ └──────────────┘ └─────────────────────────┘   │
│                                                                  │
│  ┌──────────────────────┐ ┌─────────────────────────────────┐    │
│  │ 4.咨询方案            │ │ 5.领域知识库                     │    │
│  │ 行动意图              │ │ 声明性专业基础                    │    │
│  │                      │ │                                 │    │
│  │ 消费者:              │ │ 消费者:                         │    │
│  │  AI策略 + 脚本引擎   │ │  LLM生成回复时检索               │    │
│  │ 作用:                │ │ 作用:                           │    │
│  │  规划干预/调整节奏   │ │  概念解释/鉴别/引经据典          │    │
│  └──────────────────────┘ └─────────────────────────────────┘    │
│                                                                  │
│  [+ 关系记忆: 跨类型散布, 主要承载于 2 和 4 中]                    │
└──────────────────────────────────────────────────────────────────┘
```

### 2.1 脚本变量 (Script Variables) —— 流程控制

**本质**: 脚本用来做分支判断、流程控制和内容替换的关键信息。脚本是通用的咨询套路，变量是让它落在具体用户身上的参数——脚本作者声明"这个信息我需要"，引擎通过 ai_ask 或 ai_think 显式提取并设置。

**当前状态**: 已实现。

| 维度         | 说明                                                                 |
| ------------ | -------------------------------------------------------------------- |
| **消费者**   | 脚本引擎 (条件判断、分支跳转、`{{变量}}` 占位符替换)                 |
| **作用**     | 决定咨询流程走向 —— CBT 焦虑分支还是抑郁分支？当前阶段适用哪种技术？ |
| **查询方式** | 精确键名查找，4 层作用域 (topic → phase → session → global)          |
| **更新频率** | 由 ai_ask 在对话中收集；或由 ai_think 从会谈记忆中调用               |
| **谁定义**   | 人类咨询师在 YAML 的 `output` / `var` 中声明                         |
| **存储**     | `VariableStore` 分层内存 + `user_global_variables` 表                |

#### 2.1.1 变量的双重来源

变量不是孤立存在的，它的值有两个来源：

```
变量来源 1: 对话中直接提取 (现有机制, 保留)
  ai_ask 中的 extractionMethod: direct / pattern / llm
  → 从用户单次回复中提取值
  → 适用: 单次即可收集的信息 (如"你最近感觉怎么样")

变量来源 2: 从会谈记忆中调用 (新增机制)
  ai_think 在需要时从会谈记忆查询
  → 用户可能跨多次对话提到同一个信息
  → 例如: ai_think 调用 recall("用户的核心信念")
          → 返回: "我不够好 (信心: 0.78, 首次出现: 第2次会谈)"
          → 填充变量 {核心信念} = "我不够好"
```

**这解决了什么**: 变量不再需要反复向用户收集同一个信息。AI 已经在之前的会谈中知道了，就应该直接从记忆中调取。只有记忆中没有、或信心过低、或需要更新时，才主动向用户提问。

#### 2.1.2 变量承载的三类内容

```
操作参数 (脚本需要):              进程控制 (跨回合计数):        全局事实 (跨会话):
  {情绪问题} = "焦虑"               {current_round} = 3          {用户名} = "张伟"
  {核心信念} = "我不够好"           {max_rounds} = 5             {年龄} = 34
  {治疗阶段} = "中期"               {topic_completed} = true     {诊断} = "GAD"

  ↑ 多数来源于会谈记忆               ↑ 会话内计数器                 ↑ 来源于会谈记忆或
    通过 ai_think 调用               部分需跨会话时存全局变量         入诊表单填写的客观事实
```

#### 2.1.3 职责边界

```
变量该存 (脚本流程控制需要):        变量不该存 (应交由会谈记忆):
  {情绪问题} = "焦虑"                用户描述焦虑的完整叙事和情绪细节
  {核心信念} = "我不够好"            信念形成的童年经历详情
  {年龄} = "四十岁出头"              年龄相关的具体描述和背景
  {PHQ-9得分} = 15                   得分变化的趋势和临床意义分析
  {session_count} = 5                第1-3次会谈的具体内容和进展
```

变量存的是脚本执行需要的关键信息——被显式提取并固化的结论。不要求精确（"四十岁出头"可能比"42"更贴近用户的真实表达），但要求**有意的提取**：每个变量值都是脚本作者声明"这个信息我需要"后，通过 ai_ask 或 ai_think 显式设置的结果。语义级的理解、叙事细节、推论过程由会谈记忆承载，变量在需要时从中提取结论。

### 2.2 会谈记忆 (Conversational Memory) —— 认知血肉

**本质**: AI 咨询师对来访者逐步积累的、跨会话的深度理解。是整个记忆体系的核心新增能力。

**当前状态**: 未实现。当前仅通过 `messages` 表存储单会话对话历史，缺少跨会话的语义检索和组织。

| 维度         | 说明                                                                                                                                                          |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **消费者**   | LLM (注入提示词作为上下文)、ai_think (为变量提供值来源)、AI 策略反思 (影响咨询节奏和策略选择)                                                                 |
| **作用**     | 让第 N 次会谈的 AI 咨询师"知道"前 N-1 次会谈发生了什么，让用户不重复讲述                                                                                      |
| **查询方式** | 语义搜索 + 图谱遍历 + 时间过滤                                                                                                                                |
| **更新频率** | 每个 Action 结束后 retain（提取该 Action 完整对话的结构化记忆）；Session 结束时 reflect（综合 Observation + 更新 Opinion 信心）；临床文档填写后也 retain 汇入 |
| **谁定义**   | AI 自动提取和组织，人类咨询师通过提取提示词影响提取维度                                                                                                       |
| **存储**     | 向量嵌入 + 知识图谱 + 元数据存储 (具体实现见第 4 节)                                                                                                          |

#### 2.2.1 会谈记忆需要解决的问题

**A. 跨会话事实的记忆与检索**

用户在第 2 次会谈中说了一件事，第 6 次会谈中 AI 还需要知道。不是简单地回放对话历史（token 成本太高），而是有组织地记忆和按需检索。

```
示例:
  用户 (第2次): "我妈从小就对我期望特别高，考了99分都要问我那一分去哪了"

  → 记忆提取:
    [World] 母亲对用户有高标准要求
    [Entity] "母亲" — 高期望型教养方式
    [Time] 覆盖用户的整个童年

  → 第6次会谈:
    用户: "我觉得自己永远不够好"
    AI recall("用户的完美主义倾向来源")
    → 返回: 记忆片段 → AI 可以自然地回应:
    "你之前提到过母亲对你有很高的期望..."
```

**B. 事实、经历与判断的认知分离**

咨询中需要区分三类非常不同的信息：

- **客观事实**: "用户被诊断为 GAD"、"用户服用舍曲林 50mg/天" —— 相对稳定，来自诊断或用户陈述
- **用户的经历**: "第 3 次会谈中用户详细描述了被领导当众批评的那次经历" —— 用户的第一人称叙述
- **咨询师的判断**: "用户的核心焦虑与'不被认可'的深层信念有关 (信心: 0.78)" —— 这是咨询师的**工作假设**，需要随着更多证据出现而更新

当前所有信息混在对话历史和变量中，缺少这种认知清晰度。

**C. 事实间的关联与多跳推理**

记忆不是孤岛。用户提到的不同事情之间存在内在联系：

```
"母亲高期望" ──因果──→ "完美主义倾向" ──因果──→ "工作焦虑"
     │                                              │
     └──实体── "母亲" ──实体──────────────────────────┘
                 │
                 └──时间──→ "用户报告母亲的态度在第 5 次会谈后有变化"
```

当 AI 需要理解"用户的社交回避与什么有关"时，不是找一个关键词匹配，而是沿着实体边、因果边、时间边进行多跳发现。

**D. 观点的动态演化**

咨询师的判断不是一成不变的。随着会谈深入，有些判断应该增强信心，有些应该被质疑或修正：

```
第2次会谈后:
  观点: "焦虑主要来源于工作压力" (信心: 0.70)

第4次会谈:
  用户详细描述了社交场合中的恐慌 → 观点信心下调: 0.55

第5次会谈:
  用户进一步说明社交焦虑是在工作中被领导批评后才开始的
  → 观点更新: "焦虑根源于工作关系中的权力不对等, 泛化到社交场合" (信心: 0.72)
```

**E. 叙事连贯性与矛盾发现**

用户可能跨多次会谈讲述同一个事件，每次补充新的细节。记忆系统需要：

- 将同一事件的不同描述连接起来（叙事版本追踪）
- 当存在明显不一致时标记出来（但不是作为"揭穿"，而是作为临床洞察）

```
第2次: "我和母亲关系一直很好"
第8次: (在描述童年时) "...那时候每天放学都不想回家，怕看到我妈的脸色"

→ 不视为矛盾，而是: 用户对"关系好"的定义可能需要深入探索
→ 新观点: "用户可能在'关系好'和'母亲的真实态度'之间存在认知失调 (信心: 0.45)"
```

#### 2.2.2 近期工作记忆与长期结构记忆的分工

会谈记忆存在两种不同时间尺度的需求，它们通过不同机制解决：

```
同一会话内 (近期工作记忆)               跨会话 (长期结构记忆)
─────────────────────────            ─────────────────────────
{{chat}} 占位符                      recall() 语义检索
messages 表原始对话                   Hindsight 四网络
保留最近 N 轮完整消息                  提取 + 组织 + 图谱关联
时间窗口: 本次会话                     时间窗口: 全部历史
查询方式: 按时间顺序切片                查询方式: 语义搜索 + 图谱遍历
消费者: 提示词模板拼装                  消费者: AI 理解来访者、变量填充
```

**A. 近期工作记忆: `{{chat}}` + messages 表**

`{{chat}}` 是提示词模板中的系统变量，由 `buildSystemVariables()` 在每次 action 执行时从 `context.conversationHistory` 动态构建。当前实现：取最近 5-10 条消息，格式化为 `角色: 内容` 的文本块，注入提示词。

数据来源是 `messages` 表 —— 一回合一条记录，包含 `role`、`content`、`actionId`、`timestamp`。按时间排序后过滤 `superseded` 标记的消息，重建为 `ConversationEntry[]` 注入 Session 域对象。

**为什么是一回合一条而不是整个会话存一个文本块:**

- **重跑依赖细粒度。** `flagSupersededMessages(position)` 按 action 位置精确废弃消息。存成文本块无法做部分废弃。
- **actionId 追溯。** 每条消息标记了是哪个 action 产生的，支持调试和单步回放。
- **恢复执行状态。** `restoreSession()` 按时间排序重建 conversationHistory，action 执行时按索引切片。
- **查询性能。** `WHERE session_id = ? ORDER BY timestamp` 有联合索引，百条级毫秒完成。

**messages 表是 ground truth。** 它是所有记忆的原始数据源——Hindsight 的 `retain()` 从它读取、`{{chat}}` 从它构建、临床文档从它生成、重跑和调试从它恢复。它与 Hindsight 的关系是:

```
messages 表 (原始对话记录, 不可篡改)
  │
  ├──→ {{chat}} 占位符 (取最近 N 条, 完整原文)
  │     用途: 让 LLM 知道"刚才在聊什么"
  │
  └──→ Hindsight retain() (提取事实/实体/观点, 结构化存储)
        用途: 让 LLM 知道"这个人是谁, 经历过什么"
```

两者不能互相替代。messages 保留对话的原始措辞和顺序（LLM 需要据此理解当前对话的语境走向），Hindsight 提供压缩后的结构化认知（LLM 需要据此理解来访者的背景和模式）。

**B. 长期结构记忆: recall() 检索**

超出 `{{chat}}` 窗口的对话内容，不通过手动分级压缩（先压缩 AI、再压缩用户、再压缩 action 摘要……）来塞入提示词，而是通过 `memoryRepository.recall()` 按需检索。理由:

- **Hindsight 的四路检索 + 交叉编码器已经做了"什么相关、什么不相关"的判断。** 手动写压缩规则是在重复 Hindsight 的工作，且质量更差。
- **分级压缩的维护成本不低。** 每层压缩规则的定义、触发时机、LLM 调用成本（每次压缩调一次摘要模型），而且不同 action/topic 的压缩粒度需要逐步试出来。
- **咨询场景单次会话长度有限。** 通常在 20-50 轮，假设每轮 ~500 tokens，全程 10K-25K tokens。加上提示词模板和 recall 上下文，现代模型的 128K 窗口暂时够用。瓶颈在跨会话积累，不在当前会话。

**C. 提示词中的两个记忆占位符**

```
提示词模板:
  ...
  ## 对话历史
  {{chat}}                  ← 最近 N 轮完整消息 (messages 表直接拼接)

  ## 关于来访者
  {{memory_context}}        ← recall("本次会谈到目前为止的关键讨论点")
  ...                       ← 结构化记忆上下文 (MemoryContext 四字段)
```

| 占位符               | 内容                   | 来源                              | 时间范围 |
| -------------------- | ---------------------- | --------------------------------- | -------- |
| `{{chat}}`           | 最近 N 轮完整对话      | messages 表 → conversationHistory | 本次会话 |
| `{{memory_context}}` | 结构化的来访者认知画像 | Hindsight recall()                | 全部历史 |

这避免了手动实现复杂的分级压缩策略——简单的近期完整保留 + 长期按需检索，由 Hindsight 的检索质量来保证相关性。

### 2.3 临床文档 (Clinical Documents) —— 制品快照

**本质**: 人类可读、可展示、可存档的结构化临床记录。是咨询服务中的正式"产物"。

**当前状态**: 未实现。

**掌控边界**: 人类咨询师定义**格式**（模板），AI 自主生成**内容**。

| 维度           | 说明                                                                           |
| -------------- | ------------------------------------------------------------------------------ |
| **消费者**     | 用户 (可视化展示进度)、人类咨询师 (临床审核)、AI 咨询师 (通过会谈记忆间接获取) |
| **作用**       | 展示治疗进展、存档临床记录、让用户感知"被认真对待"                             |
| **查询方式**   | 按时间点/文档类型检索 (独立版本存档)                                           |
| **更新频率**   | 按时间点创建 (入诊、每次会谈结束时)，版本化，创建后内容不篡改                  |
| **谁定义模板** | 人类咨询师预设模板（基于人类咨询师经验）；复杂场景下 AI 也可自行设计           |
| **谁生成内容** | AI 基于会谈记忆自主填充；部分字段由用户直接填写 (量表、入诊表)                 |

**模板 vs 内容 —— 临床文档的掌控边界:**

临床文档是唯一**横跨两个角色**的记忆类型:

```
人类咨询师掌控                           AI 咨询师自主
──────────────                         ──────────────
· 文档模板结构 (有哪些字段)               · 字段内容生成 (写什么)
· 量表选择 (用 PHQ-9 还是 GAD-7)         · 进展评估 (变化趋势判断)
· 笔记格式 (分几大块)                    · 临床发现 (新浮现的模式)
· 存档策略 (哪些字段做版本化)             · 治疗建议 (基于理解做出的判断)
```

为什么模板要由人类咨询师预设: 人类咨询师在长期执业中积累了经过验证的文档格式 —— 会谈笔记应包含哪些维度、量表应在何时施用、入诊表应收集哪些信息。这些是专业经验沉淀，不应每次由 AI 临时决定。

什么情况下 AI 可以自行设计: 当来访者的情况超出预设模板的覆盖范围时（如出现了预设量表未涉及的症状），AI 可以根据临床需要灵活补充自定义字段或新文档结构。但这应该是**受控的灵活** —— AI 有自主权但需要明确的触发条件。

#### 2.3.1 文档类型

**A. 用户/咨询师提交表单**

```
- 入诊登记表 (基本信息、主诉、用药史)
- 心理量表 (PHQ-9、GAD-7、睡眠质量指数等)
- 作业反馈表 (家庭作业完成情况和体验)
```

**B. AI 生成的会谈笔记**

```
每次会谈后由 AI 自动生成，模板由人类咨询师设计:

┌─────────────────────────────────────────┐
│          第{N}次咨询会谈笔记              │
│          日期: {date}                    │
│          咨询师: AI (基于{流派}框架)       │
├─────────────────────────────────────────┤
│ 1. 本次会谈主题                           │
│ 2. 用户状态 (情绪、参与度)                 │
│ 3. 讨论要点                               │
│ 4. 使用的技术与干预                         │
│ 5. 本次评估 (进展、阻抗信号)               │
│ 6. 新发现的关键信息                         │
│ 7. 家庭作业                               │
│ 8. 下次计划                               │
└─────────────────────────────────────────┘
```

#### 2.3.2 双重存储模型: 独立版本 + 并入记忆

文档一旦创建即作为**版本化制品**独立存储（不可篡改，可追溯）。同时，文档中的信息也**汇入会谈记忆**：

```
文档创建流程:
  用户填表 或 AI 生成笔记
    │
    ├──→ [独立存储] 版本化归档
    │     文档ID: doc_2026-05-18_session_5
    │     用途: 展示给用户看、临床审核、合规存档
    │
    └──→ [汇入会谈记忆]
          内容被 retain 到 World / Opinion / Observation 网络
          用途: AI 在后续会话中通过 recall 获取，无需单独查询文档表
```

**这解决了什么**:

1. **LLM 上下文统一来源**: 给 LLM 拼记忆上下文时，只需调用会谈记忆的 `recall()`，不需要额外去"文档表"里找信息。文档和对话中产生的信息在记忆层已经合并。

2. **同一信息的多次记录自动合并**:
   - 用户在第 2 次会谈后填 PHQ-9 = 15
   - 第 5 次会谈后填 PHQ-9 = 9
   - 两份量表独立存档（版本追溯）
   - 但在会谈记忆中: `PHQ-9得分: 15 → 9 (下降 6 分, 时间: 2026-03-15 → 2026-05-10)`
   - AI 可以自然地理解"用户的焦虑得分在改善"

3. **一致性**: 变量 {PHQ-9得分} = 9 与会谈记忆中的 PHQ-9 最新得分一致，因为它们来自同一源头。

### 2.4 咨询方案 (Treatment Plan) —— 行动意图

**本质**: 基于对用户的理解，形成的"接下来要做什么"的主动决策。它不是一个被动的认知记录，而是一个**行动意图的容器**。

**当前状态**: 未实现。当前脚本的 Phase→Topic→Action 是静态的，不随用户个体调整。

| 维度         | 说明                                                           |
| ------------ | -------------------------------------------------------------- |
| **消费者**   | AI 策略反思、脚本引擎 (影响 Topic/Action 的选择和参数)         |
| **作用**     | 驱动治疗进程的节奏和方向 —— 不是被动记录过去，而是主动规划未来 |
| **查询方式** | 按用户加载当前方案                                             |
| **更新频率** | 每次会谈后评估和调整                                           |
| **谁定义**   | AI 基于会谈记忆和脚本定义的治疗框架生成，人类咨询师可审核调整  |

#### 2.4.1 数据结构

```
咨询方案:
  userId: "u_123"

  治疗目标:
    - id: "goal_1"
      描述: "降低工作场景中的社交焦虑"
      测量: "GAD-7 < 10"
      当前得分: 15
      目标得分: <10
      状态: "进行中"
      创建: "2026-03-15"

    - id: "goal_2"
      描述: "识别并修正'我不够好'的核心信念"
      测量: "信念强度自评 < 3/10"
      当前得分: 8
      目标得分: <3
      状态: "进行中"

  干预策略:
    - id: "strategy_1"
      关联目标: "goal_1"
      方法: "渐进暴露 + 认知重构"
      进度: "已完成心理教育, 开始轻度暴露"

  已完成活动:
    - {类型: 会谈, 次数: 5}
    - {类型: 家庭作业, 名称: "思维记录表", 完成度: 80%}

  下一步计划:
    - 第6次会谈: 中等难度暴露练习 (小组会议发言)
    - 家庭作业: 记录暴露练习中的自动化思维

  节奏调整:
    - 原始计划: 每周1次
    - 当前: 每2周1次
    - 原因: "用户反馈进度太快, 需要更多时间消化"

  阻碍与风险:
    - 阻碍: "对暴露练习有轻度抗拒, 已通过心理教育部分缓解"
    - 风险: "无紧急风险信号; 注意: 如果社交回避加重, 需重新评估策略"
```

#### 2.4.2 与脚本、会谈记忆的关系

```
会谈记忆 (2.2)               咨询方案 (2.4)              脚本 (已有)
─────────────               ─────────────               ──────────
用户的历史事实               基于理解形成的决策            预设的 Phase→Topic→Action
用户的经历脉络               个性化的干预策略              静态治疗框架
咨询师的判断评估             目标-进展-阻碍追踪            流派特定的技术集合

     └──────────→ 为方案提供依据 ──→ 方案影响脚本的下一步选择 ←── 脚本提供治疗框架约束
```

咨询方案是**动态的、针对个体的**。同一个 CBT 脚本框架，在不同用户身上会产生不同的咨询方案——目标是不同的，节奏是不同的，技术侧重点是不同的。

### 2.5 领域知识库 (Domain Knowledge Base) —— 声明性专业基础

**本质**: 心理咨询领域的概念、理论、技术、鉴别标准的结构化知识。与脚本中的**程序性知识**（"先介绍 ABC 模型，再收集自动化思维"）互补。

**当前状态**: 未实现。当前依赖 LLM 自身训练数据中的领域知识。

**为什么需要**: LLM 的领域知识不可控 —— 它可能用认知行为流派解释，也可能混入精神动力学派的术语。当用户问 "焦虑和恐惧有什么区别" 或 "为什么我们要做这个练习" 时，需要可控的、流派一致的知识来源。

| 维度         | 说明                                                     |
| ------------ | -------------------------------------------------------- |
| **消费者**   | LLM (生成解释时的参考源)、AI 咨询师 (判断和鉴别时的依据) |
| **作用**     | 确保 AI 引用的是可控的、流派一致的领域概念               |
| **查询方式** | 语义搜索 (向量检索) + 精确标题匹配                       |
| **更新频率** | 低频 (由领域专家维护，类似 wiki)                         |
| **谁定义**   | 人类咨询师 / 领域专家                                    |

#### 2.5.1 为什么不用 Hindsight

Hindsight 是**经验记忆系统**——它的 retain/reflect 操作为"从对话中积累对一个人的跨会话理解"而设计。领域知识是**参考知识**，本质不同:

|              | 会谈记忆 (用 Hindsight)    | 领域知识 (自建)                     |
| ------------ | -------------------------- | ----------------------------------- |
| **内容来源** | 对话中自动提取             | 领域专家人工编写                    |
| **时间维度** | 随时间演化、观点动态更新   | 静态，低频修订                      |
| **作用域**   | 每个用户独立一份           | 所有用户共享                        |
| **图谱关系** | 实体间的时间/因果/经验关系 | 概念间的定义性关系 (包含/前置/导致) |
| **更新方式** | retain() 从对话提取        | 人工编辑，类似 wiki                 |

拿 Hindsight 存领域知识就像拿日记本存字典——数据形状不匹配。

#### 2.5.2 实现方案: pgvector

HeartRule 已用 PostgreSQL，项目 schema 中预留了 `embedding` 向量字段。用 pgvector 做知识库检索是零新基础设施的选择:

- **存储**: `knowledge_entries` 表 — 结构化元数据 (流派、类别、标签) + 内容 (Markdown) + 向量嵌入
- **检索**: 元数据过滤 + 向量相似度混合查询
  ```sql
  SELECT * FROM knowledge_entries
  WHERE 流派 = 'CBT' AND 类别 = '核心概念'
  ORDER BY embedding <=> query_embedding
  LIMIT 5;
  ```
- **嵌入生成**: 条目创建/更新时离线生成一次，不在每次查询时调用 LLM
- **规模**: 咨询领域概念量级在百到千，pgvector 完全够用

**不选 LangChain**: 之前已决定不引入。知识库只是"结构化元数据 + 向量相似度搜索"，不是复杂的 RAG 编排管线。pgvector 的原生 SQL 查询就足够。

#### 2.5.3 知识条目结构

```
知识条目:
  id: "kb_cognitive_distortion_001"
  标题: "自动化思维"
  所属流派: "认知行为疗法 (CBT)"
  类别: "核心概念"
  标签: ["认知", "思维", "自动化", "CBT基础"]

  内容 (Markdown):
    ## 定义
    自动化思维 (Automatic Thoughts) 是指...

    ## 特征
    1. 自发产生，不需要刻意努力
    2. 通常是简短的、片段式的
    3. 带有认知歪曲的特征
    4. 能引发强烈的情绪反应

    ## 临床示例
    用户在会议上发言后被领导提问，自动化思维可能是:
    "我说错了话"、"大家觉得我很蠢"

    ## 与其他概念的关系
    - ← 是...的前提: 认知歪曲
    - ← 被...识别: 思维记录表
    - ← 导致: 消极情绪

    可以用"脑海里的自动弹幕"作为比喻...
```

```

"第2步: 引导用户识别自动化思维"    "什么是自动化思维, 有什么特征,
                                 在实际生活中是什么样子的"

两者互补 —— 脚本告诉 AI "做什么", 知识库告诉 AI "怎么解释正在做的事"
```

## 4. 会谈记忆的实现方案

### 4.1 选择: 基于 Hindsight

会谈记忆 (2.2) 是整个记忆体系中最复杂的一块。它需要的能力包括：对话中自动提取事实和实体、实体解析与消歧、多策略混合检索、知识图谱构建与遍历、时间推理、观点信心动态更新。

经过对 Mem0、Hindsight 和自建的对比评估，选择 **Hindsight** 作为会谈记忆的实现基础。

**选择理由**:

| 能力                                                    | 自建预估                 | Hindsight      |
| ------------------------------------------------------- | ------------------------ | -------------- |
| 对话事实与实体自动提取                                  | 提示词工程 + 调试: ~2 周 | 内置           |
| 实体解析 (批量消歧, 99.5% 查询减少)                     | 算法 + 调优: ~3 周       | 内置           |
| 四路并行检索 (语义+BM25+图谱+时间) + RRF融合+交叉编码器 | 实现 + 调参: ~2 周       | 内置           |
| 知识图谱 (4种边类型 + 多跳遍历)                         | 建模 + 实现: ~3 周       | 内置           |
| 时间推理 (τ_start, τ_end, τ_mention)                    | 设计 + 实现: ~1 周       | 内置           |
| 观点信心分数动态演化                                    | 机制设计 + 实现: ~1 周   | 内置           |
| **合计**                                                | **~12 周**               | **集成 ~1 周** |

**Hindsight 概况**:

- 开源 (MIT)，可自托管 (Docker 单容器)
- TypeScript SDK (`@vectorize-io/hindsight-client`) 兼容 Vercel AI SDK (`@vectorize-io/hindsight-ai-sdk`)
- LongMemEval 准确率 91.4% (SOTA)，已验证
- v0.5.0 (2025-12 发布)，仍在活跃开发中

**风险缓解**: Hindsight API 在 1.0 之前可能变化，但通过适配层封装，变更影响局限在适配层内部。

### 4.2 Hindsight 的四网络 + 三操作模型

Hindsight 将记忆组织为四个认知分类网络，并提供三个核心操作：

```
┌──────────────────────────────────────────────────────────┐
│              Hindsight 四网络模型                           │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  World Network (W)           Opinion Network (O)          │
│  客观事实                     主观判断                     │
│  ┌──────────────────┐        ┌──────────────────┐        │
│  │ "用户被诊断为GAD" │        │ "焦虑主要来源于    │        │
│  │ "服用舍曲林50mg"  │        │  工作关系(信0.72)"│        │
│  │ "2024年3月离婚"   │        │ "核心信念: 不被    │        │
│  │ "母亲有焦虑史"    │        │  认可(信0.78)"    │        │
│  └──────────────────┘        └──────────────────┘        │
│                                                          │
│  Experience Network (B)       Observation Network (S)     │
│  亲身经历                     综合摘要                     │
│  ┌──────────────────┐        ┌──────────────────┐        │
│  │ "第3次: 用户描述   │        │ "用户-父亲关系     │        │
│  │  被领导批评的具体  │        │  画像: 疏远、有     │        │
│  │  场景和身体反应"   │        │  未解决冲突、但     │        │
│  │ "第5次: 首次主动   │        │  表达了修复意愿"   │        │
│  │  使用思维记录表"   │        │ "核心应对模式:    │        │
│  └──────────────────┘        │  回避而非直面"     │        │
│                              └──────────────────┘        │
│                                                          │
│  三操作: retain (记住) / recall (召回) / reflect (反思)     │
└──────────────────────────────────────────────────────────┘
```

**三个操作**:

| 操作        | 触发时机                   | 在咨询中的应用                                                                                   |
| ----------- | -------------------------- | ------------------------------------------------------------------------------------------------ |
| **retain**  | 每个 Action 结束后 (异步)  | 从该 Action 的完整对话中提取事实/事件/情绪 → 实体解析 → 构建图谱边 → 分类进四网络 → 更新观点信心 |
| **recall**  | 会话启动时 / AI 需要背景时 | 四路并行检索 → 返回相关记忆 → 注入 LLM 上下文                                                    |
| **reflect** | 会话结束后 / 关键节点      | 跨记忆 LLM 综合 → 形成 Observation → 更新 Opinion 信心                                           |

**HindsightMemoryAdapter 的职责 (实现 MemoryRepository 端口):**

| 能力                   | 说明                                                                                                                                                                                                                            |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **retain 提取提示词**  | 适配器本身不内置领域提示词。保留完全领域中性的默认值 (提取事实陈述、识别人物实体、提取时间信息)。领域特定的提取维度 (诊断信息、情绪状态等) 由调用方通过 `options.extractionPrompt` 显式传入 —— 这些提示词定义在 YAML 脚本模板中 |

| -------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |

#### 5.2.1 领域层 — 端口定义

领域层只定义"跨会话积累对来访者的理解需要什么"，不关心"谁来实现"。记忆域的核心端口是 `MemoryRepository`:

```typescript
// 领域端口 — 在 core-engine 中定义
interface MemoryRepository {
  retain(userId: string, messages: Message[]): Promise<void>;
  recall(userId: string, query: string): Promise<MemoryContext>;
  reflect(userId: string): Promise<ReflectionResult>;
}

// 领域对象 — 咨询抽象层级的通用认知模型
// World/Experience/Opinion/Observation 是经过验证的跨领域通用抽象:
// 无论心理咨询还是法律咨询，都需要区分"确定的客观事实"、
// "对方亲历的事件"、"我的主观判断"和"综合摘要"
interface MemoryContext {
  worldFacts: Fact[]; // 确定的客观事实 (诊断/案由/用药/证据)
  experiences: Experience[]; // 来访者/当事人亲历的第一人称事件
  opinions: Opinion[]; // 咨询师/律师的主观判断，含信心分数
  observationSummary: string; // 综合摘要画像
}

// reflect() 的返回值 — 会话结束后回顾所有记忆，综合得出新领悟:
// 哪些判断信心变了、浮现了什么新观察、发现了哪些值得关注的矛盾
interface ReflectionResult {
  updatedOpinions: Array<{ opinionId: string; confidenceDelta: number }>;
  newObservations: string[];
  contradictions: Array<{ factA: string; factB: string; analysis: string }>;
}
```

**为什么这就是通用模型，不需要按咨询领域定制**: "区分事实和判断"、"区分证据和推论"是咨询类专业服务的底层认知模式，不是心理咨询独有的。心理咨询的诊断和法律的案由都落在 `worldFacts`，咨询师的假设和律师的策略判断都落在 `opinions`。

**领域差异性不由代码承载**: 各咨询领域（心理/法律/管理）的差异通过 **YAML 脚本系统的模板和提示词** 实现——不同领域的人类咨询师编写各自的 retain 提取提示词、recall 查询模板、reflect 反思提示词、知识库条目。代码只实现"咨询"共性的抽象层，不做任何单一领域的硬编码。适配器不内置任何领域特定的提示词——领域提示词属于 YAML 脚本系统，通过 `retain()` / `recall()` / `reflect()` 的 `options` 参数传入适配器。

`HindsightMemoryAdapter` 将 Hindsight 四网络映射到 `MemoryContext`: World→worldFacts, Experience→experiences, Opinion→opinions, Observation→observationSummary。映射是 1:1 的——好的领域抽象与好的通用实现会自然收敛。

#### 5.2.1.1 跨领域验证: 法律咨询示例

用非心理学领域走通 MemoryContext 四字段，验证抽象的完整性:

**场景**: 离婚财产纠纷调解

| 字段               | 内容                                                                                                                                           |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| worldFacts         | "双方2022年5月登记结婚"、"婚后购置房产一套 (登记在甲方名下)"、"甲方2024年3月起将共同存款分批转入其胞弟账户 (银行流水已调取)"                   |
| experiences        | "第2次调解: 乙方详细描述了发现转账后的沟通过程——甲方最初否认, 后来承认但拒绝说明用途"、"第3次: 乙方描述了甲方在婚姻期间多次隐瞒收入的具体事件" |
| opinions           | "甲方的转账行为可能构成恶意转移夫妻共同财产 (信心: 0.72)"、"双方感情破裂的时间点是财产分割的关键争议点 (信心: 0.60)"                           |
| observationSummary | "乙方当事人情绪波动较大但陈述逻辑清晰; 核心诉求是财产分割公平而非惩罚性赔偿; 甲方当事人对关键问题回避态度明显"                                 |

四网络在法律咨询中自然映射:

- World = 可验证的客观证据 (登记日期、银行流水、产权登记)
- Experience = 当事人亲历的第一人称叙事 (对方的行为、对话过程)
- Opinion = 法律专业判断 (法条适用性、证据可信度、对方意图推断)
- Observation = 综合评估 (当事人状态、纠纷本质、调解前景)

这验证了 World/Experience/Opinion/Observation 的区分不是心理咨询的特化, 而是 "事实-经历-判断-综合" 这一认知模式的通用表达。心理咨询的诊断与法律的案由都落在 worldFacts, 咨询师的假设与律师的策略判断都落在 opinions。

领域层**不**依赖 Hindsight。`MemoryContext` 在 `core-engine` 中定义，`HindsightMemoryAdapter` 在 `api-server` 中实现。

其他记忆相关领域端口:

```typescript
  findByUser(userId: string): Promise<ClinicalInsight[]>;
}
```

#### 5.2.2 应用层 — 编排服务

构建在领域端口之上的编排逻辑，负责会话生命周期中的记忆操作:

```
MemoryService (应用服务):
  - onSessionStart(userId) → recall 用户上下文 → 注入 prompt
  - onActionEnd(userId, actionMessages) → retain 该 Action 完整对话 → 异步提取
  - onSessionEnd(userId, sessionId) → reflect 综合 → 触发文档生成

DocumentService (应用服务):
  - createDocument(template, sessionId) → 生成文档 → 独立存档 → 转叙述 → retain

ClinicalInsightService (应用服务, Phase 4):
  - detectContradictions(userId) → recall 候选记忆对 → LLM 分析 → 返回洞察列表
  - analyzePatterns(userId, dimension) → recall 相关记忆 → LLM 趋势分析 → 返回模式报告
  - 结果持久化到 ClinicalInsightRepository (领域端口, Phase 4 定义)
```

应用层依赖注入领域端口（通过 IoC 容器），不感知 Hindsight 的存在。

#### 5.2.3 基础设施层 — 适配器

实现领域端口，对接具体技术:

| 端口                         | 适配器                      | 实现技术                          |
| ---------------------------- | --------------------------- | --------------------------------- |
| `MemoryRepository`           | `HindsightMemoryAdapter`    | Hindsight Docker + TypeScript SDK |
| `KnowledgeBaseRepository`    | `PgKnowledgeBaseAdapter`    | PostgreSQL + pgvector             |
| `TreatmentPlanRepository`    | `PgTreatmentPlanAdapter`    | PostgreSQL                        |
| `ClinicalDocumentRepository` | `PgClinicalDocumentAdapter` | PostgreSQL                        |

`HindsightMemoryAdapter` 是 MemoryAdapter 的具体定位 —— 它不是一个独立的存在，而是实现了 `MemoryRepository` 端口、对接 Hindsight SDK 的基础设施适配器。

### 5.3 数据存储

```
HeartRule 管理 (现有 PostgreSQL):
  messages 表              — 保留 (原始对话 ground truth, 一回合一条;
                                 支持 actionId 追溯、superseded 重跑、
                                 {{chat}} 构建、retain() 数据源)
  variables 表             — 保留 (变量快照)
  user_global_variables 表 — 保留 (全局变量持久化)
  sessions 表              — 保留 (会话状态, 含 position 位置信息)
  treatment_plans 表       — 新增 (咨询方案)
  knowledge_entries 表     — 新增 (领域知识库, 含 pgvector embedding)
  clinical_documents 表    — 新增 (临床文档版本存档)

Hindsight 管理 (嵌入式 pg0):
  向量存储 + 图谱存储 + 元数据
  (HeartRule 不直接操作, 通过 MemoryRepository 端口 → HindsightMemoryAdapter 访问)
  (messages 表是 retain() 的数据源; recall() 的结果与 {{chat}} 互补)
```

## 6. 分阶段实施建议

### Phase 0: 领域接口验证 (1 周)

在投入 Hindsight 集成之前，用最小成本验证 MemoryRepository 接口的形状:

- 实现 `FakeMemoryRepository` (纯内存):
  - `retain()` → 将消息序列化到内存数组，记录调用方传入的提取提示词日志
  - `recall()` → 简单的关键词匹配，返回 `MemoryContext` (人工构造的测试数据)
  - `reflect()` → no-op，记录调用日志
- 用 `FakeMemoryRepository` 运行 2-3 次完整咨询会话
- 验证目标:
  1. `MemoryContext` 四字段在真实 recall 场景中是否够用
  2. `retain(userId, messages)` 签名是否适合异步调用模式
  3. `reflect` 的触发时机 (会话结束？话题结束？两者？) 是否正确
  4. 调用方传入的提示词参数结构 (`options.extractionPrompt` 等) 是否合理

验证通过后，`MemoryRepository` 接口冻结。Phase 1 的 `HindsightMemoryAdapter` 实现同一接口。

### Phase 1: Hindsight 集成 + 基础记忆 (2-3 周)

- 部署 Hindsight Docker 容器
- 实现 `HindsightMemoryAdapter` 封装 HindsightClient，实现 `MemoryRepository` 领域端口
- 编写咨询领域的 retain 提示词 (告诉 Hindsight 从咨询对话中提取什么)
- 实现会话启动时的 recall (注入 LLM 上下文)
- 实现每个 Action 结束时的 retain (完整 Action 对话→结构化记忆)
- 实现基础的 reflect (会话结束后的综合)

### Phase 2: 变量桥接 + 临床文档 (2-3 周)

- 实现 ai_think 从会谈记忆调取变量值 (通过 recall → VariableStore)
- 变量职责收缩: 将跨会话的语义值从全局变量迁移到会谈记忆
- 移除 `memories` 表及相关死代码 (MemoryEngine stub)
- 实现 AI 会谈笔记自动生成
- 实现双重存储: 文档独立版本存档 + 内容 retain 到 Hindsight
- 实现用户表单 (量表、入诊表) 的提交→存档→汇入记忆流程

### Phase 3: 咨询方案 + 领域知识库 (3-4 周)

- 实现咨询方案的数据模型和 CRUD
- 方案与脚本引擎的集成 (方案影响 Topic/Action 选择)
- 实现领域知识库的存储和检索
- 知识库集成到 AiSayAction 的提示词注入

### Phase 4: 矛盾检测 + 临床洞察 (2-3 周)

- 实现跨记忆语义矛盾检测管线
- 实现情绪模式 / 症状轨迹的自动分析
- 完善 reflect 操作的咨询领域提示词
- 临床洞察的呈现和记录

## 7. 关键设计决策记录

| 决策                   | 选择                                                                                                        | 理由                                                                                                                                                                                                                                                                                                                                       |
| ---------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 会谈记忆实现           | Hindsight (自托管)                                                                                          | 自带经过验证的四网络+三操作+图谱+时间推理, 避免自建~12周的重复工作; MIT开源, 可自托管; 咨询领域层仍自建                                                                                                                                                                                                                                    |
| 领域知识库实现         | pgvector (PostgreSQL 扩展)                                                                                  | 领域知识是静态参考内容 (非经验记忆)，数据形状与 Hindsight 不匹配; pgvector 已在项目 schema 中预留 embedding 字段，零新基础设施; 元数据过滤+向量相似度混合查询，适合百到千量级的结构化知识条目                                                                                                                                              |
| 咨询方案 / 临床文档    | 自建 (PostgreSQL)                                                                                           | 独立的咨询领域模型，非通用记忆问题; 临床文档需要独立版本存档                                                                                                                                                                                                                                                                               |
| 变量 vs 记忆           | 变量收缩为操作参数+进程控制；语义理解由记忆承载；变量可从记忆通过 ai_think 调取                             | 信息可溯源: 语义信息以记忆为准, 变量按需从记忆提取; 避免两处存储同一信息                                                                                                                                                                                                                                                                   |
| 临床文档存储           | 独立版本存档 + 汇入会谈记忆                                                                                 | 版本追溯 (不可篡改) + 记忆检索 (随对话记忆一起被 recall, 避免 LLM 上下文拼装时额外查询文档表)                                                                                                                                                                                                                                              |
| MemoryContext 领域模型 | 沿用 World/Experience/Opinion/Observation 四网络作为通用认知抽象                                            | "区分事实与判断"是跨咨询领域的底层认知模式; 代码只实现咨询抽象层，领域差异性 (提取提示词、查询模板、知识库) 由 YAML 脚本系统承载                                                                                                                                                                                                           |
| 记忆系统 DDD 分层      | 领域层 `MemoryRepository` 端口 + 应用层 `MemoryService` 编排 + 基础设施层 `HindsightMemoryAdapter` 实现端口 | 领域层不感知 Hindsight; 编排逻辑与具体实现分离; 遵循项目已有的 DDD + Hexagonal Architecture                                                                                                                                                                                                                                                |
| 部署模式               | Hindsight Docker + 现有 PostgreSQL                                                                          | 单容器, 嵌入式 pg0, 不增加独立数据库; 16GB内存可承受                                                                                                                                                                                                                                                                                       |
| API 稳定性风险         | 适配层封装                                                                                                  | Hindsight v0.5.0 的 API 变更影响局限在 MemoryAdapter 内部                                                                                                                                                                                                                                                                                  |
| 近期/远期记忆分工      | {{chat}} 保留最近 N 轮完整消息，超出窗口的内容通过 recall() 检索                                            | 避免手动实现复杂的分级压缩策略（先压缩 AI、再压缩用户、再压缩 action 摘要等）；Hindsight 的四路检索 + 交叉编码器已经做了相关性判断；咨询场景单次会话 20-50 轮，128K 窗口暂时够用                                                                                                                                                           |
| messages 表存储粒度    | 一回合一条记录（含 actionId、timestamp、metadata）                                                          | 需要细粒度支持: 重跑时的 superseded 标记按 action 位置精确废弃；actionId 追溯支持调试和单步回放；恢复执行状态需要按时间排序重建 conversationHistory；`WHERE session_id = ? ORDER BY timestamp` 有联合索引，百条级毫秒完成                                                                                                                  |
| retain 调用粒度        | 每个 Action 结束后（非每轮对话后）                                                                          | Action 是完整的信息收集单元，一个 Action 内的多轮对话构成连贯叙事，per-round 会割裂事实提取（同一事件的碎片分散在多个 round 中）且增加 Hindsight 实体解析负担（3-5x 的 LLM 提取调用）；per-Action 一次 retain 比 per-round 多次碎片 retain + 事后实体解析质量更高。同 Session 内后续 Action 通过 recall() 获取前面 Action 已 retain 的内容 |
