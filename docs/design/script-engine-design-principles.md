## 1. DSL 在 AI 咨询引擎中的角色

### 1.1 经验的结晶媒介

HeartRule DSL 不是配置文件格式。它是**咨询经验的结晶媒介**——咨询师将隐性知识（"怎么做咨询"）外化为显式的、可执行的、可优化的脚本。

咨询师和 AI 徒弟之间通过脚本交流：

```
咨询师（经验持有者）
    │
    │  将经验写成脚本
    ↓
  脚本（DSL）──────────────────→ AI 徒弟执行
    ↑                              │
    │                              │  灵活调整也转成脚本
    │                              ↓
    │                         调整记录（留痕）
    │                              │
    │   事后查看、评价、改进 ←──────┘
    │
    │   AI 也可基于数据优化脚本
    └──────────────────────────────┘
```

脚本是咨询师和 AI 之间的**共同语言**：咨询师"教"AI 怎么做咨询，AI 执行后把调整和结果"汇报"给咨询师。

### 1.2 DSL 定义一个咨询领域的四种经验

同一个 DSL 承载四种脚本类型，每种捕获咨询师不同层面的经验：

| 脚本类型         | 定义什么                                   | 核心问题           | 类比 |
| ---------------- | ------------------------------------------ | ------------------ | ---- |
| **咨询脚本**     | 咨询流程剧本（Phase → Topic → Action）     | "这场咨询怎么走"   | 剧本 |
| **咨询技术脚本** | 可复用的咨询技法/套路                      | "用什么方法做"     | 招式 |
| **意识脚本**     | 深度洞察力（检测阻抗、情绪突变、关键信号） | "过程中留意什么"   | 觉察 |
| **变量系统**     | 定义→提取→更新→存储→使用                   | "怎么从通用到具体" | 纽带 |

**变量系统是关键的桥梁**——同一个咨询脚本是抽象的、通用的；通过变量（提取用户的年龄、症状、家庭结构等），抽象脚本在每一次会话中落成**具体的、个性化的咨询**。变量系统打通了"通用经验"和"具体个案"。

### 1.3 三角张力：价值主张

DSL 的设计面临三个互相制约的目标：

```
              简单（咨询师能写）
              /              \
             /                \
            /      DSL 设计    \
           /       空间        \
          /                    \
    强大（模拟真实咨询）—————— 可干预（AI能理解并调整）
```

- **简单** — 咨询师能看懂、能写。不需要编程思维，不需要面对工程问题。
- **强大** — 能表达真实咨询的复杂性。有主节奏，同时能应对现场变化。
- **可干预** — AI 理解脚本语义，能在约束内安全地调整执行流程。

传统方案选两个牺牲第三个。HeartRule 的目标是三个都满足——三角张力是**价值主张**，原则和架构策略是实现手段。

### 1.4 原则与策略

**原则**回答"为什么"——是 DSL 语法设计的判断依据。**策略**回答"怎么做"——是在原则约束下应对具体问题的架构选择。

```
原则                                策略（架构选择）
────                                ────────
P1 线性优先               ←→       1.1 一级条件守卫
  （对应"简单"）                    1.2 主题展开
                                   1.3 不提供程序性控制流
                                   1.4 三种脚本分离（主线+意识+技术）

P2 不暴露工程问题          ←→       语法和配置只来自咨询领域
  （对应"简单"）                    工程决策由引擎后台解决

P3 语法确定性              ←→       Schema 先行、一字一义
  （对应"可干预"）                   结构化验证反馈、禁止语法糖
```

三条原则各对应三角的一个顶点：

- **P1 + P2** → **简单**：P1 管结构简单（不用编程思维），P2 管界面简单（不用工程思维）
- **P3** → **可干预**：AI 能准确生成和修改脚本——准确的前提是语法无歧义
- **强大**不由单条原则承载，而是 P1 约束下策略 1.4（三种脚本协同）的架构结果

## 2. 三条设计原则

### 原则一：线性优先（Linearity First）

**对应三角**：简单

**表述**：脚本是线性剧本，不是程序。咨询师读和写脚本时，思维沿着 Phase → Topic → Action 一条线走，不需要理解循环、跳转、子程序调用等程序性构造。

**哲学依据**：认知锚定原则 — 低熵符号结构（线性序列）锚定高熵智能（LLM 生成）。

**为什么需要这条原则**：如果 DSL 允许循环和跳转，咨询师就需要像程序员一样思考控制流——"这段在什么条件下重复执行？""跳过去之后怎么回来？"——认知负担急剧上升。线性优先的本质是**让咨询师保持咨询师的思维，不要变成程序员的思维**。

**DSL 设计含义**：

- ✅ `phases[].topics[].actions[]` 的三层线性结构 — 唯一的控制流
- ❌ `for` / `while` / `loop` 循环构造
- ❌ `goto` / `jump` / `skip_to` 跳转
- ❌ 子脚本调用 / `include` / `call` 引用
- ❌ 变量赋值 / 数学运算表达式

**判断标准**：如果一个构造让咨询师联想到编程语言的控制流关键字，它不应该进入 DSL。

#### 策略 1.1：一级条件守卫（Single-Level Guards）

**面对的问题**：咨询流程中需要"根据不同情况说不同的话"——这引入了分支。如何在分支存在的情况下保持线性思维？

**策略**：条件分支只做一级。Action 可带 `condition` 字段，按 actions 数组顺序依次独立评估——满足则执行，不满足则跳过。不做嵌套、不做 else 链、不做 switch/case。

**为什么这样设计**：咨询师读脚本时，从上到下扫一遍 actions 列表，每个 action 前面的 condition 告诉 ta"什么情况下说这句话"。不形成条件树——每个 condition 是独立的过滤器，不依赖其他 condition 的结果。这保持了"从上到下"的线性阅读体验。

```yaml
# ✅ 线性阅读：从上到下，每个 action 前面说明条件
actions:
  - type: ai_say
    condition: "{{risk_level}} == 'high'"
    prompt: "我们先做一个稳定化的练习..."

  - type: ai_ask
    condition: "{{risk_level}} != 'high'"
    prompt: "能具体描述一下最近一次焦虑发作的情境吗？"

  - type: ai_think
    # 无条件 = 总是执行
    prompt: "总结本轮收集到的关键信息"

# ❌ 嵌套分支——程序性思维，破坏线性
actions:
  - type: if:
      condition: "{{risk_level}} == 'high'"
      then: [...]
      else:
        if:
          condition: "{{anxiety_type}} == 'social'"
          then: [...]
          else: [...]
```

**condition 评估语义**：

| condition 值   | 行为                          |
| -------------- | ----------------------------- |
| 未设置（空）   | 总是执行                      |
| 表达式为 true  | 执行该 action                 |
| 表达式为 false | 跳过该 action，继续评估下一个 |

数组顺序即优先级——排在前面的先评估。这是线性思维的胜利：不需要 `priority` 字段，顺序本身就表达了意图。

**边界**：如果一个条件的评估依赖于另一个条件的结果（形成条件树），它超出了 DSL condition 的范畴，应交由意识系统处理。

#### 策略 1.2：主题展开（Topic Expansion）

**面对的问题**：需要在多个实体上重复相同的咨询逻辑（例如："对每一位家庭成员，问同样一组关系探索问题"）。程序员思维会引入 `for` 循环——但循环在执行时也是串行的，一次一个迭代。循环只是把"串行序列"包装成了程序性语法。

**策略**：放弃循环，让引擎把"按列表依次展开为一个个 Topic"这件事自动化。咨询师声明 `expand_by` 指向一个列表变量，引擎生成连续的 Topic 序列。全部展开，没有性能配置——咨询师不调性能参数。

**为什么在咨询领域可以这样做**：实际咨询中，需要展开的对象列表规模很小——几位家庭成员、几个症状、几个生活事件。正是这个领域特性，让我们可以彻底放弃循环语法。

```yaml
topics:
  - id: explore_caregiver
    expand_by: '{{caregivers}}'
    item_variable: caregiver # 实例中 {{caregiver.name}} 等可用
    actions:
      - type: ai_ask
        prompt: '你和{{caregiver.name}}的关系是怎样的？'
      - type: ai_ask
        prompt: '{{caregiver.name}}对你的成长有什么影响？'
```

展开后就是连续的线性 Topic 序列——Topic 1 → Topic 2 → ... → Topic N。列表变化时引擎自动同步——新增成员追加 Topic，移除成员自动去除。咨询师只需要关心"按什么列表展开"。

#### 策略 1.3：不提供程序性控制流

下列构造被明确排除在 DSL 之外，它们都可以追溯到"破坏线性"这个根原因：

| 被排除的构造                | 破坏线性的方式                 | 替代机制                |
| --------------------------- | ------------------------------ | ----------------------- |
| `for` / `while` / `loop`    | 需要咨询师理解迭代和退出条件   | `expand_by` 主题展开    |
| `goto` / `jump` / `skip_to` | 打断顺序阅读，需要追踪跳转目标 | 意识 orchestration      |
| `if/else` 配对              | 隐含互斥分支和分支树           | 一级 `condition`        |
| `switch/case`               | 多路分支，需要理解分支优先级   | 一级 `condition` + 顺序 |
| 子脚本调用                  | 需要理解调用栈和参数传递       | 未来：Topic 模板复用    |
| 变量赋值/计算               | 需要理解变量状态和求值顺序     | 变量提取引擎            |

#### 策略 1.4：三种脚本分离（主线 + 意识 + 技术）

**面对的问题**：P1 要求脚本是线性的——不能有分支、跳转、循环。但真实咨询中，咨询师需要"边执行边觉察边调整"。**灵活性不能写在主线里，放哪？**

**策略**：在 DSL 中提供三种独立的声明块——主线剧本 + 意识脚本 + 咨询技术脚本。它们共享同一个变量作用域，但走不同的执行通道：主线走确定性解释器，意识走 LLM 驱动的模式匹配引擎。

```
主线剧本                    支线觉察（意识脚本）          技法套路（咨询技术脚本）
──────────────────          ──────────────────          ──────────────────────
定义：正常情况下的咨询流程     定义：需要留意的信号和       定义：可复用的咨询技法模式
Phase → Topic → Action       干预策略                    可被主线引用或意识触发
condition / expand_by        跨轮模式识别（LLM驱动）      封装具体的咨询技术
exit_condition               检测→触发→干预              参数化，按需实例化
```

```yaml
# 一个 Phase 中三种脚本的协同
phases:
  - id: anxiety_assessment
    topics:
      - id: trigger_exploration
        actions: # ← 主线剧本
          - type: ai_ask
            prompt: '最近一次焦虑发作是什么时候？'
          - type: ai_ask
            prompt: '当时发生了什么？'

    consciousness: # ← 意识脚本
      - id: resistance_monitor
        prompt_template: resistance-detection-v1
        trigger:
          cooldown_rounds: 1
          min_rounds: 2
        intervention:
          mode: feedback

    techniques: # ← 咨询技术脚本
      - id: grounding_exercise
        ref: techniques/grounding-5-4-3-2-1
        trigger_on: '{{anxiety_level}} >= 7'
```

三种脚本协同产生的不是"一个功能丰富的脚本"，而是一个**有节奏、有觉察、有深度的执行系统**——主线保证节奏不偏，意识保证变化能被捕捉，技术脚本保证专业深度。

这正是"强大"的实现方式——不是靠一条原则，而是靠 P1 约束下催生出的架构选择。

**判断标准**：

- 如果一个逻辑描述的是"如果出现 X 状况，我应该怎么做" → 意识脚本
- 如果一个咨询技法在多个脚本中反复出现 → 咨询技术脚本
- 主线剧本只描述"正常情况下，我这样做"

### 原则二：不暴露工程问题（No Engineering Concerns Exposed）

**对应三角**：简单

**表述**：DSL 面向咨询师，不是面向工程师。脚本中的每一个语法、每一个配置项，都必须来自**咨询领域的自然问题**，而不是软件工程的优化焦虑。选择哪个大模型、怎么展开话题、性能参数如何调优——这些是引擎后台的智能要解决的问题，不应当出现在咨询师的视野里。

**为什么过去会暴露工程问题**：为了让脚本"强大灵活"，传统的做法是提供大量配置项——模型参数、展开策略、缓存开关。但这些配置的本质是把工程决策外包给了咨询师。咨询师不该思考"这个场景该用 sequential 还是 all 展开"，ta 只该思考"对哪些对象展开这个话题"。

**哲学依据**：认知锚定原则 — 咨询师用 DSL 锚定咨询经验，不是用 DSL 管理软件工程。引擎是经验的执行者，也是工程问题的屏蔽层。

**DSL 设计含义**：

- ✅ 咨询师只看到咨询领域的决策：对谁展开、提取什么变量、留意什么信号
- ✅ 工程决策由引擎后台的智能解决：模型选择、展开性能、缓存策略
- ❌ 暴露模型名称/参数让咨询师选择
- ❌ 暴露性能配置（如 `expand_strategy: sequential | all`）
- ❌ 暴露基础设施选项（如缓存开关、超时时间）

**判断标准**：如果咨询师面对一个配置项时需要理解工程概念才能做出选择，这个配置项就不该存在。引擎应该替咨询师做这个决定。

**覆盖的决策场景**：

| 场景                   | 暴露的工程问题                   | 不暴露原则           |
| ---------------------- | -------------------------------- | -------------------- |
| `for` / `while` 循环   | 循环是程序性构造，咨询师不写代码 | 不提供循环语法       |
| `expand_strategy` 配置 | 逐个/全部展开是性能优化          | 不提供展开策略选项   |
| `goto` / `jump` 跳转   | 跳转是控制流管理                 | 不提供跳转语法       |
| 模型选择配置           | 选哪个 LLM 是工程决策            | 引擎后台自动选择     |
| 变量赋值/计算          | 变量状态和求值顺序是程序语言概念 | 变量提取引擎处理     |
| 嵌套条件               | 条件树是逻辑编程                 | 意识系统处理复杂分支 |

**语法和配置的增加决策流程**：

```
提案：是否需要在 DSL 中增加 X（语法或配置项）？
    │
    ├── X 回答的是咨询领域的问题，还是工程领域的问题？
    │       └── 工程问题 → ❌ 不加入，由引擎后台解决
    │
    ├── X 在 ≥3 个独立脚本中被需要？
    │       └── 否 → ❌ 不加入
    │
    ├── X 能否由意识系统处理？
    │       └── 是 → 优先用意识，不加入 DSL
    │
    ├── X 能否用现有构造组合实现？
    │       └── 是 → ❌ 不加入
    │
    ├── X 是否需要咨询师理解编程或工程概念？
    │       └── 是 → ❌ 不加入
    │
    └── 通过 → 标记 experimental，观察后决定是否转 stable
```

第一步（领域 vs 工程）是最重要的过滤器。大多数被拒绝的提案在这一步就被拦截了——不是语法不好，而是它回答错了问题。

### 原则三：语法确定性（Syntax Determinism）

**对应三角**：可干预

**表述**：DSL 中每个语法元素有且只有一种写法，且有明确的、机器可读的约束定义。AI 面对 DSL 时不在"多种等效写法"中选择——选择越多，出错概率越大。AI 生成的脚本应能通过结构化验证即时发现错误，并获得精确的修复指引。

**为什么需要这条原则**：AI 写脚本时的主要出错来源是"猜"——猜属性名是 `extraction_method` 还是 `extractMethod`，猜枚举值是 `sequential` 还是 `one_by_one`，猜某个属性应该放在 Action 上还是 Topic 上。每当 DSL 中存在歧义、等价写法或隐式约束，AI 就有概率猜错。语法确定性的本质是**让 AI 不需要猜**。

**哲学依据**：认知锚定原则 — 低熵符号结构同时锚定人类认知和 AI 生成。DSL 的确定性不仅服务咨询师的可读性，也服务 AI 的可生成性。

**DSL 设计含义**：

- ✅ Schema 先行：每个属性有明确的类型、必填/可选、枚举值。用 JSON Schema / Zod 定义，机器可读
- ✅ 一字一义：一个概念只有一个属性名。不在不同层级复用同一个名字表示不同含义
- ✅ 结构化验证反馈：AI 生成脚本后，引擎返回的不是"语法错误"，而是精确的错误定位和修复指引
- ✅ 枚举值封闭：枚举类属性的可选值是有限且显式的。不使用开放字符串
- ❌ 语法糖：不给同一种语义提供多种等效写法
- ❌ 隐式默认值：任何默认行为必须显式声明，AI 不能依赖"没写就自动怎样"

**判断标准**：AI 是否能仅凭 Schema 定义（不需参考示例）就生成语法正确的脚本？如果 AI 需要看了示例才知道"这里应该怎么写"，语法还不够确定。

**四个策略**：

#### 策略 3.1：Schema 先行

每个属性都有精确的机器可读定义。不是写在文档里的自然语言描述，而是 Zod schema 或 JSON Schema——AI 可以直接读取并据此生成。

```typescript
// 示例：Topic 中 expand_by 相关属性的 Schema 定义
const TopicSchema = z.object({
  id: z.string().describe('Topic 唯一标识'),
  expand_by: z
    .string()
    .optional()
    .describe('指向一个列表变量，引擎为该列表的每个元素生成一个 Topic 实例'),
  item_variable: z.string().optional().describe('展开实例中，当前元素以该名称注入变量作用域'),
  actions: z.array(ActionSchema).describe('该 Topic 包含的 Action 序列'),
});
```

AI 读取这个 Schema 就知道：`expand_by` 是可选的字符串，指向列表变量；`item_variable` 只在 `expand_by` 存在时才有意义。

#### 策略 3.2：一字一义

同一个概念不在 DSL 中拥有多个名字，同一名字不在不同层级表示不同含义。

```yaml
# ❌ 不同层级用不同名字表示同一个概念
actions:
  - type: ai_ask
    extraction_method: pattern     # ← 这里叫 extraction_method
    exit_condition: "{{done}}"
    exit_decision: rule            # ← 这里叫 exit_decision

# ✅ 统一命名
actions:
  - type: ai_ask
    extraction_method: pattern
    exit_method: rule              # exit 统一用 _method 后缀
```

#### 策略 3.3：结构化验证反馈

AI 生成脚本 → 引擎验证 → 返回的不是"语法错误"，而是精确的定位和可用值列表。

```
# ❌ 模糊错误——AI 不知道哪里错了
Error: Invalid script configuration.

# ✅ 结构化验证反馈——AI 能据此修复
Error in phases[0].topics[2].actions[1]:
  - 'expand_strategy' is not a valid property. Did you mean one of:
    ['expand_by', 'item_variable', 'actions']?
  - Each Topic must have at least 1 action.
```

这种反馈让 AI 能**自动修复**——不是放弃生成，而是读错误信息 → 修正 → 重试。

#### 策略 3.4：禁止语法糖

一种语义只有一种写法。不提供"简化写法"和"完整写法"两种选择。

```yaml
# ❌ 两种等效写法——AI 需要在其中选择
# 写法 A：简写
condition: "risk_high"

# 写法 B：完整
condition: "{{risk_level}} == 'high'"

# ✅ 只有一种写法
condition: "{{risk_level}} == 'high'"
```

AI 的选择不是自由——AI 的"选择"本质是在两个都可能正确的选项中滚动骰子。每次滚动都有概率出错。去掉选择，去掉出错概率。

## 4. 原则的优先级

当原则之间出现张力时：

1. **P1 线性优先** — 最高优先。线性结构是 DSL 的根基。
2. **P2 不暴露工程问题** — 当线性结构已保证时，确保界面不泄露工程细节。
3. **P3 语法确定性** — 语法设计必须支持 AI 高准确率生成。当"确定性"与"灵活性"冲突时，优先确定性。

P1 和 P2 方向一致——都服务"简单"——通常不冲突。P3 可能与 P1 产生张力：例如，为了提高 AI 生成准确率，可能需要引入更严格的 Schema 约束或额外的元数据字段。此时 P1 优先——不能为了确定性而破坏线性结构。
