## 1. 为什么需要「意识」

### 1.1 咨询师的两种思维活动

一个有经验的人类咨询师，在会谈过程中同时在运转**两种不同性质的思维**：

```
咨询师在听来访者说话时：

  思维A（回应驱动）:                       思维B（观察驱动）:
  "你想说的是..."                          "他又提到母亲了，第三次了"
  "能具体描述那次被批评后你的感受吗？"        "上次他说关系很好，这次描述的完全是另一回事"
  "你说的这种情况，在心理学上叫做..."         "他对这个话题有明显的回避"
  "我们试一个练习..."                       "愤怒的情绪转瞬即逝——他在压下去"

  特点:                                    特点:
  · 朝外的——要说给来访者听                   · 朝内的——不直接对来访者说
  · 按咨询计划推进                           · 识别状况对计划进行调整
  · 每次用户回复需要有回应                    · 可能10次回复后才产生一个实质性洞察
```

这两种思维**同时发生、互不阻塞**。咨询师从来不是"先观察完，再开始说话"——他一面自然地回应来访者，一面在脑中累积观察和判断。

HeartRule 引擎用两条架构路径来分别模拟这两种思维：

- **主线**：负责思维A——**回应**来访者。它按脚本推进对话，产出语言、行为（如出示图表、触发动作）等对外的输出。引擎中由Phase→Topic→Action 的脚本体系在支撑它。
- **支线**：负责思维B——运行**意识**。它不直接对来访者说话，而是在背后观察对话、监测信号，必要时向主线提出回应策略建议。一个脚本中可以根据 Phase/Topic 启动不同的意识。

两条线共享同一个对话流和记忆池，同时运转、互不阻塞——正如人类咨询师的两颗大脑。

### 1.2 一个案例：主线能处理的 vs 支线意识应该捕获的

以下是一个 CBT 焦虑咨询的片段，展示主线与支线意识的协作如何在三轮对话中递进。

**背景**：李先生，34 岁，第 4 次咨询。当前 Phase: "核心问题探索"，Topic: "工作焦虑的触发模式"。本 Phase 的脚本中配置了「情绪否定检测」意识，同时还有一个「自责句式检测」意识因阈值不足未触发。

> **前情**：第 2 次会谈中，用户谈到被领导批评时说：「上次被领导批评后，我什么都没说，回家自己生了很久的闷气，觉得自己特别没用。」

```
第1轮
  AI (ai_ask): "上次你提到工作中经常感到焦虑。这两周有没有具体的触发场景？"
  用户: "上周老板在全员会上批评我们部门的项目延期了。我当时特别生气，
         但是当着所有人的面什么都不敢说，就一直忍着。"

第2轮
  AI (ai_ask): "上次你也说过，被批评后会把情绪压下去——那次你回家自己
       生了很久的闷气。这次你说'特别生气'，能多说一点吗？"
  用户: "其实也没什么，老板说得也对，确实是我们延期了。我这个人可能
         就是太敏感了——上次朋友也说我小题大做，想太多了。"
```

在第 1 轮中，主线按脚本收集触发场景。同时，**recall** 自动用用户原话检索历史记忆，命中了第 2 次会谈的相似表述。这条记忆被注入第 2 轮提示词——注意第 2 轮 AI 的第一句话（"上次你也说过...那次你回家自己生了很久的闷气"），这正是 recall 对主线的可见影响。

现在看第 2 轮中用户做了什么：他说了"其实也没什么"——在 AI 追问情绪之后，立刻收回。而且不止一层：

- "其实也没什么" ← 直接否定情绪的重要性
- "老板说得也对" ← 合理化对方，削弱自己情绪的正当性
- "我这个人可能就是太敏感了" ← 把问题归因为自身性格缺陷
- "朋友也说我小题大做" ← 引用外部观点佐证自我否定

一个"特别生气"被四层自我否定包裹。如果没有意识干预，主线在"核心问题探索"的任务框架下，自然会沿着用户打开的对话线索继续——可能是追问朋友关系，也可能回到收集更多触发场景。这都是合理的脚本执行，不是主线做错了什么。只是主线聚焦在「推进信息收集」这个任务上，不会自动注意到「用户在被追问情绪时收回了情绪」这个现象本身。

```
第3轮
  AI (ai_ask): "你刚说了'特别生气'，然后马上就说'其实也没什么'了。
       先不管是不是太敏感——那个生气的瞬间，你心里想做什么？想说什么？"
  用户: "我当时就想站起来说'这不是我的问题，是客户一直在改需求'。
         但我做不到，从小到大都这样，有意见也憋着。"
```

**第 2 轮和第 3 轮之间发生了什么**：第 2 轮主线回应完成后，支线异步运行了「情绪否定检测」意识。它检测到：用户在被追问情绪时，用四层否定收回了自己表达的情绪。触发后，它向第 3 轮提示词注入建议：「用户在否定自己的情绪。不要接受他的自我否定——温和地把他的情绪还给他，帮他把被否定的那个'特别生气'展开。」

**对比**——如果主线没有收到这条建议，第 3 轮更可能的回应是顺着用户引出的话题走：「你朋友说你小题大做？能具体说说那次吗？」——这是合理的咨询回应，但它接受了用户的自我否定，绕过了那个被压下去的愤怒。而有了意识建议后，第 3 轮 AI 做了不同的选择：不接受"其实也没什么"，把"特别生气"还给他，并追问生气时的行为冲动（"想做什么？想说什么？"）。

**这条对话展示了什么**：

- **主线做了它该做的事**：按脚本收集信息（第 1 轮），利用 recall 关联跨会谈模式（第 2 轮），共情和追问（第 3 轮）。每一步都是正确的。
- **支线意识做了一件主线不会做的事**：检测到用户在被追问情绪时否定自己的情绪——并且是在 AI 的追问方向（"能多说一点吗？"）已经触及情绪之后，用户主动收回的。
- **意识改变了主线的行为**：有意识和没有意识，第 3 轮走了两条不同的路。前者跟着用户的自我否定走（"朋友说你什么？"），后者把被否定的情绪还给他（"先不管是不是太敏感——那个生气的瞬间"）。主线本身有能力走这两条路，但走哪条路的判断，来自意识。

（本 Phase 还配置了「自责句式检测」意识，监测"是我不好""我太敏感了"等自我归因句式是否跨轮重复。本轮它仅在第 2 轮出现一次，未达到 `min_rounds=2` 的触发阈值——如果后续对话中再次出现，它会在那一轮触发干预。）

### 1.3 从案例到架构：人类咨询师经验的两种沉淀方式

```
人类咨询师的经验
        │
        ├──→ 「做什么」──→ 主线 (Phase→Topic→Action)
        │      · 这个阶段该收集什么信息
        │      · 用什么技术、按什么流程
        │      · 产出: 回应（语言、行为等）
        │
        └──→ 「留意什么」──→ 支线意识 (consciousness)
               · 在这个阶段中，从什么角度观察
               · 启动哪些意识、识别什么信号
               · 产出: 对主线回应策略的建议
```

一个咨询师在写脚本时，同时在表达两种经验：「做什么」和「留意什么」。主线已经为"做什么"提供了完整的编码格式——Phase→Topic→Action。本设计为"留意什么"提供同等级别的编码格式——在 Phase/Topic 下声明意识、配置触发条件、定义干预方式。两种经验共享同一套脚本体系，共同构成一个完整的咨询会话定义。

## 2. 运行机制

### 2.1 每轮的运转顺序

主线和支线是两条独立的执行路径——各自调用 LLM，各自产出结果。它们共享的是数据层（对话流、记忆池、recall 结果），不是线程。每轮用户回复后，系统的运转顺序如下：

```
每轮用户回复后:

  1. recall 联想（主线同步阶段开始）
     用户原话 + 变量名锚点 → Hindsight recall → 记忆片段
     → 同时服务于主线和支线意识

  2. 主线 LLM 生成回应（同步——用户等待）
     接收: chat 上下文 + recall 联想 + 当前脚本状态
     产出: 给用户的回应 + 用户语义完整性标记（utterance_complete: boolean）
     → 主线在理解用户输入时，天然知道用户是"讲到一半"还是"说完了完整意思"
     → 回应立即返回给用户，主线本轮的同步工作完成

  3. 支线运行意识分析（异步——用户不等待，在主线回应之后执行）
     a. 检查主线的语义完整性标记：如果用户本轮仅说了半句话（utterance_complete=false），
        跳过本轮意识分析——不完整的输入无法支持有效判断
     b. 收集所有活跃意识的 recall 需求，合并为一次 recall（如有）
     c. 按上下文窗口和触发频率分组：相同窗口和频率的意识可合并为一次 LLM 调用；
        意识数量过多时拆分为多次调用，以保证分析质量
     d. 各意识产出结构化分析结果
     e. 如果两个或以上意识同时触发了干预 → 仲裁 LLM 评估冲突、合并建议
        （单个意识触发的干预直接进入下一步，不经过仲裁层）
     f. 统一后的干预建议注入下一轮主线提示词，或调整脚本执行流程

     其中 process_quality（流程质量监测）作为内置意识始终参与，不使用 recall——
     它仅观察近几轮的对话即可判断。监测基于五个变量综合评估当前轮状态：
     信息完整度、用户投入度、情绪强度、回答相关性、进度建议，
     最终判定为 blocked / off_topic / insufficient / normal 四种状态之一，
     产出 rephrase / comfort / accept_partial / skip 等策略建议。
     脚本定义的意识按需加入。
```

关键设计点：

- **语义完整性门控**：主线在理解用户输入时，天然知道用户是"讲到一半"还是"说完了完整意思"。支线用这个标记作为意识分析的前置条件——用户话只说了一半时不触发分析，避免基于不完整输入做无效判断。`cooldown_rounds` 是补充约束（"即使完整，也不要每轮都跑"），而非唯一门控。
- **同步/异步分离**：主线生成回应是同步的——用户等待这步完成。意识分析是异步的——用户已经收到回应，不感知意识的运行时间。
- **执行独立，数据共享**：主线和支线各自独立调用 LLM，各自有独立的提示词和输出目标。但它们共享同一个对话流、记忆池和 recall 结果——支线看到的对话和主线看到的是一致的。
- **合并不是规则，是优化**：相同上下文窗口和触发频率的意识可以合并为一次 LLM 调用以节省成本，但这取决于调度层的判断——意识过多时拆分以保证分析质量，需要不同 recall 上下文的意识也无法合并。
- **仲裁层**：只有当两个或以上意识同时触发干预时，才启动仲裁 LLM。仲裁不重新做识别分析，而是检查建议是否存在冲突、按严重程度排优先级、合并互补建议、消除矛盾。单个意识触发的干预直接通过。
- **干预方式**：意识触发后有三种干预路径——(a) 向主线提示词注入策略建议，影响回应方式；(b) 调整话题（切换、暂停、取消、插入）；(c) 调整话题内动作（修改动作顺序、替换动作参数）。(b)(c) 需要更高的严重级别和更严格的触发条件。具体走哪条路由 `intervention.mode` 配置。
- **跨轮传递**：意识的产出不能影响当前轮（回应已经发出），只能注入下一轮。

### 2.2 轻量干预与重量干预

主线总是快的——用户每轮都在等待回应。但意识不是一概而论的"慢"。真实咨询师的两类留意可以对应两种不同深度的干预：

|                  | 轻量干预                                        | 重量干预                                                          |
| ---------------- | ----------------------------------------------- | ----------------------------------------------------------------- |
| **真实对应**     | 咨询师即时注意到信号，下一句话就调整            | 咨询师跨时间积累判断，形成策略调整                                |
| **触发门槛**     | 低——本轮对话即可判断                            | 高——需要跨轮/跨会话累积证据                                       |
| **典型触发条件** | 检测到信号 + 严重度达阈值                       | 同一信号累积出现达 `min_rounds`，或 `insightForSlowThinking` 非空 |
| **干预方式**     | 向主线提示词注入策略建议                        | 调整脚本流程（切换话题、调整动作序列）                            |
| **生效时机**     | 下一轮                                          | 可能需要多轮积累后才产出最终判断                                  |
| **典型意识**     | process_quality（每轮评估）、emotion_trajectory | strategy_adaptation（策略调适）、contradiction_detect             |

一个意识走轻量还是重量，由它自身的 `intervention.mode` 配置和累积的证据决定——轻量干预的提示词注入和重量干预的流程调整是同一套机制在不同证据强度下的输出。主线不参与这个决策：它只负责按脚本和当前上下文生成回应，recall 联想是信息检索，不是"思考"。

### 2.3 意识的生命周期

#### 2.3.1 意识与脚本的绑定

意识定义在 YAML 脚本的 Phase 或 Topic 级别。理由是：

- 不同 Phase 需要留意的信号不同（评估阶段留意情绪基线，干预阶段留意认知歪曲）
- 意识列表和主线话题列表是配套的——咨询师在写「这个阶段主线做什么（回应什么）」的同时，自然知道「支线该留意什么（启动哪些意识）」
- 不在当前 Phase/Topic 范围的意识不加载，减少计算成本

**内置意识的例外**：内置意识不绑定任何 Phase 或 Topic，由系统始终加载——它们是所有咨询领域都需要的通用观察层，不需要在 YAML 中声明。当前定义了两种：

- **`process_quality`（流程质量监测）**：每轮评估对话流程是否正常。`cooldown_rounds=0`，`recall.enabled=false`，`context_window=3`。走轻量干预，产出话术级策略建议（rephrase / comfort / accept_partial / skip）。
- **`strategy_adaptation`（执行策略调适）**：当轻量干预多次尝试后流程仍然受阻，评估当前执行计划本身是否失效。`min_rounds` 更高、`context_window` 更大、需要 recall 查跨轮历史。走重量干预，产出脚本级调整建议（切换话题、调整动作序列）。不轻易触发——只在累积证据表明策略失效时才干预。

#### 2.3.2 触发机制

```
每个 Phase/Topic:
  ├─ 内置意识始终参与（process_quality + strategy_adaptation）
  ├─ 绑定 1-N 个脚本定义意识
  ├─ 每个意识有:
  │   ├─ 冷却时间（cooldown_rounds）：避免频繁触发（内置意识为 0）
  │   ├─ 上下文窗口（lookback_messages）：观察多少轮对话
  │   └─ 是否需要 recall 记忆上下文
  │
  └─ 执行（仅当 user_utterance_complete=true 时）:
      ├─ 收集需要 recall 的意识的查询方向
      ├─ 做一次 recall（合并所有意识的记忆需求）
      ├─ 合并所有意识的提示词 + 共享的记忆上下文 → 一次 LLM 调用
      └─ 解析各意识的输出
```

#### 2.3.3 意识的输出

每个意识产出结构化字段：

```typescript
interface ConsciousnessResult {
  consciousnessId: string; // 意识标识
  triggered: boolean; // 是否检测到关注信号
  severity: 'low' | 'medium' | 'high';
  summary: string; // 检测到的信号简述
  suggestedIntervention: string | null; // 给主线的建议
  insightForSlowThinking: string | null; // 如果值得深挖，给慢思考的线索
}
```

如果 `triggered = false`，说明本轮在该视角下无关注信号，不产生干预。

如果 `suggestedIntervention` 非空，注入主线 prompt（通过 `session.metadata.latestMonitorFeedback` 通道，由统一的意识执行管线管理）。

如果 `insightForSlowThinking` 非空，可以触发慢通道做深度 recall + LLM 综合。

### 2.4 意识的识别方式与干预手段

一个意识在系统中的运作可概括为：**识别特定状况 → 评估干预必要性 → 执行干预**。

**识别方式**。意识如何判断"状况出现了"？分两种：

| 方式         | 机制                                                                                         | 适用场景                                                                          |
| ------------ | -------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| **直接识别** | 意识 LLM 分析当前对话片段，直接判断信号是否出现。检测到即判定 `triggered: true`              | 单轮内就能判断的模式——如情绪否定（"其实也没什么"立刻收回情绪）                    |
| **累计识别** | 意识检测到信号后不立即触发，记录出现次数。同一模式跨轮出现达到 `min_rounds` 阈值时才判定触发 | 需要确认是模式而非偶然的信号——如自我归因句式（"是不是我哪里没做好"需跨至少 2 轮） |

**干预手段**。意识触发后如何影响主线？分三种：

| 方式                     | 机制                                                                                            | 示例                                                  |
| ------------------------ | ----------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| **向主线提示词注入建议** | 意识的 `suggestedIntervention`（含判断理由和策略建议）注入下一轮主线 LLM 提示词。不改变脚本结构 | 情绪否定检测 → 注入"不接受他的自我否定，把情绪还给他" |
| **调整话题**             | 切换当前 Topic：暂停、取消当前话题，或插入新话题                                                | 流程严重受阻 → 暂停当前 Topic，插入一个情绪安抚话题   |
| **调整话题内动作**       | 修改当前 Topic 下的动作序列：跳过某个 Action、调整顺序、替换参数                                | 信息收集方式不当 → 将 `ai_ask` 调整为更温和的变体     |

调整话题和调整动作的干预需要比注入提示词更高的 `severity_threshold` 和更严格的触发条件。具体走哪种干预路径，由意识的 `intervention.mode`（feedback / orchestration / both）和严重级别共同决定。

### 2.5 内置意识与脚本定义意识

意识系统分为两个层次，共享相同的执行管线和反馈通道：

| 层次             | 定义方式                         | 加载方式                    | 例子                                                                                 |
| ---------------- | -------------------------------- | --------------------------- | ------------------------------------------------------------------------------------ |
| **内置意识**     | 代码内置，不随脚本变化           | 始终加载，所有会话共享      | `process_quality`（流程质量）——轻量干预；`strategy_adaptation`（策略调适）——重量干预 |
| **脚本定义意识** | YAML 脚本中 Phase/Topic 级别声明 | 按当前 Phase/Topic 动态加载 | emotion_trajectory, contradiction_detect, resistance_monitor                         |

内置意识的设计原则：**默认启动，无需声明**。编写脚本的咨询师不需要关心它们的存在——它们作为基础设施自动运行。但它们的提示词可以被 Custom 层覆盖，以适应不同咨询领域的判断标准。

`process_quality` 是原 Monitor 系统的重构形态；`strategy_adaptation` 是新定义的重量干预层意识。两者都实现统一的 `ConsciousnessResult` 接口，在同一管线上运行。

两者的干预都通过同一个反馈通道注入主线 prompt。运行时，内置意识始终参与执行管线，脚本定义意识按需加入。相同上下文窗口和触发频率的意识可以合并为一次 LLM 调用以节省成本，意识数量过多时则拆分以保证分析质量。

## 3. YAML 脚本格式

### 3.1 基本结构

```yaml
# CBT 焦虑干预脚本 (示例)
phases:
  - id: assessment
    topics:
      - id: evaluate_anxiety
        actions: [...]

    # 绑定在 Phase 级别的意识
    consciousness:
      # 内置意识（始终加载，YAML 中无需声明，以下仅展示配置形态）
      # - id: process_quality           # 流程质量监测：轻量干预
      #   built_in: true
      #   cooldown_rounds: 0
      #   recall.enabled: false
      #   context_window: 3
      #   intervention.mode: feedback
      # - id: strategy_adaptation       # 执行策略调适：重量干预
      #   built_in: true
      #   cooldown_rounds: 5
      #   recall.enabled: true
      #   context_window: 10
      #   intervention.mode: orchestration

      - id: emotion_trajectory
        name: 情绪轨迹检测
        description: 追踪用户在评估阶段的情绪变化模式
        prompt_template: emotion-detection-v1 # 指向提示词模板
        recall:
          enabled: true
          focus: # 该意识关注哪些记忆维度
            - experience # 用户经历
            - opinion # 已有判断
          query_hint: '用户情绪表达的变化趋势，情绪触发因素'
        trigger:
          cooldown_rounds: 2 # 每 2 轮最多触发一次
          min_rounds: 3 # 至少积累 3 轮对话才开始分析
        context_window: 8 # 观察最近 8 轮
        intervention:
          mode: feedback # feedback | slow_thinking | orchestration | both
          severity_threshold: medium # low/medium 以上才触发干预

      - id: contradiction_detect
        name: 叙事矛盾检测
        description: 检测用户是否存在前后表述不一致
        prompt_template: contradiction-detection-v1
        recall:
          enabled: true
          focus:
            - experience
            - worldFacts
          query_hint: '用户对关键关系/事件的描述变化，前后不一致的信号'
        trigger:
          cooldown_rounds: 3
          min_rounds: 5
        context_window: 10
        intervention:
          mode: slow_thinking # feedback | slow_thinking | orchestration | both

      - id: resistance_monitor
        name: 阻抗监测
        description: 检测用户是否在回避或抵触当前话题
        prompt_template: resistance-detection-v1
        recall:
          enabled: false # 不需要记忆上下文
        trigger:
          cooldown_rounds: 1
          min_rounds: 2
        context_window: 5
        intervention:
          mode: feedback # feedback | slow_thinking | orchestration | both
```

### 3.2 格式字段说明

| 字段                              | 类型                                                       | 说明                                                                               |
| --------------------------------- | ---------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `id`                              | string                                                     | 意识唯一标识                                                                       |
| `built_in`                        | boolean                                                    | 是否为内置意识。内置意识始终加载，不绑定 Phase/Topic，不在 YAML 中声明。默认 false |
| `name`                            | string                                                     | 人类可读名称                                                                       |
| `description`                     | string                                                     | 该意识从什么角度观察什么                                                           |
| `prompt_template`                 | string                                                     | 指向 `_system/config/{scheme}/` 下的提示词模板名                                   |
| `recall.enabled`                  | boolean                                                    | 是否需要先调取记忆上下文                                                           |
| `recall.focus`                    | string[]                                                   | 关注的记忆类型（experience / opinion / worldFacts / observation）                  |
| `recall.query_hint`               | string                                                     | 作为 recall 查询的补充方向，与用户原话一起构成 recall 输入                         |
| `trigger.cooldown_rounds`         | number                                                     | 最小间隔轮数                                                                       |
| `trigger.min_rounds`              | number                                                     | 至少积累多少轮对话才开始分析                                                       |
| `context_window`                  | number                                                     | 观察多少轮对话上下文                                                               |
| `intervention.mode`               | 'feedback' \| 'slow_thinking' \| 'orchestration' \| 'both' | 干预方式：反馈到提示词 / 触发慢思考 / 调整脚本流程 / 反馈+慢思考                   |
| `intervention.severity_threshold` | 'low' \| 'medium' \| 'high'                                | 低于此严重级别不触发干预                                                           |

## 4. 实施路径

### Phase 1: 意识框架 + 一个示例意识（2-3 周）

- **重构 Monitor 代码为统一意识管线**：
  - `MonitorOrchestrator` 的核心调度逻辑演化为 `ConsciousnessRunner`——负责收集所有活跃意识、合并 recall 需求、合并提示词、调度一次 LLM 调用、解析多意识输出
  - `AiAskMonitorHandler` + Monitor 提示词模板 → 重构为 `process_quality` 内置意识的处理器，功能和提示词内容不变，改为实现统一的 `ConsciousnessHandler` 接口
  - 保持 `session.metadata.latestMonitorFeedback` 反馈通道不变，不破坏已有行为
- 实现脚本定义意识的 YAML 解析和绑定（Phase/Topic 级别）
- 实现意识合并执行管线：
  - 收集需要 recall 的意识的查询方向 → 拼成一次 recall
  - 合并所有意识的提示词（内置 + 脚本定义）+ 共享记忆上下文 → 一次 LLM 调用
  - 解析各意识输出
- 实现一个示例脚本定义意识：`emotion_trajectory`（情绪变化检测）
- 验证内置意识（原 Monitor）和脚本定义意识在同一管线上协作

### Phase 2: 多意识 + 慢思考联动（2-3 周）

- 添加 2-3 个新意识（矛盾检测、阻抗监测、认知歪曲识别）
- 实现意识的不同 `intervention.mode`：反馈到提示词、触发慢思考、调整脚本流程
- 实现意识的冷却时间和上下文窗口控制
- 测试多意识合并调用的成本和质量

### Phase 3: 意识提示词模板系统（1-2 周）

- 将意识提示词模板纳入现有的两层模板解析体系（`_system/config/custom/{scheme}/consciousness/`）
- 支持领域定制意识模板（CBT 领域 vs 心理动力学领域的不同观察维度）
