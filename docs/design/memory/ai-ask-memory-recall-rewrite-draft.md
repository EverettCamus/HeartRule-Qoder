# ai_ask 的记忆调用

> **本文回答一个问题**：ai_ask（脚本里的提问动作）在什么情况下需要查记忆，每种情况用什么机制。
>

## 1. 三个问题

主线 LLM 的 prompt 里只有「最近聊天」的有限回合——本次会谈早些的内容、跨会谈的内容都不在。凡是 AI 需要用到窗口外信息的时候，就是记忆该介入的时候。ai_ask 上有三个这样的时候：

**问题一：听不懂用户在说什么。** 用户说「上次说的那个事，我回去又想了想」「李光最近又联系我了」——指代的东西在窗口外。不查记忆，AI 只能反问"李光是谁？"

**问题二：被反问，答不上依据。** 用户说「那你觉得我该怎么办？」——AI 这一轮从追问者变成回答者。"该怎么办"要有既往方案、用户试过什么、效果如何做依据。不查，只能给空泛的通用建议，像第一次见面的机器人。

**问题三：要收的信息，用户以前讲过，又问一遍。** 脚本规划本话题要了解「小时候的主要抚养者」，不代表用户之前没提过。收集前先回顾一遍记忆，AI 开口就能带上"你之前提过…"，而不是让用户把讲过的话再讲一遍。

另有一个不是"查不查"、而是"查到了能不能用"的问题：**记忆里的东西，要不要直接写成变量的值？——不写**（§7）。

## 2. 速览：问题 → 机制

| #   | 什么时候                                | 出什么问题                                         | 机制                                                                                                    | 花多少                                                 | 在哪节 |
| --- | --------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ | ------ |
| 1   | 每轮回复前，话里有指代                  | AI 不知道「那件事 / 李光」指什么，只能反问"是谁？" | 回复**开头的判定字段**（§3.0）：要查才查，检索词也在里面写好（给出专名就另取实体）→ 片段并入本轮 prompt | 无额外调用：判定字段几十 token；要查时另加 ≤200ms 检索 | §3.1   |
| 2   | 每轮回复前，用户反问                    | **真要引既往事实时**没有依据，像第一次见面的机器人 | 同一处判定认这句话**缺什么** → 缺才查（专名交给 `entities`，`query` 只管"事"）                          | 与指代共用同一处判定                                   | §3.2   |
| 3   | 进入一个话题时                          | 脚本要收的信息用户以前讲过，AI 又问一遍            | 变量**值为空的**由**装配侧直接查**一次，本话题共用——这一处**不发判定**（§3.3）                          | 每话题 ≤1 次检索；无额外调用，**也不多发一次生成**     | §3.3   |
| 4   | 引擎要判断矛盾 / 情绪轨迹 / 阻抗 / 危机 | 不是"回复不懂"，是"觉察缺证据"                     | 各意识在自己的异步通道里各查各的                                                                        | 不占用户等待                                           | §8     |
| 5   | 任何时候（边界问题）                    | 记忆里有，要不要写成变量的值                       | **不写**——变量权威在信息点文档                                                                          | —                                                      | §7     |

执行者只有两类，这就是"快通道 / 慢通道"的全部含义：

- **主线**（快通道）：用户等着回复，所以必须快——**在用户可接受的等待预算内跑完的那条链**；判断并入主线生成（§3.0），不额外调用 LLM。查记忆本身仍是一次本地 HTTP。
- **意识层**（慢通道）：后台跑，用户不等——可以慢、可以用 LLM 做深度分析。

```
一次 ai_ask 里，记忆在三个点介入：

  进入话题 ──▶ [3] 收集前回顾：本话题要收的变量里，值还空着的 → 装配侧直接查（每话题一次，不发判定）
                 │
  用户说话 ──▶ [1/2] 指代 / 反问：主线开口先给判定字段 —— none 直接回 / block 先查再回 / defer 先回、查到的下轮带上
                 │
                 ▼
            记忆片段并入 {{memory_context}} ──▶ 主线 LLM 生成回复（用户等待中：要查时 1 次检索 + 1 次重生成）
                 │
  后台 ──────▶ [意识层] 矛盾 / 轨迹 / 阻抗 / 危机 各自 recall —— 不占用户等待，LLM 可用
```

## 3. 主线上的三个触发点

三处都归本文，但**只有两处要判**：§3.1 指代 / §3.2 反问交给**主线 AI 的判定字段**（§3.0）——指代是"话里有钩子"；反问只是一个**时机**（AI 被放进答题席，查不查仍看它要说的那句话缺什么）。§3.3 收集前回顾**不用判**：要收哪些变量、值空不空，代码都算得出来，装配侧直接查。代码那套字面检查只做记录，不参与判定。

判断纪律是**宁可多查**——查了没用只花一点时间，真正贵的是漏查，AI 当着用户的面犯蠢。这条纪律写在主线提示词的判定段里（附 D）。

### 3.0 判断者：主线回复开头的判定字段

**它是什么**：主线 AI 回复的**同一次生成**里，输出开头先给判定字段，其余字段照常跟在其后。判定字段**不给用户看**：引擎读到它、把它摘掉，据此决定这一轮怎么走。

判定只回答一件事：**只靠现在这些已知，够不够支撑这一轮回复**。

判定字段的输入，是模型本来就看得见的东西：本轮用户原话（连发先拼接，§4）、当前话题与要收的变量及其空值状态、最近聊天窗口、时机（用户回复 / 进入话题）。
输出是严格 JSON 的**开头四个字段**（模板原有的那份 JSON，这四个排在最前面）：

| 字段       | 是什么                                                                                    |
| ---------- | ----------------------------------------------------------------------------------------- |
| `recall`   | 这一轮怎么走——三种取值，见下                                                              |
| `query`    | 检索词（§4）：要查时给，不查时空串                                                        |
| `entities` | 本轮原话里的专名（人名、地名、机构名）——硬规则（「怎么判」第 2 条）与实体渲染（§9）都看它 |
| `reason`   | 一句话说明为什么这么判（供日志与实证）                                                    |

**三种取值**：

| `recall` | 这一轮怎么走                                                               | 什么时候用                               |
| -------- | -------------------------------------------------------------------------- | ---------------------------------------- |
| `none`   | 不查，直接回复                                                             | 靠已知够用——大多数轮                     |
| `defer`  | 先回复，同时查一次，查到的记忆**下一轮**带上。回复里不许猜那个不知道的东西 | 有钩子，但不写它这一轮也答得完整——先接住 |
| `block`  | 先查，拿到记忆后**重新生成**再回复                                         | 有钩子，不写它就答不出、答空，或只能反问 |

**怎么判**：按顺序问两句。

1. **这一轮有没有钩子？** 钩子 = 用户这句话里指向「你说过、但我看不见的东西」的那个话头——「那件事」指的东西不在最近对话里、冒出一个没见过的名字、用户在问「我该怎么办」、要收的变量他以前讲过。**没有钩子 → `none`**（寒暄、表达情绪、回应上一句，大多如此）。
2. **有钩子就不许猜它——把这一轮想说的那句话先写出来，看它带不带那个东西：**
   - **带**——话里必须交代它是谁 / 是什么 / 发生过什么 / 该怎么办，不写它就答不出、答空，或只能反问「你指的是？」→ `block`。**人名、地名、机构名在最近对话里没出现过**，几乎一定落在这一类（硬规则，附 D）。
   - **不带**——不写它也完整（共情、接着问、确认一句）→ `defer`；再自检一遍：这句话里不能出现任何对它的预设——不猜它是谁、不编他说了什么。**`defer` 与 `block` 之间拿不准 → `block`**：多查的代价是慢一轮，猜错的代价是不实的回复，两个方向不对等（"宁可多查"）。

判据落在"这一轮想说的那句话写不写得出来"上——是模型做得到的一次试写，不是让它估自己"接不接得住"。**判据里也没有"查不查得着"**：模型读不到记忆库，估不出查了到底有没有——碰不中只能反问，是 `defer` 存在的原因，不是每天用的判据。

**为什么不单起一道判定，而是并进回复里**——两笔账：

|                      | 单起一道判定                    | 并进回复                              |
| -------------------- | ------------------------------- | ------------------------------------- |
| 大多数轮（不需要查） | 多一次串行 LLM 调用，每轮都要等 | 只多几十个 token 的时间——用户感觉不到 |
| 要查的轮             | 判定 + 检索 + 生成回复          | 判定字段 + 检索 + 重新生成            |

判定要用的上下文（原话、窗口、变量）主线本来就要预填；并进生成，边际成本只有那几十个输出 token；单起一次调用要**多预填一份 prompt**。咨询场景里"大多一轮就能回"（待实测：附 D 待验证 7），按轮平摊，这笔账赢在常见情形上。

⚠️ 要查的轮要付第二次生成：重开就得把主线 prompt 再预填一遍，那一轮与"单起一道判定"基本打平——赢的是常见轮。有一扇门能把这笔也省掉：让模型判 `block` 时**写完判定字段就停下**，记忆到手后**接着同一条生成往下写**（判定字段、记忆、正文同属一个回合），前缀缓存还能用上。做不做取决于 provider 的续写 / 工具调用形态（待实测：附 D 待验证 9）。

**调用侧怎么做**：

1. **判定字段先不给用户看**：它解析出来之前，输出不发给用户（界面只有"正在思考"态）。读到 `recall` 即判；到上限（N 个 token / 毫秒，待实测）仍判不出，走第 4 条。
2. **判 `block` 时让模型停下**：提示词要求"判 `block` 就写完判定字段停下、不写其余字段"（附 D）——这次生成到判定字段处自然结束，引擎不必去学"掐断流"这回事（各家中止语义不一，还要处理竞态）。模型不听、继续往下写也照旧丢弃，第 1 条保证用户看不到；要不要顺手掐断省那几个 token，等实测发现白写的量明显再说。
3. **只重新生成一次**：第二次生成时提示词里注明"记忆已注入，本轮直接作答，判定字段给 `none`"；**每个用户输入最多触发一次检索**（硬限，防循环；§3.3 装配侧那一次不算在内）。
4. **判不出来就当 `block`**：解析先宽容（空格、大小写、多余字段都算合法）；还是取不到判定字段——开头写了别的东西，或到上限还没读到——就按 `block` 处理：弃掉这次生成，用 §4 的固定拼法（原话 + 变量名）查一次，重新生成。方向与"宁可多查"一致，也不必为"判不出来"再起一次调用。字面检查那条路不参与这个判断（见下）。
5. **预填充（可选）**：支持 assistant 预填充的模型，把开头预填成 `{"recall":"`，逼它从这里往下写——格式守约率会显著提高。

**判定可能"装作知道"**：判定与回复由同一个模型在同一次生成里完成——它不认识「李光」，却可能顺着话头顺畅地编下去。这是本机制最实的风险，两条对冲：一是提示词里那条硬规则（专名没出现过 → `block`，附 D）；二是**留一套字面检查当观测点**——代码每轮跑一遍词表和分词（命中"那件事 / 老样子"，或切出窗口里没出现过的陌生词），毫秒级、不调 LLM，**只记录不干预**：它说"要查"而判定字段给 `none` 的轮次，就是这个风险的样本，攒够样本再决定要不要给它否决权。它同时也是**性能退路**——若实测发现判定并入生成不达标（延迟，或判定字段老守不住格式），再让它来真判。这条路的能力上限已经实测过（换个句式就漏、纯指代词分不清所指在不在窗口里，见评审包附 C）；词表里有什么、怎么跑，见评审包附 F。**判定字段判不出来时也不交给它**——按 `block` 兜底（第 4 条）。

反方向也有个风险：判 `block` 等于"这一轮先不说话"。提示词若写成"你不许说话"，模型就可能为了开口而倾向 `none`——附 D 因此把它写成流程的正常一步：你先判，引擎把记忆给你，你再完整作答。

代价的另一面也要认：判断要和正文表达抢同一份注意力——判得准不准、正文质量有没有被拖累，都得实测（附 D 待验证 3）。

### 3.1 指代：用户说「那件事」「李光」

**什么时候查**：每轮用户回复后、主线生成回复前，由判定字段读本轮原话（连发多条先拼接成一条，§4）。

**怎么判**（§3.0 的两问）：

| 这轮的话里有什么                                   | 判                                               | 为什么                                           |
| -------------------------------------------------- | ------------------------------------------------ | ------------------------------------------------ |
| 指代词（那件事 / 上次 / 老样子），**所指在窗口内** | 不查                                             | AI 自己看得见                                    |
| 指代词，**所指在窗口外**                           | 查                                               | 不查就只能反问"你指的是？"                       |
| 专名（李光 / 阿黄），窗口内没出现过                | 查，并把名字写进 `entities`                      | 名字是最硬的检索指纹；这一轮据此渲染实体态（§4） |
| 专名，窗口内已出现                                 | 不查                                             | 窗口里有，AI 自己看得见                          |
| 人称代词（他 / 她 / 他们）                         | 看窗口里能不能对上人：对得上 → 不查；对不上 → 查 | 能对上人还查，是白花一次检索（案例 20）          |

**不做**：词表、分词、窗口字面检查——判定由模型做（§3.0）。那套字面检查只做记录（§3.0，细则见评审包附 F），它的漏查面见评审包附 C 发现 1。

**判定与正文同源**：两者在同一个 prompt 里，不存在"判定看得见、正文看不见"的错位。字面检查那条路要自己保证同源——它用的「最近聊天」必须与主线 prompt 共用同一个函数或常量（细则见评审包附 F）。

**查什么**：见 §4（指代轮通常写「原话 + 变量名」；专名很硬时判定字段也可以只带原话）。

**结果怎么用**：记忆片段并入本轮 prompt，AI 就能接上话——"你说的那个方案，是上次我们聊的…"。

**为什么宁可多查**：误查 = 一次本地检索，用户无感；漏查 = AI 追问一轮，用户能感觉到蠢。这条纪律写在判定段里（附 D）：拿不准时倾向查。

### 3.2 反问：用户说「那你觉得我该怎么办？」

**这是时机，不是判据**：用户把问题抛回来，AI 被放进答题席。**答不答、答什么，由咨询框架定**——这一轮该给建议、该先澄清、该只共情、还是该把"你想让我替你做决定"本身当材料谈，是框架 / 策略的事，**不属于记忆机制的职权**。记忆只在"这一轮定下来的那句话，缺不缺窗口外的事实"上说话；判据仍走 §3.0 两问。

**框架经验往往往反方向压**：用户直接要方案，常常是"想让人替他决定"——与模板 `话术调整策略` 里「不知道」「自我批评」是同一类信号。标准动作之一是**先不接**（"你要的是我拿个主意，还是先一起把这事看明白？"），这句话成立所需的事实为零。**不接的反问，判定就是 `none`**。

| 这一轮定下来的那句话                                       | 缺窗口外事实吗                         | 判定                                                            |
| ---------------------------------------------------------- | -------------------------------------- | --------------------------------------------------------------- |
| 先澄清 / 只共情 / 把反问本身当材料谈（**不引既往事实**）   | 不缺                                   | `none`（`query` 空串；附 D 示例 6）                             |
| 要给建议、要引"上次我们聊过…"                              | 缺                                     | `block`；`query` 写**那一轮需要哪些面**（附 D 示例 3）          |
| 那句话里带**专名**（「我该不该跟李光断了？」）             | 缺——不给建议也得先知道李光是谁         | `block`；**专名交给 `entities`，`query` 只管"事"**（§4 实体臂） |
| 话里带**伦理硬定的那半**（"我这样算不算焦虑症"——不给诊断） | 那一半永远不缺；"我这样"那半看窗口内外 | 两半分开判——同一句反问里框架管一半、记忆管一半                  |

- 第三行与 §3.1 的专名一条**同源**：它要查，**不是因为它叫"反问"**，是因为句子里有个窗口内没出现过的名字。把它记在反问名下，正是本节要纠正的旧写法。
- **反例比正例重要**：模型若把"反问"当成"必查"，一上来就给 `block`——白花一次检索 + 一次重生成，还挤掉一次本该先澄清的机会。

**查什么**：判定字段写出的 `query`（§4）。要引既往事实时，写法仍是"需要什么信息"（附 D 示例 3）——查的是既往方案、他试过什么、效果如何，不是"我该怎么办"这五个字。检索词写的是"需要什么信息"而不是原话，这是这一轮最实在的收益。

**结果怎么用**：真给建议时，回答要有既往方案与案例历史做依据——"上次我们聊到…，你说试了三天有点用，要不这次…"。

**为什么单列一节**：反问轮的失败不是"听不懂"，而是"答不实"——**当这一轮真要答时**，输出的是建议而不是问题，没有依据的建议在咨询场景里是有害的（用户会照着做）。但"要答"这个前提由框架给，不由本节给。

> ⚠️ **框架侧的缺口**（不属本文，记 backlog）：默认模板的 `话术调整策略` 七行里**没有"用户反问"这一行**——"这一轮走哪个 move"目前由模型按准则自选。要不要补一行，是模板侧的事。

### 3.3 收集前回顾：要收的信息，他讲过没有？

**什么时候查**：**进入话题时**（该话题第一个动作执行前），一次。

**怎么查**：这一处**不用判定**。要收哪些变量、值空不空，代码都算得出来：静态解析本话题内全部 ai_ask 的 `output` 变量（脚本里写死的，0 LLM），取**当前值为空**的（文档装载没读到、本会话也还没收到）。**都有值 → 不查**；有空值 → **装配侧直接拼检索词、直接查**，结果注入本话题首问的 prompt。

模型在这件事上没有多余信息——变量名和话题名都在代码手里，让它判一次等于白花一次生成（§3.0 那种"判完还要重生成"的账，在这里整笔省掉）。

```
进入话题（首个 action 执行前）
  → 解析本 topic 内全部 ai_ask 的 output 变量（脚本已知，0 LLM）
  → 过滤：值已非空（文档装载 / 本会话已收集）→ 跳过
  → 有空值 → 代码拼检索词（话题名 + 空值变量名）→ recall()   ← 1 次 HTTP，无判定、无额外生成
  → 结果存 session.metadata.topicPrefetch[topicId]
  → 本话题内每次 ai_ask 生成 prompt 时，注入 {{memory_context}} 的「本话题已知信息」段
  → AI 自然衔接："你之前提过小时候主要是奶奶带大的，能多说说那时候吗？"
  → 变量值仍由用户回复提取（§7：回顾不写值）
```

**例子**（话题「童年抚养者」有两条 ai_ask，分别收 `{主要抚养者}`、`{抚养方式}`，装载后均为空）：

- 进入话题 → 代码拼出「童年抚养者——关于主要抚养者、抚养方式」→ recall → 命中第 2 次会谈「小时候主要是奶奶带大的，父母常年在外」
- 有回顾的首问："我记得你之前提过小时候主要是奶奶带大的——那时候的日子，你愿意多说说吗？"
- 无回顾的对照："你小时候主要是谁在照顾你？" → 用户："这个我之前说过了呀"

**为什么在话题入口**（而不是更早或更晚）：

| 位置                 | 问题                                                                                           |
| -------------------- | ---------------------------------------------------------------------------------------------- |
| ai_ask 首轮          | 变量逐个查（同话题多个 ai_ask 就查多次）；结果只能在这一轮用掉，真要综合就没有余量             |
| 会话启动             | 要预判整场会谈的变量，而话题队列会被意识层调整（插入 / 重排 / 深度切换）——预判不准，且启动变慢 |
| **话题入口**（选定） | 变量清单静态可解析**且确定**（队列怎么调整，进话题时它都在）；一次查询摊到本话题多个 ai_ask 上 |

**成本**：值全非空的话题不发检索；有空值的话题每话题最多 1 次检索——**不在生成里判，也没有重生成**，这是它比 §3.1 / §3.2 那两处更省的地方。

**它换掉的是什么**：检索词由代码拼（话题名 + 变量名），不再由模型写成一句自然问法。这里没有用户原话可挖，模型的输入与代码完全相同——能差的只是措辞。这点措辞值不值一次生成，交给实测（附 D 待验证 5 一并量）。

> 进话题那一轮，如果用户刚好也在说话（上一话题的收尾回复），装配侧这一次检索会和判定字段可能触发的那一次撞在同一轮。两条查询目的不同，各发各的；§3.0「每个用户输入最多一次检索」管的是判定那一次。

## 4. 查询怎么拼

三个触发点都要一段**检索词**，**由主线 AI 在判定字段里写**（§3.0），不由代码拼——唯二的例外是判不出来时的固定拼法（§3.0 第 4 条）与 §3.3 的装配侧回顾（那一处没有用户原话，代码拼）。下面说清"为什么这么写"——附 D 那段提示词里的几条约束就是从这儿来的。

两个判定触发点，按钩子的种类分成四种情况，判定字段写出来长这样（示例取自附 D，实际措辞由模型决定）：

| 钩子是哪一种 | 这一轮                                                        | 检索词主要装什么                                                                                     | `entities` |
| ------------ | ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | ---------- |
| 有专名（6）  | 用户说「李光最近又联系我了」，话题在收 `{核心信念, 睡眠质量}` | 专名 + 这一轮关于它的事，用原话措辞：`李光最近又联系我了，我挺烦的`——专名够硬，没带变量名            | 写出该专名 |
| 无专名的指代 | 用户说「那件事」「老样子」——原话零信息                        | 原话（它本身就是钩子）+ 当前话题的变量名（补范围）；原话失效时全靠变量名（案例 4）                   | 空         |
| 人称代词     | 用户说「他怎么说？」                                          | 原话 + 变量名；窗口里对不上人才走到这一轮，查的是"这个人是谁"                                        | 空         |
| 反问（12）   | 用户说「那你觉得我该怎么办？」                                | **不抄原话**——写这一轮需要什么信息：`来访者问「该怎么办」——此前聊过的应对方案、他试过哪些、效果如何` | 空         |

这三条是给判定字段的**提炼要求**，按这版措辞进提示词（附 D）：

- **具体优先**：专名、事件、时间线索、用户的原话词——能带的都带上。30~80 字是"别塞噪声"，不是"越短越好"。
- **变量名只在它圈定范围时才拼**（最多 2 个），不机械罗列。
- **不编造**：`query` 里除脚本变量名和"需要什么信息"的描述外，不出现用户没说过的具体人名、事件；`entities` 只写本轮原话里的专名，不写从记忆里联想起的名字——那是要查的东西，不是查询条件。

**两个成分各干什么**：

- **原话 = 钩子**：指出这一轮具体在说哪件事、哪个人。「李光」这样的罕见专名是最硬的钩子——检索器几乎靠它直接命中。但钩子不一定有：用户说「那件事」「老样子」时，原话零信息，检索器无从下手（案例 4）。
- **变量名 = 范围**：脚本里写死的，零信息损失、永远可用，把检索框在"我们正在了解什么"里；也是 §3.3 装配侧回顾唯一能有的东西。原话失效时全靠它（案例 4）。

只有原话 → 泛泛召回，不知道往哪儿找；只有变量名 → 知道范围，不知道这一轮问的是哪一面；而所指跟当前话题无关时，变量名还会把检索整批拉去当前话题的旧料——**这是它带偏的弱点**（案例 13）。两个成分的价值在这里；**要不要都用，是判定字段自己的判断**（专名很硬时可以只带原话，案例 6；指代跟当前话题无关时可以不带变量名，案例 13）。

**约束各归各家**：

| 规矩             | 属于谁             | 内容                                                                                                                                                                                  |
| ---------------- | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 连发先拼接       | 两条路都有         | 用户连发多条时先拼成一条再送判断、再入检索，否则指代落在后几条会被漏掉（案例 9）                                                                                                      |
| 判定字段的软约束 | 主线提示词（附 D） | 30~80 字；成分按上表挑（具体优先、变量名按需、不编造）                                                                                                                                |
| 装配侧拼法       | 代码（§3.3）       | 话题名 + 空值变量名——这一处没有原话，模型也无从贡献                                                                                                                                   |
| 长度上限 200 字  | 固定拼法           | 超过则取「头 100 字……尾 100 字」，中间丢掉（案例 11）                                                                                                                                 |
| 变量名最多 2 个  | 固定拼法           | 超过按声明顺序取前 2——防止"范围"那半句盖过"钩子"                                                                                                                                      |
| 原话不清洗       | 固定拼法           | embedding 对语气词、错别字鲁棒；不做文本清理                                                                                                                                          |
| 时间锚点         | 调用侧             | 每轮 recall 都带当前时间（`queryTimestamp`，ISO）——"上次 / 最近"这类相对时间表达靠它解析，recency 评分也要它做基准（ADR 004 决策 3 写"按需"，这里定成"每轮"：参数而已，简单且可预期） |

> 200 字是 embedding 输入预算（约 300-400 token）的安全上限——它是"装不装得下"的边界，不是"有没有用"的边界。判定字段的检索词也有限长（30~80 字），但那是"别把噪声塞进去"，不是装不下。

**原话不是越长越好**（这条只管固定拼法的截断；判定字段写什么由它自己定）：钩子的数量与字数不成正比——500 字的失眠夜可能整篇只有一个钩子，300 字自述可能散落三个。固定截断隐含"信息均匀分布"的假设，对长文必损，固定拼法才要头尾写法（评审包附 F）。

**指代够不够用，看它指的是哪一段**：主线 LLM 每轮手里关于"过去"只有三样东西——已收集的变量、最近 5 条对话（ai_ask 的窗口，`slice(-5)`；ai_say 是 10 条）、本轮的召回结果——指代落在哪一样上，结论完全不同：

| 「他 / 那件事 / 李光」指的是                     | 主线自己懂吗                         | 靠什么解决                               |
| ------------------------------------------------ | ------------------------------------ | ---------------------------------------- |
| 最近 2-3 轮内的事                                | 懂                                   | 靠主线自己                               |
| 本话题更早、但已收进变量                         | 大致懂——变量值是有损摘要，细节可能缺 | 靠变量值（细节缺时按"碰不中"处理）       |
| 本话题更早的原文、没进变量                       | 不懂（掉出 5 条窗口）                | 靠召回——碰得中就有，碰不中就没有         |
| 上次会谈的人、事，**有专名**（案例 6 的李光）    | 不懂                                 | 靠实体臂（见下）                         |
| 上次会谈的人、事，**无专名**（"上次那个老同学"） | 不懂                                 | 只能靠语义碰——碰不中就反问               |
| 三样都没有                                       | 不懂                                 | 靠反问「你指的是？」——真人咨询师也这么干 |

> 本表说的是"靠什么解决"，不是"查不查"。**查不查由判定字段决定**（§3.0）：它分得清所指在窗口内还是窗口外——所以"靠主线自己"的那两行，真的不查了。

**三条不做**：

- **不做读时指代消解**：材料捞回来后，主线 LLM 读着原话 + 材料，自己就对上了——消解是它的免费副作用。判定字段只判"要不要查"，不解析"那件事是什么"；再解析一遍是重复劳动。
- **不做引擎侧查询改写**：检索词由判定字段自己写（附 D 示例 3）。"把「那件事」改写成自洽问句"这件事本来就不便宜——单做要一次 LLM 调用；而判定字段反正要输出别的东西，写检索词是顺带产出，不必为此再起一次调用。
- **不加大对话窗口**：加大窗口能盖住一部分"本话题更早"，但那是拿认知预算换覆盖，且盖不住跨会话。补召回比加大窗口对。

**实体臂——「李光是谁」的落点（待实证）**：人名、关系这类跨会话信息，Hindsight 在**写时**（retain）已把它们抽成实体节点（`canonical_name`、共现关系、首次/末次出现），读时随 `response.entities` 一起回来（Hindsight 官方把它渲染成 prompt 的 `ENTITIES:` 段；这里改成随本轮联想一起渲染，理由见 §9）。三层各归各，别混：

| 层         | 谁控                                                  | 怎么定                                                                                               |
| ---------- | ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 检索臂     | bank 配置（`enable_graph_retrieval`），**不在调用侧** | 不逐轮切——调用侧根本控不到它                                                                         |
| 取回实体态 | 每轮 recall 都取（`includeEntities` 不逐轮切）        | **不逐轮切**：判定漏了专名时实体态还在手里；成本只是服务端合成与传输，不占 prompt 预算（"宁可多查"） |
| 渲染       | §9（`formatMemoryContext`）                           | **只在这个轮次有专名时渲染**那一小块                                                                 |

**当前实现差距**：适配器只读 `response.results`，实体段被丢了（§11）。

两处未实证（随「实体臂」故事一并验）：① Hindsight 按 query **怎么挑**实体——是拿名字精确取，还是语义召回一片；② **存量**记忆有没有实体节点（写时抽取是后加的能力，老数据未必有）。取不到时的退路是反问，不猜。

**判定字段能缓解**：模型看得见这层关系，可以干脆不写变量名；但缓解不是保证，判错时退回"无专名"那一行——反问。

> ⚠️ **两处待定**（评审包附 B 有记）
>
> 1. **呈现给判定字段的变量名用哪个**：取变量声明里的 `name`——ADR 007 决策 3 起变量名本身就是中文（`name: 治疗阶段`），做检索范围正合适。存量脚本只有英文 id（`target_variable: "user_name"`）：按原样放进提示词，检索质量略降但不报错，等 ADR 007 迁移自然解决；要不要为存量脚本另作处理，待定。
> 2. **要查的那一轮把哪一批变量呈现给判定字段**：当前动作要收的那个优先，不足 2 个再按声明顺序，从本话题待收集且为空的变量里补。判定字段拿到的是这批候选，用不用、用几个由它定——最多 2 个。

## 5. 预算：多快、几次、留多久

- **判定不额外调用 LLM**：判定是主线回复输出的**开头**（§3.0），输出几十 token；要查的轮多一次重新生成——**重新生成的预填成本**取决于 provider 的前缀缓存（有则基本打平，无则那一轮多预填一遍主线 prompt）。延迟**待实测**——"判断不调 LLM、检索 ≤200ms"这条红线（ADR 006 决策 3：快通道保持 0 LLM）的前半句不再成立（见评审包附 E 决策 2）。
- **整轮预算**（判定字段 + 检索 + 生成回复）**尚未定义**——本文只约束下面这一段。
- **一次查记忆 ≤200ms**（本地 HTTP 到 Hindsight，纯检索不调 LLM）；超时或 Hindsight 不可用 → 返回空 MemoryContext，静默降级，不阻塞主流程。
- **每个用户输入最多查一次**：一次判定给出一个检索词，`defer` 与 `block` 都只查这一次；重新生成不再判、不再查（§3.0 第 3 条）。§3.3 装配侧那一次是进话题时发的，不占这个额度。
- **实体态每轮都取**，不按轮切（`includeEntities` 恒定开）；**上限 200 token**（Hindsight 的 `maxEntityTokens` 默认 500，这里调小）。**只有渲染分轮**——§9 只在这轮有专名时渲染它（§4 实体臂）。本轮的「相关人物」子块与本轮记忆片段是两笔独立预算（§9），各自设限。
- **结果只保留最近 5 轮**（`fastHits` 滚动淘汰）：5 轮前的联想在当前语境下大概率已失效，同时防止 memoryContext 无界膨胀。`defer` 查到的记忆下轮带上，天然落在 `fastHits` 里。意识层的洞察不受此限（综合结论生命周期更长）。
- 三路扩展（附 A，默认关闭）若启用并超预算，降级顺序：先砍关联事件 → 再砍类似事件 → 只留原始查询。
- **投机检索不做**：检索是本地调用，本可以在主线开始生成的同时用原话先发一次（判定 `none` 就白花一次检索，用户无感；判 `block` 时那 200ms 就不在关键路径上）。收益有限（判定字段本身也要时间），且它把"每轮都花一次检索"当默认——等实测出"要查的轮里检索等待占比明显"再谈。

## 6. 查哪种记忆

| 记忆类型        | 对"理解用户这轮的话"的帮助                                                                      |
| --------------- | ----------------------------------------------------------------------------------------------- |
| **experience**  | 最直接——"用户之前说过类似的经历吗？"                                                            |
| **observation** | 高——用户/咨询师沉淀过的信念与模式（"我觉得吃药没用"被 consolidate 成带证据引文的观察，ADR 005） |
| **world**       | 低——用户陈述的事实性信息（"在 XX 公司工作"），主要用于避免事实错误                              |

recall 只有这三类可取。**案例公式化（咨询师的工作假设）不在表里**——它走 Hindsight 的 mental model，是另一套 API（自己定义问题、后台重写、读取零 LLM），在会话启动时读入，不经这张表的 recall（ADR 005 决策 2）。

**不做类型区分，统一 recall**：不只是"不筛"，而是**显式传三类**——Hindsight 的 `types` 不传时**默认只返回 world + experience，observation（归纳判断）会被静默漏掉**（SDK v0.9.1 `RecallRequest.types`）。所以每轮 recall 固定带 `['world', 'experience', 'observation']`；语义匹配到的都返回、按相关度排序。LLM 在 prompt 里看到的是一段结构化的"相关记忆片段"，自己判断哪些有用。

## 7. 边界：记忆不替 AI 写变量

**一句话：记忆的回顾结果只作为上下文给 AI 看，不写进变量的值。**变量的权威是[信息点文档](../decisions/007-variable-document-boundary.md)（ADR 007 决策 2）。

**为什么空值变量需要回顾**：跨会话值的权威是信息点文档，脚本工程师在脚本里声明变量与信息点的映射。但**没被映射的变量，文档里根本没有这个信息点**——而"用户以前讲过没有"不取决于脚本有没有计划收集它。所以：装载之后**值仍为空**的待收集变量，先做一次记忆回顾（§3.3）。

**为什么不把回顾结果写成变量的值**——三条理由指向同一件事：

- **没有修正面**：值一旦写入并驱动退出决策（"这个变量有了，不用再问"），本次会谈就少收集了本该收集的信息；而人能改的是文档，这一项恰恰没有信息点。
- **记忆值可能过时、不精确，或表达形式不同**：让它带着写一句确认式提问"你之前提过…，是这样吗？"是稳妥的；固化成当前值等于把不确定性藏进流程控制。
- **写进去就产生消费依赖**：下游 condition / 退出决策按精确标量用，会逼出 bridge 那套新鲜度与合并策略的复杂度——ADR 007 决策 6 刚把它砍掉。

**与变量刷新的分工**（[variable-memory-bridge](variable-memory-bridge.md) §4.1 piggyback）：两者都是"提前准备"（Action N 备 N+1 / 进话题备本话题），区别在产出——一条只把记忆给 AI 看（本文），一条刷新变量的值（bridge）。

| 维度     | 本文：只给上下文                  | bridge：刷新变量值                                             |
| -------- | --------------------------------- | -------------------------------------------------------------- |
| 触发时机 | 进入话题时（收集前）              | Action N 执行时（前瞻 N+1 引用的变量）                         |
| 目标集   | 本话题待收变量中**值为空**者      | N+1 引用的变量 ∩ `autoRefresh ≠ false`——**与"是否待收集"无关** |
| 产出     | 预备上下文（注入 prompt，不写值） | 变量值（写 store，`source: 'llm_piggyback'`）                  |

⚠️ **待补的闸门**：**本话题待收集且当前为空的变量，不应进 piggy 的目标集**。现行 bridge 的写入门槛只有"非空"（§4.5 Phase B）、没有"原本有值"，而 §4.4 把临床判断类默认置 `autoRefresh: true`（核心信念、主要压力源、情绪状态——恰是待收集变量最常见的类）。于是待收集变量一旦被邻近动作引用（`condition` 尤其容易：§4.3 规定条件分支"收集所有分支中引用的变量"），piggy 会在用户还没被问到时就写出一个值，且其 LLM 视野里含刚注入的「本话题已知信息」——这正是本节禁止的"从记忆预填"，且该值直接喂退出决策。ADR 007 决策 6 关掉了 recall 侧的空值兜底，却没在 piggy 侧补同样的闸门，**漏洞是那条决策的残留**。闸门落在 [bridge 修订故事（Epic D）](../../scrum/backlog.md)。

> **另有一条写值的路是合法的**：**已映射**变量在装载时的 recall 兜底（ADR 007 决策 4：文档信息点 → Hindsight recall 兜底 → 默认值 → 未定义），发生在会话启动、走显式 fallback 链。本节管的是**无映射**的空值待收集变量。

**升级路径（待实证）**：若实证发现"AI 明明看到了回顾内容，仍从零追问"，再考虑把回顾结果写进变量 store（`source: 'memory_prefetch'` + 证据锚，并从退出决策中排除）——先验证不加的情况。

## 8. 另一条线：意识层的记忆调取（异步）

ai_ask 只负责主线上那三个触发点。**觉察判断类的调取**（矛盾比对、情绪轨迹、阻抗、危机趋势、话题衔接）不归它——那些是意识层的活，各意识在自己的后台通道里 recall，不占主线延迟预算（机制见[意识系统设计 §2.7](../consciousness/consciousness-system.md)）。

**触发**：某个意识的 `insightForSlowThinking`（string，见[意识系统 §2.3.3](../consciousness/consciousness-system.md)）非空时，触发深度 recall + LLM 综合。主线 LLM 不感知、不负责触发——主线回应来访者，意识层觉察信号并决定"什么值得深挖"。

| 调取方 | 通道                       | 触发                               | 查询                              | 目的             |
| ------ | -------------------------- | ---------------------------------- | --------------------------------- | ---------------- |
| 主线   | 同步，判定随生成 + ≤200ms  | 两个判定触发点（§3.1 / §3.2）      | 判定字段写出的检索词（附 D）      | 懂用户说什么     |
| 主线   | 进话题时一次，装配侧       | 本话题有待收空值变量（§3.3）       | 代码拼：话题名 + 变量名           | 收信息前知道多少 |
| 各意识 | 异步，多线程，不占主线延迟 | 各意识 `recall.enabled` + 触发阈值 | 各意识 `recall.query_hint` + 原话 | 觉察判断的证据   |

**ai_ask 侧的契约**（硬约束）：

1. **fire-and-forget**：异步运行，不阻塞主线（5-30s，轴 9 `relaxed_30s`）。
2. **产出 DeepInsight 存入 `session.metadata.deepInsights`**（类型见[意识系统 §2.6](../consciousness/consciousness-system.md)）。
3. **注入前经时效性门控**：`formatMemoryContext()` 的「深度洞察」段只渲染 `relevanceCheck != "过期"` 的条目（§9）。
4. **只有建议权**：洞察注入 prompt 后由主线 LLM 自己判断是否采纳；不直接修改脚本流程（不跳过话题、不插入动作）。

## 9. 数据结构与渲染

命中后：recall 结果合并进 `session.metadata.memoryContext`，下一轮 `buildSystemVariables()` 自动带入 prompt；渲染格式即下面 `formatMemoryContext()` 的输出。四段各有自己的生命周期：

```typescript
interface SessionMemoryContext {
  // 会话启动时加载的基础画像（initializeSession 时设置，会话内不变）
  baseline: MemoryContext;

  // 收集前回顾（进入话题时写入，本话题内有效；仅空值变量，§3.3）
  topicPrefetch: Array<{
    topicId: string;
    variables: string[]; // 本次纳入回顾的变量名
    context: MemoryContext;
  }>;

  // 主线要查的轮的联想（最近 5 轮，滚动淘汰）
  fastHits: Array<{
    round: number;
    query: string;
    context: MemoryContext; // 实体态随本轮一起存，取的时候不分轮（§4 实体臂）
  }>;

  // 意识层深度洞察（持久累积，带时效性标记；类型见意识系统 §2.6）
  deepInsights: DeepInsight[];
}
```

`formatMemoryContext()` 分段渲染（`base-action.ts`）：

```markdown
## 关于来访者

{baseline}

## 本话题已知信息

{topicPrefetch 中当前话题的条目（§3.3）}

## 本轮相关记忆

{fastHits 最近 5 轮合并渲染；某轮给出了专名时，在该轮内附「相关人物」子块（§4 实体臂）}

## 深度洞察

{deepInsights 中 relevanceCheck="有效" 的条目，按时间倒序}
```

> **实体为什么不单列一段**：它随每一轮的联想一起产生，生命周期与那一轮的联想完全一致（同滚动淘汰）。单列一段会多出一个没人负责淘汰的段落。

**淘汰规则**：baseline 不变（会话级稳定）；topicPrefetch 话题级——离开话题即失效，不跨话题累积；fastHits 滚动保留最近 5 轮（与渲染同数——留着不渲染的轮次没有机制会回头去看）；deepInsights 持久保留，`relevanceCheck="过期"` 的不展示，超过 10 条移除最旧。

## 10. 案例集

> **场景常量**：第 3 次会话；ai_ask 正在收集 `{核心信念, 睡眠质量}`；`u` = userId；变量名串 = `关于核心信念、睡眠质量`。
> 「判定」= **期望的判定字段输出**（§3.0 输出开头的判定字段；措辞由模型定，此处给期望值）。**案例 1–3 不适用**——收集前回顾归装配侧、不发判定（§3.3），那三条看的是"发不发检索"。
> 「检索去向」= 检索词**预期**命中的记忆区域——recall 统一跨类型检索（§6 不做类型过滤），此处描述预期而非限制。
> 「期待返回」= **设计预期，非实测**——「三路查询实证」故事将逐条核对；本案例集是验收案例的单一出处。
>
> **四处最容易被判错的**（这四条是 2026-09-14 定下的验收基准）：
>
> | 案例 | 判定要点                                                              |
> | ---- | --------------------------------------------------------------------- |
> | 4    | 先看「那个事」落在窗口内还是窗口外——**窗口内不查**                    |
> | 6    | 专名窗口内没出现过 → 查，并把名字放进 `entities`（§9 据此渲染实体态） |
> | 13   | 指代跨到别的话题时**可以不带变量名**（带了反而把检索拉偏，§4）        |
> | 20   | 人称代词：**窗口里能对上人就不查**；对不上才查                        |
>
> 其余案例的判定按 §3.0 的两问标准走。各条「判定」一列给的是**期望的判定字段输出**——模型未必照期望走，案例集正是用来量这个偏差的（附 D 待验证 2：拿它当测试集跑，逐条比对漏查 / 误查）。

### 一、收集前回顾（案例 1-3）

> 场景（与上方常量不同）：第 3 次会话，进入话题「童年抚养者」，两条 ai_ask 分别收 `{主要抚养者}`、`{抚养方式}`。

**案例 1｜空值 + 记忆有**（§1 问题三的样本）

- 触发: 进入话题；本话题 ai_ask 的 `output`（主要抚养者、抚养方式）解析后**均为空** → 装配侧直接查，**不发判定**（§3.3）
- 检索词: 代码拼——`童年抚养者——关于主要抚养者、抚养方式`
- 检索去向: experiences / worldFacts 中既往关于抚养者的叙述
- 期待返回: 「第 2 次会谈：小时候主要是奶奶带大的，父母常年在外」

**案例 2｜非空 → 跳过**

- 触发: 文档装载后本话题变量全非空 → 装配侧不发检索（§3.3 静态先筛）
- 机制解读: 权威在文档（ADR 007 决策 2）——文档有的，记忆不掺和

**案例 3｜空值 + 记忆无 → 不劣化**

- 回顾空手 → 按原样从零提问（"你小时候主要是谁在照顾你？"）
- 机制解读: 回顾只增不减——召回为空时，行为与没有这个机制时完全一致

### 二、指代与反问轮（案例 4-13）

**案例 4｜「上次说的那个事，我回去又想了想」**（指代回复）

- 判定: 先看所指落在哪里——窗口内 → `{"recall":"none"}`（不查）；窗口外 → `{"recall":"block","query":"上次说的那个事，我回去又想了想 —— 关于核心信念、睡眠质量"}`（原话零信息，变量名是唯一还能指路的东西）
- 检索去向: 原话部分几乎无命中（"那个事"不可解析）；实际靠变量名
- 期待返回: 变量名范围内的上一会话记录。**"那个事"所指能否命中不确定**——命中是赚到，碰不中就是碰不中
- 机制解读: 碰不中时 AI 自然反问"你指的是？"，咨询场景可接受，不算劣化（"窗口内不查"见 §10 头）

**案例 5｜「上次你说睡前别看手机，我试了三天，是不刷了，但一躺下就开始想工作的事」**

- 判定: `{"recall":"block","query":"上次你说睡前别看手机，我试了三天，是不刷了，但一躺下就开始想工作的事 —— 关于核心信念、睡眠质量"}`——原话全量 + 变量名；「工作的事」是这轮的新钩子
- 检索去向: experiences（工作压力事件、既往失眠成因）；「工作的事」是本轮新出现的钩子，牵引前几轮没命中的区域
- 期待返回: 「第 1 次会谈：项目临近上线，压力很大」——下一问可沿"工作的事"深挖
- 机制解读: 指代 + 新钩子 = 快通道查询里价值最高的一类

**案例 6｜「李光最近又联系我了」**（专名指代）

- 判定: `{"recall":"block","query":"李光最近又联系我了","entities":["李光"]}`——专名够硬，不带变量名（带不带由判定字段定，§4）
- 检索去向: 专名随原话入查询，检索器按罕见 token 命中关于李光的存量
- 期待返回: 李光的既往事实与相关叙述（谁、什么关系、发生过什么）
- 机制解读: 判定字段看出「李光」是专名、窗口内没出现过 → 查，并把它放进 `entities`；§9 据此**在本轮渲染**实体态（实体态本身每轮都取，§4 实体臂），"李光是谁、跟他什么关系"随本轮联想一并给出。**从识别到注入 prompt、到 LLM 生成回复的逐步走查见附 C**——那是规则路径的走查（含分词边界的实测发现），判定并入生成后的步骤变化见附 C 开头

**案例 7｜「就是睡不着，还是老样子」**

- 判定: `{"recall":"block","query":"就是睡不着，还是老样子 —— 关于核心信念、睡眠质量"}`——「老样子」是空钩子，只能靠变量名指路
- 检索去向: experiences 睡眠相关存量
- 期待返回: 既往睡眠叙述——大概率与前几轮 fastHits 重复
- 机制解读: 「老样子」是指代；旧钩子召回已知内容，冗余是判定的代价，无害且刷新窗口

**案例 8｜「你上次问我的时候我说'还好'，其实那次之后更糟了」**（引用前文）

- 判定: `{"recall":"block","query":"你上次问我的时候我说'还好'，其实那次之后更糟了 —— 关于核心信念、睡眠质量"}`——强标记 + 原话
- 检索去向: 那次"还好"的对话记录——原话直指已存内容
- 期待返回: 那次问答的完整记录，AI 可衔接"你上次说还好，现在能多说一点吗"
- 机制解读: 「你上次问我的时候」是强标记；原话查询命中率最高的类型

**案例 9｜连发三条：「其实我最近老做同一个梦」＋「梦见考试没带笔」＋「就像上次考试前那段时间一样」**

- 判定: `{"recall":"block","query":"其实我最近老做同一个梦。梦见考试没带笔。就像上次考试前那段时间一样 —— 关于核心信念、睡眠质量"}`——连发先拼接，指代落在最后一条
- 检索去向: experiences（既往梦 / 考试相关叙述）；「上次考试前」牵引考试焦虑类事件
- 期待返回: 既往考试焦虑相关叙述（若有）

**案例 10｜「上次会谈聊到的那个方案，我回去试了，好像有点用」**（跨会谈指代）

- 判定: `{"recall":"block","query":"上次会谈聊到的那个方案，我回去试了，好像有点用 —— 关于核心信念、睡眠质量"}`——跨会谈指代，窗口内没有
- 检索去向: 跨会话 experiences（「上次会谈」明确指向非本次会话）
- 期待返回: 上次会谈给出的方案记录，AI 可衔接"你试的是哪部分？具体怎么有用了"

**案例 11｜500 字长文，指代落在中段**（节略：开头「最近事情特别多，工作上一堆烂摊子……」；中段「……就像李光当年对我那样……」；结尾「……所以最近状态特别差」）

- 判定: 判定字段自己写检索词——它读得到全文：「最近事情特别多，工作上一堆烂摊子」是这轮最具体的钩子，中段的「李光」它也看得见，带不带由它定
- 对照（固定拼法）: `{头100字}……{尾100字} —— 关于核心信念、睡眠质量`——头尾窗口命中工作压力，中段的「李光」被截断丢失
- 检索去向: 工作压力 / 状态叙述；中段的「李光」判定字段读得到，可以带进检索（固定拼法下它被截断丢失）
- 期待返回: 工作压力相关叙述；「李光」带进去了的话，关于他的存量也一并回来
- 机制解读: ⚠️ 中段损失只属于固定拼法（§4 约束各归各家）；判定字段读得到全文，这个损失不再必然。改进方向见附 A.2（分段检索，待实证）

**案例 12｜「那你觉得我该怎么办？」**（反问——**这一轮真要引既往事实**的那种）

- 判定: `{"recall":"block","query":"来访者问「该怎么办」——此前聊过的应对方案、他试过哪些、效果如何"}`——不抄原话，写需求（附 D 示例 3）
- 检索去向: 与变量名相关的既往记忆与方案记录
- 期待返回: 既往记忆供 AI 引用（"上次我们聊到……"）
- 机制解读: 这里的"要查"**不来自"用户反问"这件事**，而来自这一轮定下来的那句话（给建议）缺既往事实——框架若把这一轮定成"先澄清"，同一句话就该给 `none`（案例 12-a）

**案例 12-a｜同一句反问，但这一轮先澄清**（反问——**不引既往事实**）

- 判定: `{"recall":"none"}`——`query` 空串。这一轮定下来的那句话是"你要的是我拿个主意，还是先一起把这事看明白"，不引任何既往事实（§3.2 表第 1 行；附 D 示例 6）
- 检索去向: —（不查）
- 期待返回: —
- 机制解读: **给 `block` 就是白花钱**（一次检索 + 一次重生成），还挤掉一次本该先澄清的机会。这是"反问必查"的反例，和案例 12 配对用

**案例 12-b｜「你说我该不该跟李光断了？」**（反问 + 专名——查，但**不是因为它是反问**）

- 判定: `{"recall":"block","query":"李光——他是什么人、与来访者是什么关系、两人之间发生过什么事","entities":["李光"]}`——专名交给 `entities`（实体态取关系那半），`query` 只管"事"（§3.2 表第 3 行）
- 检索去向: 「李光」的存量（实体态 + 两人之间的事）
- 期待返回: 李光是谁（前同事）、两人之间发生过什么
- 机制解读: 这一轮的"要查"来自 §3.1 的专名一条——名字在窗口内没出现过；**与"反问"这个时机无关**。不给建议也得先知道李光是谁，否则只能当众问"李光是谁？"

**案例 13｜「我妈上次说的那句话，我一直记着」**（指代——指的是别的话题）

- 判定: `{"recall":"block","query":"我妈上次说的那句话，我一直记着"}`——不带变量名：它看得见这轮指代跟当前话题无关，变量名会把检索拉去当前话题的旧料
- 检索去向: ⚠️ 指代落在别的话题上——变量名串「核心信念、睡眠质量」是主题先验，可能把检索整批拉去当前话题的旧料
- 期待返回: 期望碰中"我妈说过的那句话"那一段；碰不中属预期内
- 机制解读: 变量名带偏的弱点（§4）——指代与当前话题无关时，"范围"那半句会盖过"钩子"；判定字段看得见这层关系、可以不带变量名，弱点缓解（缓解不等于保证）。「我妈」是通名不是罕见专名，实体臂也帮不上（§4 实体臂）；碰不中时 AI 自然反问"你妈说的哪句话？"

### 四、边界（案例 20）

**案例 20｜「他还是那样」**

- 判定: 判定字段识别人称代词，并看窗口里能不能对上人——**对得上就不查**，对不上才查
- 判定: 窗口里能对上人 → `{"recall":"none"}`；对不上 → `{"recall":"block","query":"他还是那样 —— 关于核心信念、睡眠质量"}`
- 检索去向: 变量名拉回的相关存量；若窗口内最近提到某人则一并命中
- 期待返回: 与变量名相关的记忆（查询对"他指谁"帮不上，但变量名划出了范围）

## 附 D：判定段的提示词与输出契约（草案）

> 判定段**并入主线提示词**（不是一次独立调用）：主线 AI 每次回复，在输出的开头先给判定字段，其余字段照常——与模板原有的那份 JSON 同一份输出、同一次解析。调用侧负责缓冲、解析、兜底，以及 `block` 时的收笔（§3.0）。
> **住所**：Default 层模板 `config/prompt-defaults/ai_ask_v1.md` 的最末，与它的输出格式块合写；Custom 层可**整段覆盖**（沿用 Custom > Default 两层解析）。
> **引擎写死的是接口**——四个字段名与三个取值（见下）：模板能改的只是措辞；改了字段名，解析即失败、按 `block` 兜底（§3.0 第 4 条）。装载时模板校验盯这一条（契约表「校验」行）。
> **判定段只管两处**：§3.1 指代与 §3.2 反问。§3.3 收集前回顾不发判定（装配侧直接查，§3.3）。
> **本文只定提示词与输出契约，不定用哪个模型**——判定与回复用同一个模型，这正是「判定并入生成」的含义。判定质量不达标时的退路见评审包附 E 决策 3 / 4。

### 判定段（写进模板的哪一段、长什么样）

位置：模板的**最末**，紧挨它的输出格式块——格式约束离生成越近，守约率越高；判定四字段则写在**输出的开头**（模板那份 JSON 的头四个字段，排在第一行的 `{{output_list}}` 之前）。

```
## 开口之前：先写判定字段

在你输出的 JSON **最前面**加上下面四个字段，其余字段照常跟在后面（严格 JSON，不加代码块围栏）：

{"recall":"…","query":"…","entities":[…],"reason":"…", …其余字段照常…}

它回答一件事：**只靠上面那些已知（最近对话 + 已收集变量），够不够支撑你这一轮的回复。**

{"recall":"none"}                                  ← 够用，直接回复
{"recall":"defer","query":"…","entities":[…]}      ← 有钩子，但不写它这一轮也答得完整：先接住，记忆下一轮补上
{"recall":"block","query":"…","entities":[…]}      ← 有钩子，不写它就答不出、答空，或只能反问

怎么选（按顺序问两句）：
- ① 这轮有没有指向「你说过、但我看不见的东西」的话头？没有 → none。
  大多数轮如此：寒暄、表达情绪、回应你上一句，或指代的东西**就在上面的最近对话里**——你看得见，不用查。
- ② 有钩子，就不许猜它——**把这一轮想说的那句话先写出来，看它带不带那个东西**：
  带（话里必须交代它是谁 / 是什么 / 发生过什么 / 该怎么办，不写它这一轮就答不出）→ block。
  不带（不写它也说得完整：共情、接着问、确认一句）→ defer：先接住，记忆下一轮补上；
  **回复里不能出现任何对未知信息的预设**——不要猜那个人是谁、不要编他说了什么。
  拿不准带不带 → block。多查只慢一轮，猜错是不实的回复。
  **人名、地名、机构名在最近对话里没出现过** → block；
  以往会谈里的事、你只能靠记忆才知道的事，同样 → block。
  **判 block 时，写完这四个字段就停笔，不要再写其余字段**——引擎会把记忆给你，你随后再完整作答。
  这是流程的正常一步，不是「这轮不让你说话」。

query（30~80 字）——先看这轮是哪种钩子，按它装：

| 钩子                   | 例                       | query 里装什么                                                 |
| ---------------------- | ------------------------ | -------------------------------------------------------------- |
| 有专名                 | 「李光最近又联系我了」   | 专名 + 这轮关于它的事，用原话措辞                              |
| 无专名的指代           | 「那件事」「老样子」     | 原话 + 当前话题的变量名（原话零信息时，变量名是唯一的方向）    |
| 人称代词               | 「他怎么说？」           | 原话 + 变量名                                                  |
| 反问（要引既往事实时） | 「那你觉得我该怎么办？」 | 不抄原话——写这一轮需要什么信息：既往方案、他试过什么、效果如何；**不引既往事实的反问轮给 `none`**（`query` 空串，示例 6） |

- 不写整句问句，写"需要什么**面**"；具体优先——专名、事件、时间线索能带的都带上。虚词（"是什么""找出"）会进关键词臂当词项、挤掉内容词，这是它不如"需要什么面"的原因。30~80 字是"别塞噪声"，不是"越短越好"。
- 变量名只在它确实圈定范围时才拼上（如"关于核心信念、睡眠质量"），最多 2 个，不要机械罗列。
- none 时 query 为空串。除了变量名和"需要什么信息"的描述，不要出现用户没说过的具体人名、事件。

entities 只列**本轮用户原话里**的专名（人名、地名、机构、作品名），普通名词不放；不要写你从记忆里想起的名字——那是要查的东西，不是查询条件。没有则 []。

**两个臂分工**：专名给 `entities`（实体态给"他是谁、什么关系"），`query` 只管"事"——「你说我该不该跟李光断了？」写成 `{"query":"李光——他是什么人、与来访者是什么关系、两人之间发生过什么事","entities":["李光"]}`，别把"关系"整件事都压给 `query`。
reason 一句话（供日志与实证）：给 none / defer 写"钩子是什么"（如「那个方案」就在最近对话里），给 block 写"缺了什么"（如「李光」是专名，最近对话里没出现过）。
```

> 进入话题时的收集前回顾**不走这里**——那一处没有用户原话，装配侧解析出空值变量后直接用代码拼检索词（§3.3），判定段不必为它写任何东西。

### 样例（判定字段 + 其余字段连起来长什么样）

```
【1 · 专名指代 → block】
{"recall":"block","query":"李光最近又联系我了，我挺烦的","entities":["李光"],"reason":"「李光」是专名，最近对话里没出现过，我不知道他是谁、跟来访者什么关系"}
（写完这四个字段即停笔 → 引擎查记忆 → 重新生成：判定给 none，正文写进 content）
{"recall":"none","reason":"记忆已注入","content":"李光又来找你了——你之前提过他，是你前同事，一直想拉你合伙创业。他这次联系你，你挺烦的。……"}

【2 · 指代落在窗口内 → none】
最近对话：… AI：上次那个方案后来怎么样了？
{"recall":"none","reason":"「那个方案」所指就在最近对话里，我看得见","content":"那个方案你又想了想——是觉得哪一块不合适？"}

【3 · 反问 → block】
{"recall":"block","query":"来访者问「该怎么办」——此前聊过的应对方案、他试过哪些、效果如何","entities":[],"reason":"这一轮我要给建议，需要既往方案与尝试记录做依据"}

【4 · 情绪表达 → none】
{"recall":"none","reason":"纯情绪宣泄，没有指向窗口外的东西，接着共情即可","content":"唉，这种"哪儿都不对"的感觉，挺熬人的。……"}

【5 · 反问，但这一轮不引既往事实 → none】
{"recall":"none","reason":"这一轮先澄清他要的是建议还是空间，不引任何既往事实","content":"你问我该怎么办——你是想让我拿个主意，还是先陪你把这事看明白？"}
```

> 样例里模板的其余字段（`response_plan` / `assessment` / `progress` / `exit` …）照常写，为省篇幅只留了 `content`；判 `block` 的样例给的是第一次生成，记忆注入后重新生成的那次见样例 1 的下半。收集前回顾没有判定样例——它不发判定（§3.3），样例在 §10 案例 1。
