## 附 B：改动记录（评审用——正文不含版本沿革，全在这里）

**继任稿 v2 · 第一次全面修订**（2026-09-18，**机制改动——待人批准**）。八条评审意见，逐条落点：

① **「窗口外」这个词取消**（§1 开头、§1 正文、附 A.4、附 B.2 样例 2/4）——换成「聊过、但最近对话里没有」这类直白说法；附录 A.2「靠什么解决」表里那一格同改。这个词读者得先学一遍才能用，收益不抵学费。

② **§1 补第四个问题「觉察缺证据」**（§1 新增一段 + 三条例子 + §1.1 全景加一条后台通道）——原三问的触发者都是用户的话，意识层那类（矛盾 / 情绪轨迹 / 危机）触发者**是引擎自己的觉察**，原先不在这章，导致后面主线与意识层分不干净。§1 收尾点明：前三问是同一条（钩子），第四问问的是"证据够不够"，走另一条通道。

③ **判定字段改序：`reason` 排到最前**（§2 字段表、§2 顺序说明、附 B.1 判定段、附 B.2 五条样例、附 B.3 契约表）——模型逐 token 生成，先写的条件化后写的；`reason` 在最后就成了事后合理化，对检索词毫无影响。`reason` 的用途同时收窄并说白：**给日志与实证看**，用户看不到、下游不用它。顺序是设计的一部分，这条本身进待验证（继任稿附 C.3 ⑤，A/B 比 query 命中率）。

④ **「钩子」就地定义**（§1 收尾）——原稿在 §2 直接用了这个词却没交代，现补一句：AI 这一轮要说的话，指着一个它看不见的东西。

⑤ **人物卡（原「实体臂」）——这是本次最大的一处机制改动**（§4.2 新增一条、附 C.1 数据结构与渲染、附 C.6 整节重写、附 A.2 表、backlog Epic A 故事）。原写法是"实体态随本轮联想存、随本轮淘汰、附在该轮里渲染"，等于把**人**当成"某一轮的联想"。新写法：实体态取出后**按 `canonical_name` upsert 成人物卡**，会话内保留（上限 10 张，末次提及最旧者先走），**渲染只在"这一轮提到这个人"时**——判定字段写了专名，或代码拿卡里的名字字面扫最近对话扫到。**不额外发检索**：卡来自既有的那次 recall。核查 SDK 后还改掉两处事实：实体态**默认就随 recall 返回**（`IncludeOptions.entities` 不传即开，`null` 才关），且带回的是实体自己的 observations（"current mental model of an entity"）——「李光的关键信息」不需要我们自己总结、也不需要多一次 LLM 调用，适配器把这一段整个丢了而已。

⑥ **要点的是"这件事的概要"，不是某一次聊天的片段**（§4.2 新增一条、附 C.2 末段、附 C.7 一行）——`preferObservations` 端口里早就有、从来没开过。开启后已被归纳掉的原始片段让位给归纳本身（腾出的位置补后面的结果，条数不减），渐进生效、不会掏空记忆；原文仍在，顺着 observation 的 `sourceFactIds` 回查。

⑦ **同一主题的最新一次**（§3.2 末行 + blockquote、附 A.2 案例 26）——原稿把「那件事」当纯语义问题。补上第二个维度：语境（话题相关）之外还有**新鲜度**（同主题最后一次）。两道一起用：每轮 recall 带 `queryTimestamp` 做时间锚，检索表达再写明时间意图。能不能稳定挑出来进待验证（继任稿附 C.3 ⑥），**验收案例 26 随本次补上**（"同一主题前后聊过两次、第 2 次细讲"，与案例 10 的区别是那里只聊过一次）。

⑧ **犯错时：不设检测器**（§4.3 整节重写、附 C.4 删性能退路、评审包附 E 决策 3/附 F 表头随之改）——原 §4.3 的三种错按"往哪边倒"混着写。改成分三种错一张表，关键是**哪种自愈**：漏查自愈（用户下一句就补上了）、误查不用治（用户无感）、**装作知道不自愈**——那才是要挡的，靠 §3.3 的硬规则挡，不靠事后检测。为漏查加检测器（分词、词表）走不通：字面规则不懂语义，要真判就得再请一个 LLM，那是第二次判定，不是"检查"。真到判定并入生成顶不住，退路是**把判定拆成独立一次 LLM 调用**，不是回头用规则路径——「性能退路」这个说法整个删掉（附 E 决策 3、附 F 表头）。

**附 A 案例集补成可整跑**（2026-09-18，**非机制改动**）——表头补「**怎么当测试集跑**」：每个用例三件输入（最近对话里有什么 / 没有什么、变量当前值、本轮原话），「判定」列即期望输出，**比对 `recall` 取值与检索词的关键成分，不比措辞**（措辞由模型定，附 C.3 ②）；一条原话对应两种状态的两处（案例 4、20）拆成两个用例各跑一次，反问轮 12 / 12-a 是同一输入的两个分支、由夹具钉住；案例 9 / 11 / 18 的正文属测试数据，放夹具不放正文。表头同时删掉两处 v2 表里已不存在的列名（「检索去向」「期待返回」）。

**v0.10.0：白话重写并入 + 三条裁定**（2026-09-16，**机制改动——待人批准**）。

**并入**：白话稿的 §1–§9 / §11 行文并入重写稿（**设计内容以重写稿为准**——白话稿停在 v0.9.10 的机制状态，直接照搬会把 v0.9.11–v0.9.13 退回去），§10 案例集 / 附 A / 附 D 原样接回；白话稿文件留作对照，定稿时删。合并时做了两次全稿扫：`判定行 → 判定字段`（合并后 0 处残留）、`锚点 → 变量名`（§4 与 §10 统一到"变量名"，术语表随之删掉"锚点"一行）。

**三条裁定**（人裁，逐条落在正文）：

① **收集前回顾整个归装配侧，不发判定**（§3.3）——要收哪些变量、值空不空，代码都算得出来（脚本里写死的 `output` 变量 + 当前值），模型在这件事上没有多余信息，让它判一次等于白花一次生成。改后：§3 开头从"三个触发点都由判定"改成"三个触发点、两处要判"；§2 第 3 行、§8 分工表（多一行"主线 / 进话题时一次 / 装配侧"）、§10 案例 1（「判定」→「触发」+ 代码拼的检索词）、附 D（`query` 表删"收集前回顾"行、删示例 5、契约表"时机先筛"一行改为"不管收集前回顾"、样例重新编号）随之改。**代价**：检索词不再由模型写成一句自然问法，退成代码拼的「话题名 + 变量名」——这点措辞值不值，并入附 D 待验证 5 一起量（附 A.2 那条"固定拼法才有的问题"因此仍有意义）。**附带解决**了本稿待定项 5：那一项问的是"话题首个动作可能是 ai_say，判定字段给谁看"——装配侧直接跑之后，这个问题不存在了。

② **实体态每轮都取，渲染分轮**（§4 实体臂 / §5 / §9 / §11）——`includeEntities` 不按轮切（Hindsight 默认就是开：不传即开），取回上限统一 `maxEntityTokens: 200`；**渲染**仍只看这一轮给没给 `entities`——§9 据此决定渲不渲染那份实体态。原写法是"判定给出专名才取"（省一次服务端合成），改成"取回来放在手里，渲不渲染另说"：判定漏了专名时实体态还在，成本只是服务端合成与传输、不占 prompt 预算（与"宁可多查"同向）。三层由此在 §4 分清：**检索臂**（bank 配置 `enable_graph_retrieval`，调用侧根本控不到）→ **取回**（每轮）→ **渲染**（分轮）。§11 的 port 缺项随之从两项变一项——只需补 `maxEntityTokens`，`includeEntities` 不进端口（它不按轮切）。

③ **`fastHits` 存 5 轮、渲染 5 轮**（§9）——原稿两处数字对不上（存 5、渲 3），人裁统一到 5：第 4、5 轮没有任何机制会回头去看，留着不渲染纯是占内存。

**重写稿轮（白话重写，已并入 v0.10.0）**：不改设计，只换说法。**三处对照**——左＝旧草稿原话，右＝重写后（原则见 `.claude/skills/heartrule-design-docs` › 表达原则）：

| 草稿                                                                                     | 本稿                                                               |
| ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 引擎**扣住**这第一行不发用户，解析它决定：**放行**、**记账**，还是让它**收笔**、查完重答 | 判定字段**不给用户看**：引擎读到它、把它摘掉，据此决定这一轮怎么走 |
| **静态先筛**——文档装载后本话题变量全非空，不把「收集前回顾」交给判定                     | 装载后变量都有值 → 不查（判定不参与）                              |
| 每轮同时跑一遍**审计探针**（<1ms），只记录不干预                                         | 那套字面检查只做记录，不改判                                       |

`放行 / 记账` 是白话重写删掉的两个词——它们是"直接回复"和"查到的下轮带上"的别名，各只出现一次，读者为它们付的学费收不回来。

**v0.9.13**：**反问降为时机**（2026-09-16，**机制改动——待人批准**）+ Hindsight 检索方式核对——① §3.2 原来写着"用户把问题抛回来……这一轮算「接不住」，给 `recall=block`"，把两个未经证明的前提（**反问必答**、**答必给方案**）塞进了记忆机制的判据。改后：**答不答、答什么由咨询框架定**（这一轮该给建议 / 先澄清 / 只共情 / 把反问本身当材料），记忆只在"这一轮定下来的那句话缺不缺窗口外的事实"上说话，判据仍是 §3.0 两问；"不接的反问 → `none`"。框架经验往往往反方向压——用户直接要方案常是"想让人替他决定"（与模板 `话术调整策略` 里「不知道」「自我批评」同类），标准动作之一是先不接，而这句话所需的事实为零。② §3 开头三触发点改为**不同级**（指代 = 话里有钩子；反问 = 时机；收集前回顾 = 装配侧先筛）。③ §2 速览第 2 行随之改（"出什么问题"一列原先预设必答）。④ 附 D 的 `反问` 行收窄为"要引既往事实时"，新增**示例 6**（反问给 `none`）——原五条样例里反问一律 `block`，会把模型教成"看到反问就查"。⑤ §10 案例 12 保留并注明它属"真要引既往事实"的那种，**新增 12-a**（同一句反问、这一轮先澄清 → `none`）**与 12-b**（反问 + 专名 → `block`，与 §3.1 同源）——案例 12 的"要查"不来自"用户反问"，来自那句缺既往事实。⑥ §6「不做类型区分」改为**显式传三类**：SDK v0.9.1 `RecallRequest.types` 不传时默认只返回 world + experience，**observation 会被静默漏掉**。⑦ 附 D 增"两臂分工"（专名给 `entities` 取关系、`query` 只管"事"），"不改写成问句"改为"不写整句问句、写需要什么面"（虚词会进 **BM25 关键词臂**当词项）——Hindsight 是多臂混合：语义 + 关键词 + 时间臂 + 实体图臂 → RRF → 交叉编码器重排。⑧ §4 增"时间锚点"一行：每轮 recall 带 `queryTimestamp`（ADR 004 决策 3 写"按需"，此处定成"每轮"）。⑨ §11 增 port 缺项一行（`RecallOptions` 无 `includeEntities` / `maxEntityTokens`）。

**v0.9.12**：判定段的**住所与形态**定案（2026-09-16 人裁）——① **住所**：判定段住 **Default 层模板**（`config/prompt-defaults/ai_ask_v1.md`）的**最末**，与它的输出格式块合写；Custom 层可**整段覆盖**（沿用 Custom > Default 两层解析），Default 这份随引擎版本走。裁定理由：提示词模板是引擎机制的一部分——字段名与取值在代码里写死，模板能改的只是措辞；"拼接"方案要把两份产出拼成一份输出，不值当。② **接口**：代码写死的是**接口**（四个字段名 `recall` / `query` / `entities` / `reason` + 三个取值 `none` / `defer` / `block`）；覆写改坏字段名 → 解析失败 → 按 `block` 兜底（§3.0 第 4 条，方向保守），装载时由 `validateTemplate()` 盯这一条（防覆盖后静默降级）——归实现故事。③ **形态**：判定四字段**并进模板那份 JSON 的开头**，不是"第一行判定 + 第二行起正文"——Default 模板的产出本来就是**一份严格 JSON**（`output_list` / `response_plan` / … / `content`，末句"不要附加任何其他文本"），一份输出、一份解析；预填充 `{"recall":"` 正好落在这份 JSON 的开头；判 `block` 的收笔 = 写完四个字段停笔。正文随之改写 §3.0 / §5 / §11 与附 D 里"首行 / 第一行 / 第二行起正文"的措辞（旧形态从未落地实现，不算推翻）。④ 附 D「待验证」表加**「过线」列**（9 条只给"过线长什么样"，数值待首轮案例集实测后由人填；1 / 2 / 7 三条优先——它们决定这套机制值不值）。⑤ 附 D 输出契约表新增「住所」「接口」「校验」三行，「位置」一行改为"输出的**开头**"。草稿版本行此前停在 v0.9.10（未随上一条同步），本次一并对齐到 v0.9.12。

### C.1 逐步走查

**0 · 会话恢复**

- 输入：sessionId + 用户消息 → 过程：恢复执行态（位置、4 层变量、对话历史）→ 输出：窗口 5 条、两个变量均为空
- 可行性：✅ 现有链路（`processUserInput`），无新增依赖

**1 · 连发拼接**

- 输入：单条消息 → 过程：无连发，原样通过 → 输出：同上
- 可行性：✅ 字符串操作

**2 · 触发检测**（规则，0 LLM，<10ms）

- 输入：本轮原话 + 窗口文本 + 词表
- 过程：① 指代词表逐条正则——本句不含「那件事 / 上次 / 老样子 / 你上次说的」等，不命中；② jieba 分词 → 未知 token 视为专名候选 → 窗口检查
- 中间结果（实测，`jieba.cut`，与 @node-rs/jieba 同源词典、未逐条比对）：`['李光', '最近', '又', '联系', '我', '了', '，', '我', '挺烦', '的']`——「李光」切成单 token、不在通用词库 → 候选；窗口文本不含「李光」→ 命中
- 输出：`{ type: 'referent', source: 'properNoun', referent: '李光' }`
- 可行性：✅ 正则与 `includes` 完全确定；本例分词恰好通过。⚠️ **换句式会漏**——见 C.2 发现 1

**3 · 免查检查**

- 输入：候选专名 + 窗口文本 → 过程：`windowText.includes('李光')` → 输出：false → 不跳过
- 可行性：✅ 纯字面检查；硬约束是窗口必须与主线 prompt 同源（ai_ask `slice(-5)`）

**4 · 构造查询**（确定性，0 LLM）

- 输入：原话 + 锚点集合（当前动作要收的 `{核心信念}` 优先，按声明顺序补 `{睡眠质量}`）
- 过程：原话 15 字 ≤ 200 不截断 → 拼接 `原话 + " —— 关于" + 锚点串`
- 输出：`recall(u, "李光最近又联系我了，我挺烦的 —— 关于核心信念、睡眠质量")`
- 可行性：✅ 全部字符串操作。⚠️ 张力：罕见专名本身已是强指纹，锚点那半句在此轮**主要起稀释作用**——见 C.2 发现 2

**5 · recall**（≤200ms，0 LLM）

- 输入：userId + 查询串 + 给出专名时才带的 `includeEntities: true`（§4 实体臂）
- 过程：本地 HTTP 到 Hindsight，跨类型检索，按相关度排序
- 输出（**设计预期，非实测**）：`results` = 第 1 次"李光是我前同事……说想合伙创业"、第 2 次"李光又发消息了……我有点烦"；`entities` = 实体节点「李光」（`canonical_name`、首次/末次出现、共现）
- 可行性：✅ 调用机制成立（适配器已有 recall + 异常降级）。⚠️ 两个条件：命中排序是语义相似度的统计行为，未实测；`entities` 两处未实证（§4），且**当前适配器只遍历 `response.results`**（`hindsight-adapter.ts:85`），实体段会被丢掉——接线属「指代实体臂」backlog 故事

**6 · 合并进 memoryContext**

- 输入：`MemoryContext` → 过程：`fastHits.push({ round, query, context })` → 输出：滚动窗口多一条
- 可行性：✅ 纯数据操作（§9 结构，未实现）

**7 · 注入 prompt（渲染）**

- 输入：`session.metadata.memoryContext` → 过程：`buildSystemVariables()` → `formatMemoryContext()` → 模板替换 → `{%memory_context%}` 展开
- 输出（§9 设计态）：

  ```markdown
  ## 本轮相关记忆

  - 李光是我前同事，辞职之后还总联系我，说想合伙创业
  - 李光又发消息了，说想合伙创业。我有点烦
    ［相关人物］李光：来访者前同事；首次提及 2026-08-20；最近 2026-08-27
  ```

- 可行性：✅ 模板拼接（`formatMemoryContext` 在 `base-action.ts:384`，ai_ask / ai_say 都调用）。⚠️ 两点：片段**没有"第几次会谈"标签**——适配器只透传 `occurred_start/end` 与 credibility，会话号系统给不出（发现 3）；实体子块是设计态，待接线

**8 · 主线 LLM 生成回复**

- 输入：ai_ask 模板 + 窗口 5 条（无「李光」）+ `{{collected_variables}}` + `{%memory_context%}`
- 过程：单次 LLM 调用（主线唯一的 LLM 调用）
- 输出（**设计预期示例**）："李光又来找你了——你之前提过他，是你前同事，一直想拉你合伙创业。他这次联系你，你挺烦的。我想接着问一句：这种'烦'，是烦他总打扰你，还是他勾起了你'什么都做不好'的那种感觉？"
- 可行性：✅ 机制成立——前一句的身份衔接 = 记忆片段 + 窗口内容的**免费消解**（主线读着材料自己对上的，快通道没做任何判断，§4 三条不做之一）；后一句回收 `{核心信念}` = ai_ask 的任务约束。⚠️ 质量依赖步骤 5 的命中；不命中则反问"李光是？"——兜底，案例集认可（案例 4）

### C.2 审计汇总

| 步骤                              | 性质             | 结论                                         |
| --------------------------------- | ---------------- | -------------------------------------------- |
| 0 / 1 / 3 / 4 / 6 / 7（机械部分） | 确定性           | ✅ 输出可由输入 + 过程得到                   |
| 2（分词那条路）                   | 确定性，但有边界 | ⚠️ 本例通过，换句式会漏（发现 1）            |
| 5（recall + entities）            | 有条件           | ⚠️ retain 前提已满足；命中质量与实体段待实证 |
| 8（LLM 回复）                     | 免费副作用       | ✅ 机制成立，质量随步骤 5                    |

**发现 1（实测）· 分词边界是这条链上最实的弱点**：同一个名字换句式就变——

| 原话               | `jieba.cut`                   | 候选                                                                                                   |
| ------------------ | ----------------------------- | ------------------------------------------------------------------------------------------------------ |
| 李光最近又联系我了 | `['李光', ...]`               | ✅ 命中                                                                                                |
| 李光是我前同事     | `['李', '光是', '我前', ...]` | ❌ 「李」「光是」都在词库，候选消失——**漏查**；且「我前」是被合并出的垃圾 token、不在词库 → **误触发** |

名字接「是」时被「光是」吃掉。漏查后果 = AI 当众问"李光是？"；误触发代价小（多一次 recall，查询仍用整句原话）。**处置**：① 把"名字 + 邻字（是/说/又/和…）"做成实现故事的回归案例；② 评估检测规则是否从"未知 token"放宽到"姓氏字 + 名"组合模式；③ 词典里已收的常见人名（张伟、王芳一类）不在此路覆盖范围内，同样漏。

**发现 2 · 专名轮里锚点主要是稀释**：罕见专名是很硬的检索指纹，"关于核心信念、睡眠质量"那半句在此轮主要贡献噪声。本条针对的是**固定拼法**——它必须拼；判定并入生成后，这层判断归判定行（§10 案例 6 的期望输出就不带锚点）。要不要把它写进固定拼法的规则，与 §4 待定②、案例 13 同属实证范畴，列入实体臂 / 三路实证的样本即可。

**发现 3 · 片段没有会话标签**：retain 已带 `documentId = actionId`，但 recall 条目不映射回会话 / 轮次，AI 只能靠 `occurred_start` 与内容推断时序。要不要在 retain metadata 里带 sessionId、渲染时标"第 1 次会谈"——重写稿未言明，属实现选择，待定。

> 本附录的三个发现都指向同一件事：**规则路径的能力上限是已知的、可接受的，但它的边界要沉到实现故事的回归案例里**，不能留在正文的一行描述中。

## 附 E：待提 ADR 草稿——008 主线触发的判断并入生成

> **状态：草稿，待人批准**（批准后整段搬到 `docs/design/decisions/008-*.md`，无 frontmatter；并更新 `docs/design/README.md` 索引与 `architecture-constraints.md`）。
> 按机制讨论纪律（[开发节奏系统 §8](../../process/development-rhythm.md)）先给两份现状，待人验证：
>
> - **静态现状**：继任稿 §2（判定字段，含末段的审计探针）+ §3（路标 / 缺什么 / 组合规则 / 三个时机的判定线）+ 附 F（规则路径：词表正则 → 分词未知词候选 → 窗口字面检查 → 查询拼装）+ 继任稿附 C.3（固定拼法：200 字截断、变量名 ≤2、不清洗）；实现侧全未落地（继任稿附 C.7 当前实现差距）。
> - **动态现状**：附 C 九步走查——规则路径下一次指代轮的完整链路（案例 6「李光」），逐步验证过可行性，并实测出分词边界（发现 1）与锚点稀释（发现 2）。

### 背景

规则路径的能力上限已由附 C 逐条实测：**同一个名字换个句式就漏**（「李光最近又联系我了」能切出「李光」，「李光是我前同事」被切成「李 / 光是 / 我前」），**纯指代词分不清所指在不在窗口内**（案例 4、20 只能一律查），**「用户已经交待过」这种判断根本做不了**（"李光是我前同事"这类句子，规则看不出它已经把话说清楚）。这些不是词表长短的问题，是"字面规则"这条路本身的天花板。

第二笔账是**顺序**。项目自己的设计原则是**渐进规则化（CLAUDE.md 设计原则 3）：先让 LLM 干，只在它一致性失败处加规则**——而按字面规则设计这条路把顺序做反了：先造词表 + 分词端口 + 窗口检查，再去补它的漏。附 C 的实测正是"失败处"，而失败处指向的修法不是再加规则。

第三笔账是**判断放在哪里**。判断单起一次调用，会给**每一轮**都加上一份串行等待与一份额外预填的 prompt——而咨询场景大多数轮并不需要查记忆（假设，待实测）。把这笔税平摊到不需要它的轮上不划算；把判定放进主线生成的开头，边际成本只有几十个输出 token，要查的轮才付一次重生成。

### 决策 1：主线触发的判断并入生成——回复开头先给判定字段

**结论**：**两个判定触发时机（指代 / 反问）**由**主线回复开头的判定字段**处理——判定字段给 `recall` ∈ `none`（不查）/ `defer`（先答、记忆下轮带上）/ `block`（收笔、查完重答），并附 `query`（检索词）与 `entities`（专名）。引擎扣住它，解析后决定放行、记账，或让这次生成在判定字段处收笔、查完重答（继任稿 §2，判定标准即该节的两问）。提示词与输出契约见继任稿附 B。规则路径只做审计探针（决策 3）。

**字段顺序**（2026-09-18 补充）：四字段的**顺序也是接口的一部分**——固定为 `reason` → `recall` → `entities` → `query`。模型逐 token 生成，先写的条件化后写的：`reason` 排最前，模型得先把"缺什么"想清楚再落判定与检索词；排最后就成了事后合理化。解析不依赖顺序，但从宽要求守这个序（继任稿 §2 / 附 B.3）。这条本身待实测（继任稿附 C.3 ⑤）。

**收集前回顾不判**（2026-09-16 补充）：要收哪些变量、值空不空，代码静态可判且确定——装配侧解析出空值变量后直接拼检索词、直接查（继任稿 §3.6），不进判定字段。判定段只覆盖指代与反问两处。

**住所与接口**（2026-09-16 补充）：判定段**住在 Default 层提示词模板**（`config/prompt-defaults/ai_ask_v1.md`）的末尾、与它的输出格式块合写，Custom 层可整段覆盖；代码写死的是**接口**——四个字段名（`recall` / `query` / `entities` / `reason`）与三个取值（`none` / `defer` / `block`），模板能改的只是措辞。判定四字段写在**模板那份输出 JSON 的开头**（与主线回复同属一次生成、一份输出）。

**反问只是时机**（2026-09-16 补充）：用户把问题抛回来时，"答不答、答什么"由**咨询框架**定（该给建议 / 该先澄清 / 只共情），记忆只在"这一轮定下来的那句话缺不缺最近对话里没有的事实"上说话——**不接的反问给 `none`**（继任稿 §3.5）。

**理由**：判断"这轮靠已知够不够"是语义判断，不是字面判断；判定的上下文（原话、窗口、变量）主线本来就要预填，放进生成里边际成本只有几十个输出 token；顺带解决了实体臂的开启条件（`entities`）与两种时机撞车的问题（一次判定覆盖）。不单起调用则常见轮零额外等待——这是它比"生成前一道判定"更优的地方。

### 决策 2：快通道的定义从「0 LLM」改为「用户等待预算内」

**结论**：「快通道 / 慢通道」不再以"调不调 LLM"划线，改以**预算**划线——在用户可接受的等待预算内跑完的是快通道，后台跑、用户不等的是慢通道。**部分推翻 [006 决策 3](../decisions/006-retrieval-layer-scope.md)（"快通道保持 0 LLM"）**，以及 [004](../decisions/004-memory-model-calibration.md) 遗留项里的同一处理意见（"走规则，LLM 升级移到慢通道"，004:184）。

**理由**：0 LLM 是手段不是目的——目的是"用户不等"。"规则快"只在规则判得对时才有价值；判错的代价（AI 当众问"李光是谁"）落在用户身上。这条红线一旦被当成目的，就会把全部复杂度压在规则侧。006 决策 3 的另一半——"不在快通道里做能力升级式的 LLM 摘要"——仍然成立，本决策只放开"判断"这一步。

### 决策 3：规则路径只做审计探针（**性能退路已撤回**，2026-09-18）

**结论**：词表 + 分词 + 窗口检查那条路留在继任稿 §2 末（用法）与附 F（细则），只承担**一个**角色：**每轮都跑、只记录不干预**的审计探针——"规则说要查而判定给 none"的轮次是"模型装作知道"风险的观测点。它**不参与判定**：输出开头没有合法判定字段、或头部缓冲超时，按 `block` 兜底（决策 4）。

**它不是性能退路**（2026-09-18 改）：这一条原先留着"延迟或守约率实测不达标时整条退回用它"。撤回——它判不了。「延迟或守约率不达标」要的是**判断**，而字面规则不懂语义：同一个名字换个句式就漏、纯指代词分不清所指在不在最近对话里，退回用它等于用一个已知更差的判手。真要退，退的是**把判定拆成一次独立的 LLM 调用**（继任稿附 B 的判定段原样搬出去）——那时付的是一轮一次的等待，而不是换成规则。附 F 随之只作探针细则保留。

**理由**：它的边界已被附 C 实测清楚，重写一遍是浪费；且它零成本（<1ms）、可离线，做探针不占用户等待。"装作知道"是本机制最实的风险，而它是唯一能自动标出候选轮的现成资产——**唯一的例外在意识层**：那边可以请第二个 LLM 复核（慢通道，用户不等，继任稿 §5）；快通道不设检测器（继任稿 §4.3）。

### 决策 4：失败方向是保守的，且不靠新增调用兜底

**结论**：输出的开头不是合法判定字段（或头部缓冲超时）→ 当作 `block` 处理：弃掉这次生成，用继任稿附 C.3 的固定拼法查一次、重生成。**不为此再起一次 LLM 调用**，也不交给规则路径。静态可判的部分一律留在装配侧——**整个收集前回顾**（解析待收空值变量 → 代码拼检索词 → 查询 → 注入本话题 prompt）都不经判定（v0.10.0 ①，见继任稿 §3.6 与附 B.3 契约表）。

**理由**：错误成本不对称（误查便宜、漏查伤用户）——判不出来时按最保守的方向走，只是执行者从规则换成了固定动作。静态部分留在代码里是因为它确定性成立，没有理由花一次判断去问。

### 后果

- **正面**：常见轮零额外等待（不需要查的轮只多几十 token）；判断质量不再受分词边界与人称代词限制；查询质量提升（反问轮能查到"需要什么"而不是抄原话）；案例 4/20 一类白查省下来；实体臂开启条件变干净；"窗口同源"随判定并入生成自动成立（判定与正文同一个 prompt）；文档里规则体系的维护成本不再压在主线上。
- **成本**：要查的轮多一次重生成（预填账取决于前缀缓存；模型自己收笔时或可续写免掉）；判不出来时按 `block` 兜底会白付一次重生成（格式守约率决定这条路径有多冷，继任稿附 C.3 待验证 ①）；判断从"专门问一件事"变成"和正文抢注意力"，模型**可能装作知道**，判定与正文相互干扰的风险待实证（继任稿附 C.3 待验证 ④）；规则路径成为需要维护的第二条路（决策 3）——现在只为探针而存在，将来只可能删掉。
- **遗留跟进**：① 案例集 4/6/13/20 的判定已按 2026-09-14 裁定改写（继任稿附 A 开头），随实现落地为测试基准；② 判定实现的故事与「ai_ask 快通道实现」故事的拆分/改写（backlog Epic A）；③ 判定段的实证迭代（继任稿附 C.3 待验证表）；④ [意识系统](../consciousness/consciousness-system.md) §2.7 分工表里"主线：0 LLM"一行同步；⑤ 投机检索（继任稿 §4.2 末，"不做"）等实测有数再议——它在继任稿里保留，"不做"的结论未变。

## 附 F：规则路径细则（审计探针用）

> 规则路径现在只承担审计探针这一个角色（继任稿 §2「这套判法的两个风险」一段）。**它不是性能退路**——那条退路已撤回（附 E 决策 3，2026-09-18）：字面规则判不了语义，真退是把判定拆成独立一次 LLM 调用。这里备它的完整细则，只按"做探针"实现。

**词表里有什么**（约 60-80 条；引擎给默认词表，Custom 层可追加 / 覆盖，与 prompt 两层解析同模式）：

| 组       | 例子                                                                           |
| -------- | ------------------------------------------------------------------------------ |
| 指示指代 | 那 / 这 + 件事、个人、次、种、会儿、时候                                       |
| 时间指代 | 上次 / 上回 / 前几次（+ 会谈、说的、聊的）；之前 / 当时 / 那天 / 那晚 / 那时候 |
| 惯用语   | 老样子                                                                         |
| 强标记   | 你上次说的 / 你让我做的 / 你给我的                                             |
| 人称     | 他 / 她 / 它 / 他们（常见，但无法做免查检查 → 一律默认查，案例 20）            |
| 反问句式 | 你觉得呢 / 我该怎么办 / 你怎么看 / 你说呢 / 我该不该（§3.2）                   |

**词表不求穷尽**：汉语代词全量有数百条，绝大多数与调记忆无关（"我""什么样"不需要查）——只收"咨询场景里指代了窗口外内容"的几类，随实证增删：漏了加一行、误报删一行。

```ts
// 本轮检测（连发拼接后执行，0 LLM，无 I/O）——给出的是「规则会说要不要查」，探针照此记录
function detectTrigger(utterance: string, windowText: string): TriggerResult {
  for (const re of REFERENT_PATTERNS) {
    // ① 指代词表：命中即记（不做窗口检查）
    if (re.test(utterance)) return { type: 'referent', source: 'pattern' };
  }
  for (const token of segment(utterance)) {
    // ② 专名候选：窗口里没有 → 记
    if (isUnknownToken(token) && !windowText.includes(token)) {
      return { type: 'referent', source: 'properNoun', referent: token };
    }
  }
  for (const re of COUNTER_QUESTION_PATTERNS) {
    // ③ 反问句式：命中即记
    if (re.test(utterance)) return { type: 'counterQuestion' };
  }
  return { type: 'none' }; // 规则说这轮不查
}
```

三条实现约束：

| 约束             | 内容                                                                                                                                                                                                                                                 |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 正则单扫         | 词表全部编译为正则逐条 test，单轮 <1ms                                                                                                                                                                                                               |
| 窗口检查只给专名 | 只有专名候选做窗口检查——检查只有"没找到 → 查"一个失败方向，永远不会因为它漏掉该查的；代价是"字面出现 ≠ AI 真能解析"，方向安全                                                                                                                        |
| 窗口同源         | 窗口检查用的「最近聊天」必须与主线 prompt 的最近聊天**共用同一个函数/常量**——两边不一致会导致最坏情况：检查说"窗口里有"而 LLM 实际没看到，AI 在无上下文下硬答。注意两个动作的窗口长度不同（ai_ask 5 条、ai_say 10 条），**各自与自己的 prompt 同源** |

分词走 **@node-rs/jieba**（Rust 绑定，实测切 1184 词约 0.12ms，预编译二进制无工具链依赖）；**不用**分词库自带的人名标注（召回约 0.65，且把地名当人名——"阿富汗""桂林"假阳性）。`segment` / `isUnknownToken` 由 **SegmenterPort** 端口承载：core-engine 保持零依赖，api-server 提供 jieba 实现（六边形架构）。

**规则口径**：专名在「最近聊天」窗口内 → 它说不查；纯指代词一律说查。探针照此记。

**已知边界**（附 C 实测）：未知 token 这条路在「李光是我前同事」上会漏（被「光是」吃掉），且「我前」这类合并出的垃圾 token 会误触发——所以它只做探针，不是等价替代。

**再往下的升级路径（待评审）**：规则召回不足时，新增**「指代补漏」意识**——异步复核主线未命中的轮次，把漏掉的指代解析结果注入下一轮（模型能力用异步换回来，ADR 004）。仍不足再考虑 ONNX 小分类器（3-55ms，但引入模型基建与训练数据）。挂 [意识系统设计 §2.7](../consciousness/consciousness-system.md) 待评审。
