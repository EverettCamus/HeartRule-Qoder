## 1. 问题

ai_ask 负责向来访者收集信息。**引擎级业务需求一句话：来访者提到「最近聊天」窗口里解不开的内容（那件事、上次说的、李光、阿黄），或把问题抛回给咨询师时，AI 在回复前查会谈记忆搞懂指什么、有什么依据，不再重复追问已经知道的信息。**

主线 LLM 的 prompt 只携带「最近聊天」的有限回合——**本次会谈早些的内容和跨会谈的内容都不在**。当用户回复依赖这些窗口外的上下文时，不调记忆 AI 就只能反问"李光是谁？"或给出空泛的回复。快通道（本文）承担的就是这条主线侧的同步调取；觉察判断类调取（矛盾比对、情绪轨迹、阻抗、危机趋势、话题衔接）归意识层各意识，见[意识系统设计 §2.7](../consciousness/consciousness-system.md)。

**第二条引擎级业务需求：脚本要收集的信息，用户过往会谈可能已经讲过。** 本话题要了解「小时候的主要抚养者」，不代表用户之前没提过——收集前先回顾记忆，AI 开口就能带上一句"你之前提过…"，而不是让用户把自己讲过的话再讲一遍。同一条快通道，触发点在**话题入口**，且只对**当前值为空**的待收集变量生效（§3.1）。

## 2. 总体流程

ai_ask 的记忆调用分为两路，构成**快/慢双通道架构**（主线同步调取 / 意识层深度调取）：

```
ai_ask 启动
  │
  ├─[阶段1] 快通道 (主线同步调取) ── 三个触发：话题入口预取（空值变量，
  │             §3.1）、每轮回复的指代检测、反问检测（§3.2）；命中则按密度分诊
  │             （§3.3）构造查询 → recall() → 结果注入 prompt
  │             ≤200ms，纯检索无 LLM 调用
  │
  └─[阶段2] 慢通道 (异步深度分析) ── 由意识层 `insightForSlowThinking` 触发
                → 机制细节见 [意识系统设计 §2.6](../consciousness/consciousness-system.md)
                → 产出 DeepInsight 洞察 → 注入后续轮次
                异步运行，不阻塞用户（本文 §4 仅保留 ai_ask 侧契约）
```

### 快/慢双通道设计原则

| 维度             | 快通道                                                                           | 慢通道                               |
| ---------------- | -------------------------------------------------------------------------------- | ------------------------------------ |
| **目的**         | 懂用户说什么——「指的什么？答有什么依据？」；收信息前知道多少——「这个讲过没有？」 | 深挖——「背后有什么深层模式？」       |
| **触发**         | 话题入口预取 + 指代检测 + 反问检测（§3.1/§3.2）                                  | 意识层 `insightForSlowThinking` 触发 |
| **查询来源**     | 密度分诊: 纯锚点 / 原话+锚点 / 头尾截断+锚点（0 LLM，§3.3）                      | LLM 生成概念化查询方向               |
| **延迟**         | ≤200ms（一次 HTTP 到 Hindsight）                                                 | 5-30s（多次 LLM + recall）           |
| **阻塞用户**     | 是（但延迟极低）                                                                 | 否（fire-and-forget）                |
| **LLM 调用**     | 0                                                                                | 2-3 次（查询生成 + 综合 + 可选门控） |
| **结果生命周期** | 保留最近 5 轮                                                                    | 持久保留（带时效性校验）             |
| **失效风险**     | 语义鸿沟（情绪陈述 vs 事件叙述）                                                 | 时效性错位（产出时话题已转移）       |

### 变量与记忆的边界：权威在文档，记忆只补上下文

一个自然的想法是：ai_ask 启动时根据待收集的变量名查记忆，命中则预填初值，再决定"跳过提问 / 确认式提问 / 正常收集"。这个想法**去掉"预填初值"就成立**——回顾记忆是对的，把回顾结果写成变量的值是不对的。分开说：

**为什么需要回顾**：跨会话状态的权威是[信息点文档](../decisions/007-variable-document-boundary.md)（ADR 007 决策 2），脚本工程师在脚本里声明变量与信息点的映射。但**没被映射的变量，文档里根本没有这个信息点**——而"用户过往讲过没有"不取决于脚本有没有计划收集它。所以：装载之后**值仍为空**的待收集变量，要先做一次记忆回顾（§3.1 话题入口预取）。

**为什么不把回顾结果写成变量的值**：

- **空值变量没有文档修正面**——它的值一旦由记忆写入并驱动退出决策（"这个变量有了，不用再问"），本次会谈就少收集了本该收集的信息；而人类咨询师能改的是文档，恰恰这一项没有信息点，无从修正（ADR 007 的人类修正面落空）。
- **记忆值可能过时、不精确，或以不同形式表达了当前要收集的概念**——让 LLM 带着它写一句确认式提问（"你之前提过…，是这样吗？"）是稳妥的；把它固化成变量的当前值，则把不确定性藏进了流程控制。
- **值一旦写入就产生消费依赖**——下游 condition / 退出决策按精确标量用，逼出 bridge 那套新鲜度与证据强度的合并策略，而 ADR 007 决策 6 刚把这套复杂度砍掉（会话内只剩 piggyback 一个刷新源）。

所以快通道的做法是：**recall 记忆片段 → 作为「预备上下文」注入 prompt → LLM 自然衔接或确认**；变量值仍走正常流程（用户回复 → 提取）。不需要 `onRecall` 策略层来决定"跳过还是确认"——没有值需要策略层去处理，而且这是 LLM 自己擅长的事。

**升级路径（待实证）**：若实证发现"AI 明明看到了预备上下文，仍从零追问"，再考虑把回顾结果写入变量 store（`source: 'memory_prefetch'` + 证据锚，并从退出决策中排除）——先验证不加的情况（渐进规则化）。

**两条通道：值通道 / 上下文通道**（与 [variable-memory-bridge](variable-memory-bridge.md) §4.1 piggy 的关系）：

两者都是**前瞻式准备**（Action N 备 N+1 / 进话题备本话题），区别在产出——一条写**值**，一条只给**上下文**。边界不在"谁管收集、谁管使用"：同一个动作可以既是被 piggy 的读集、又是收集的写集——bridge §4.3 按**引用**解析前瞻变量（与动作类型无关），§4.4 唯一过滤轴是 `autoRefresh`（与"是否待收集"无关）。真正的边界是**变量粒度 + 一条写值红线**：

| 维度     | 上下文通道（本文 §3.1 预取）                        | 值通道（bridge §4.1 piggy）                                       |
| -------- | --------------------------------------------------- | ----------------------------------------------------------------- |
| 触发时机 | 进入话题时（收集前）                                | Action N 执行时（前瞻 N+1 的引用）                                |
| 目标集   | 脚本静态解析：本 topic 待收集变量中**当前值为空**者 | Action N+1 引用的变量 ∩ `autoRefresh ≠ false`——与"是否待收集"无关 |
| 产出     | 预备上下文（注入 prompt，**不写值**）               | 变量值（写 store，`source: 'llm_piggyback'`）                     |
| 要解决的 | 别让用户重复讲过的话                                | 防"收集到使用之间"的补充信息漏掉                                  |

**写值红线：本 topic 待收集且当前为空的变量，不进 piggy 目标集。** 现行 bridge 的写入门槛只有"非空"（§4.5 Phase B），没有"原本有值"；§4.4 又把临床判断类默认置 `true`（核心信念、主要压力源、情绪状态——恰是待收集变量最常见的语义类）。于是待收集变量一旦被邻近动作引用（`condition` 尤其容易：§4.3 规定条件分支"收集所有分支中引用的变量"），piggy 会在用户还没被问到时就写出一个值——而那个 LLM 的视野里就有刚注入的「本话题预备」。这正是本节禁止的"从记忆预填"，且该值直接喂退出决策（跳过收集、人无从修正）。ADR 007 决策 6 关掉了 recall 侧的"空值兜底"，却没在 piggy 侧补上同样的闸门——**漏洞是那条决策的残留**。闸门落在 [bridge 修订故事（Epic D）](../../scrum/backlog.md)，本文只声明边界。

> **另有一条写值的路是合法的**：**已映射**变量在装载时的 recall 兜底（ADR 007 决策 4：文档信息点 → Hindsight recall 兜底 → 默认值 → 未定义），发生在会话启动、走显式 fallback 链。本节管的是**无映射**的空值待收集变量。

## 3. 阶段 1: 快通道 —— 主线同步调取

### 3.1 触发一：话题入口预取（空值变量）

**进入话题时**（该 topic 首个 action 执行前）静态解析本 topic 全部 ai_ask 的 `output` 变量，取**当前值为空**者（文档装载没读到、本会话也还没收集）拼成一次 recall——本次话题要收集的信息里，哪些用户过往已经讲过，先回顾一遍：

```
进入话题（首个 action 执行前）
  → 静态解析本 topic 内全部 ai_ask 的 output 变量（脚本已知，0 LLM）
  → 过滤：值已非空（文档装载 / 本会话已收集）→ 跳过，不进查询
  → 空值变量名拼接 → recall(userId, "关于{变量1}、{变量2}")   ← 1 次 HTTP，0 LLM
  → 结果存 session.metadata.topicPrefetch[topicId]
  → 本 topic 内每次 ai_ask 生成 prompt 时，注入 {{memory_context}} 的「本话题预备」段
  → LLM 自然衔接: "你之前提过小时候主要是奶奶带大的，能多说说那时候吗？"
  → 变量值仍由用户回复提取（§2：预取不写值）
```

例子（话题「童年抚养者」，两条 ai_ask 分别收集 `{主要抚养者}`、`{抚养方式}`，装载后均为空）：

- 进入话题 → `recall(u, "关于主要抚养者、抚养方式")` → 命中第 2 次会谈「小时候主要是奶奶带大的，父母常年在外」
- 有预取的首问: "我记得你之前提过小时候主要是奶奶带大的——那时候的日子，你愿意多说说吗？"
- 无预取的对照: "你小时候主要是谁在照顾你？" → 用户："这个我之前说过了呀"

**为什么触发点在话题入口**：

| 位置                 | 问题                                                                                            |
| -------------------- | ----------------------------------------------------------------------------------------------- |
| ai_ask 首轮（改前）  | 变量逐个查（同 topic 多个 ai_ask 就查多次）；结果只能在收集轮用掉，真要综合就没有余量           |
| 会话启动             | 要预判整场会谈的变量，而话题队列会被意识层调整（插入/重排/深度切换）——预判不准，且启动变慢      |
| **话题入口**（选定） | 变量清单静态可解析**且确定**（队列怎么调整，进话题时它都在）；一次 recall 摊到本话题多个 ai_ask |

值非空的话题成本为 0（不查）；空值话题每 topic 最多 1 次 recall（≤200ms、0 LLM）——不违背"回回不慢"（§3.4）。

**与触发二/三的关系**：预取服务"收集前知道多少"（话题粒度、一次）；指代/反问检测服务"本轮回复怎么解"（回合粒度、每轮）——互补，各管一段。

### 3.2 触发二/三：指代检测与反问检测

每轮用户回复后、主 LLM 生成回复前，做两个确定性检测（0 LLM）——**命中才调记忆，未命中跳过**，不为"丰富背景"每轮白查：

**为什么这两个时刻要查**：

- **指代轮缺「听懂」**：指代项（那件事、李光）解不开，AI 就不懂用户说什么——能解开它的内容在「最近聊天」窗口外。查的是「**指的什么**」。
- **反问轮缺「依据」**：AI 这一轮从追问者变成回答者——答"我该怎么办"要有既往方案、用户试过什么、效果如何做依据。查的是「**答有什么依据**」。

漏查的代价：指代轮 AI 只能反问"李光是谁？"；反问轮只能给空泛的通用建议，像第一次见面的机器人。

```
用户回复（可能连发多条）
  → ① 连发拼接: 自上一问以来未处理的消息拼接为「本轮原话」
  → ② 指代检测: 命中指代词表（§3.3）且指代项不在「最近聊天」窗口内 → 查
  → ③ 反问检测: 命中反问句式（§3.3）→ 查
  → ④ 均未命中 → 跳过本轮 recall（话题入口预取 + baseline 已提供背景）
  → 命中 → 密度分诊（话题入口/B/C，§3.3）→ 按类构造查询 → recall()
      ← 纯 Hindsight 检索，无主线 LLM 调用
  → 合并 MemoryContext → 存储到 session.metadata.memoryContext
  → 下一轮 buildSystemVariables() 自动带入 prompt
```

**免查条件**（指代检测的例外）：指代项能在「最近聊天」窗口内解析则不查——专名类做字符串近似检查（窗口内出现"李光"则免查）；纯指代词（"那件事""上次"）无法做这种检查，默认查（多查一次便宜，漏查则 AI 犯蠢）。

**检测的实现方式**（0 LLM，主线每轮 <10ms）：

三条实现原则：

1. **正则单扫**：指代/反问词表全部编译为正则，逐条 test，单轮 <1ms。词表命中的轮次**不做**窗口检查——纯指代词无法检查，且"那个"类泛词在窗口里几乎必然出现过（AI 自己的问话里就有），做字面检查会把真指代误放跑。
2. **免查检查专名专属**：只有专名候选（分词未知词）才做窗口检查——把「最近聊天」窗口消息拼成一个字符串，`windowText.includes(专名)` 命中则免查。检查只有"没找到 → 查"一个失败方向，永远不会因检查而漏掉该查的；近似的代价是"字面出现 ≠ 语义可解析"（窗口里有"李光"只是大概率有上下文，不保证 AI 真知道李光是谁）——方向安全。
3. **窗口同源**：免查检查用的「最近聊天」窗口，必须与主线 prompt 的最近聊天截取**共用同一个函数/常量**——两边窗口不一致时会出现最坏情况：检查说"窗口里有李光"而 LLM 实际没看到，AI 在无上下文下硬答。

```ts
// 本轮检测（连发拼接后执行，0 LLM，无 I/O）
function detectTrigger(utterance: string, windowText: string): TriggerResult {
  for (const re of REFERENT_PATTERNS) {
    // ① 词表指代：命中即查（不查窗口）
    if (re.test(utterance)) return { type: 'referent', source: 'pattern' };
  }
  for (const token of segment(utterance)) {
    // ② 专名候选：窗口检查，没有则查
    if (isUnknownToken(token) && !windowText.includes(token)) {
      return { type: 'referent', source: 'properNoun', referent: token };
    }
  }
  for (const re of COUNTER_QUESTION_PATTERNS) {
    // ③ 反问句式：命中即查
    if (re.test(utterance)) return { type: 'counterQuestion' };
  }
  return { type: 'none' }; // 跳过本轮 recall
}
```

- 词表条目示例：`/那(?:件|个|次|种|会儿|时候)/`、`/你(?:上次|之前|以前|刚才)?(?:说的|让我做的|给我的)/`、`/(?<!其)(?:他|她|它)们?/`（负向断言排除"其他"）、`/我该(?:怎么|怎么办|咋办|不该)/`。
- 专名检测走 **@node-rs/jieba 分词**（Rust 绑定，实测切 1184 词约 0.12ms，预编译二进制无工具链依赖）+ **未知词规则**：分词后不在通用词库、非停用词的 token 视为专名候选。不依赖分词库自带的人名标注（召回约 0.65，且把地名当人名——"阿富汗""桂林"假阳性）。
- `segment` / `isUnknownToken` 由 **SegmenterPort** 端口承载——core-engine 保持纯逻辑零依赖，api-server 以 @node-rs/jieba 实现（六边形架构）。

**错误成本不对称**：误触发 = 一次 ≤200ms 本地检索，无感；漏触发 = AI 追问一轮，下一轮可补救。词表因此**不求穷尽**（约 60-80 条，按咨询场景收敛，§3.3），召回率靠实证测量、证据驱动增删——漏了加一行，误报删一行（渐进规则化）。

**升级路径（待评审）**：规则召回不足时，新增**「指代补漏」意识**（脚本定义意识，LLM 异步跑在支线）——事后复核主线未命中的轮次，把漏掉的指代解析结果注入下一轮。主线保持 0 LLM，模型级能力用异步换回来（ADR 004：LLM 升级走慢通道）。若仍不足，再考虑 ONNX 小分类器（3-55ms，但引入模型基建与训练数据）。挂[意识系统设计 §2.7](../consciousness/consciousness-system.md) 待评审。

**分工边界**：快通道 = 主线同步调取的唯一通道。觉察判断类调取（矛盾比对、情绪轨迹、阻抗、危机趋势、话题衔接）由意识层各意识在自己的多线程通道里 recall，不占主线延迟预算——见[意识系统设计 §2.7](../consciousness/consciousness-system.md)。

**可选增强（待实证，ADR 006 决策 2）**："类似事件 / 关联事件"视角的三路扩展见 [memory-retrieval-types.md §2.11](memory-retrieval-types.md)——默认关闭，先验证不加的情况；启用时超出预算按 §3.4 降级。三路扩展的预期效果示例（未实证）：

- 用户说"还是和之前一样睡不着"，当前在收集 {睡眠质量, 情绪状态}
- 原始查询命中: 第3次会谈"失眠是因为项目压力"，第5次"试过褪黑素没效果"
- 类似事件（抽象: 睡眠障碍 反复发作）: 命中第2次"高三时也失眠过一阵"
- 关联事件（时间窗口: 近期）: 命中"上周提到项目验收临近，压力加大"

### 3.3 查询构造：触发词表 + 密度分诊

**触发词表**（确定性，0 LLM）：

1. **指代词表**：那/这 + 件事/个人/次/种/会儿/时候；上次/上回/前几次（+会谈/说的/聊的）；之前/当时/那天/那晚/那时候；老样子；你上次说的/你让我做的/你给我的（强标记）；他/她/它（人称指代——常见但无法免查检查，默认查，见案例 E1）。专名类（李光、阿黄）词表装不下，走**分词未知词规则**：分词后不在通用词库、非停用词的 token 视为专名候选，命中即触发；查询时专名随原话入查询，检索器按罕见 token 自己命中。
2. **反问句式**：你觉得呢 / 我该怎么办 / 你怎么看 / 你说呢 / 我该不该——用户把问题抛回，AI 的回答必须有既往方案与案例历史做依据（案例 R9）。

两个词表都命中不了 → 跳过本轮 recall（§3.2）——本轮原话就在「最近聊天」上下文里，AI 懂它在说什么，不花这趟检索。

**词表的量级与收敛原则**：词表不求穷尽——汉语代词全量（人称/指示/疑问及变体）有数百条，但绝大多数与调记忆无关（"我""什么样"不需要查）。词表只收「咨询场景里指代了窗口外内容」的几类，总量约 60-80 条，是一个随证据演化的配置表：实证测召回，漏了加一行、误报删一行（渐进规则化）。引擎默认词表，Custom 层可追加/覆盖（与 prompt 两层解析同模式）。

**查询构造——理解模型：查询是「本轮焦点的探针」，不是「原话的压缩」。**

recall 查询的任务是给检索器一个「这轮会谈在关注什么」的语义指纹，去记忆库找匹配的存量。它不需要携带原话本身——本轮原话已在主线的「最近聊天」上下文里；查询要的只是指纹。但主线 prompt 只带「最近聊天」的有限回合：**本次会谈早些的内容和跨会谈的内容都不在**——正是这些窗口外的内容需要靠查询从记忆里取回来。

焦点有两个确定性来源，天然分层：

- **框架焦点** = 当前收集的变量名——零信息损失、永远可用，是查询的**主线**，它定义"什么算相关"。
- **内容焦点** = 用户原话——高熵、方差极大，是查询的**修正**，它定义"具体关注哪个方面"——指代轮里，指代项（李光/那件事）就是最重要的内容焦点。

原话的价值是**话题指纹**——能标识"它和哪些存量是同一主题"的语义内容。指纹密度与字数不成正比：500 字失眠夜全篇可能只有一个指纹；300 字自述可能散落三个指纹。固定截断隐含"信息均匀分布"的错误假设，对长文本必损指纹。

**分诊规则**（确定性，0 LLM；话题入口预取与指代/反问触发轮共用）：

| 类       | 适用                  | 查询构造                                                              |
| -------- | --------------------- | --------------------------------------------------------------------- |
| 话题入口 | 进入 topic 时（§3.1） | `recall(userId, "关于{变量1}、{变量2}")`（仅空值变量，每 topic 1 次） |
| B 装得下 | 触发轮且 ≤200 字      | `recall(userId, "{本轮原话} —— 关于{变量1}、{变量2}")`                |
| C 装不下 | 触发轮且 >200 字      | `recall(userId, "{头100字}……{尾100字} —— 关于{变量1}、{变量2}")`      |

> 200 字 = embedding 输入预算的安全上限（约 300-400 token），与指纹无关——它是"装不装得下"的边界，不是"有没有指纹"的边界。

**通用规则**：

1. **锚点变量数 ≤2**（超过取 output 声明顺序前 2），防锚点稀释。
2. **连发先拼接再检测**（§3.2 ①）——否则连发碎片会漏掉落在后几条里的指代。
3. **原话不清洗**——embedding 对语气词、错别字鲁棒，0 LLM 原则下不做文本清理。
4. **免查条件**（§3.2 ②）：指代项能在「最近聊天」窗口内解析则免查——专名类做字符串近似检查；纯指代词无法检查，默认查。
5. **C 类认中段损失**——头尾保语境与落点；⚠️ 指代项落在中段时会被截断丢失（案例 R8），多查询/分段检索实验优先级因此提升，挂「三路查询实证」故事，默认关闭。

**代词轮的检索指纹**：查询里的指纹不是代词本身——「那件事」零贡献（它指代的东西没有语义指纹，谁也匹配不上）；整句原话提供**语境指纹**（这段话落在哪个话题区域），锚点提供**框架指纹**（限定在收集变量相关的存量里找）；专名是例外——罕见 token 本身就是强指纹，检索器几乎靠它直接命中（案例 R3）。快通道**不做指代消解**（消解 = 语义理解 = LLM）：不消解、直接探针，把"这件事指什么"的活留给检索器用语义相似度去碰。

**为什么分类不再多**：查询构造只有三个形状（纯锚点 / 原话+锚点 / 截断+锚点）。能撑出更多类别的维度在 0 LLM 下不可判定——它们解释每类会在哪里出错，是实证故事的测量目标：

| 维度         | 取值                     | 可判定性                       |
| ------------ | ------------------------ | ------------------------------ |
| 长度         | ≤200 / >200              | ✅（分诊键）                   |
| 连发结构     | 单条 / 多条连发          | ✅（分诊键）                   |
| 对话功能     | 信息提供 / 元对话 / 反问 | ✅近似（触发词表）             |
| 指纹密度     | 单 / 多                  | ❌（理解性：解释 C 类损失）    |
| 指纹新颖性   | 新 / 旧                  | ❌（理解性：解释查询冗余）     |
| 指纹可解析性 | 直接 / 指代              | ❌（理解性：解释锚点救场，R1） |
| 指纹相关性   | 贴题 / 离题              | ❌（理解性：解释锚点拉回）     |

**语义鸿沟**（情绪陈述 vs 事件叙述）由锚点弥合：变量名给 Hindsight 的语义检索提供领域框架——这不需要任何额外 LLM 调用。快通道保持 **0 LLM**（ADR 004：走规则，LLM 升级移到慢通道）——命中率不理想时先验证不加的情况；升级路径是慢通道（意识触发，见 §4），不在快通道内加 LLM 摘要。

**三路扩展的抽象层**（待实证，§3.2）同理：事件概念抽象走规则，零 LLM。

### 3.4 延迟约束

- 目标 ≤200ms（一次 localhost HTTP 到 Hindsight，纯检索不调 LLM）
- 话题入口预取每 topic 最多 1 次：本 topic 待收集变量全非空 → 0 次（不查）
- 启用三路扩展（待实证，§3.2）超出预算时的**降级顺序**: 先砍关联事件 → 再砍类似事件 → 只留原始查询
- 超时则返回空 MemoryContext，不阻塞主流程
- 如果 Hindsight 不可用（连接失败），静默降级

### 3.5 淘汰策略

快通道结果仅保留**最近 5 轮**。超过 5 轮的自动从 `memoryContext.fastHits` 中移除。原因：

- 5 轮前的联想在当前对话语境下大概率已失效
- 防止 `memoryContext` 无界膨胀
- 慢通道结果不受此限制（慢通道产出的是综合洞察，生命周期更长）

### 3.6 该调用哪种记忆类型？

| 记忆类型         | 与"实时理解用户回复"的关系                                                                                                                     | 优先级   |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| **experience**   | 最直接 — "用户之前说过类似的经历吗？"                                                                                                          | **最高** |
| **observation**  | 高 — 用户/咨询师沉淀过的信念与模式："我觉得吃药没用"这类表述会被 consolidate 为带证据引文的观察（ADR 005）；AI 看到用户对药物的抵触及其证据链  | **高**   |
| **mental model** | 中高 — 常驻公式化/工作假设（如"用户抵触药物背后的原因链"）随证据由后台重写；**会话启动时零成本读入 baseline**，不逐轮 recall（ADR 005 决策 2） | **中高** |
| **world**        | 低 — world 存的是用户陈述的事实性信息（如"用户在XX公司工作"），对于理解当前回复的直接帮助较小，更多用于避免事实错误                            | **低**   |

**不做类型区分，统一 recall。** recall 内部跨类型检索，语义匹配到的都返回，按相关度排序。LLM 在 prompt 里看到的是一段结构化的"相关记忆片段"，自己会判断哪些有用。

### 3.7 案例集：收集前预取（P1-P3）+ 主线触发（R1-R9）+ 免查反例（N1-N6）+ 边界（E1）+ 意图层调取指针（C1-C5）

> **场景常量**：第 3 次会话；ai_ask 正在收集 `{核心信念, 睡眠质量}`；`u` = userId；锚点串 = `关于核心信念、睡眠质量`。
> 「检索去向」= 查询文本**预期**命中的记忆区域——recall 统一跨三网络检索（§3.6 不做类型过滤），此处描述预期命中区域而非检索限制。
> 「期待返回」= **设计预期，非实测**——「三路查询实证」故事将逐条核对这些预期；本案例集是验收案例的单一出处。
> 意图层调取案例（C1-C5）的机制在 [意识系统设计 §2.7](../consciousness/consciousness-system.md)，此处只做指针。

**P 类：收集前预取（话题入口，空值变量）**

> 场景（与上方常量不同）：第 3 次会话，进入话题「童年抚养者」，其两条 ai_ask 分别收集 `{主要抚养者}`、`{抚养方式}`。

**P1 空值 + 记忆有**（§1 第二条业务需求的样本）

- 预取: 装载后两变量均为空 → `recall(u, "关于主要抚养者、抚养方式")`
- 检索去向: experiences / worldFacts 中既往关于抚养者的叙述
- 期待返回: 「第 2 次会谈：小时候主要是奶奶带大的，父母常年在外」
- 机制解读: AI 首问带上"你之前提过…"；变量值仍由本轮回复提取——**预取不写值**（§2）

**P2 非空 → 预取跳过**

- 若 `{主要抚养者}` 由信息点文档装载到值 → 不进查询；本 topic 变量全非空 → 本 topic 0 次 recall
- 机制解读: 权威在文档（ADR 007 决策 2）——文档有的，记忆不掺和

**P3 空值 + 记忆无 → 不劣化**

- 预取空手 → 按原样从零提问（"你小时候主要是谁在照顾你？"）
- 机制解读: 预取只增不减——召回为空时，行为与没有这个机制时完全一致

**R 类：主线触发命中 → 查**

**R1「上次说的那个事，我回去又想了想」**（指代回复）

- 查询: `recall(u, "上次说的那个事，我回去又想了想 —— 关于核心信念、睡眠质量")`
- 检索去向: 原话部分几乎无命中（"那个事"指代不可解析）；实际检索由锚点承担
- 期待返回: 上一会话关于核心信念的讨论记录（"那个事"所指内容大概率在其中）
- 机制解读: 纯指代词无法免查检查 → 默认查；原话失效时锚点是唯一可解析焦点

**R2「上次你说睡前别看手机，我试了三天，是不刷了，但一躺下就开始想工作的事」**

- 查询: 原话全量 + 锚点
- 检索去向: experiences（工作压力事件、既往失眠成因叙述）；「工作的事」是新指纹，牵引前几轮未命中的区域
- 期待返回: 「第1次会谈：项目临近上线，压力很大」——下一问可沿"工作的事"深挖
- 机制解读: 指代（上次你说）+ 新指纹 = 快通道查询高价值类型

**R3「李光最近又联系我了」**（专名指代）

- 查询: `recall(u, "李光最近又联系我了 —— 关于核心信念、睡眠质量")`
- 检索去向: 专名随原话入查询，检索器按罕见 token 命中 worldFacts/experiences 中关于李光的存量
- 期待返回: 李光的既往事实与相关叙述（谁、什么关系、发生过什么）
- 机制解读: 专名检测走分词未知词规则（词表装不下，§3.3）；免查检查先行——窗口内无"李光"则查

**R4「就是睡不着，还是老样子」**

- 查询: 原话 + 锚点
- 检索去向: experiences 睡眠相关存量
- 期待返回: 既往睡眠叙述——大概率与前几轮 fastHits 重复
- 机制解读: 「老样子」入指代词表；旧指纹召回已知内容，冗余是 0 LLM 分诊的代价，无害且刷新窗口

**R5「你上次问我的时候我说'还好'，其实那次之后更糟了」**（引用前文）

- 查询: 原话 + 锚点
- 检索去向: experiences（dialogue channel 中那次"还好"的对话记录——原话直指已存内容）
- 期待返回: 那次问答的完整记录，AI 可衔接「你上次说还好，现在能多说一点吗」
- 机制解读: 「你上次问我的时候」是强标记；原话查询命中率最高的类型

**R6 连发三条：「其实我最近老做同一个梦」＋「梦见考试没带笔」＋「就像上次考试前那段时间一样」**

- 查询: 连发拼接后: `recall(u, "其实我最近老做同一个梦。梦见考试没带笔。就像上次考试前那段时间一样 —— 关于核心信念、睡眠质量")`
- 检索去向: experiences（既往梦/考试相关叙述）；「上次考试前」牵引考试焦虑类事件
- 期待返回: 既往考试焦虑相关叙述（若有）
- 机制解读: 指代落在最后一条——连发先拼接再检测（§3.2 ①），否则碎片检测会漏掉它

**R7「上次会谈聊到的那个方案，我回去试了，好像有点用」**（跨会谈指代）

- 查询: 原话 + 锚点
- 检索去向: experiences 跨会话（「上次会谈」明确指向非本次会话）
- 期待返回: 上次会谈给出的方案记录，AI 可衔接「你试的是哪部分？具体怎么有用了」
- 机制解读: 跨会谈内容本就不在「最近聊天」窗口——快通道的核心价值场景

**R8 500 字长文，指代落在中段**（节略：开头「最近事情特别多，工作上一堆烂摊子……」；中段「……就像李光当年对我那样……」；结尾「……所以最近状态特别差」）

- 查询: `recall(u, "{头100字}……{尾100字} —— 关于核心信念、睡眠质量")`
- 检索去向: 头尾窗口 → 工作压力/状态叙述；「李光」在中段被截断丢失，相关存量漏查
- 期待返回: 工作压力相关叙述——但「李光」相关内容大概率缺席
- 机制解读: ⚠️ C 类最坏情况——认中段损失（§3.3 规则 5），多查询/分段检索实验优先级因此提升

**R9「那你觉得我该怎么办？」**（反问）

- 查询: 原话 + 锚点（触发轮且 ≤200 字 → B 类）
- 检索去向: 焦点相关的既往记忆与方案记录
- 期待返回: 当前焦点相关的既往记忆，供 AI 生成回答时引用（"上次我们聊到……"）
- 机制解读: 应答型回复——下一轮是回答而非追问，AI 的回答必须有既往方案与案例历史做依据

**N 类：免查反例（触发词表未命中 → 跳过）**

| 案例                                                             | 为什么跳过                                                                                     |
| ---------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| N1「嗯」                                                         | 零指纹零指代——AI 刚问完，过渡词无需查                                                          |
| N2「你们这个 AI 问来问去有什么用，根本帮不了我」                 | 元对话攻击，无指代无反问——阻抗处理归意识层（见 C3）                                            |
| N3「唉，我也不知道该怎么说，就是很烦，烦得不行，感觉哪儿都不对」 | 情绪宣泄无指代——本轮原话在窗口内，AI 懂她在说什么                                              |
| N4「哦不对，我说错了，不是天天失眠，是就这两周特别严重」         | 自我更正无指代——更正内容照常进入主线上下文；更正的权威性处理归 retain/写回侧                   |
| N5 500 字失眠夜长文（无指代）                                    | 触发检测在分诊之前（§3.2 ②④）——长文不等于触发，无指代无反问同样跳过；其指纹留给 retain 侧沉淀  |
| N6「嗯，但是我还是睡不好」                                       | 转折句，无指代无反问——剔除过渡词后虽有实质内容，但触发词表不命中；内容就在窗口内，不花这趟检索 |

**E 类：边界**

**E1「他还是那样」**

- 检测: 「他」命中人称指代；免查检查——纯指代词无法字符串检查 → 默认查
- 查询: 原话 + 锚点
- 检索去向: 锚点拉回的焦点存量；若窗口内最近提到某人则一并命中
- 期待返回: 焦点相关记忆（查询对「他」指谁也帮不上，但锚点仍提供焦点）
- 机制解读: 多查一次便宜，漏查则 AI 犯蠢——纯指代词一律默认查

**意图层调取指针（C1-C5）**（意识层多线程 recall，不占主线延迟；机制见 [意识系统设计 §2.7](../consciousness/consciousness-system.md)）

| 案例                                                            | 所属意识                                        | 意图层 recall 需求                |
| --------------------------------------------------------------- | ----------------------------------------------- | --------------------------------- |
| C1 用户说「我其实挺喜欢和人打交道的」，与既往「我讨厌社交」矛盾 | contradiction_detect                            | 本轮关键断言 + 既往矛盾表述做比对 |
| C2 用户说「我最近好像没那么容易生气了」                         | emotion_trajectory                              | 既往情绪表达，评估情绪轨迹        |
| C3「你们这个 AI 问来问去有什么用」（N2 同源）                   | resistance_monitor                              | 该话题（睡眠）的既往参与度        |
| C4「有时候真想一了百了」                                        | 危机信号评估（紧急路径）                        | 既往危机陈述的频率/严重度         |
| C5 用户提到「我最近开始跑步了」                                 | strategy_adaptation（话题衔接提案扩展，待评审） | 新内容勾连的既往话题线            |

> C4 在主线侧无指代无反问，快通道跳过；危机趋势的判断证据（既往危机陈述）由意识层在紧急路径上 recall 取得——这正是快/慢分工的典型样本。

## 4. 阶段 2: 慢通道 —— 异步深度分析（ai_ask 侧契约）

慢通道机制细节（两阶段深度检索、DeepInsight 卡片、硬限制、时效性门控、场景示例）见 [意识系统设计 §2.6](../consciousness/consciousness-system.md)。本文只保留 ai_ask 侧的契约：

### 4.1 触发来源

慢通道由**意识层**触发——某个意识的 `insightForSlowThinking`（string，见 [意识系统 §2.3.3](../consciousness/consciousness-system.md)）非空时，触发深度 recall + LLM 综合。主线 LLM 不感知、不负责触发慢通道；主线和支线分工明确：主线回应来访者，支线觉察信号并决定"什么值得深挖"。

### 4.2 ai_ask 侧契约（硬约束）

1. **fire-and-forget**：异步运行，不阻塞主线（5-30s，轴 9 `relaxed_30s`）
2. **产出 DeepInsight 存入 `session.metadata.deepInsights`**（类型定义见 [意识系统 §2.6](../consciousness/consciousness-system.md)）
3. **注入前经时效性门控**：`formatMemoryContext()` 在「深度洞察」段只渲染 `relevanceCheck != "过期"` 的条目（§6）
4. **慢通道只有建议权**：洞察注入 prompt 后由主线 LLM 自己判断是否采纳；不直接修改脚本流程（不跳过 Topic、不插入 Action）

## 5. recall 的检索句子来源

recall 不是用原始对话消息当查询，而是用"当前 ai_ask 在收集什么"和"用户说了什么关键内容"两者组合。

| 阶段                       | 查询驱动                                                                        | 例子                                                                                                         | LLM 调用                               |
| -------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | -------------------------------------- |
| 快通道（话题入口预取）     | 本 topic 待收集变量（**仅空值**）名列表拼接（收集前回顾，别让用户重复讲过的话） | `recall(userId, "主要抚养者、抚养方式")`                                                                     | 0                                      |
| 快通道（指代/反问轮）      | 指代/反问检测命中；密度分诊: B 原话+锚点 / C 头尾截断+锚点（§3.2/§3.3）         | B 类示例: `recall(userId, "李光最近又联系我了 —— 关于核心信念")`                                             | 0                                      |
| 快通道（触发轮，可选增强） | 三路: 原始 + 类似事件(抽象) + 关联事件(时间窗口)（待实证，默认关闭）            | 原始: `"上周和老板大吵一架 —— 关于工作压力"`<br>类似: `"人际冲突 爆发性争执"`<br>关联: `"上周同期 生活变化"` | 0（抽象走规则；快通道无 LLM 升级路径） |
| 慢通道                     | 小模型生成 2-3 个概念化查询（机制见意识系统 §2.6）                              | `recall(userId, "完美主义倾向 童年教养 关联")`                                                               | 1（查询生成）                          |

## 6. memoryContext 结构演进

当前 `memoryContext` 是扁平对象，改为分层结构以支持快/慢通道各自独立生命周期：

```typescript
interface SessionMemoryContext {
  // 会话启动时加载的基础画像（initializeSession 时设置，会话内不变）
  baseline: MemoryContext;

  // 话题入口预取（进入 topic 时写入，本话题内有效；仅空值变量，§3.1）
  topicPrefetch: Array<{
    topicId: string;
    variables: string[]; // 本次纳入预取的变量名
    context: MemoryContext;
  }>;

  // 快通道近日联想（最近 5 轮，滚动淘汰）
  fastHits: Array<{
    round: number;
    query: string;
    context: MemoryContext;
  }>;

  // 慢通道深度洞察（持久累积，带时效性标记；DeepInsight 类型见意识系统 §2.6）
  deepInsights: DeepInsight[];
}
```

`formatMemoryContext()` 分段渲染（`base-action.ts`）：

```markdown
## 关于来访者

{baseline}

## 本话题预备

{topicPrefetch 中当前话题的条目（§3.1 收集前预取）}

## 本轮相关记忆

{fastHits 最近 3 轮合并渲染}

## 深度洞察

{deepInsights 中 relevanceCheck="有效" 的条目，按时间倒序}
```

**淘汰规则**：

- baseline: 不变（会话级稳定性）
- topicPrefetch: 话题级——离开话题即失效（下个话题的预取覆盖），不跨话题累积
- fastHits: 滚动窗口，最新 5 轮保留，超出自动移除
- deepInsights: 持久保留，但 `relevanceCheck="过期"` 的不展示；超过 10 条的移除最旧条目

## 7. 调用时机总结

| 阶段                       | 何时触发                                         | 目的                                         | 记忆类型侧重                                          | 阻塞用户 | 延迟                       | LLM 调用 |
| -------------------------- | ------------------------------------------------ | -------------------------------------------- | ----------------------------------------------------- | -------- | -------------------------- | -------- |
| 快通道（话题入口预取）     | 进入 topic 时（仅空值变量）                      | 本话题要收的信息用户过往讲过没有——收集前回顾 | experience, observation（mental model 并入 baseline） | 是       | ≤200ms（每 topic 一次）    | 0        |
| 快通道（指代/反问轮）      | 指代/反问检测命中后、生成回复前                  | 指代落地/应答依据，让 AI 懂用户说什么        | experience + observation 混合                         | 是       | ≤200ms                     | 0        |
| 快通道（触发轮，可选增强） | 同上，启用事件性描述视角扩展（待实证，默认关闭） | 联想历史类似事件 + 同期关联事件              | experience 为主，混合                                 | 是       | ≤200ms（超出预算按序降级） | 0        |
| 慢通道                     | 意识层 `insightForSlowThinking` 触发             | 挖掘矛盾、发现深层模式                       | 三种 fact type + mental model                         | 否       | 5-30s                      | 2-3      |
