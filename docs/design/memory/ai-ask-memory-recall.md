## 1. 四个问题

主线 LLM 的 prompt 里只有「最近聊天」的有限回合——**本次会谈早些的内容、跨会谈的内容都不在**。凡是 AI 要用到"聊过、但最近对话里没有"的东西，就是记忆该介入的时候。ai_ask 上有四个这样的时候：

**一、听不懂用户在说什么。** 用户说「上次说的那个事，我回去又想了想」「李光最近又联系我了」——指的是什么，最近对话里没有。不查记忆，AI 只能反问"李光是谁？"

**二、被反问，答不上依据。** 用户说「那你觉得我该怎么办？」——AI 这一轮从追问者变成回答者。真要给建议，那句话得有既往方案、用户试过什么、效果如何做依据。不查，只能给空泛的通用建议，像第一次见面的机器人。

**三、要收的信息，用户以前讲过，又问一遍。** 脚本规划本话题要了解「小时候的主要抚养者」，不代表用户之前没提过。收集前先回顾一遍，AI 开口就能带上"你之前提过…"，而不是让用户把讲过的话再讲一遍。

**四、不是"回复缺东西"，是"觉察缺证据"。** 前三问都是"AI 要开口，发现手边没有"——前两问由用户的话引出，第三问是进话题时引擎自己数出来的空值变量（§3.6）。还有一类，触发者是引擎自己的觉察：后台觉出一个信号，要判断这信号真不真、是不是趋势，也要证据。

- 「我其实挺喜欢和人打交道的」——和既往那句「我讨厌社交」顶上了：是他真变了，还是我听岔了？
- 「我最近好像没那么容易生气了」——真好转，还是这一周顺？
- 「有时候真想一了百了」——既往提过没有？有没有一起定过安全计划？

这一类不走主线，各意识在自己的后台通道里各查各的（§6）；触发通道为什么不同，见 §1.1。

**前三个问题看着不同，其实是同一条：AI 这一轮要说的话，指着一个它看不见的东西。** 本文把它叫**钩子**——§2 的判定、§3 的检索表达都绕着它转。第四个问题不问钩子，问"证据够不够"，走的是另一条通道。

### 1.1 全景：记忆在四个点介入

```
进入话题 ──▶ [三] 收集前回顾：本话题要收的变量里，值还空着的 → 代码直接查（每话题一次）
                │
用户说话 ──▶ [一/二] 判定字段：none 直接回 / defer 先回、下轮补上 / block 先查再回
                │
                ▼
         记忆片段并入 {{memory_context}} ──▶ 主线 LLM 生成回复
                │
后台 ──────▶ [意识层] 矛盾 / 情绪轨迹 / 阻抗 / 危机 各自 recall —— 不占用户等待
```

执行者只有两类，这就是"快通道 / 慢通道"的全部含义——**分的不是记忆的种类，是谁在等**：

- **主线**（快通道）：用户等着回复，所以必须快——在用户可接受的等待预算内跑完的那条链。触发者是用户的话（问题一、二）或进话题时引擎自己数出来的空值变量清单（问题三，§3.6），判断并入主线生成（§2），不额外调用 LLM；查记忆本身是一次本地 HTTP。
- **意识层**（慢通道）：后台跑，用户不等——可以慢，可以用 LLM 做深度分析（§6）。触发者是引擎自己的觉察（问题四）。

## 2. 怎么判

判断者是**主线 AI 自己**。它在生成这一轮回复的**同一次生成**里，输出的**开头**先给判定字段，其余字段照常跟在后面——模板那份输出本来就是一份 JSON，判定四字段排在最前。引擎读到它、把它摘掉，据此决定这一轮怎么走；判定字段**不给用户看**。

判定只回答一件事：**只靠这些已知（最近对话 + 已收集变量），够不够支撑这一轮的回复。**

四个字段**按这个顺序写**（都是输出的最前面，其余字段照常跟在后面）：

| 字段       | 装什么                                                                                                                                                                                                                              |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `reason`   | 一句话说明为什么这么判——有钩子的（`defer` / `block`，以及钩子就在最近对话里的 `none`）写钩子是什么，判 `block` 再补一句缺了什么，压根没钩子的 `none` 写"这轮没有指向最近对话外的话头"。**给日志与实证看**：用户看不到，下游也不用它 |
| `recall`   | 这一轮怎么走——三档，见下表                                                                                                                                                                                                          |
| `entities` | 这一轮原话里的专名（人名、地名、机构、作品名）；没有则 `[]`                                                                                                                                                                         |
| `query`    | 检索词（§3.1 / §3.2 两张表）：要查时给，不查时空串                                                                                                                                                                                  |

> **顺序是设计的一部分，不是排版。** 基于大模型是串行生成，前面输出的token影响后面的特性，这里特安排先输出“reason”。这通常能提升“recall”判断的准确性，相当于是要它**先把"缺什么"想清楚**，再落判定和检索词——若排在最后，就成了写完之后的事后合理化，对检索词一点影响都没有；`entities` 排在 `query` 前，是**先把人名交代出去**，`query` 才好写这一轮要问的那一面（§3.3）。同样的 token 数，换个位置而已。（这条待实测：附 C.3 ⑤）

**三档**：

| `recall` | 这一轮怎么走                                                       | 什么时候用                               |
| -------- | ------------------------------------------------------------------ | ---------------------------------------- |
| `none`   | 不查，直接回复                                                     | 靠已知够用——大多数轮                     |
| `defer`  | 先回复（回复里不含任何对未知信息的预设），同时查一次，**下轮**带上 | 有钩子，但不写它这一轮也答得完整         |
| `block`  | 这次生成到此收笔 → 查一次 → 记忆注入后**重新生成**再回复           | 有钩子，不写它就答不出、答空，或只能反问 |

**判据是两句，按顺序问**：

1. **这一轮有没有钩子？** 钩子 = 这一轮要说的话指向「你说过、但我看不见的东西」（§1 定义）——它出现在两处：用户话里的路标（§3.1），或"这一轮得引既往依据"（反问，§3.5）。**没有 → `none`**——寒暄、表达情绪、回应上一句，大多如此。
2. **有钩子就不许猜它——把这一轮想说的那句话先写出来，看它带不带那个东西**：
   - **带**（话里必须交代它是谁 / 是什么 / 发生过什么 / 该怎么办，不写就答不出、答空或只能反问）→ `block`。
   - **不带**（不写它也完整：共情、接着问、确认一句）→ `defer`；并自检：这句话里不能出现任何对它的预设——不猜它是谁、不编他说了什么。
   - **带不带拿不准 → `block`**：多查的代价是慢一轮，猜错的代价是不实的回复，两个方向不对等。

判据落在"这一轮想说的那句话写不写得出来"上——是模型做得到的一次试写，不是让它估自己"接不接得住"。**判据里没有"查不查得着"**：模型读不到记忆库，估不出查了到底有没有；碰不中只能反问，那是 `defer` 存在的理由，不是每天用的判据。

**为什么并进生成，而不是单起一道判定**：**为了响应速度。** 判定若单独起一道 LLM 调用，用户等回复的路上就多压一次完整生成——每轮都等；并进生成，判定只是主线这次生成开头多写的几十个 token。

并进之后，真要两次生成的只剩少数轮：不需要查记忆的轮（大多数）只有一次调用；需要查的轮里，判 `defer` 的（先回复、记忆下轮带上，§3.4 / §3.5）也只有一次；只有判 `block` 的轮才收笔重来。输入账同向——两次调用要把内容大半相同的 prompt（原话、最近对话、变量）预填两遍，并进生成只预填一遍。

判 `block` 的那几轮慢一点，用产品机制化解，不砍判定：界面先给一句"我想一下…"配上动效，像真人咨询师——有的话答得快，有的话要想一想。

> 这笔账押在"大多数轮不需要查记忆"上——它从逻辑上应当成立，但要实证（路径见附 C.3 ③）；`block` 轮重开的预填成本记在 §5.2。

**调用侧四条**：

1. **头部缓冲**：判定字段读出来之前，输出不发给用户（界面只有"正在思考"态）；到上限仍读不出，走第 4 条。
2. **判 `block` 就收笔**：提示词要求"判 `block` 时写完这四个字段就停"（附 B）——这次生成自然结束，引擎不必去学"掐断流"（各家中止语义不一，还要处理竞态）。模型不听、继续往下写也照旧丢弃，第 1 条保证用户看不到。`reason` 排在最前还有个附带好处：收笔时它已经把"缺什么"写完了。
3. **只重新生成一次**：第二次生成时提示词注明"记忆已注入，直接作答，判定字段给 `none`"；**每个用户输入最多查一次**（硬限，防打转）。
4. **判不出来就按 `block` 兜底**：解析从宽（空格、大小写、多余字段都算合法）；仍读不出判定字段，就弃掉这次生成，按附 C.3 的固定拼法查一次、重新生成。不为此再起一次 LLM 调用。

> 支持 assistant 预填充的模型，把开头预填成 `{"reason":"` 能显著提高格式守约率（开头是 `reason`，预填充串随之改）。

**这套判法的失败倾向只有一条：模型会顺着往下写，不会停下来。** 判定四字段排在正文之前——写它的那一刻，正文还不存在，等于让它先猜"我接下来要说的那句话，带不带那个东西"；猜错了没有回头路：写到一半才需要"李光是谁"，开头的 `none` 已经写出去了。它不会停，会把那个东西编出来——"继续说"是它唯一的动作，"停下来等信息"逆着它（附 B 把它写成流程的正常一步，就是为这个）。

同一条倾向，两个出口：

- **判了 `none` 却编下去**（"装作知道"）：用户多半看不出来——编的是过去对话的转述；等认出来，假事实已经进了上下文。这是 §5.3 里唯一不自愈的错。对冲是 §3.3 的硬规则（专名在最近对话里没出现过 → 必须 `block`），外加附 C.4 的**字面检查**——每轮跑一遍、只记录不干预，攒的就是这条风险的样本。
- **判 `block` 像"这一轮先不说话"**：模型为了能开口，可能倾向 `none`。

判得准不准、正文有没有被判定拖累，都要实测（附 C.3 ④）。

## 3. 识别特征与检索表达

**指代与反问两处共用一套账**：先在用户话里找路标（§3.1）→ 再看这一轮要向记忆要哪一面（§3.2）→ 按组合规则拼出检索词（§3.3）；**收集前回顾不用这套**（没有原话可挖，代码直接拼，§3.6）。**§3.4 起是三个时机各自的用法**：指代与反问两处要分三档（§3.4 / §3.5），收集前回顾不用判（§3.6）。

### 3.1 路标：用户话里给了什么线索

| 路标     | 用户话里长什么样           | 进 query 的方式                                                                                                   | 进 query 的那一段              |
| -------- | -------------------------- | ----------------------------------------------------------------------------------------------------------------- | ------------------------------ |
| 专名     | 李光、阿黄                 | 原样进 query，**同时**进 `entities`<br>例：「李光最近又联系我了」                                                 | 李光                           |
| 指代词   | 那件事、老样子、你上次说的 | 原话本身就是钩子，**整句**进 query<br>例：「上次说的那个事，我回去又想了想」                                      | 上次说的那个事，我回去又想了想 |
| 人称代词 | 他、她、他们               | **整句**进 query——信息量低，靠变量名补范围<br>例：「他还是那样」                                                  | 他还是那样 + 变量名            |
| 时间词   | 上个月、上次会谈、最近     | 原样进 query——它同时是给检索侧的新鲜度信号（§3.2 末行）<br>例：「上次会谈聊到的那个方案，我回去试了，好像有点用」 | 上次会谈                       |
| 事件词   | 被同事出卖、出车祸         | 原样进 query——**比变量名具体，优先于变量名**<br>例：「上次你说睡前别看手机，我试了三天，但一躺下就想工作的事」    | 工作的事                       |
| 无       | 嗯、唉、我也不知道该怎么说 | 没有路标，**也不是反问（§3.5）** → 没有钩子 → `none`                                                              | —                              |

> 专名和代词要分开看：**专名是硬的**——它在最近对话里出现过没有，一眼可判，没出现过就是硬规则必查；**代词是软的**——「他」指向谁，得看最近对话里对不对得上人。

### 3.2 缺什么：这一轮要向记忆要哪一面

| 缺什么                       | 什么时候                                        | query 问的面                                                     | 拼出来的 query                                                   |
| ---------------------------- | ----------------------------------------------- | ---------------------------------------------------------------- | ---------------------------------------------------------------- |
| 这个人是谁、与来访者什么关系 | 专名 / 代词（这一轮要交代他是谁、两人什么关系） | 「{名字}——他是什么人、与来访者是什么关系、两人之间发生过什么事」 | `李光——他是什么人、与来访者是什么关系、两人之间发生过什么事`     |
| 这件事是什么                 | 泛指指代                                        | 原话 + 变量名（圈范围）                                          | `上次说的那个事，我回去又想了想——关于核心信念、睡眠质量`         |
| 这件事的前情与结果           | 用户讲了件**可能已经聊过**的事                  | 事件词 + 「以前聊过没有、聊到哪、后来怎样」                      | `工作的事——以前聊过没有、聊到哪、后来怎样`                       |
| 既往方案与他试过的           | 反问、这一轮要引依据                            | 「此前聊过的应对方案、他试过哪些、效果如何」                     | `来访者问「该怎么办」——此前聊过的应对方案、他试过哪些、效果如何` |
| 这件事最新的一次             | 同一主题聊过多次                                | 主题 / 变量名 + 「最近一次」                                     | `那件事——关于核心信念、睡眠质量，最近一次`                       |

> **同一件事聊过多次时，要的是最近那一次**——「那件事」有时间性。每轮 recall 都带 `queryTimestamp`（相对时间表达的解析基准、recency 评分的时间锚，§5.2），检索表达再把时间意图写明——两道一起用。能不能稳定挑出"同主题最后一次"，靠实证（附 C.3 ⑥；验收案例 26）。

### 3.3 组合规则

一轮常常不止一个钩子——「我该不该跟李光断了？」= 反问 + 专名。拼检索词时：

- **名字给 `entities`，要问的那一面给 `query`**：专名按 §3.1 原样留在 `query` 里、**同时**进 `entities`——`entities` 是给后端做实体匹配的硬标识，它会带回"这个人是谁、与来访者什么关系"（附 C.6）；`query` 写这一轮要向记忆要的那一面（§3.2 五行之一）。**反问 + 专名同时出现时，`query` 走"既往方案与他试过的"那一面**——"这个人是谁"由 `entities` 那条路带回来，不必在检索词里重复；
- **时间词叠加**进 query；
- **变量名只在它确实圈定范围时才拼**，最多 2 个——**指代跨到别的话题时不拼**，否则检索整批被拉去当前话题的旧料（案例 13）；
- **指代类整句带上原话**：原话就是钩子本身，它指出这一轮具体在说哪件事、哪个人；
- **硬规则**：人名、地名、机构名在最近对话里没出现过 → 必查（`block`）；
- **不编造**：`query` 里不出现用户没说过的具体人名、事件；`entities` 只写这一轮原话里的专名——从记忆里想起的名字是要查的东西，不是查询条件；
- **具体优先**：专名、事件、时间线索、用户的原话词，能带的都带上。30~80 字是"别塞噪声"，不是"越短越好"。

> **原话与变量名各干什么**：原话指出这一轮在说哪件事；变量名圈范围（脚本里写死的，永远可用）。只有原话会泛泛召回，只有变量名则不知道这一轮问的是哪一面——**要不要都用，是判定字段自己的判断**。

### 3.4 指代：用户说「那件事」「李光」

**三档怎么分**：

| 判定    | 这一档的条件                                                       | 例                                                                                                                                         |
| ------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `none`  | 所指就在最近对话里——AI 自己看得见                                  | 上一句 AI 刚问「上次那个方案后来怎么样了？」，用户答「上次那个方案，我又想了想」→ 不查，直接接                                             |
| `defer` | 有钩子，但这一轮要说的那句话不写它也完整（回复里也不预设它是什么） | 用户说「还是老样子」——所指（上次那个状态）不在最近对话里，但这轮只是接住：「嗯，老样子。这阵子过得怎么样？」→ 先回，同一轮查一次、下轮带上 |
| `block` | 不写它就答不出、答空，或只能反问「你指的是？」                     | 同样是「上次那个方案，我又想了想」，但最近对话里没提过这个方案（是上次会谈说的）→ 先查清楚再回                                             |

> **专名走硬规则**（§3.3）：人名、地名、机构名在最近对话里没出现过 → 必查（`block`），不看它这一轮重不重要；出现过才轮到上面三档。人称代词不走硬规则——对不上人时按上面三档判，多半落在 `defer`（附 A.5）。名字压过三档有两个理由：**人不随时间失效**——事有时间性（§4.1），李光是谁第 3 轮问和第 6 轮问是同一个答案；**名字上编造最扎眼**——把"李光"当熟人顺着说，用户一眼看出 AI 在装。

> 指代够不够用，要看它指的是哪一段：最近 2-3 轮内的、已收进变量的、本话题更早没进变量的、上次会谈有专名的、上次会谈无专名的——分别靠主线自己 / 变量值 / 召回 / 实体备忘（§4.1）/ 反问解决。**这张表说的是"靠什么解决"，不是"查不查"**；查不查由上面三档定。对照见附 A.2。

### 3.5 反问：用户说「那你觉得我该怎么办？」

**识别特征**：用户把问题抛回来——「你觉得呢」「我该怎么办」「你怎么看」「你说呢」「我该不该」。这一轮 AI 从追问者变成回答者。

但**"反问"只是时机，不是判据**。这一轮到底走哪个方向——给建议、先澄清、只共情、还是把"你想让我替你做决定"本身当材料谈——由咨询框架定；记忆只在"**这一轮定下来的那句话，缺不缺最近对话里没有的事实**"上说话。

**三档怎么分**：

| 判定    | 这一档的条件                                                                      | 例                                                                                   |
| ------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `none`  | 这一轮定下来的那句话**不引既往事实**                                              | 先澄清："你要的是我拿个主意，还是先一起把这事看明白？" · 只共情 · 把反问本身当材料谈 |
| `defer` | 先用不依赖既往事实的话接住（共情 / 反过来问），依据下轮带上                       | 「换谁都会想先捋清楚——你先说说，最卡的是哪一步？」                                   |
| `block` | 这一轮**真要给建议**、要引"上次我们聊过…"——那句话缺既往方案、他试过什么、效果如何 | "上次我们聊到…你说试了三天有点用，要不这次…"                                         |

**这一处最容易判反**：把"反问"当成"必查"，一上来就给 `block`——白花一次检索 + 一次重生成，还挤掉一次本该先澄清的机会（案例 12 与 12-a 配对看）。

另有一种情况：这一轮的话里带专名（「我该不该跟李光断了？」）→ 查，但**不是因为它是反问**，是因为那个名字在最近对话里没出现过——归 §3.3 的硬规则。

**检索词按 §3.2 的"既往方案与他试过的"那一行拼**——**不抄原话**，写"这一轮需要什么面"，不是"我该怎么办"这五个字（拼出来什么样，见该行「拼出来的 query」列）。带专名时按 §3.3 拆开：名字进 `entities`（`query` 里也照样带着它），**`query` 仍走"既往方案与他试过的"那一面**——"这个人是谁"由实体态带回来，不再占检索词（案例 12-b）。

### 3.6 收集前回顾：要收的信息，他讲过没有？

**这一处不用判定**——要收哪些变量、值空不空，代码都算得出来。

**识别特征**：进入话题时（该话题第一个动作执行前），静态解析本话题内全部 ai_ask 的 `output` 变量，取**当前值为空**的（文档装载没读到、本会话也还没收到）。这一处**没有用户原话**。

**三档在这一处退化成两行**：

| 情况       | 做什么                                                      |
| ---------- | ----------------------------------------------------------- |
| 变量全非空 | 不查——文档装载或本会话已经收到，记忆不掺和                  |
| 有空值     | **代码直接查**：拼检索词 → recall → 注入本话题首问的 prompt |

**为什么这里没有三档**：判定字段存在的理由是"信息不对称"——有些判断只有模型做得来（所指在最近对话里还是不在）。这一处不存在不对称：变量名和话题名都在代码手里，代码不比模型少知道什么。让它判一次，等于白花一次生成。

**检索表达**：`话题名 —— 关于{空值变量名}`，例如 `童年抚养者——关于主要抚养者、抚养方式`。这里没有原话可挖，模型能贡献的只有措辞，不值得为它多一次生成。

**结果怎么用**：注入「本话题已知信息」段，本话题内每个 ai_ask 都带着它；AI 开口自然衔接——"你之前提过小时候主要是奶奶带大的，那时候的日子，你愿意多说说吗？"变量值仍由用户回复提取（§5.1 边界）。

**为什么在话题入口**：本话题要收的变量清单静态可解析**且确定**——话题队列会被意识层调整（插入 / 重排 / 深度切换），但进话题时它都在；一次查询摊到本话题多个 ai_ask 上，每话题最多 1 次检索。

> 进话题那一轮，用户可能也在说话（上一话题的收尾回复）——这一处的检索与判定字段可能触发的那一次各发各的，目的不同；"每个用户输入最多查一次"管的是判定那一次。

> §3.4 与 §3.5 的 `defer` 那一行、§3.6 的「无三档」结论，是按 §2 的判据推出来的写法，尚无实测——这三处随实现观测，判错就改。

## 4. 查到怎么用

查回来的记忆按段并入 prompt，各段的形状与淘汰见附 C.1。其中「实体备忘」单说——**只有它按"这个实体被提到"来定去留**（别的段各有各的依据）。

### 4.1 实体备忘：查到的人和物，怎么留住

**问题出在"事"和"人"不一样。** 第 1 轮来访者说「李光最近又联系我了」，这一轮查回来了李光是谁；到第 6 轮他只说「他还是那样」——这一轮未必再查得到李光，可这句话只有知道李光是谁才接得住。事有时间性：「上次说的那个事」指的是哪一次，隔几轮就旧了，按轮丢掉不要紧。人没有：李光是谁，第 3 轮问和第 6 轮问是同一个答案，它不属于任何一轮。

**做法三句**：

1. **随路取**——每次 recall，记忆后端顺手带回实体的"当前认识"（李光的那几条 observations），不额外发一次查询；
2. **按名字存**——带回来的按名字存成一份**实体备忘**，会话内留着（存法、上限与淘汰见附 C.1）；
3. **提人才给**——只有这一轮提到了它，才把这份备忘渲染进 prompt。怎么算"提到了"：判定字段写了这个专名，或代码在最近对话里字面扫到了备忘里已有的名字（附 C.1）。

**为什么不是别的做法**：每轮把十份备忘全喂进去，白占预算，还稀释了这一轮真正相关的东西；让主线自己读对话总结一份，多一次调用、多一份延迟，记下的还是转述不是原话；拿备忘当查询索引（备忘里没有就再查一次）是把缓存当成了权威——这一轮真需要，recall 本来就会把李光再带回来。

**它是什么**：`session.metadata.entityMemos` 里的一份缓存（结构见附 C.1）。prompt 侧的东西——不额外发检索、不写变量值（§5.1）、不跨会话；权威始终在记忆后端，清了再取一次就是。它和 fastHits 是两笔账：**fastHits 是"最近几轮聊过什么"，实体备忘是"这个人是谁"**。

**备忘上写什么，归领域**：引擎只管取、存、什么时候显示；**按哪几栏读**由提示词模板给——默认模板一份通用读法（是什么 / 跟来访者什么关系 / 来访者怎么看他），专业领域在自己的 Custom 层改。主栏是"关系"，而且不止人：「一中」这三个字，可能是来访者就读过的学校、初恋读过的学校，也可能是他最近采访过的学校——同名不同事，差别全在"跟他什么关系"。这是**给主线的读法提示，不是把数据切成几栏**：备忘里的内容原样来自记忆后端，我们不再总结一次（附 C.6）。

## 5. 代价与边界

### 5.1 边界：记忆不写变量值

**记忆的回顾结果只作为上下文给 AI 看，不写进变量的值。**变量的权威是[信息点文档](../decisions/007-variable-document-boundary.md)（ADR 007 决策 2）。

**为什么空值变量需要回顾**：跨会话值的权威是信息点文档，脚本工程师在脚本里声明变量与信息点的映射。但**没被映射的变量，文档里根本没有这个信息点**——而"用户以前讲过没有"不取决于脚本有没有计划收集它。所以：装载之后**值仍为空**的待收集变量，先回顾一次（§3.6）。

**为什么不写值**，三条指向同一件事：值一旦写入并驱动退出决策（"这个变量有了，不用再问"），本次会谈就少收集了本该收集的信息，而人能改的是文档、这一项恰恰没有信息点；记忆值可能过时、不精确或表达形式不同——让它带着写一句确认式提问"你之前提过…，是这样吗？"是稳妥的，固化成当前值等于把不确定性藏进流程控制；写进去就产生消费依赖，下游 condition / 退出决策按精确标量用，会逼出 bridge 那套新鲜度与合并策略的复杂度（ADR 007 决策 6 刚把它砍掉）。

**与变量刷新的分工**（[variable-memory-bridge](variable-memory-bridge.md) §4.1 piggyback）：两者都是"提前准备"，区别在产出——一条只把记忆给 AI 看（本文），一条刷新变量的值（bridge）。

| 维度     | 本文：只给上下文              | bridge：刷新变量值                                             |
| -------- | ----------------------------- | -------------------------------------------------------------- |
| 触发时机 | 进入话题时（收集前）          | Action N 执行时（前瞻 N+1 引用的变量）                         |
| 目标集   | 本话题待收变量中**值为空**者  | N+1 引用的变量 ∩ `autoRefresh ≠ false`——**与"是否待收集"无关** |
| 产出     | 上下文（注入 prompt，不写值） | 变量值（写 store，`source: 'llm_piggyback'`）                  |

**一条待补的闸门**（落在 [bridge 修订故事（Epic D）](../../scrum/backlog.md)）：本话题待收集且当前为空的变量，不应进 piggy 的目标集——现行 bridge 的写入门槛只有"非空"、没有"原本有值"，而临床判断类默认 `autoRefresh: true`（恰是待收集变量最常见的类）。漏洞是 ADR 007 决策 6 的残留。**另有一条写值的路是合法的**：已映射变量在装载时的 recall 兜底（ADR 007 决策 4，走显式 fallback 链，发生在会话启动）；本节管的是**无映射**的空值待收集变量。

> 升级路径（待实证）：若实证发现"AI 明明看到了回顾内容，仍从零追问"，再考虑把回顾结果写进变量 store——先验证不加的情况。

### 5.2 代价：多快、几次、留多久

- **判定不额外调用 LLM**：它只是主线那次生成输出开头的几十个 token，不需要查的轮（大多数）只多这一点时间。整轮预算尚未定义，本文只约束下面这几条。
- **要查的轮多一次重新生成**：判 `block` 时模型收笔，记忆到手后重新生成一次；预填成本取决于 provider 的前缀缓存。
- **一次查记忆 ≤200ms**（本地 HTTP 到 Hindsight，纯检索不调 LLM）；超时或 Hindsight 不可用 → 返回空、静默降级，不阻塞主流程。
- **每个用户输入最多查一次**（指判定那一次；§3.6 的收集前回顾另算）：一次判定给一个检索词，`defer` 与 `block` 都只查这一次，重新生成不再判、不再查。
- **联想只保留最近 5 轮**（滚动淘汰）：5 轮前的联想大概率已失效，同时防止 `memoryContext` 无界膨胀。`defer` 查到的记忆下轮带上，天然落在里面；意识层的洞察不受此限。
- **实体备忘不占检索预算**（§4.1）：它随既有的那次查回来，**不额外发检索**；占的是渲染预算，而渲染是有条件的——这一轮提到它才渲染。
- **实体态每次 recall 都取**（不按需取），上限 200 token；「本轮相关实体」段与本轮记忆片段是两笔独立预算。取回来是为喂备忘，不是为渲染（附 C.6）。
- **归纳优先于原始片段**（`preferObservations`）：谈到一件事时，要的是"这件事的概要"，不是某一次聊天的完整片段——Hindsight 把 experience 归纳成 observation 时，开启这个开关会让被归纳过的原始片段让位给归纳本身（腾出的位置补后面的结果，不会变少）。原始片段不丢：observation 上挂着 `sourceFactIds`，要证据时按 id 回查（附 C.2）。
- 三路扩展（附 C.5，默认关闭）若启用并超预算，降级顺序：先砍关联事件 → 再砍类似事件 → 只留原始查询。
- **投机检索不做**：检索本来是一次本地调用，可以在主线开始生成的同时用原话先发一次——判 `none` 就白花一次（用户无感），判 `block` 时那 200ms 就不在关键路径上。收益有限（判定字段本身也要时间），且它把"每轮都花一次检索"当默认——等实测出"要查的轮里检索等待占比明显"再谈。

### 5.3 犯错时往哪边倒

**先分清三种错。**

| 错                       | 代价                                                               | 自愈吗                                                                         |
| ------------------------ | ------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| **漏查**（该查没查）     | 两种下场：AI 追问一轮（"李光是谁？"），或顺着写下去把它编出来      | 追问**自愈**——用户当场就说了，下一轮信息自己进来了；编造就是"装作知道"，不自愈 |
| **误查**（查了不该查）   | 白花一次检索（判 `block` 时多一次重生成）                          | 不用治——判定字段不给用户看，用户无感                                           |
| **装作知道**（编出来的） | 多半看不出来——编的是过去对话的转述；等认出来，假事实已经进了上下文 | **不自愈**——这才是要挡的那个                                                   |

- **漏了就漏了**：不设检测器、不设补救流程——漏查要么走"追问"那条路自愈，要么就落成下面那个"装作知道"（§2 说后者才是模型的天然倾向）。**不为它加第二次 LLM 调用，也不把主线判定质量的账记到意识层头上**（两处都没人认领）。
- **编造另外算**：它不是"记忆不好"，是硬规则要挡的——专名在最近对话里没出现过 → 必须查（§3.3）。这条对冲的是"顺着话头编下去"，不是靠事后检测。
- **宁可多查**：误查是三种错里最轻的（一次本地检索，用户无感；判 `block` 时多一次重生成，也只是慢一轮，不是错）；漏查和编造都要用户买单。判定拿不准时倾向查——这条纪律写在判定段的提示词里（附 B）。
- **查不到就反问，不猜**：记忆里没有，AI 自然问"你指的是？"——真人咨询师也这么干。回顾与召回都**只增不减**：召回为空时，行为与没有这个机制时完全一致。

## 6. 意识层调记忆

ai_ask 只负责主线上的三处（§1 问题一~三）。**觉察判断类的调取**（§1 问题四）不归它——那些是意识层的活，各意识在自己的后台通道里 recall，不占主线延迟预算（机制见[意识系统设计 §2.7](../consciousness/consciousness-system.md)）。**它属于"觉察缺证据"，不属于"AI 要开口、发现手边没有"**——这是它和主线三处的根本区别，也是它为什么可以慢。

| 调取方 | 通道                           | 触发                               | 查询                              |
| ------ | ------------------------------ | ---------------------------------- | --------------------------------- |
| 主线   | 同步：判定随生成 + 检索 ≤200ms | 指代 / 反问两处（§3.4 / §3.5）     | 判定字段写出的检索词              |
| 主线   | 同步：进话题时一次，代码直接发 | 本话题有待收空值变量（§3.6）       | 话题名 + 空值变量名               |
| 各意识 | 异步（后台）                   | 各意识 `recall.enabled` + 触发阈值 | 各意识 `recall.query_hint` + 原话 |

各意识各自要什么证据，举例（不穷举，机制在各意识自己的定义里）：

| 意识                   | 要判断的                       | 要查的证据                               |
| ---------------------- | ------------------------------ | ---------------------------------------- |
| `contradiction_detect` | 这轮说的与既往顶上了，谁是真的 | 既往那几句的原话与当时语境               |
| `emotion_trajectory`   | 是真好转，还是这一阵顺         | 跨会谈的情绪状态记录                     |
| `resistance_monitor`   | 这次的阻抗是新的还是老样子     | 既往的阻抗信号与当时的干预               |
| 危机趋势               | 这个信号要不要升级             | 既往危机记录与一起定过的安全计划         |
| `strategy_adaptation`  | 新提的事和既往议题有没有关系   | 既往议题与已试过的策略（话题衔接，待定） |

**触发**：某个意识的 `insightForSlowThinking`（string，见[意识系统 §2.3.3](../consciousness/consciousness-system.md)）非空时，触发深度 recall + LLM 综合。主线 LLM 不感知、不负责触发——主线回应来访者，意识层觉察信号并决定"什么值得深挖"。

**ai_ask 侧的契约**（硬约束）：

1. **fire-and-forget**：异步运行，不阻塞主线（5-30s）。
2. **产出 DeepInsight 存入 `session.metadata.deepInsights`**（类型见[意识系统 §2.6](../consciousness/consciousness-system.md)）。
3. **注入前经时效性门控**：渲染「深度洞察」段时只取 `relevanceCheck != "过期"` 的条目（附 C.1）。
4. **只有建议权**：洞察注入 prompt 后由主线 LLM 自己判断是否采纳；不直接修改脚本流程（不跳过话题、不插入动作）。

## 附 B：判定段的提示词与输出契约

> 判定段**并入主线提示词**（不是一次独立调用）：主线 AI 每次回复，在输出开头先给判定字段，其余字段照常——与模板原有的那份 JSON 同一份输出、同一次解析。
> **住所**：Default 层模板 `config/prompt-defaults/ai_ask_v1.md` 的最末，与它的输出格式块合写；Custom 层可**整段覆盖**（沿用 Custom > Default 两层解析）。
> **接口由代码写死**：四个字段名与三档取值；模板能改的只是措辞——改了字段名，解析即失败、按 `block` 兜底（§2 第 4 条）。装载时模板校验盯这一条。
> **判定段只管两处**：§3.4 指代与 §3.5 反问。§3.6 收集前回顾不发判定（代码直接查）。
> **判定与回复用同一个模型**，这正是「判定并入生成」的含义。判不出来时按 `block` 兜底（§2 第 4 条）；若"并入生成"整体不达标（格式老守不住、延迟超标），退路是**把这段判定拆成一次独立的 LLM 调用**，不是回头用规则路径。

### B.1 判定段（写进模板的哪一段、长什么样）

位置：模板的**最末**，紧挨它的输出格式块——格式约束离生成越近，守约率越高；判定四字段则写在**输出的开头**（模板那份 JSON 的头四个字段）。

```
## 开口之前：先写判定字段

输出的 JSON 开头先写这四个字段，顺序照下面，其余字段照常跟在后面（严格 JSON，不加围栏）：

{"reason":"…","recall":"…","entities":[…],"query":"…", …其余字段照常…}

它回答一件事：只看最近对话与已收集变量，够不够支撑这一轮的回复。

- **reason**：一句话——有钩子写钩子是什么、缺的是什么；没有就写"这轮没有指向最近对话外的话头"。先想清缺什么，再落 recall 和 query；给日志看，用户看不到。
- **recall** 三档：`none` 够用，直接回复｜`defer` 有钩子，但不写它也答得完整——先接住，下轮补｜`block` 有钩子，不写它答不出、答空，或只能反问。

怎么选（按顺序问两句）：

- ① 这一轮要说的话，有没有指向「你说过、但我看不见的东西」？有路标算有（见下面的表），反问轮看这一轮得不得引既往依据；都没有 → `none`——寒暄、情绪、回应上一句，或指代的东西就在最近对话里（你看得见），大多如此。
- ② 有钩子就不许猜它：把这一轮想说的那句话先写出来，看带不带——
  带（不写它这轮就答不出）→ `block`；不带（共情、接着问、确认一句都说得完整）→ `defer`，回复里不许出现对未知信息的预设；拿不准 → `block`（多查只慢一轮，猜错是不实的回复）。
  **人名、地名、机构名在最近对话里没出现过 → `block`**，不看它这一轮重不重要。
  判 `block` 就写完这四行停笔——引擎把记忆给你，你随后再完整作答（正常一步，不是不让你说话）。

**entities**：只列本轮原话里的专名（人名、地名、机构、作品名），普通名词不放；别写你从记忆里想起的名字——那是要查的东西，不是查询条件。没有则 `[]`。

**query**（30~80 字）＝ 路标 + 要哪一面：

- 路标（话里有什么就原样带上什么）：专名（李光）→ 原样进 query，同时进 entities；指代词（那件事、老样子）→ 原话整句；人称代词（他）→ 原话，靠变量名补范围；时间词（上个月）→ 原样；事件词（被同事出卖）→ 原样，比变量名具体、优先。
- 要哪一面（这一轮缺什么就问什么）：
  - 这个人是谁、与来访者什么关系 →「{名字}——他是什么人、与来访者是什么关系、两人之间发生过什么事」
  - 这件事是什么 → 原话 + 变量名
  - 这件事的前情与结果（可能以前聊过）→ 事件词 +「以前聊过没有、聊到哪、后来怎样」
  - 既往方案与他试过的（这一轮要引依据）→「此前聊过的应对方案、他试过哪些、效果如何」
  - 同一主题聊过多次 → 主题 +「最近一次」
- 一轮可能不止一个钩子（「我该不该跟李光断了？」= 反问 + 专名）：名字进 entities——"这个人是谁"由实体态带回来；query 走这一轮要问的那一面（反问轮就是「既往方案」那一面），时间词叠加进 query。
- 不写整句问句，写"要什么面"；具体优先——专名、事件、时间线索都带上。30~80 字是"别塞噪声"，不是"越短越好"。
- 变量名只在确实圈定范围时拼上（最多 2 个，如"关于核心信念、睡眠质量"）；指代跨到别的话题就不拼。
- `none` 时 query 为空串；除变量名与"要什么信息"外，不出现用户没说过的具体人名、事件。
```

### B.2 样例（判定字段 + 其余字段连起来长什么样）

```
【1 · 专名指代 → block】
{"reason":"「李光」是专名，最近对话里没出现过，我不知道他是谁、跟来访者什么关系","recall":"block","entities":["李光"],"query":"李光——他是什么人、与来访者是什么关系、两人之间发生过什么事"}
（写完即停笔 → 引擎查记忆 → 重新生成：判定给 none，正文写进 content）
{"reason":"记忆已注入","recall":"none","content":"李光又来找你了——你之前提过他，是你前同事，一直想拉你合伙创业。他这次联系你，你挺烦的。……"}
（这一轮检索回来的「李光」实体态进实体备忘，之后提到他就直接带上——附 C.1）

【2 · 指代落在最近对话里 → none】
最近对话：… AI：上次那个方案后来怎么样了？
{"reason":"「那个方案」所指就在最近对话里，我看得见","recall":"none","content":"那个方案你又想了想——是觉得哪一块不合适？"}

【3 · 反问 → block】
{"reason":"这一轮我要给建议，需要既往方案与尝试记录做依据","recall":"block","entities":[],"query":"来访者问「该怎么办」——此前聊过的应对方案、他试过哪些、效果如何"}

【4 · 情绪表达 → none】
{"reason":"纯情绪宣泄，没有指向最近对话外的东西，接着共情即可","recall":"none","content":"唉，这种"哪儿都不对"的感觉，挺熬人的。……"}

【5 · 反问，但这一轮不引既往事实 → none】
{"reason":"这一轮先澄清他要的是建议还是空间，不引任何既往事实","recall":"none","content":"你问我该怎么办——你是想让我拿个主意，还是先陪你把这事看明白？"}
```

> 样例里模板的其余字段（`response_plan` / `assessment` / `progress` / `exit` …）照常写，为省篇幅只留了 `content`。收集前回顾没有判定样例——它不发判定（§3.6），样例见案例 1。

### B.3 输出契约（写在调用侧）

| 项             | 约定                                                                                                                                                                                    |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 住所           | Default 层模板的最末；Custom 层可整段覆盖。Default 这份随引擎版本走                                                                                                                     |
| 接口           | 四个字段名与三档取值由代码写死；模板改了字段名即解析失败、按 `block` 兜底                                                                                                               |

## 附 C：细则

### C.1 数据结构与渲染

recall 结果合并进 `session.metadata.memoryContext`，下一轮 `buildSystemVariables()` 自动带入 prompt。各段各有自己的生命周期：

```typescript
interface SessionMemoryContext {
  baseline: MemoryContext; // 会话启动时加载的基础画像，会话内不变
  topicPrefetch: Array<{
    // 收集前回顾：进入话题时写入，本话题内有效（§3.6）
    topicId: string;
    variables: string[]; // 本次纳入回顾的变量名
    context: MemoryContext;
  }>;
  fastHits: Array<{
    // 要查的轮的联想：最近 5 轮，滚动淘汰
    round: number;
    query: string;
    context: MemoryContext;
  }>;
  entityMemos: {
    // 实体备忘：按名字存，不随轮丢（§4.1、附 C.6）
    [canonicalName: string]: {
      observations: Array<{ text: string; mentionedAt?: string }>; // Hindsight 的实体态原样存
      lastMentionedRound: number; // 渲染排序与淘汰用
      lastFetchedRound: number; // 这份备忘是哪一轮的检索带回来的
    };
  };
  deepInsights: DeepInsight[]; // 意识层洞察：持久累积，带时效性标记
}
```

`formatMemoryContext()` 分段渲染（`base-action.ts`）：

```markdown
## 关于来访者

{baseline}

## 本话题已知信息

{topicPrefetch 中当前话题的条目}

## 本轮相关实体

{这一轮提到的实体，各渲染一份备忘：判定字段写了它，或代码在最近对话里扫到备忘里已有的名字}

## 本轮相关记忆

{fastHits 最近 5 轮合并渲染}

## 深度洞察

{deepInsights 中 relevanceCheck="有效" 的条目，按时间倒序}
```

> **实体备忘为什么单列一段**（原来是附在那一轮里的）：别的段的去留各有依据（会话级 / 话题级 / 最近 5 轮 / 时效性门控），只有它挂在"这个实体被提到"上（§4.1）——按轮淘汰等于把"李光是谁"当成"某一轮的联想"。段名写「本轮相关实体」：里面不只人，还有动物、学校、地方。

**淘汰规则**：baseline 不变；topicPrefetch 话题级——离开话题即失效；fastHits 滚动保留最近 5 轮（与渲染同数——留着不渲染的轮次没有机制会回头去看）；entityMemos 按次淘汰——末次提及最旧的先走，上限 10 份、每份留最近 5 条 observations，会话结束即消失（它是 prompt 侧缓存，权威始终在 Hindsight，清了再取一次就是）；deepInsights 持久保留，`relevanceCheck="过期"` 的不展示，超过 10 条移除最旧。

**备忘的渲染触发怎么判**：判定字段的 `entities` 只管"这一轮原话里的专名"，所以「他还是那样」这种话不会写进 `entities`——但备忘里可能已经有"李光"。补一条**零 LLM 的字面匹配**：拿备忘里的名字去扫最近对话的文本，扫到就渲染。要找的名字是现成的，不是猜的，比判定段那套分词可靠得多（附 C.4 的字面检查是另一回事——那个要猜专名，这个不用）。

### C.2 查哪种记忆

| 记忆类型        | 对"理解用户这轮的话"的帮助                                                                      |
| --------------- | ----------------------------------------------------------------------------------------------- |
| **experience**  | 最直接——"用户之前说过类似的经历吗？"                                                            |
| **observation** | 高——用户/咨询师沉淀过的信念与模式（"我觉得吃药没用"被 consolidate 成带证据引文的观察，ADR 005） |
| **world**       | 低——用户陈述的事实性信息（"在 XX 公司工作"），主要用于避免事实错误                              |

recall 只有这三类可取；**案例公式化（咨询师的工作假设）不在表里**——它走 Hindsight 的 mental model，是另一套 API，会话启动时读入（ADR 005 决策 2）。

**不做类型区分，而是显式传三类**：Hindsight 的 `types` 不传时默认只返回 world + experience，observation 会被静默漏掉（SDK v0.9.1 `RecallRequest.types`）。所以每轮 recall 固定带 `['world', 'experience', 'observation']`，语义匹配到的都返回、按相关度排序；LLM 自己判断哪些有用。每轮 recall 都带当前时间（`queryTimestamp`）——"上次 / 最近"这类相对时间表达靠它解析。

**概要优先于原始片段**：`preferObservations: true`（SDK v0.9.1 `IncludeOptions`）。observation 是 Hindsight 从多条 raw fact 归纳出来的，打开后**已被归纳掉的那些原始 fact 不再单独返回**，空出的位子由后面的结果补上（条数不减）。要的正是这个——「谈到一件事，给的是这件事的概要」，而不是十几条零碎的对话片段。它是**渐进的**：只压制"已经被归纳过"的 fact，归纳尚未发生的照样返回，所以不会把记忆掏空；被压掉的原文也还在，observation 带着 `sourceFactIds`，要展开细节顺着这条线索走（ADR 005 决策 1 的保结构映射）。当前端口已经有这个参数（`RecallOptions.preferObservations`），只是从来没开过（C.7）。

### C.3 固定拼法与待验证清单

**固定拼法**（只在判定字段读不出来时用）：原话 ≤200 字则 `原话 + " —— 关于" + 变量名`；超过则取「头 100 字……尾 100 字」。变量名最多 2 个（按声明顺序），原话不清洗（embedding 对语气词、错别字鲁棒）。200 字是 embedding 输入预算的安全上限——它是"装不装得下"的边界，不是"有没有用"的边界；钩子的数量与字数不成正比，固定截断对长文必损，判定字段自己写检索词则不受这条约束。

**待验证**（前三条决定这套机制值不值）：① 判定字段的格式守约率；② 案例集当测试集跑，逐条比对漏查 / 误查；③ 「大多数轮不需要查」这个假设——它成立，并进生成这笔账才赢。验证路径三步：识别特征（§3.1 路标表）→ 提示词（附 B 判定段）→ 在真实咨询会话里跑，看判 `none` 的轮占比与漏查率（§5.3）；④ 判断与正文抢注意力对回复质量的影响；⑤ **`reason` 写在 `recall` 之前是否真的让检索词更准更稳**——同一案例集跑两种字段顺序，比 query 命中率与判定一致性（§2"先写因、再落果"是推断，不是实测）；⑥ **"同一主题最后一次"能不能稳定挑出来**——`queryTimestamp` 只提供时间锚，"哪一次是同主题的最后一次"要靠语义判断（§3.2）；⑦ 前缀缓存未命中时那一轮的实际延迟；⑧ 模型自己收笔、记忆到手后**接着同一条生成往下写**（省掉第二次预填）在自家 provider 上是否可行。

### C.4 字面检查（只记录，不参与判定）

每轮跑一遍：词表正则（那件事 / 老样子 / 你上次说的 / 他 / 我该怎么办 …）+ 分词未知词（不在通用词库、非停用词的 token 视为专名候选），毫秒级、不调 LLM。**它只记录**——"它说要查而判定给 `none`"的轮次是"装作知道"风险的样本，攒够样本再决定要不要给它否决权（§2）。

已知边界（实测）：同一个名字换句式就漏（「李光最近又联系我了」能切出「李光」，「李光是我前同事」被切成「李 / 光是 / 我前」）；纯指代词分不清所指还在不在最近对话里。**这是"字面规则"这条路的天花板，不是词表长短的问题**——所以它只做探针，不做判手。

> **让它来真判是走不通的**：要理解语义就得再请一个 LLM，那已经不是"检查"，是第二次判定——多一次调用、多一份延迟，换来的只是"错得少一点"（§5.3：漏查要么自愈（追问），要么落到"装作知道"由硬规则挡，不值得为它再加一层）。真到"判定并入生成"顶不住的地步（格式老守不住，或延迟超标），退路是**把判定拆成一次独立的 LLM 调用**（附 B 的判定段原样搬出去），不是回头用它。

### C.5 扩展项（待实证，默认关闭）

**三路扩展**：原始查询 + 类似事件（抽象）+ 关联事件（时间窗口），见 [memory-retrieval-types.md §2.11](memory-retrieval-types.md)。抽象走规则、零 LLM；默认关闭，先验证不加的情况。

**分段检索**：长文（案例 11）在固定拼法下中段会丢；判定字段自己写检索词则不受这条截断规则约束。优先级取决于这类长文有多常见。

### C.6 实体备忘的数据从哪来（实体态；已核实 SDK，待实证质量）

**Hindsight 已经在维护"这个人的当前认识"，而且默认就送回来。** 写时（retain）它把人名、关系抽成实体节点；读时 `response.entities` 里带的是实体自己的 observations——`EntityStateResponse = { entity_id, canonical_name, observations[{text, mentioned_at}] }`，SDK 对它的原话是 "current mental model of an entity"（v0.9.1 `dist/index.d.ts`）。**「李光的关键信息」的直接来源就是它**：不用我们自己总结，也不用额外调一次 LLM。取回开关是高层客户端的 `includeEntities`——**默认就带**，显式 `false` 才关（SDK 把它映射成 `entities: null`）；预算走 `maxEntityTokens`（不传按后端默认；客户端那个 500 只出现在显式 `true` 的路径上，别当后端默认用）。`chunks`、`source_facts` 才是默认关的那两个。

三层各归各：

| 层           | 谁管                   | 怎么做                                                          |
| ------------ | ---------------------- | --------------------------------------------------------------- |
| **检索臂**   | Hindsight 的 bank 配置 | `enable_graph_retrieval`，不在调用侧                            |
| **取回**     | 每次 recall            | 默认就带；`maxEntityTokens` 给预算（值待实测，先 200，见 §5.2） |
| **存与渲染** | 我们自己（附 C.1）     | 按 `canonical_name` upsert 成实体备忘；只在"这一轮提到它"时渲染 |

**为什么每次 recall 都取、不按需取**：判定漏写专名时（比如那句是「他还是那样」），实体态已经在手里了，不用回头再查一次；成本只是一次 HTTP 里多几十行 JSON，不占 prompt 预算（渲染才占，而渲染是有条件的）。

**四处待实证**：① Hindsight 按 query 怎么挑实体——精确取名字，还是语义召回一片（影响"没提到李光的那轮会不会回来一堆人"）；② observations 的质量与颗粒度——真能给到「前男友 / 他出过轨」这一层，还是只有名字与共现；③ 存量记忆有没有实体节点（写时抽取是后加的能力，老数据未必有）；④ 后端能按类型声明要点（人物要哪几栏、学校要哪几栏），但那份配置是整库一份、取回又不标类型——先靠自由抽取，抽得太散再验这条路。前三条都能用案例集验；取不到时的退路是反问，不猜（§5.3）。

> **直查单体有一条路，暂不走**：后端有 `GET /entities`（列表）与 `GET /entities/{entity_id}`（单体），但只在 SDK 生成层（`listEntities` / `getEntity`），高层 `HindsightClient` 上没暴露。暂不用——recall 已经把实体态带回来了，为它单开一条调用等于多一次 HTTP 去取手边就有的东西。若实测发现"备忘被淘汰了、这个人又被提到"这种情况常见，再走这条路补一刀。

**当前实现差距**：适配器只读 `response.results`，实体段整个被丢了（C.7）。
