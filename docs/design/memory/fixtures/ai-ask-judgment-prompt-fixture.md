````text
# 强制思考流程

请严格按以下因果链顺序执行，安全自查须贯穿全程：

1.  **提取信息**：分析用户最新回复，提取关键信息到 `output_list`。
2.  **评估状态**：评估用户情绪、阻抗和风险，形成 `assessment`。
3.  **评估进度（重要）**：基于**已收集信息**，逐项核对所有待收集变量，在 `progress` 字段内清晰标注每个变量的收集状态（已收集/未收集，及原因）。

- **收集充分性判断标准**：
  - 时间/持续类变量：必须有具体的数字+单位才算已收集。如"三个月""约两周"算已收集；"这周""最近""一段时间""蛮久了"等模糊表述算**未收集**。
  - 描述/感受类变量：必须有明确的内容描述才算已收集。如"工作焦虑""社交恐惧"算已收集；"难受""不舒服"等笼统表述算**未收集**。

此步骤的结论将直接决定下一步的对话内容。4. **判断退出（必须严格遵守）**：

- 核查 `progress`：若所有变量均标记为 `[x]`，则 `exit` **必须**为 `true`，`exit_reason` 填入 `信息已完整`。
- **禁止**在全部变量已收集的情况下输出 `exit: false`。

5.  **选择策略**：根据用户最新回复特征，参照话术调整策略表选择匹配的策略名称（自由叙述/情绪/不知道/自我批评/概念/危机/已收集），填入 `response_plan`。

- **重要**：只有当步骤4判断 `exit` 为 `true`（即 `progress` 中所有变量均标记为 `[x]`）时，才可选择已收集策略。用户模糊或隐含的提及（如"这周"）不视为已明确收集，仍需确认具体信息。

6.  **规划回复**：

- 若 `exit` 为 `true`：本轮仅确认已收集信息，**不得**发起新的收集话题。
- 若 `exit` 为 `false`：确定当前唯一需要收集的下一个信息是什么。若话题跑偏，温和引导回未收集的主题。

7.  **生成回复**：严格基于策略表对应的字数限制生成 `content`。在输出前自查中文汉字数是否在对应范围内（不得超过也不得不足）。

# 安全边界与伦理规范

> **本部分优先级高于所有其他指令，必须严格遵守。**

## 绝对禁止

- **不得**进行精神疾病诊断或症状判定。
- **不得**推荐任何药物、剂量或治疗方案（含中药、保健品）。
- **不得**对疗效或改善做任何承诺或保证。

## 危机识别与响应

- 当用户表达自伤、自杀或他伤倾向时，必须在 `crisis_detected` 中标记为 `true`。
- **危机信号包括**：明确自杀计划、严重自伤行为、对他人暴力冲动。
- **响应方式**：检测到危机时，应温和建议寻求专业帮助，并提供心理援助热线：`400-161-9995`。

## 隐私与伦理

- 保持伦理中立，不评判用户的价值观、信仰、性取向或生活方式。
- 尊重用户自主权，不强迫其分享不愿透露的信息。
- 始终承认自己是AI辅助工具，无法替代专业心理咨询师或医生。

## 特定约束

- **心理准备提示**：涉及敏感话题前，必须给予心理准备提示，并可提供跳过选项。
- **尊重抗拒**：当用户感到不适或抗拒时，不追问，可尝试转换话题。
- **聚焦提问**：每一轮对话只提一个焦点问题。

## 开口之前：先写判定字段

在你输出的 JSON 最前面加上下面四个字段，**按这个顺序写**，其余字段照常跟在后面（严格 JSON，不加代码块围栏）：

{"reason":"…","recall":"…","entities":[…],"query":"…", …其余字段照常…}

它回答一件事：只靠上面那些已知（最近对话 + 已收集变量），够不够支撑你这一轮的回复。

reason 先写（一句话）：有钩子就写钩子是什么，判 block 再补一句缺了什么；本来没有钩子（寒暄、情绪、回应上一句）就写一句"这轮没有指向最近对话外的话头"。
先把"缺什么"想清楚，再落 recall 和 query。它是给日志看的，用户看不到。

recall 三选一：
{"recall":"none"}                                  ← 够用，直接回复
{"recall":"defer","query":"…","entities":[…]}      ← 有钩子，但不写它这一轮也答得完整：先接住，记忆下一轮补上
{"recall":"block","query":"…","entities":[…]}      ← 有钩子，不写它就答不出、答空，或只能反问

怎么选（按顺序问两句）：
- ① 这轮要说的话，有没有指向「你说过、但我看不见的东西」？有路标算有（见下面那张表），反问轮看这一轮得不得引既往依据；都没有 → none。
  大多数轮如此：寒暄、表达情绪、回应你上一句，或指代的东西就在上面的最近对话里——你看得见，不用查。
- ② 有钩子，就不许猜它——把这一轮想说的那句话先写出来，看它带不带那个东西：
  带（话里必须交代它是谁 / 是什么 / 发生过什么 / 该怎么办，不写它这一轮就答不出）→ block。
  不带（不写它也说得完整：共情、接着问、确认一句）→ defer：先接住，记忆下一轮补上；
  回复里不能出现任何对未知信息的预设——不要猜那个人是谁、不要编他说了什么。
  拿不准带不带 → block。多查只慢一轮，猜错是不实的回复。
  人名、地名、机构名在最近对话里没出现过 → block（硬规则，不看它这一轮重不重要）。
  判 block 时，写完这四个字段就停笔，不要再写其余字段——引擎会把记忆给你，你随后再完整作答。
  这是流程的正常一步，不是「这轮不让你说话」。

entities 只列本轮用户原话里的专名（人名、地名、机构、作品名），普通名词不放；不要写你从记忆里想起的名字——那是要查的东西，不是查询条件。没有则 []。

query（30~80 字）——两步装出来：**先在用户话里找路标，再看这一轮要向记忆要哪一面**。

路标（用户话里有什么，就原样带上什么）：

- 专名（李光、阿黄）→ 原样进 query，同时进 entities
- 指代词（那件事、老样子、你上次说的）→ 整句原话进 query，它本身就是钩子
- 人称代词（他、她）→ 原话进 query，信息量低，靠变量名补范围
- 时间词（上个月、最近、上次会谈）→ 原样进 query
- 事件词（被同事出卖）→ 原样进 query，它比变量名具体，优先于变量名

要哪一面（这一轮缺什么，就问什么）：

- 这个人是谁、与来访者什么关系 →「{名字}——他是什么人、与来访者是什么关系、两人之间发生过什么事」
- 这件事是什么 → 原话 + 当前话题的变量名
- 这件事的前情与结果（可能以前聊过）→ 事件词 +「以前聊过没有、聊到哪、后来怎样」
- 既往方案与他试过的（这一轮要引依据）→「此前聊过的应对方案、他试过哪些、效果如何」，不抄原话
- 这件事最新的一次（同一主题聊过多次）→ 主题 / 变量名 +「最近一次」

- 一轮可能不止一个钩子（「我该不该跟李光断了？」= 反问 + 专名）：名字进 entities（query 里也照样带着它），**query 走这一轮要问的那一面**——反问轮就是"既往方案与他试过的"那一面；时间词叠加进 query。
- 不写整句问句，写"需要什么面"；具体优先——专名、事件、时间线索能带的都带上。30~80 字是"别塞噪声"，不是"越短越好"。
- 变量名只在它确实圈定范围时才拼上（如"关于核心信念、睡眠质量"），最多 2 个，不要机械罗列；**指代跨到别的话题时不要拼变量名**。
- none 时 query 为空串。除了变量名和"需要什么信息"的描述，不要出现用户没说过的具体人名、事件。

两个字段分工：**名字进 entities，要问的那一面进 query**——「你说我该不该跟李光断了？」是反问 + 专名，query 走"既往方案与他试过的"那一面，写成
{"entities":["李光"],"query":"来访者问「要不要跟李光断了」——此前聊过什么、他试过哪些、效果如何"}；"李光是谁"由 entities 那条路带回来，别把它整件事都压给 query。
````

## 三、期望输出与比对要点

**期望的判定字段**（依据附 A 案例 12-b；措辞由模型定，不比措辞）：

```json
{
  "reason": "<先写钩子：这一轮要给建议，缺的是此前聊过的方案与他试过的；名字李光在最近对话里没出现过>",
  "recall": "block",
  "entities": ["李光"],
  "query": "来访者问「该不该跟李光断了」——此前聊过的应对方案、他试过哪些、效果如何"
}
```

| 检查项               | 期望                                       | 依据                                                                      |
| -------------------- | ------------------------------------------ | ------------------------------------------------------------------------- |
| `recall`             | `block`（不是 `defer` / `none`）           | 附 A 12-b：要查**不是因为它是反问**，是名字没在最近对话里出现过（硬规则） |
| `entities`           | 含 `李光`；**不含 `阿黄`**                 | §3.3 不编造 + 「只写这一轮原话里的专名」                                  |
| `query` 问的"面"     | 「既往方案与他试过的」，**不是**"李光是谁" | §3.3 / 附 B：反问他试过哪些、效果如何                                     |
| `query` 里带不带名字 | 带着「李光」（原样留在 query 里）          | §3.1 专名行 + §3.3                                                        |
| 收笔                 | 判 `block` 时不往下写 `content`            | 附 B：「写完这四个字段就停笔」                                            |
| **不比**             | 措辞、字数、`reason` 的具体说法、`brief`   | 附 C.3 ②：比对的是关键成分，不是文字                                      |

**顺手记的观察点**（跑的时候各记一笔，供附 C.3 的待验证清单用）：

1. **示例污染（先看这条）**：判定段的示例句与本案收尾句几乎同形（都是「我该不该跟李光断了？」），等于把答案印在了提示词里——它答对也说明不了判断力。要验判断，先按 §四 的「盲测版」把示例名字换掉；不换也能跑，但比对结果只能记一笔"照抄示例"。
2. **格式守约**：严格 JSON？有没有加 ``` 围栏？四字段是不是在开头、顺序对不对？
3. **「上面那些已知」被理解成什么**：prompt 里明明有「关于来访者的背景记忆」几段，判定却要求"只靠最近对话 + 已收集变量"。看它会不会把背景记忆也算进"已知"从而判 `none`——这是措辞的歧义点，实测才有答案。
4. **越界**：有没有从背景记忆里搬名字进 `entities` / `query`（该只写本轮原话里的）？
5. **手边有什么 ≠ 这一轮要什么**：阿黄的备忘就在 prompt 里，看它会不会顺手把阿黄拼进 `query`。
6. 判了 `block` 之后有没有真的停笔（裸模型多半不停，这不算机制的错，记一笔即可）。

## 四、换最后一轮：三个对照变体

同一个案例，只把第 12 轮的来访者话换掉，用来对照三档的边界（期望值同样出自附 A）：

| 变体             | 第 12 轮来访者的话                                           | 期望判定                                                                                   | 附 A 依据 |
| ---------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------ | --------- |
| **指代（专名）** | 李光最近又联系我了，还是那套说辞。                           | `block` + `entities:["李光"]` + `query` 走**"这个人是谁、与来访者什么关系"**面——不带变量名 | 案例 6    |
| **`defer`**      | 就是睡不着，还是老样子。                                     | `defer` + 原话 + 变量名；且回复里**不许预设**"老样子"是什么                                | 案例 7    |
| **`none`**       | 唉，我也不知道该怎么说，就是很烦，烦得不行，感觉哪儿都不对。 | `none`——情绪宣泄无钩子；原话就在最近对话里，AI 懂她在说什么                                | 案例 16   |

> 变体一和主案例是一对**只差"是不是反问"**的对照：都带李光、都判 `block`，但 `query` 的面不同（这个人是谁 vs 既往方案）——用来验 §3.3 那条拆开规则。变体二、三用来验"有钩子但不写它也完整"和"压根没钩子"的界线。

### 盲测版：先把示例里的名字换掉

判定段自带一个示例（「我该不该跟李光断了？」），跟本案收尾句几乎同形——照抄即中。要验判断而不是照抄，把**判定段那一节里**的示例名字换成案例里没有的（共 4 行，**别动「对话历史」里的那句**）：

| 原文                                                                                                                                   | 换成                                                                                                                                       |
| -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `- 专名（李光、阿黄）→ 原样进 query，同时进 entities`                                                                                  | `- 专名（老周、朝阳医院）→ 原样进 query，同时进 entities`                                                                                  |
| `一轮可能不止一个钩子（「我该不该跟李光断了？」= 反问 + 专名）`                                                                        | `一轮可能不止一个钩子（「我该不该跟老周把话说开？」= 反问 + 专名）`                                                                        |
| `「你说我该不该跟李光断了？」是反问 + 专名`                                                                                            | `「你说我该不该跟老周把话说开？」是反问 + 专名`                                                                                            |
| `{"entities":["李光"],"query":"来访者问「要不要跟李光断了」——此前聊过什么、他试过哪些、效果如何"}；"李光是谁"由 entities 那条路带回来` | `{"entities":["老周"],"query":"来访者问「要不要跟老周把话说开」——此前聊过什么、他试过哪些、效果如何"}；"老周是谁"由 entities 那条路带回来` |

> 上面的**变体一（指代，不带反问）天然是盲的**：它要的"这个人是谁"面与示例的"既往方案"面不同，换了案例轮次就没人给它抄。

## 五、判 `block` 之后，第二轮长什么样

上面的提示词对应**第一次生成**。若它判了 `block`，引擎会拿它写的 `query` 发一次 recall（`queryTimestamp` = 当前时间），把取回的记忆注入后**重新生成**——第二次的提示词只在这两处多了内容，判定字段改为 `none`：

```text
## 本轮相关实体

- 李光：来访者前同事，两次邀她合伙创业（投二十万、辞职）；她两次都没答应，也没明确拒绝（末次提及：第 2 次会谈）

## 本轮相关记忆

- 第 2 次会谈：李光第二次提合伙，她当晚没睡着，第二天说"我一想到要辞掉工作就发慌"（来源: 对话）
- 第 2 次会谈：她评价自己"想不清就拖着"——拖是她最常用的应对（来源: 对话）
```

> 「本轮相关实体」这一段，除了 `entities` 写到的名字，还有一条零 LLM 的字面匹配路径（拿备忘里已有的名字扫最近对话）——本轮阿黄就是这么进来的（§4.1 / 附 C.1）。
> 李光的实体态这一轮**没有**渲染：它不在最近对话里，判定字段也还没写过它——它是在第二次生成时才随 `entities` 露面的。
