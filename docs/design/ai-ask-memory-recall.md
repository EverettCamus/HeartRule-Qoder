# ai_ask 中调用会谈记忆的设计

## 1. 问题

ai_ask 负责向来访者收集信息。当 ai_ask 执行时，AI 咨询师应该怎么调取已有的会谈记忆？

## 2. 总体流程

ai_ask 的记忆调用分为两个阶段，构成**快/慢双通道架构**：

```
ai_ask 启动
  │
  ├─[阶段1] 快通道 (同步联想) ── ai_ask 启动时用待收集变量名做一次 recall；
  │             此后每轮用户回复后，用「用户原话 + 当前收集变量名」
  │             拼接查询 → recall() → 结果注入 prompt
  │             ≤200ms，纯检索无 LLM 调用
  │
  └─[阶段2] 慢通道 (异步深度分析) ── 由意识层触发（详见 [意识系统设计](consciousness-system.md)）
                → 小模型生成深度查询方向 → 多路并行 recall
                → LLM 综合 → 产出洞察卡片 → 注入后续轮次
                异步运行，不阻塞用户
```

### 快/慢双通道设计原则

| 维度             | 快通道                             | 慢通道                               |
| ---------------- | ---------------------------------- | ------------------------------------ |
| **目的**         | 联想——「这人之前说过相关的吗？」   | 深挖——「背后有什么深层模式？」       |
| **触发**         | ai_ask 启动时 + 每轮用户发言后自动 | 意识层 `insightForSlowThinking` 触发 |
| **查询来源**     | 用户原话截断 + 当前收集变量名拼接  | LLM 生成概念化查询方向               |
| **延迟**         | ≤200ms（一次 HTTP 到 Hindsight）   | 5-30s（多次 LLM + recall）           |
| **阻塞用户**     | 是（但延迟极低）                   | 否（fire-and-forget）                |
| **LLM 调用**     | 0                                  | 2-3 次（查询生成 + 综合 + 可选门控） |
| **结果生命周期** | 保留最近 5 轮                      | 持久保留（带时效性校验）             |
| **失效风险**     | 语义鸿沟（情绪陈述 vs 事件叙述）   | 时效性错位（产出时话题已转移）       |

### 为什么不从记忆预填变量值

一个自然的想法是：ai_ask 启动时根据待收集的变量名查记忆，命中则预填初值，再决定"跳过提问 / 确认式提问 / 正常收集"。但这里混淆了两件事：

- **让 LLM 知道相关历史**（记忆上下文注入 prompt）——这是必须的
- **给变量赋初值**（变量预填）——这是多余的

LLM 看到 prompt 中的记忆片段，自然会写出"上次你提到 X，现在还是这样吗？"的确认式提问，或写出衔接历史信息的精准追问。不需要一个 `onRecall` 策略层来控制"跳过还是确认"——这是 LLM 自己擅长的事。

变量预填还引入了一个更根本的问题：**变量的权威来源是记忆还是用户输入？** 预填暗示记忆中的值可以直接当作变量的当前值来用。但记忆中的信息可能过时、不够精确、或以不同形式表达了当前正在收集的概念。变量的值应该通过正常的 ai_ask 流程（用户输入 → LLM 提取）来获得——记忆的作用是让这个流程更智能，而不是替代它。

因此快通道的做法是：recall 记忆片段 → 注入 prompt → LLM 自然引用。不做变量预填，不做 onRecall 策略。

## 3. 阶段 1: 快通道 —— 同步联想

### 3.1 启动时 recall

ai_ask 首轮启动时，用待收集的变量名做一次 recall，结果作为记忆上下文注入首轮 prompt：

```
ai_ask 启动
  → 解析 output 中待收集的变量名列表
  → 拼接查询: recall(userId, "用户的核心信念、近期情绪状态、工作压力事件")
  → 返回 MemoryContext → 注入首轮 prompt 的 {{memory_context}}
  → LLM 在生成首轮提问时自然引用相关历史
```

例子：

- ai_ask 配置收集 `{核心信念}`
- recall("用户的核心信念相关") → 命中: 第1次会谈"我觉得自己永远不够好"
- 记忆片段注入 prompt → LLM 生成: "上次你提到感觉自己永远不够好，现在还是这样吗？"

这就够用了。变量名作为查询，召回相关记忆，LLM 自然写出更精准的问题。不需要判断"该 skip 还是 confirm"——LLM 结合当前对话语境，比代码规则更能做出恰当判断。

### 3.2 每轮 recall

每轮用户回复后，主 LLM 生成回复前，用一次轻量 recall 快速联想历史相关记忆。查询构造遵循引擎默认检索增强（见 [memory-retrieval-types.md §2.11](memory-retrieval-types.md)）：

```
用户回复了一段话
  → 轻量判断: 是否为"事件性描述"（有主体+动作+情境）?
  │    ├─ 否 → 单路查询: 用户原话截断(≤200字) + 当前收集变量名列表
  │    └─ 是 → 三路查询:
  │          · 原始查询: 用户原话截断 + 变量名列表
  │          · 类似事件: 原话抽象为事件概念 → 检索历史类似事件
  │          · 关联事件: 以原话时间点为窗口 → 检索同期生活变化
  → recall()  ← 纯 Hindsight 检索，无主线 LLM 调用
  → 合并 MemoryContext → 存储到 session.metadata.memoryContext
  → 下一轮 buildSystemVariables() 自动带入 prompt
```

例子（三路命中）：

- 用户说"还是和之前一样睡不着"，当前在收集 {睡眠质量, 情绪状态}
- 原始查询: `"还是和之前一样睡不着 —— 关于睡眠质量,情绪状态"`
  - 命中: 第3次会谈"失眠是因为项目压力"，第5次"试过褪黑素没效果"
- 类似事件查询（抽象: 睡眠障碍 反复发作）: 命中第2次"高三时也失眠过一阵"
- 关联事件查询（时间窗口: 近期）: 命中"上周提到项目验收临近，压力加大"
- AI 回复: "你上次说褪黑素试了没效果，这周睡眠有新的变化吗？你之前高三时也失眠过，当时是怎么恢复的？"

### 3.3 查询构造：用户原话 + 变量名锚点（原始查询）

原始查询（三路中的基础路）直接用用户原话做 recall，语义向量可能跨不过「情绪陈述」和「事件叙述」之间的鸿沟。变量名作为概念锚点，给 Hindsight 的语义检索提供一个领域框架：

```
recall(userId, "{用户原话截断(≤200字)} —— 关于{当前收集的变量名列表}")
```

这不需要任何额外 LLM 调用。如果命中率仍不理想，后续可以加一层极短 LLM 摘要（如把"我觉得自己永远不够好"压缩为"自我否定认知"），但先验证不加的情况。

**扩展查询的抽象层**与上述机制一致：类似事件查询的"事件概念抽象"先走规则，命中率不理想时升级为极短 LLM 摘要。

### 3.4 延迟约束

- 目标 ≤200ms（一次 localhost HTTP 到 Hindsight，纯检索不调 LLM）
- 三路查询超出预算时的**降级顺序**: 先砍关联事件 → 再砍类似事件 → 只留原始查询
- 超时则返回空 MemoryContext，不阻塞主流程
- 如果 Hindsight 不可用（连接失败），静默降级

### 3.5 淘汰策略

快通道结果仅保留**最近 5 轮**。超过 5 轮的自动从 `memoryContext.fastHits` 中移除。原因：

- 5 轮前的联想在当前对话语境下大概率已失效
- 防止 `memoryContext` 无界膨胀
- 慢通道结果不受此限制（慢通道产出的是综合洞察，生命周期更长）

### 3.6 该调用哪种记忆类型？

| 记忆类型         | 与"实时理解用户回复"的关系                                                                                                                     | 优先级   |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| **experience**   | 最直接 — "用户之前说过类似的经历吗？"                                                                                                          | **最高** |
| **observation**  | 高 — 用户/咨询师沉淀过的信念与模式："我觉得吃药没用"这类表述会被 consolidate 为带证据引文的观察（ADR 005）；AI 看到用户对药物的抵触及其证据链  | **高**   |
| **mental model** | 中高 — 常驻公式化/工作假设（如"用户抵触药物背后的原因链"）随证据由后台重写；**会话启动时零成本读入 baseline**，不逐轮 recall（ADR 005 决策 2） | **中高** |
| **world**        | 低 — world 存的是用户陈述的事实性信息（如"用户在XX公司工作"），对于理解当前回复的直接帮助较小，更多用于避免事实错误                            | **低**   |

**不做类型区分，统一 recall。** recall 内部跨类型检索，语义匹配到的都返回，按相关度排序。LLM 在 prompt 里看到的是一段结构化的"相关记忆片段"，自己会判断哪些有用。

## 4. 阶段 2: 慢通道 —— 异步深度分析

### 4.1 触发来源

慢通道的触发由**意识层**负责，不走 ai_ask 主线。具体机制见 [意识系统设计 §2.3.3](consciousness-system.md)——某个意识产出 `insightForSlowThinking` 非空时，触发慢通道做深度 recall + LLM 综合。

主线 LLM 不需要知道自己触发了慢通道，也不需要在 JSON 响应中附加 `pendingDeepRecall` 标记。主线和支线分工明确：主线负责回应来访者，支线（意识）负责觉察信号并决定"什么值得深挖"。触发慢通道是意识层的工作，不是主线的工作。

### 4.2 两阶段深度检索

**阶段 A：LLM 生成深度查询方向**

```
输入：
  - 意识层 insightForSlowThinking 中的 context 和 direction
  - 用户最新回复原文
  - 最近 10 轮对话摘要（轻量截断即可）

小模型生成 2-3 个概念化查询短语：
  例: ["完美主义倾向 童年教养 关联", "自我评价模式 形成时期", "母亲期望 认知影响"]

模型：用小模型即可（节省成本），不参与主线对话的模型
```

**阶段 B：多路并行 recall + LLM 综合**

```
并行 recall(userId, 查询1)
并行 recall(userId, 查询2)
并行 recall(userId, 查询3)
  → 合并结果 → 去重（按 content 相似度 >80% 去重）
  → 如果命中 >5 条新记忆 → 判断是否需要聚焦检索
    → 如果需要 → 再做 1 轮聚焦 recall（最多 2 轮迭代）
  → LLM 综合分析 → 产出 DeepInsight 卡片
```

### 4.3 硬限制

| 限制项           | 值   | 原因                                       |
| ---------------- | ---- | ------------------------------------------ |
| 最大检索迭代     | 2 轮 | 防止递归检索失控（初查 → 聚焦深挖 → 停止） |
| 最大 LLM 调用    | 3 次 | 查询生成(1) + 综合(1) + 可选时效性门控(1)  |
| 最大 recall 调用 | 5 次 | 3 路并行初查 + 2 路聚焦深挖                |
| 单次超时         | 30s  | 超时则产出部分结果或放弃                   |

### 4.4 产出：DeepInsight 卡片

```typescript
interface DeepInsight {
  id: string; // 唯一标识
  timestamp: Date;
  triggerRound: number; // 触发时的轮次
  triggerContext: string; // "第5轮：用户说'我觉得自己永远不够好'"
  insight: string; // "用户在第2次会谈中描述母亲高期望的教养方式（考99分问1分去哪了），这与当前表达的自我否定形成清晰的因果链。建议引导用户区分'母亲的期望'和'自己的价值'。"
  confidence: number; // 0-1，LLM 自评
  sourceFragments: Array<{
    // 支持溯源
    content: string;
    sessionLabel: string; // "第2次会谈"
  }>;
  relevanceCheck: string; // "有效" | "过期" | "待验证"
  suggestedAction: string | null; // 给主线的建议，如 "引导用户区分怕被评价 vs 怕说错话"
}
```

### 4.5 结果注入与时效性门控

慢通道产出后：

1. 存储到 `session.metadata.deepInsights: DeepInsight[]`
2. 注入前做**时效性门控**（可选，Phase 2 加）：
   - 用一个极短 LLM 调用判断："当前对话在第 N 轮，主题是 X。以下洞察是否仍然相关？"[洞察内容] → 是/否
   - 标记 `relevanceCheck: "有效" | "过期"`
3. `formatMemoryContext()` 在「深度洞察」段落下展示 `relevanceCheck != "过期"` 的条目
4. **慢通道只有建议权**：洞察注入 prompt 后，由主线 LLM 自己判断是否采纳。慢通道不直接修改脚本流程（不跳过 Topic、不插入 Action）

### 4.6 发现关联和深层模式（场景 C）

```
意识层检测到用户这次聊的"社交回避"与之前的工作话题有某种联系
  → insightForSlowThinking: { direction: "探索社交回避与工作压力的关联" }
  → 慢通道 recall("社交回避"), 同时跨域搜索 "工作压力" "人际关系"
  → 记忆中有: 第2次 "朋友聚会常找借口不去"，第5次 "小组会议不敢发言"
  → 同时 mental model 常驻公式化已有线索: "社交焦虑可能从工作关系泛化而来"（随证据刷新，is_stale 提示是否需重审）
  → 产出 insight → relevanceCheck: "有效" → 注入后续对话
  → 后续 AI 追问更有方向，比如引导用户区分 "怕被评价" vs "怕说错话"
```

### 4.7 验证矛盾或变化（场景 D）

```
意识层检测到用户对母亲关系的描述似乎和之前不一致
  → insightForSlowThinking: { direction: "用户-母亲关系的叙事一致性" }
  → 慢通道 recall("用户-母亲关系")
  → 记忆中有: 第2次 "关系一直很好" + 第8次 "放学不想回家，怕看我妈的脸色"
  → 觉察到张力，产出 insight
  → 后续追问不带判断但更精准: "之前提到有时候不想面对她，现在有变化吗？"
```

### 4.8 慢通道的 recall 策略

慢通道被触发后，recall 比快通道更广更深:

| 记忆类型         | 策略                                                                                                                                               |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| **experience**   | 不只是查当前话题，而是关联话题（比如用户现在说"工作压力"，也查"家庭关系""身体健康"，找跨域关联）                                                   |
| **observation**  | 查 AI 沉淀的模式笔记 — "之前有没有类似的模式被记录？"；兼查矛盾：信念级观察带 refine 历史（strengthened/weakened），与 experience 原始表述核对冲突 |
| **mental model** | 查常驻公式化是否 stale — "对该案例的整体工作假设是否需要因新证据重审？"（刷新后台自动做，慢通道判断是否提醒）                                      |
| **world**        | 查用户的基本事实 — "用户的生活背景中有没有相关的结构性因素？"                                                                                      |

## 5. recall 的检索句子来源

recall 不是用原始对话消息当查询，而是用"当前 ai_ask 在收集什么"和"用户说了什么关键内容"两者组合。

| 阶段                       | 查询驱动                                         | 例子                                                                                                         | LLM 调用                             |
| -------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ | ------------------------------------ |
| 快通道（启动）             | 待收集变量名列表拼接                             | `recall(userId, "核心信念、情绪状态、工作压力")`                                                             | 0                                    |
| 快通道（每轮）             | 用户原话截断(≤200字) + 当前收集变量名拼接        | `recall(userId, "我觉得自己永远不够好 —— 关于核心信念")`                                                     | 0                                    |
| 快通道（每轮，事件性描述） | 三路: 原始 + 类似事件(抽象) + 关联事件(时间窗口) | 原始: `"上周和老板大吵一架 —— 关于工作压力"`<br>类似: `"人际冲突 爆发性争执"`<br>关联: `"上周同期 生活变化"` | 0（抽象走规则，可升级极短 LLM 摘要） |
| 慢通道                     | 小模型生成 2-3 个概念化查询                      | `recall(userId, "完美主义倾向 童年教养 关联")`                                                               | 1（查询生成）                        |

## 6. memoryContext 结构演进

当前 `memoryContext` 是扁平对象，改为分层结构以支持快/慢通道各自独立生命周期：

```typescript
interface SessionMemoryContext {
  // 会话启动时加载的基础画像（initializeSession 时设置，会话内不变）
  baseline: MemoryContext;

  // 快通道近日联想（最近 5 轮，滚动淘汰）
  fastHits: Array<{
    round: number;
    query: string;
    context: MemoryContext;
  }>;

  // 慢通道深度洞察（持久累积，带时效性标记）
  deepInsights: DeepInsight[];
}
```

`formatMemoryContext()` 分段渲染（`base-action.ts`）：

```markdown
## 关于来访者

{baseline}

## 本轮相关记忆

{fastHits 最近 3 轮合并渲染}

## 深度洞察

{deepInsights 中 relevanceCheck="有效" 的条目，按时间倒序}
```

**淘汰规则**：

- baseline: 不变（会话级稳定性）
- fastHits: 滚动窗口，最新 5 轮保留，超出自动移除
- deepInsights: 持久保留，但 `relevanceCheck="过期"` 的不展示；超过 10 条的移除最旧条目

## 7. 调用时机总结

| 阶段                       | 何时触发                             | 目的                              | 记忆类型侧重                                          | 阻塞用户 | 延迟                       | LLM 调用 |
| -------------------------- | ------------------------------------ | --------------------------------- | ----------------------------------------------------- | -------- | -------------------------- | -------- |
| 快通道（启动）             | ai_ask 首轮启动时                    | 让 LLM 知道相关历史，使提问更精准 | experience, observation（mental model 并入 baseline） | 是       | ≤200ms                     | 0        |
| 快通道（每轮）             | 每轮用户回复后、生成回复前           | 联想相关历史，让 AI 精准回应      | experience + observation 混合                         | 是       | ≤200ms                     | 0        |
| 快通道（每轮，事件性描述） | 同上，检测到事件性描述时触发视角扩展 | 联想历史类似事件 + 同期关联事件   | experience 为主，混合                                 | 是       | ≤200ms（超出预算按序降级） | 0        |
| 慢通道                     | 意识层 `insightForSlowThinking` 触发 | 挖掘矛盾、发现深层模式            | 四种类型全面检索                                      | 否       | 5-30s                      | 2-3      |

## 8. `require` 属性：收集紧迫度

OutputField JSON Schema 中已有 `require` 字段，定义变量的收集紧迫度：

| require 值         | 含义                           |
| ------------------ | ------------------------------ |
| `"即时"`           | 必须立刻获得，最关键的信息     |
| `"本次对话内"`     | 优先本次获取                   |
| `"可推迟"`（默认） | 本次拿不到可推迟到下次         |
| `"持续跟踪"`       | 不主动提问，仅在用户提及时记录 |

`require` 的语义是**收集紧迫度**，影响但不依赖记忆调用。具体作用的场景：

1. **退出判断**：`ai_ask` 的 exit_condition 是否需要确保 `"即时"` 变量全部收集完毕才能退出？`"可推迟"` 变量可以未收集就退出
2. **LLM 提问优先级**：多个待收集变量时，`"即时"` 的应该优先追问
3. **后续 Topic 规划**：TopicPlanner 可以根据还有哪些 `"即时"` 变量未收集，决定是否需要插入追问话题

**当前状态**: `require` 在 Schema 中已定义，但运行时代码 `AiAskAction` 未读取它。本次落地需要让代码实际消费 `require` 字段以支持 exit 判断。
