## 1. 核心模型：咨询过程 = 话题队列的逐项执行

### 1.1 一个隐喻

真实咨询师的工作方式：

1. 会谈开始前，心中有一个**大致议程**——今天要聊哪些话题
2. 会谈进行中，按照议程**逐项推进**，每个话题结束后自然过渡到下一个
3. 但议程不是锁死的——如果来访者突然提到一个重要线索，咨询师会**临时调整**：把当前话题暂停，插入一个深入探索的话题，之后再回到原话题
4. 如果时间紧张，咨询师会**跳过**优先级低的话题，或把某个话题**压缩**成快速版

HeartRule 的核心领域模型就是这个过程的直接映射：

```
咨询过程 = 话题队列的生成 + 逐项执行 + 意识层动态调整
```

### 1.2 三个本体论判断与三条架构不变量

本节是全文档的承重墙，分为两层，两层的认识论地位不同：

- **本体论判断**——对咨询会谈过程的本质提炼。判断可能错，检验方式是模型的使用：当模型反复表达不了真实咨询现象、迫使脚本作者绕路时，应修订判断本身。
- **架构不变量**——由判断推出、或为守护判断的可执行性而施加的系统纪律。不变量可能被违反，执行方式是设计评审：违反不变量的设计需要先修订本节，而非绕过。

**判断一（结构）：咨询会谈过程是话题单元的串行组合；话题单元是动作的串行组合。**

两级组合都是串行的——任一时刻只有一个话题处于活跃状态，话题内 Action 自上而下依次执行。复杂性不在层级内部（无分支、无循环、无跳转），而在层级之间：对组合本身的调整（见判断三）。

> 注："串行"的精确含义是"任一时刻只有一个活跃话题"。紧急插入（interrupt）会切开被冻结话题的时间线，但这一表述在该场景下依然成立（见附录 B）。

**判断二（粒度）：话题单元是最小的可复用完整经验单元。**

三个子判断：

- **完整**——话题回答"要达成什么 + 怎么做"（目标 + Action 序列），是承载咨询经验的最小闭环。
- **最小**——动作太小：单个 ai_ask 离开话题语境不构成完整经验；阶段太大：绑定具体流程，难以跨脚本复用。
- **可复用**——同一话题单元可被多个脚本、多次会话使用。

**推论：咨询技术是"为复用而发布的话题单元模板"。** CBT 箭头向下、5-4-3-2-1 着陆技术——每个技术天然是话题尺寸的：一个目标 + 一段 Action 序列。在**定义层**，它以独立的咨询技术脚本工件存在——有自己的版本、参数和库，可被会谈脚本引用或被意识层插入（见[脚本引擎设计原则 §策略1.4](script-engine-design-principles.md#策略-14三种脚本分离主线--意识--技术)）；在**运行时**，它实例化为与主线话题同构的队列条目（见不变量一）。会谈脚本与咨询技术脚本是两种不同的脚本形态，共享同一个经验粒度。

**证伪条件**：如果实践中脚本作者反复需要复用"半个话题"（动作片段）或"跨话题的固定组合"（整个阶段），说明粒度判断错误，应修订本判断。（多话题协议式技术是否构成此类证据，留待实践检验。）

**判断三（计划）：计划是对话题单元的组合，且这个组合在会谈中随实际进展持续被调整。**

会谈前的计划（脚本展开的初始队列）只是**默认组合**；真实对话总是偏离脚本编写时的假设——重要线索出现、时间压力、危机信号，都要求在会谈中调整组合。计划不是流程图，是可变的序列。

---

**不变量一（无嵌套执行）：所有话题一律串行摊开，不存在话题内调用另一个话题的机制。**

由判断二——话题是复用的最小粒度——直接推出：被复用的技术进入队列时，它就是一个普通话题条目，顺序排在当前话题之后（或紧急插入时冻结当前话题、移到队首之后），别无特殊待遇。因此，无论来源是会谈脚本、咨询技术脚本还是意识层临时创建（`source: 'main' | 'technique' | 'ad_hoc'`，见 §3.4），入队后一律同构——执行引擎眼中只有队列条目及其 `actions` 序列，不存在"来源"这个维度。技术脚本的"调用"是**实例化 + 入队**，不是"调用-返回"：没有调用栈，没有子程序语义，"返回"是队列顺序的自然结果。

**不变量二（唯一编排结构）：话题队列是唯一的编排数据结构。**

编排指"接下来进行哪个话题"这类决策的表达。所有对**计划**的修改——主线脚本的"剧本"、意识层的重量干预、时间压力的"调度"——都通过对队列的操作实现。不存在第二套任务系统、调度表或调用栈。队列即计划。

三个不构成反例的边界：变量池是证据不是编排；意识层的触发状态（如冷却计数）决定意识**何时**出手、不决定话题走向；轻量干预（提示词注入，见 §4.3）影响当前 Action 的表达方式、不改变话题序列——三者均不在编排之列。

由判断一、判断三推出：串行组合 ⇒ 序列结构；组合可调整 ⇒ 队列操作。意识层的高熵判断被压缩为封闭的操作集（六种队列操作，见 §4.2）——这是熵减架构在编排层的体现。

**不变量三（唯一修改者）：意识层是唯一的队列修改者。**

主线执行引擎只做一件事：取队首话题，执行其 Action 序列，完成后取下一个。它不思考"下一步该做什么"，不判断"当前策略是否失效"，不决定"是否需要插入安抚话题"。所有队列修改——插入、取消、重排、深度切换、紧急度调整——都由意识层发起。

一个显式豁免：expand_by 展开（见 §3.2）是脚本声明的**兑现**——由主线引擎在列表变量就绪时执行，属于队列生成的延续，不属于修改。不变量三只约束对既定计划的**偏离性调整**。

注意：这条不是从咨询现象中提炼的（真实咨询师的执行与元认知是同一个头脑），而是**纯粹的架构纪律**——读写分离让执行可预测、调整可追溯。它的评判标准是收益与代价，不是真假。

### 1.3 执行循环

```
┌─────────────────────────────────────────────────────────┐
│                    话题队列（动态）                       │
│  ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐     │
│  │Topic₀│  │Topic₁│  │Topic₂│  │Topic₃│  │Topic₄│  ... │
│  └──────┘  └──────┘  └──────┘  └──────┘  └──────┘     │
│      ▲                                                  │
│      │  队列操作（插入/取消/重排/调整深度/变更紧急度）      │
│      │                                                  │
│  ┌───┴──────────────┐    ┌──────────────────────┐       │
│  │    意识层         │    │    主线执行引擎        │       │
│  │  观察对话上下文    │    │  取队首话题 → 执行其   │       │
│  │  检测信号 → 决策   │    │  Action 序列 → 完成后  │       │
│  │  是否需要调整队列   │    │  取下一个话题          │       │
│  └──────────────────┘    └──────────────────────┘       │
│           ▲                          │                   │
│           │       对话上下文          │                   │
│           └──────────────────────────┘                   │
└─────────────────────────────────────────────────────────┘
```

执行循环：

1. 主线引擎从队列顶部取出当前话题
2. 执行话题内的 Action 序列（ai_say、ai_ask 等），产生用户可见的对话
3. 当前话题的 Action 全部完成后，该话题出队
4. 意识层在每轮对话后异步运行：观察对话上下文，判断是否需要调整队列。如需调整——插入新话题、取消未执行话题、调整优先级、切换深度版本——修改队列
5. 主线引擎取下一个队首话题，继续执行

这个循环持续到队列为空，或会话被用户终止。

## 2. 话题的构成：由最小的智能动作组成

### 2.1 话题：从目标到动作序列

一个话题单元是多轮对话的容器。它回答两个问题：

- **要达成什么**：话题的目标（意图）
- **怎么做**：达成目标所需的智能动作序列

咨询师在规划一个话题时，脑子里不会出现"循环该怎么做""分支该怎么写"——ta 想的是：

> "先问他最近一次焦虑发作是什么时候（ai_ask），然后根据他的回答，我判断一下焦虑的核心触发模式（ai_think），再把这个模式解释给他听（ai_say），最后再问他一个验证性的问题（ai_ask）。"

这就是一个话题内的 Action 序列：

```yaml
topic:
  topic_id: trigger_exploration
  topic_goal: '识别焦虑发作的核心触发模式'
  actions:
    - action_type: ai_ask
      action_id: ask_recent_episode
      config:
        content: '最近一次焦虑发作是在什么情境下发生的？'

    - action_type: ai_think
      action_id: analyze_trigger_pattern
      config:
        content: '结合用户之前的陈述，分析这次发作的可能触发模式'

    - action_type: ai_say
      action_id: explain_pattern
      config:
        content: '将分析结果用非专业语言解释给用户，并邀请他确认'

    - action_type: ai_ask
      action_id: ask_other_contexts
      config:
        content: '这个模式在其他情境下也出现过吗？'
```

### 2.2 智能动作：最小执行单元

每个 Action 是主线引擎的**原子执行单元**——不可再分的最小对话交互。当前定义了五种类型：

| Action 类型 | 咨询室中的动作             | 核心能力                                  | 用户感知                   |
| ----------- | -------------------------- | ----------------------------------------- | -------------------------- |
| `ai_ask`    | 向来访者提问，收集信息     | 生成问题 → 等待输入 → 提取变量 → 判断退出 | 被问了一个问题，需要回答   |
| `ai_say`    | 向来访者介绍、解释、告知   | 组织信息 → 选择表达方式 → 输出            | 听到一段讲解               |
| `ai_think`  | 咨询师内部思考，不对外输出 | 分析已有信息 → 加工出结论 → 写入变量      | 无感知                     |
| `ai_draw`   | 用图形/可视化方式呈现信息  | 选择图表类型 → 生成可视化 → 输出          | 看到一张图                 |
| `ai_fill`   | 引导来访者系统填表         | 呈现表单 → 引导填写 → 校验 → 存储         | 在引导下填写一份结构化表单 |

每个 Action 类型有不同的运行时行为——不同的引擎调用路径、不同的等待/推进逻辑、不同的变量交互方式。这些差异决定了它们不能简单地用一个通用 `task` 加 `mode` 参数替代（详见 §5 的边界判断）。

### 2.3 话题内的线性结构

话题内的 Action 序列是**严格线性的**——自上而下，依次执行。这是判断一第二级串行（话题 = 动作的串行组合）的直接体现，也是"脚本即剧本"的核心表达（详见 [脚本引擎设计原则 §P1](script-engine-design-principles.md#原则一线性优先linearity-first)）。

复杂度的控制由三个机制承担：

- **condition 守卫**：Action 可带 `condition` 字段，跳过不满足条件的 Action。但 condition 是独立的一级过滤器——不形成嵌套条件树。
- **exit_condition**：`ai_ask` 可在满足条件时提前结束，进入下一个 Action（而非循环）。
- **意识层干预**：需要复杂分支或动态调整时，不在话题内处理——交给意识层调整话题队列（如插入一个深度探索话题）。

```yaml
actions:
  - action_type: ai_say
    action_id: stabilization_exercise
    condition: "{{risk_level}} == 'high'"
    config:
      content: '我们先做一个稳定化的练习...'

  - action_type: ai_ask
    action_id: ask_episode_detail
    condition: "{{risk_level}} != 'high'"
    config:
      content: '能具体描述一下最近一次焦虑发作的情境吗？'
      exit_condition: '{{mentioned_trauma}} == true' # 提到创伤则提前结束
```

条件不满足 → 跳过 → 看下一个。满足 → 执行 → 结束后看下一个。始终保持线性阅读体验。

## 3. 队列的生成：从咨询脚本生成默认话题计划

### 3.1 脚本即计划

咨询师编写 YAML 脚本，本质上是在定义一个**默认话题计划**。脚本的 Phase → Topic → Action 层次结构，被引擎解析后展开为初始话题队列：

```
YAML 脚本                              初始话题队列
─────────                             ────────────
phases:
  - phase_id: assessment
    topics:
      - topic_id: chief_complaint       Topic("chief_complaint", urgency=10, ...)
        actions: [...]
      - topic_id: symptom_history       Topic("symptom_history", urgency=8, ...)
        actions: [...]
  - phase_id: intervention
    topics:
      - topic_id: cbt_psychoeducation   Topic("cbt_psychoeducation", urgency=7, ...)
        actions: [...]
      - topic_id: cognitive_restructure Topic("cognitive_restructure", urgency=9, ...)
        actions: [...]
```

引擎遍历脚本的 Phase → Topic 层级，为每个 Topic 创建队列条目。队列中的每个条目携带：

- 话题的唯一标识（`id`）
- 所属 Phase 信息
- Action 序列（可含 condition 和 exit_condition）
- 默认紧急度
- 预设时间估算
- 可选的深度版本（快速版 / 标准版 / 详细版）

### 3.2 动态展开：脚本声明，引擎执行

部分话题不能预先确定数量——需要根据运行时的变量动态生成。脚本通过 `expand_by` 声明，引擎在队列生成时执行展开：

```yaml
topics:
  - topic_id: explore_caregiver
    expand_by: '{{caregivers}}' # 指向一个列表变量（schema 尚未约定此字段）
    item_variable: caregiver # 每个元素注入为 {{caregiver}}（schema 尚未约定此字段）
    actions:
      - action_type: ai_ask
        action_id: ask_relationship
        config:
          content: '你和{{caregiver.name}}的关系是怎样的？'
      - action_type: ai_ask
        action_id: ask_influence
        config:
          content: '{{caregiver.name}}对你的成长有什么影响？'
```

如果 `{{caregivers}}` 的值为 `["母亲", "父亲", "姐姐"]`，引擎展开为三个话题：

```
Topic("explore_caregiver::母亲", item_context={caregiver: {name: "母亲", ...}}, ...)
Topic("explore_caregiver::父亲", item_context={caregiver: {name: "父亲", ...}}, ...)
Topic("explore_caregiver::姐姐", item_context={caregiver: {name: "姐姐", ...}}, ...)
```

展开的时机由列表变量决定：若变量在初始队列生成时已有值，立即展开；若变量在会谈中才被提取（如上例的 `{{caregivers}}` 来自评估阶段的对话），则在变量就绪时展开。无论何时展开，都是一次性全部展开——不逐个按需展开。咨询场景中展开列表的规模很小（几位家人、几个症状），按需展开带来的复杂性和不确定性远大于其价值。展开是脚本声明的兑现，由主线引擎执行，不属于意识层的队列修改（见不变量三的豁免）。

咨询师不需要声明"逐个展开还是全部展开"——引擎替 ta 做决定。这是 [P2（不暴露工程问题）](script-engine-design-principles.md#原则二不暴露工程问题no-engineering-concerns-exposed) 的直接体现。

### 3.3 队列排序

初始队列按脚本声明顺序排列（Phase 内按 Topic 顺序，Phase 间按 Phase 顺序）。紧急度影响后续的意识层重排——初始队列本身不按紧急度排序，因为脚本编写顺序已经表达了咨询师的意图。

### 3.4 咨询技术脚本的队列条目化

按判断二的推论，咨询技术是为复用而发布的话题单元模板；按不变量一，它被引用时实例化为与主线话题同构的队列条目。当咨询技术脚本被引用时，它与主线话题使用**完全相同的队列条目格式**：

```
队列中的每个条目：
  ├── id: string                    # 唯一标识
  ├── source: 'main' | 'technique' | 'ad_hoc'  # 来源标记（用于调试和评估）
  ├── goal: string                  # 话题目标
  ├── actions: Action[]             # Action 序列
  ├── urgency: number               # 动态紧急度
  ├── estimated_duration: number    # 预估时间（分钟）
  ├── depth: 'quick' | 'standard' | 'deep'  # 深度版本
  ├── phase_id: string              # 所属 Phase
  └── metadata: Record<string, any> # 扩展元数据
```

`source` 字段标记来源但并不影响执行——执行引擎只看 `actions`。来源标记用于：

- 调试时追溯队列条目从何而来
- 评估时统计技术脚本的使用频率和效果
- 意识层在调整时可以区分"主线话题"和"技术话题"（如果需要不同的调整策略）

技术脚本的 `trigger_on`（见[脚本引擎设计原则 §策略1.4](script-engine-design-principles.md#策略-14三种脚本分离主线--意识--技术)）是**声明式意识规则**——由意识层求值，通过标准队列操作（insert/interrupt）插入技术话题；主线引擎不求值 `trigger_on`。"会谈脚本中引用技术"与"意识层插入技术"因此归并为同一条执行通道，不变量三不受威胁。

## 4. 队列的调整：意识层对队列的动态调整

### 4.1 不变的与可变的

初始队列是**默认计划**，不是**最终流程**。默认计划基于脚本编写时对典型情况的假设——真实对话总是偏离假设。

- **不变的**：主线引擎始终按队列顺序执行，不跳过、不插入、不重排。
- **可变的**：队列本身（内容、顺序、深度、紧急度）。

意识层是连接"不变执行引擎"和"可变队列"的桥梁——它观察对话中发生的事，判断默认计划是否需要调整，如果需要，直接修改队列。

### 4.2 六种队列操作

意识层可以发起以下队列操作：

| 操作                      | 语义                                       | 触发示例                                                                     |
| ------------------------- | ------------------------------------------ | ---------------------------------------------------------------------------- |
| **插入（insert）**        | 在指定位置添加新话题                       | 检测到阻抗 → 在当前话题后插入情绪安抚话题                                    |
| **紧急插入（interrupt）** | 冻结当前话题，立即执行新话题，完成后恢复   | 用户提及自杀意念 → 冻结当前话题，立即执行危机评估话题                        |
| **取消（cancel）**        | 移除队列中尚未执行的话题                   | 得知来访者父亲已去世 → 取消所有与该父亲相关的 `explore_caregiver::父亲` 话题 |
| **重排（reorder）**       | 调整队列中尚未执行话题的顺序               | 检测到时间压力 → 将高紧急度话题提前，低紧急度话题后移                        |
| **深度切换（depth）**     | 将尚未执行的话题切换为快速版/标准版/详细版 | 时间不足 → 后续话题全部切换为快速版；发现重要线索 → 某个话题扩展为详细版     |
| **紧急度调整（urgency）** | 变更话题的紧急度（影响后续重排决策）       | 基于对话进展动态调整——已部分覆盖的话题降紧急度，新发现的高价值话题升紧急度   |

每次操作的目标是同一个数据结构：话题队列。操作之间可能级联——例如取消一个话题后，后续话题自动前移；紧急度调整后可能触发重排。

紧急插入不可嵌套：同一时刻至多一个冻结话题。紧急话题执行中再次触发 interrupt 时，新紧急话题插入当前紧急话题之后，按队列顺序执行（仍是队列语义，非抢占）——这把"队列而非调用栈"的性质锁死在操作定义里（见不变量二）。

### 4.3 干预的触发与分级

不是所有队列操作都在同一门槛下触发。意识系统的设计区分**轻量干预**和**重量干预**（详见 [意识系统设计 §2.2](consciousness-system.md#22-轻量干预与重量干预)）：

|                | 轻量干预                          | 重量干预                                |
| -------------- | --------------------------------- | --------------------------------------- |
| **干预方式**   | 向主线提示词注入策略建议          | 调整话题队列（插入/取消/重排/深度切换） |
| **触发门槛**   | 低——本轮对话即可判断              | 高——需要跨轮累积证据                    |
| **生效时机**   | 下一轮                            | 可能多轮积累后产出判断                  |
| **典型发起者** | `process_quality`（流程质量监测） | `strategy_adaptation`（策略调适）       |

队列操作（插入、取消、重排、深度切换、紧急度调整）属于重量干预——不轻易触发。主线绝大多数时间在"低头执行"当前话题的 Action 序列，意识层在后台积累证据，累积到阈值才出手调整队列。

### 4.4 调整后的队列一致性

队列被修改后，主线引擎在**下一个话题开始前**感知到变化——当前话题执行中不受影响。这保证了调整的"无干扰性"：即使意识层决定取消当前话题的下一个兄弟话题，当前话题的 Action 序列仍然完整执行完毕。

## 5. Action 类型边界判断：如何决定一个动作是否独立成类型

### 5.1 问题

随着咨询领域扩展，新的交互形式会被需要——"角色扮演"、"家庭作业布置"、"正念引导"、"空椅对话"——每一个似乎都可以成为一种 Action 类型。又或者，像我们一开始讨论的：为什么不把所有 Action 合并成一个通用 `task`，用一个 `mode` 参数区分？

这需要一个**系统性的判断方法**——不是依赖直觉，而是基于可追溯、可辩论的标准。

### 5.2 四步判断法

#### 第一步：领域性测试

**问题**：这个区分来自咨询师对对话动作的自然命名，还是来自工程实现的差异？

**判断**：请一位非技术的咨询师描述 ta 的会谈过程。ta 会不会自然地说出这个动作的名字？

- 咨询师自然会说"这里我问ta一个问题"、"这里我告诉ta一个概念"、"这里我自己分析一下" → `ai_ask`、`ai_say`、`ai_think` 通过
- 咨询师不会说"这里我做一个信息收集任务" → "信息收集"是工程师从数据流倒推的抽象，不通过

**依据**：[P2 不暴露工程问题](script-engine-design-principles.md#原则二不暴露工程问题no-engineering-concerns-exposed) — "DSL 中的每一个语法、每一个配置项，都必须来自咨询领域的自然问题"。

**反例**：如果把 `ai_ask` 和 `ai_fill` 合并为一个"信息收集类 Action"——这是从"都产出变量"这个工程视角做的抽象，不是咨询师的体验。咨询师不会说"我收集一下信息"，ta 会说"我问ta几个问题"或"我让ta填这个量表"——它们是咨询室里两种不同的动作。

#### 第二步：咨询师体验测试

**问题**：咨询师在规划会谈时，能否自然地用已有类型名来指代这个动作？

**判断**：如果咨询师认为"这里我就是告诉ta（ai_say）"——那就不需要新类型。如果咨询师说"这里我做的是XX，叫 ai_say 不准确"——那 XX 值得考虑成为独立类型。

**示例**：

- "这里我让他画出来" → 用 `ai_say` 不自然（"说"和"画"是不同的输出形式），但用 `ai_draw` 自然 → 通过
- "这里我让他角色扮演" → 用 `ai_ask` 不自然（不是"问"，是"演"），用 `ai_say` 也不自然 → 候选新类型 `ai_roleplay`

**注意**：这一步只判断"已有类型能否自然表达"，不直接决定"一定需要新类型"。通过第二步只意味着进入第三步。

#### 第三步：行为差异测试

**问题**：候选类型的运行时行为是否与已有类型有本质差异？

**判断标准**：以下四个维度至少有一个不同，才算本质差异：

| 维度             | 含义                                                    | 示例                                                                          |
| ---------------- | ------------------------------------------------------- | ----------------------------------------------------------------------------- |
| **用户交互模式** | 用户如何参与？等待输入？主动输出？无感知？              | `ai_ask` 等待用户输入；`ai_say` 不等待；`ai_think` 无用户感知                 |
| **变量交互方式** | 从变量池读取什么？写入什么？                            | `ai_ask` 写入新变量；`ai_think` 读取变量并写入新结论；`ai_say` 只读变量       |
| **推进逻辑**     | 如何进入下一个 Action？自动推进？等用户？等待条件满足？ | `ai_ask` 等输入 + exit_condition；`ai_say` 自动推进；`ai_fill` 等表单校验通过 |
| **监控需求**     | 是否需要独立的 Monitor 线程？                           | `ai_ask` 可能需要（检查回答质量）；`ai_say` 通常不需要                        |

如果四个维度全部与已有类型相同——那就是同一个东西，不应独立。

**示例**：`ai_draw` 和 `ai_say`

- 用户交互模式：相同（都是主动输出，不等待用户输入）
- 变量交互方式：相同（都只读变量）
- 推进逻辑：相同（都自动推进）
- 监控需求：相同（都通常不需要 Monitor）

→ 四维度全部相同。`ai_draw` 不值得成为独立类型，它可以是 `ai_say` 的一个呈现参数（如 `format: visual`）。

反例：`ai_fill` 和 `ai_ask`

- 用户交互模式：**不同**（ai_ask 是自然语言对话，ai_fill 是结构化表单）
- 变量交互方式：**不同**（ai_ask 提取自由文本中的变量，ai_fill 直接映射表单字段到变量）
- 推进逻辑：**不同**（ai_ask 是退出条件判断，ai_fill 是表单校验通过）
- 监控需求：相同

→ 三个维度不同。`ai_fill` 值得成为独立类型。

#### 第四步：U 路径测试

**问题**：候选类型是否走过一条本质上不同的 U 型思维路径？

**判断**：回顾每个 Action 类型的 U 型转换方向：

| Action 类型 | U 路径方向                                        | 抽象压缩的内容                         |
| ----------- | ------------------------------------------------- | -------------------------------------- |
| `ai_ask`    | 用户具体回答 → 领域抽象 → 专业追问策略 → 具体提问 | 从用户回答中抽象出信息缺口             |
| `ai_think`  | 累积变量 → 分析框架 → 诊断策略 → 结构化结论       | 从跨轮信息中抽象出模式                 |
| `ai_say`    | 专业知识 + 变量 → 个性化表达策略 → 具体回应       | 从专业知识中抽象出适合这个人的表达方式 |

如果候选类型的 U 路径与已有类型**完全相同**（只是提示词的措辞不同），它不应是独立类型。

**示例**：假设有人提议 `ai_explain`（解释概念）作为独立类型。它的 U 路径是"专业知识 → 表达策略 → 具体解释"——与 `ai_say` 完全相同。它只是 `ai_say` 的一种提示词变体，不应独立。

反例：`ai_fill` 的 U 路径是"表单设计知识 + 用户信息 → 字段适配策略 → 引导式填写"——这与 `ai_ask` 的"用户回答 → 信息缺口 → 追问"是不同的抽象方向。通过。

### 5.3 决策流程图

```
提议新 Action 类型 X
    │
    ▼
第一步：领域性测试
    ├── X 来自工程师的数据流抽象，而非咨询师的动作命名？ → ❌ 不独立
    │
    ▼
第二步：咨询师体验测试
    ├── 咨询师能自然用已有类型名指代 X？ → ❌ 不需要新类型
    │
    ▼
第三步：行为差异测试
    ├── 与最接近的已有类型相比，四个维度全相同？ → ❌ 合并为一个类型 + 参数
    │
    ▼
第四步：U 路径测试
    ├── U 路径与已有类型完全相同？ → ❌ 只是已有类型的提示词变体
    │
    ▼
    ✅ X 成为独立 Action 类型（标记 experimental，观察后决定是否转 stable）
```

### 5.4 现有类型的评审

用这个框架回看现有的五种类型：

| Action     |    第一步：领域性     | 第二步：已有类型能指代？ | 第三步：行为差异 | 第四步：U 路径不同？ | 结论                                             |
| ---------- | :-------------------: | :----------------------: | :--------------: | :------------------: | ------------------------------------------------ |
| `ai_ask`   |          ✅           |            —             |       基准       |         基准         | 核心类型                                         |
| `ai_say`   |          ✅           |            —             |       基准       |         基准         | 核心类型                                         |
| `ai_think` |          ✅           |            —             |       基准       |         基准         | 核心类型                                         |
| `ai_draw`  | ⚠️ 咨询师会说"画出来" |   `ai_say` 可能自然？    |     全部相同     |         相同         | **待评审**：倾向于降为 `ai_say` 的 `format` 参数 |
| `ai_fill`  |   ✅ 咨询师说"填表"   |     `ai_ask` 不自然      |    三维度不同    |         不同         | **保留**：行为差异显著                           |

`ai_draw` 是一个边界案例——咨询师确实会说"画"，但运行时行为与 `ai_say` 无本质差异。如果未来的可视化能力变得复杂（需要选择图表类型、等待用户交互式探索），它可能重新获得独立类型的资格。现在标记为 **review**，让使用数据说话。

### 5.5 不使用反证法

以上四步是**正证法**——提议新类型的人需要证明它值得独立。

我们不使用**反证法**（"只要找不到不独立的理由，就可以独立"），因为反证法会导致类型膨胀——任何微小的差异都可以被主张为"找不到不独立的明确理由"。正证法把举证责任放在提议方：你必须证明新类型的领域性、不可替代性、行为差异性和 U 路径独特性。

这与 [TDD式渐进规则化](heartrule-design-philosophy-v2.md#33-八大显式设计原则) 的原则一致：不要预先设计完美的类型分类体系，只在现有类型**无法自然表达**某个咨询动作时，才增加新类型。

## 附录 A：话题队列操作的优先级规则

当多个队列操作同时被触发时（例如时间压力触发重排，同时又检测到需要紧急插入），按以下优先级执行：

1. **紧急插入（interrupt）** — 安全相关，最高优先级
2. **取消（cancel）** — 避免无效工作
3. **深度切换（depth）** — 影响后续操作的预估时间
4. **插入（insert）** — 在重排之前确定队列内容
5. **紧急度调整（urgency） + 重排（reorder）** — 在内容确定后调整顺序

## 附录 B：话题的生命周期

```
[脚本声明] → [展开] → [入队] → [等待] → [激活] → [执行中] → [完成]
                ↑                    │          │
                │                    │          │
             expand_by           [取消]    [冻结/恢复]
          动态生成多个               │          │
          队列条目               从队列移除   紧急插入时
                                           临时挂起
```

- **展开**：expand_by 声明的 Topic 在列表变量就绪时展开为多个具体条目（变量若依赖会谈中的提取，展开相应延迟，见 §3.2）
- **入队**：进入话题队列，按紧急度和声明顺序排列
- **等待**：在队列中等待前面的 Topic 执行完毕
- **激活**：成为队首，主线引擎开始执行其 Action 序列
- **执行中**：Action 序列逐个执行。此状态下的 Topic 不受队列重排影响（只影响后续 Topic）
- **完成**：所有 Action 执行完毕，出队
- **取消**：从队列移除（仅可取消尚未激活的 Topic）
- **冻结/恢复**：紧急插入时，当前执行中的 Topic 被冻结；紧急话题完成后恢复。冻结不可叠加——同一时刻至多一个冻结话题（见 §4.2）
