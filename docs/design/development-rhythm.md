# HeartRule 开发节奏系统

> 本文档约束**我们怎么一起工作**：四个方法的分工与咬合、一次工作的端到端走法、什么时候与 AI 讨论、讨论后产出什么、哪些必须人审。
>
> 一句话：**DDD 管平台侧建模，专家系统建模管引擎侧建模，Scrum 管需求与计划，spec-driven 管执行与验证。**

## 1. 起源

2026-08-14 诊断出开发节奏失控，症状四条：

- 21 个 commit 堆在本地未推送——**没有终点**
- 设计文档膨胀至 85KB 仍在"完善中"——**没有封板**
- 没有 backlog / sprint 计划 / DoD 检查点——**没有节奏标记**
- 引擎"智能实现思路"的讨论没有专门位置，泄漏进设计文档和 sprint 工作

本文档用四个方法的分工解决以上问题。它是**活文档**，按 §10 演进规则演进。

## 2. 概念关系：四个方法

四个方法**不是平行层，是各管一摊**：

| 方法                                   | 管什么             | 步骤 / 单位                                            | 文档路径                               | 完成态                                          |
| -------------------------------------- | ------------------ | ------------------------------------------------------ | -------------------------------------- | ----------------------------------------------- |
| **DDD**                                | 平台侧领域怎么建模 | 事件风暴(按需) → 战略设计(边界/UL) → 战术设计(聚合/VO) | `docs/ddd/` + `docs/design/` UL / 代码 | 战略文档 `decision-recorded`；战术设计落进 spec |
| **专家系统建模**（本体驱动，案例验证） | 引擎智能怎么建模   | 本体先行 → 机制设计 → 案例验证（§8）                   | `docs/design/` 机制文档 + ADR          | 收敛为 机制文档/ADR/spec/story（§8）            |
| **Scrum**                              | 什么时候交付什么   | story 为交付单位，sprint 为节奏                        | `docs/scrum/`                          | 故事级 DoD 勾选（§5）                           |
| **spec-driven**（superpowers）         | 单个故事怎么做     | 头脑风暴 → spec → plan → TDD                           | `docs/superpowers/specs` + `plans/`    | 验收通过的故事                                  |

**接缝关系**（四个方法怎么咬合，这是关键）：

- **spec 是 DDD 战术设计的落点**：不碰限界上下文边界 → spec 本身就是战术设计；碰边界（新限界上下文、新通用语言、改上下文关系）→ 先做战略设计（更新 `docs/ddd/` + UL），再写 spec。
- **plan 与 sprint-plan 不是一回事**：plan 是 spec-driven 的产物（一个故事怎么实现的步骤清单）；sprint-plan 是 Scrum 的产物（一周排哪些故事）。名字里都有 plan，但 plan 管故事内部，sprint-plan 管一周。
- **story 是 Scrum ↔ spec-driven 的接缝**：sprint 选故事（Scrum），故事被认领后走 spec-driven。分工一句话——**story 管范围，spec 管设计，plan 管步骤**。
- **专家系统建模的接缝 = 机制文档 → story → spec**：引擎智能的 epic 先进专家系统建模（§8），机制文档成熟后拆成 story 进 backlog/sprint，story 走六步时战术设计进 spec；关键决策经 ADR 进决策库。机制讨论每次必须收敛，不允许无产出结束（§8）。

> **两条流分离**：平台业务（用户、会话、脚本管理）走 DDD **轻量建模**；引擎智能（意识、记忆、recall、干预策略）走**专家系统建模**（§8）。引擎机制是"我们在设计什么"（智能的实现方式），不是"我们怎么工作"——它进 `docs/design/` 存放，与地图层的领域建模、设计哲学混居，层归属见 [README 索引](README.md)。这是 HeartRule 与普通业务系统最不一样的地方。

## 3. 需求流与路由

**需求流三分类**（每个 epic / story 先分三类；这是三分类的单一出处）：

- **平台级 · 咨询内容类**——具体咨询域的需求（如抑郁概念化的要求）→ 直接 YAML scripts + templates 实现，无需新机制；
- **平台级 · 功能类**——平台功能需求（人类咨询师审核咨询过程、看咨询笔记、干预咨询计划）→ 常规 DDD 开发；
- **引擎级**——需要引擎新能力（"咨询师会谈中能觉察信号并调整议程"）→ 专家系统建模（§8）。

**路由表**（一次典型工作的端到端走法；每一行的产出物与落点展开在 §4 表）：

| 节点              | 一行做法                                                           | 详见              |
| ----------------- | ------------------------------------------------------------------ | ----------------- |
| 提出意图          | 一句话 + 价值，随时可提、不急着拆（新 session 开工是常见时机）     | §4 表 · §5 意图区 |
| 拆解意图          | 拆成 epic（组名 + 一句话）写进 backlog，标注来源意图               | §4 表 · §5        |
| 需求判断          | 每个 epic / story 先分三类                                         | 本表上方          |
| 平台侧建模        | 事件风暴（按需）→ 战略设计 → context map + UL                      | §6                |
| 引擎侧建模        | 任务层找锚 → 补本体 → 机制设计 → 案例验证                          | §8                |
| 拆 story          | sprint 计划时按目标从 epic 拆本周要做的；每个 = 一个可见增量 + DoD | §5                |
| 每个 story 走六步 | 领域概念检查 → 头脑风暴 → spec → plan → 实现 → 验收                | §7                |

> 这些节点不是瀑布——第 4/5 行的"边界/规则"是草稿，允许反悔（贵的晚拍板，§6）；最后三行常常交织。

## 4. 人机协同协议

单人 + AI 协同开发的核心问题：**什么时候找 AI 讨论、讨论后生成什么、哪些必须由人审核**。

| 阶段                   | 何时与 AI 讨论            | 产出物（落点）                                                              | 人审什么                                           |
| ---------------------- | ------------------------- | --------------------------------------------------------------------------- | -------------------------------------------------- |
| 提出意图               | 新 session 开始、灵感浮现 | 意图一句话 + 价值（确认后写进 backlog 意图区）                              | 确认意图与价值                                     |
| 拆解意图               | 意图确认后                | epic 划分（组名 + 一句话）写进 backlog，标注来源意图                        | 确认 epic 划分（内聚、不重不漏）                   |
| 需求判断               | 需求冒出来，分不清三类    | epic 分类（§3 三分类）+ backlog 条目                                        | 确认归类与用户价值                                 |
| 平台侧事件风暴         | 遇到新咨询域/新边界       | 事件/命令/聚合草图 → context map + UL                                       | 边界和术语由你（领域专家）定                       |
| 本体先行（任务层分解） | 引擎级需求确认后          | 任务层条目（新任务 + 分解）写进 `docs/design/ontology.md`                   | 任务分解符合咨询实践（任务锚）                     |
| 引擎侧机制设计         | 本体/任务层出现新任务缺口 | 机制设计草稿（触发/判断/干预）                                              | 机制是否真捕获咨询智慧                             |
| 案例验证               | 机制设计成型，要验证      | 验证对话片段 + 验收结论（§8）                                               | 案例合理性、验收结论                               |
| 战略设计               | 边界画完，要定上下文关系  | `docs/ddd/` 战略文档 / UL 更新                                              | 这是咨询智慧的封装                                 |
| 拆 story               | 设计成型，要切交付        | backlog 故事 + DoD                                                          | 确认增量可见、DoD 合理                             |
| 领域概念检查           | 每个 story 头脑风暴前     | 概念清单 + 缺口报告（domain-check）                                         | 确认概念准确、补缺失定义                           |
| 头脑风暴               | 认领 story 后             | brainstorm 笔记（场景/触发/边界/关系/约束）                                 | 业务规则正确                                       |
| 写 Spec                | brainstorm 后             | spec（领域模型片段 + 正负例 + 审查清单）                                    | 领域模型片段与你的意图一致                         |
| 写 Plan                | spec 通过后               | plan（实现步骤，不新增领域建模）                                            | 不违反架构约束                                     |
| 实现与测试             | plan 通过后               | 代码 + 测试 + DDD 合规自查报告                                              | **抽查**：报告新增项（机械项 AI 查，语义项你抽查） |
| 验收                   | 实现后                    | 验收报告（平台 GWT / 引擎案例对话）                                         | 最终验收，决定是否合并                             |
| 节奏回顾               | 每 sprint 末              | sprint-plan 四行小结（计划 vs 实际 / 目标达成与下周方向 / 故事粒度 / 堵点） | 判断流程是否调整                                   |
| 持续治理               | 持续                      | ADR / 约束清单 / 案例库 / backlog 维护（各见 §5/§6/§8）                     | 批准 ADR 与领域模型变化                            |

> 除标注外默认全人审——只有「实现与测试」是抽查。

**不可委托给 AI（必须你拍板）**：咨询伦理判断（如危机干预策略）、领域边界的最终划分、架构风格的最终选择、业务规则的最终解释、通用语言的定义。**核心原则**：审核门落在**"人类咨询智慧被建模"的地方**，不落在"代码能不能跑"的地方——代码能不能跑由测试验证；人要审的是 AI 无法自己验证的领域判断：边界画对没、术语是不是咨询师真用的词、机制是否真捕获了咨询智慧、spec 是否忠实于意图。**你是咨询智慧的来源，所以审的是"建模是否忠实"，不是"实现是否可行"。**

**AI 可自动审核（出报告，不需你介入）**：代码与 Spec 一致性（测试）、DDD 合规自查（新增概念/接口、UL 对照、约束违反、层依赖变化）、文档格式与引用规范、测试覆盖率达标。

**产出物规则（住所）**：每个产出物必须写明**下一个读者与住所**——谁读它、在哪个时刻读、到哪去找。写不出下一个读者的产出物不生产；有下一个读者而没有住所的产出物是流程泄漏点。判断"这个产出物落哪"：先找下一个读者（例：意图的下一个读者是 sprint 计划），再定住所（→ backlog 意图区）。（另一条产出物规则管收敛，在 §8。）

## 5. 时钟：轻量 Scrum

**节奏**：每周一个 sprint（兼职节奏，先跑着，以后可调）。**仪式只有 sprint 计划**（先看活跃意图/epic 定目标 → 从 backlog 选故事 → 定每故事 DoD）。不设 review/retro 仪式——增量检验靠每故事验收（§7），方向判断靠 sprint 末四行小结。

**载体**：

- `docs/scrum/backlog.md` — 产品待办（需求池）。顶部**意图区**登记意图一句话 + 价值 + 状态（`活跃`/`未拆`/`已拆成 epic`/`放弃`）：拆不出 epic 的模糊意图先进意图区（状态=未拆），想清楚了再拆；连一句话都写不出的才留在对话里；拆成 epic 时标注来源意图。下方按 epic 分组（epic = 组名 + 一句话），同一条主线上的故事放一组、组间少依赖（§12 借入的按内聚分组）。**随时可加**（标注来源），维护动作是排序和清理失去价值的条目（含意图区），不设时间窗口。
- `docs/scrum/sprint-plan.md` — 当前 sprint。sprint 目标（从意图区的活跃意图中选，写成**结果句**——本周结束时可验证的状态，如"记忆系统全绿 + 两条文档封板"）、选中的故事清单（含 DoD）、状态。每次 sprint 覆盖，旧计划留在 git 历史；sprint 末填四行节奏小结。

**Story 来源**（写 backlog 时标注来源）：

| 来源              | 说明                                      | 示例                                   |
| ----------------- | ----------------------------------------- | -------------------------------------- |
| 引擎智能点        | 本体/任务层缺口推导的智能点，按复杂度拆分 | 「情绪否定检测」→ 意识触发 story       |
| 平台功能          | 平台侧领域建模识别的功能点                | 「转人工」流程                         |
| 架构演进需求      | 架构检查或回顾中发现的调整需求            | 统一反馈通道缺失 → 补 story            |
| 领域模型/本体调整 | 模型调整后需要落地的新概念                | 本体缺「阻抗」→ 补本体并更新 YAML 模板 |

**故事类型与 DoD**（DoD 即流程分叉）：

| 故事类型         | DoD                                                                                    | 走法                                                                                                        |
| ---------------- | -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `[feature]`      | 测试通过 + lint/typecheck 通过 + commit + push + sprint-plan 标记 done                 | 完整六步（§7）                                                                                              |
| `[intelligence]` | 收敛出 机制文档 / ADR / spec / backlog 故事 + 拆出的实现故事进 backlog + commit + push | 机制**未定型**的设计故事：第 1 步（领域概念检查）后按 §8 做机制设计讨论；机制定案后拆出的实现故事走完整六步 |
| `[design]`       | 文档达到 `decision-recorded`（必要时追加 ADR）+ commit + push                          | 不走六步：一致性检查（文档概念与 UL/本体对得上）→ 关键决策补 ADR → 封板                                     |

**故事粒度**：一个故事应在 1–2 个会话内完成；引擎智能点故事还应自带验证对话片段（§8）。若某工作"需要先写一篇大设计"，它本质是战略设计议题，先走 §3 路由，产出决策后再拆成小故事。

## 6. 地图：DDD（平台侧，轻量建模）

**适用面**：DDD 用于平台侧（用户、会话、脚本管理）——传统业务，轻量建模。引擎智能的**建模**不走 DDD 事件风暴，走专家系统建模（§8）；但引擎机制的**实现代码**仍守 DDD 结构纪律——限界上下文、端口、战术设计照样进 spec。

**事件风暴是发现手段**：遇到新咨询域 / 新边界时，AI 辅助枚举「领域事件 → 命令 → 聚合 → 限界上下文」，产出 context map + UL。它是**按需工具**——平台业务简单时可极简甚至跳过，不是必做仪式。

**战略 vs 战术的分界 = 可逆性**：战略（限界上下文、上下文映射、通用语言）改起来贵——代码和团队一旦围着边界建起来，重画边界极贵；战术（聚合、实体、值对象、领域服务）改起来便宜——单个聚合内部重构不动边界。**贵的晚拍板、便宜的随手做。** 战略设计不追求一次性完成——每次调整后立即更新领域文档，不攒着；架构是**渐进涌现**的。

**状态语义**（每篇设计文档 frontmatter 的 `status`）：

| 状态                | 含义                                                          |
| ------------------- | ------------------------------------------------------------- |
| `draft`             | 尚未验证，正在成形                                            |
| `active`            | 正在被实现/使用的活文档                                       |
| `decision-recorded` | 关键决策已记录（ADR），封板；仅当实现或新证据与之矛盾时才修订 |
| `superseded`        | 被其他文档取代                                                |

**封板规则**：文档在关键决策落入 ADR 后，`active` → `decision-recorded`，**停止积累**——不再往里加内容；新想法另起 ADR / 新文档 / backlog 探索项。修订是**证据驱动**的：实现碰壁、e2e 暴露问题、或领域理解深化时才打开修订，改完重新封板。

**载体与治理**：战略设计 → `docs/ddd/`；领域建模 → `docs/design/`；ADR → `docs/design/decisions/`（AI 生成草案，你批准；批准后更新约束清单）。**架构约束清单**（`docs/design/architecture-constraints.md`，首次需要时创建）：不可违反的红线（平台 DDD + 引擎机制不变量，如"意识是唯一队列修改者"），是 §7 第 5 步自查报告的**检查依据**。它出身两条：渐进规则化（约束清单是补丁落点）+ AI 每次开工是新上下文，需要机器可查的红线。

> `docs/design/` 是**混层目录**——机制文档（引擎机制）与领域建模（地图层）并存，层归属以 [README 索引](README.md) 的「层」列为准；顶层文档超过 20 篇时按「层」列物理拆分子目录。README 维护状态总表，是地图的"一页视图"。

## 7. 施工队：spec-driven（单故事六步流程）

每个 story 按六步走（superpowers 流程 + HeartRule 自己的两层约定：领域概念检查、DDD 合规自查）。**战术设计在 Spec 阶段完成，Plan 阶段不做领域建模。** superpowers 本身不含这两步门禁，靠本文档约定生效。故事类型分叉见 §5。

1. **领域概念检查**（头脑风暴前）——AI 列出 story 涉及的领域概念：这些概念叫什么、在 UL/本体里吗、属于哪个限界上下文、关系是否已定义。发现缺失或冲突 → **按概念归属补齐**：代码概念补 UL，咨询知识概念走本体（§8），只有边界或上下文关系变化才触发战略设计调整；更新领域文档后再继续。→ 产出 `domain-check`，落 `docs/superpowers/domain-checks/`（草稿纸不是约定，定期清理）。
2. **头脑风暴**（需求澄清，非领域建模）——澄清：用户场景、触发信号（**正例+负例**）、边界条件、与现有概念的关系、需要新增的架构约束。
3. **写 Spec**——功能描述 + 验收标准（Given-When-Then，**必须含正例和负例**）+ 数据模型 + 接口定义 + **领域模型片段（DDD 战术设计落点）** + 异常处理 + **人工审查清单**（验收时逐项打勾）。
4. **写 Plan**——实现步骤 + 测试计划。**不新增领域建模决策**；发现需要调整领域模型 → 回 Spec 改。
5. **实现与测试**——AI 生成代码 + 测试 + 运行 + 修复 + **DDD 合规自查报告**（对照 §6 架构约束清单：新增概念/接口、UL 对照、约束违反、层依赖变化）。机械项 AI 自查可靠；语义项（换马甲另起炉灶）不可靠——你抽查报告里的新增项。
6. **验收与记录**——分两类：**平台故事**对照 Spec 验收标准（GWT）逐项勾完；**引擎故事**用案例对话验证。验证片段存入测试案例库（§8）。

**规格落点**：spec → `docs/superpowers/specs/`，plan → `docs/superpowers/plans/`（已有先例），domain-check → `docs/superpowers/domain-checks/`。

## 8. 引擎机制：专家系统建模（本体驱动，案例验证）

**HeartRule 的本质**：把人类咨询智慧（咨询师怎么问、怎么觉察、怎么调整议程）建模成 LLM + 脚本能执行的机制。所以开发过程会不断讨论**具体智能的实现方式**——记忆怎么调取、意识怎么触发、话题队列怎么动态调整。

**为什么单列一节**：这类机制设计**不适合 DDD 事件风暴，也不适合 spec-driven 头脑风暴**——那两者假设你在"探索业务领域 / 发现需求"，而机制设计是在"设计智能的实现方式"。对象不同，需要单独的位置与纪律。

**方法：本体先行 → 机制设计 → 案例验证**（本体为主，案例为辅）。

1. **本体先行**——先建知识模型再写代码，三层骨架（取自 CommonKADS，不照搬全理论）：
   - **任务层**：咨询师在会谈中要完成什么任务、怎么分解——主线思维、意图思维、话题队列都在这一层。**新智能点从任务层的缺口来**：任务层拆出一个新任务，才有对应的 story。
   - **领域层（本体）**：任务涉及的概念及其关系（如"阻抗""情绪否定"与话题、意识的关系），与平台侧 UL 分别维护——本体概念变成代码里的类名、枚举、字段时，在 UL 登记一行（指向本体文档）。**这是 UL 登记的单一出处。**
   - **推理层**：任务怎么用概念做判断——触发判断、议程调整判断。
   - > 名实说明："本体先行"指**知识模型先行**，三层的第一层就是任务层——所以落到操作上是**先到任务层找锚**：新任务挂到已有任务，挂不上先补任务层条目，再补领域层概念、设计机制。
2. **机制设计**——用认知任务分析拆解"咨询师做这个任务时需要哪些判断"，提炼成机制：触发条件、判断依据、干预方式；结构化为参数（冷却时间、上下文窗口、干预模式等）。
3. **案例验证**——用模拟/真实对话片段验证机制是否真捕获了咨询智慧。案例以本体推演为主、启发为辅：默认从任务缺口来，案例在验收处必出现、在启发处可有可无；偶尔先遇到一个真实案例，顺着它提炼任务补进本体，不算犯规。**验证案例可由 AI 起草模拟对话**（AI 的强项），你确认合理性后使用（单一出处）。

**本体维护纪律**：**任务锚**——每个新词都回答"哪个任务需要它"，写不出来就是造词，不进；**复用优先**——引入成熟机制（RAG、知识图谱等）时先找现成的，不从零造。

**架构渐进涌现**：意识系统、记忆框架等核心架构**不是一次性设计完成**，而是在开发具体智能点的过程中逐步抽象和固化（"贵的晚拍板"，§6，在引擎侧的具体形态）。

**推翻前先看清现状**：要推翻或大改已有机制时，AI 先把现有实现整理成两份说明——**静态**（有哪些组件、各自干什么、怎么关联）和**动态**（关键场景里组件怎么交互），你验证说明正确后再动手改（§12 借入的棕地实践）。

**可追溯性闸门**：每个机制文档开头必须写清它服务的**引擎级业务需求**（一句话用户价值）——"这个机制让谁在什么场景得到什么价值"。写不出来说明没有需求锚点，是技术自嗨，不写。需求先按 §3 三分类归类，只有引擎级由机制承载——机制文档回答"怎么做"，锚定的业务需求回答"要什么"。

**产出物规则（收敛）**：机制讨论**事件驱动**——讨论不排期（灵感随时开），但**产出物受排期约束**：收敛出的实现 story 一律进 backlog，由 sprint 计划定进本周还是下周，不许"讨论顺手就把活干了"。每次讨论必须收敛为以下之一（落点即载体；其中机制文档/ADR/spec/backlog 故事即习惯所称"四选一"，加上本体文档共五种落点）：

1. **本体文档更新**——讨论补了任务层/领域层/推理层条目 → `docs/design/ontology.md`；
2. **机制设计文档**——思路是引擎实现机制（如记忆调取、意识触发、队列调整）→ `docs/design/` 对应文档（锚定引擎级业务需求）；
3. **ADR**——关键决策已定 → `docs/design/decisions/`；
4. **spec**——思路已成型、可交付实现 → `docs/superpowers/specs/`：锚（一句话价值 + 任务锚）写进 spec 开头，机制说明写进 spec 的设计段落；同一机制复用出第二个场景时，必须提炼回机制文档；
5. **backlog 故事**——思路还需实施 → `[intelligence]` 故事进 backlog。

若一次讨论无法收敛，明确标记为 backlog「智能设计议题」下的**探索项**（exploration item），注明未决问题，下次继续——不允许"无产出地聊到哪算哪"。

**机制的归宿**：机制文档成熟后（**成熟 = 案例验证通过 + 你确认可拆**），拆成 `[feature]` 故事流入时钟层（backlog → sprint），由 sprint 计划排期；实现中再冒出未定型的机制，另开 `[intelligence]` 设计故事，不让实现故事边做边设计。机制设计不是终点——流入 backlog 才是。

**测试案例库 = 一等公民**：每个智能点 story 验收时把验证对话片段存入 `packages/core-engine/test/`（如 `eval/`、`integration/`），作为回归测试核心资产**持续运行**——每次改引擎代码后跑一遍，确保没有回归。它是领域专家知识的沉淀，与 Spec 并列管理。平台故事验收走 GWT 勾选（§7 第 6 步）。

## 9. 每会话开工约定

Claude Code 在 HeartRule 仓库启动会话时：

1. **先看 `docs/scrum/sprint-plan.md` 和 `docs/scrum/backlog.md`**——知道当前 sprint 做什么、哪些故事 in-progress、池子里有什么；**你有新意图就直接提**，AI 协助写进 backlog 意图区，想清楚了再拆成 epic（§4 表）；然后**主动提出本会话的工作计划草案**（做什么、按什么顺序、预计产出），你批准后再动手（§12 借入的 AI 主动提案）。
2. **若涉及设计**，查 `docs/design/README.md` 确认相关文档状态，遵守封板规则（§6）。
3. **若涉及引擎机制**，按 §8 收敛规则执行，产出物必须落地。
4. **人机分工**：参照 §4 协议——AI 生成，人审关键建模决策。

人类侧同样：开工前扫一眼 sprint-plan；做完一个故事主动触发 DoD 检查；AI 生成的 spec/机制文档在落库前由人审核。

## 10. 演进规则

本文档自身按**渐进规则化**（Progressive Rulification）演进：

- 让流程先宽松运行，在**反复出问题的地方**加一条明确规则；
- 规则被证明多余时删掉；
- **季度体检（不是仪式）**：每季度回顾一次本节奏系统是否还适配——审的是**本文档自身**（这套约定还适不适合项目），不是产品增量，也不是某个 sprint 的协作。你哪天想起来了和 AI 聊一次，产出修订建议。

## 11. 示例迭代：「情绪否定检测」意识

以"情绪否定检测"为例走一遍完整流程。

**来源**：本体/任务层缺口推导的引擎智能点，拆为两个 story——Story A：意识配置的 YAML 解析（spec + plan 落 `docs/superpowers/`）；Story B：`emotion_negation_detect` 触发逻辑。

**Story A 六步**：领域概念检查发现 `ConsciousnessDefinition` 无定义（代码概念）→ 补 UL；头脑风暴澄清 YAML 字段与 Phase/Topic 绑定；Spec 含 YAML 示例、解析规则、领域模型片段（`ConsciousnessDefinition` 值对象）、正例（合法配置）+ 负例（缺必要字段）；Plan 列解析器文件、Schema 校验、测试用例；实现出解析代码 + 单元测试 + DDD 合规自查报告（你抽查新增项）；验收对照 GWT 逐项勾完。

**Story B**（六步同构，略）：正例「用户说'其实也没什么'→触发」、负例「'我觉得有点难过'→不触发」；验收用案例对话——模拟新对话发现误触发 → 回 Spec 调整阈值，验证片段入库。

**迭代回顾**：发现"情绪否定"与"阻抗"概念边界模糊 → 触发本体修订，在本体中重新划定二者边界（已列入 [ontology](ontology.md) 开放问题）。

## 12. 外部参照：AI-DLC 与借入机制

AI-DLC（AI 驱动开发生命周期，AWS 的 AI 原生开发方法论）全文见 `docs/reference/AI驱动开发生命周期（AI-DLC）方法定义.md`。本文档**不整体采用**它，只借入几条适用的机制。

**为什么只是参照，不是底座**：AI-DLC 管的是"用 AI 建软件"（多团队 × 企业场景），管不了"建 AI 产品"——引擎智能怎么建模（§8）在它里面没有对应物。它的团队仪式（mob 推演、PRFAQ）、改名（Sprint → Bolt）和运维阶段，对单人 + AI 没有增益，不采用。

**借入的三条**（各一行，落点即本表）：

1. **意图 → epic → story 拆解链**（§3、§5）——AI-DLC 的 Intent → Unit → Bolt 简化版；借它的划分规则：**按"内聚"分组，不按"进度"分组**——同一条智能主线上的故事（如记忆收尾 + 封板）天然一组。
2. **AI 主动提案**（§9）——AI-DLC 的"反转对话"在单人场景的落地形式：每次开工 AI 先读 sprint-plan 和 backlog，再主动提出工作计划草案，你批准后动手，而不是等你逐条下指令。
3. **大改前先整理现状**（§8）——AI-DLC 的棕地实践：改现有系统前先把代码整理成静态/动态两份说明，人验证后再动手；对"迭代中推翻智能实现"特别有用。

**评估过、不借的一条**：人在决策节点把关（AI-DLC 叫"人类监督 = 损失函数"）——与 §4 核心原则（审核门落在"人类咨询智慧被建模"的地方）是同一回事，本文档已有更细的落地（协议表 + 人工审查清单），不重复引入。

> 维护规则：借入的机制必须是在本项目跑得起来的规则，不接受"听起来高级但用不上"的概念。某条借入机制被证明没用，按 §10 演进规则删掉。
