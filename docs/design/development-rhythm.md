# HeartRule 开发节奏系统

> 本文档是 HeartRule 项目的人类 + AI 协同工作约定。它约束**我们怎么一起工作**：DDD / Scrum / spec-driven 三者的关系、一次典型工作的端到端走法、什么时候与 AI 讨论、讨论后产出什么、哪些需要人审核。
>
> 一句话：**DDD 管内容、Scrum 管时间、spec-driven 管方法；引擎机制是独立的内容流（专家系统建模），讨论产出物驱动。**

## 1. 起源

2026-08-14 的会话中诊断出项目开发节奏失控，症状：

- 21 个 commit 堆在本地未推送——**没有终点**
- 设计文档膨胀至 85KB 仍在"完善中"——**没有封板**
- 仓库里没有 backlog / sprint 计划 / DoD 检查点——**没有节奏标记**
- AI 引擎的"智能实现思路"讨论没有专门位置，泄漏进设计文档和 sprint 工作

本文档用「三个工具 + 一个内容流」的概念关系解决以上问题。它是**活文档**：按第 10 节规则演进。

## 2. 概念关系：三个工具 + 一个内容流

HeartRule 开发里用到三套方法 + 一条独立内容流。它们**不是平行层，是各管一个轴**：

| 工具                           | 管什么轴                             | 步骤 / 单位                                            | 仓库载体                               | 完成态                                |
| ------------------------------ | ------------------------------------ | ------------------------------------------------------ | -------------------------------------- | ------------------------------------- |
| **DDD**                        | 内容（what）——领域怎么建模           | 事件风暴(发现) → 战略设计(边界/UL) → 战术设计(聚合/VO) | `docs/ddd/` + `docs/design/` UL / 代码 | 战略文档 `decision-recorded`          |
| **Scrum**                      | 时间（when）——什么时候交付什么       | story 为交付单位，sprint 为节奏                        | `docs/scrum/`                          | 故事级 DoD 勾选                       |
| **spec-driven**（superpowers） | 方法（how）——单个故事怎么做          | 头脑风暴 → spec → plan → TDD → review                  | `docs/superpowers/specs` + `plans/`    | 一个可运行增量                        |
| **引擎机制**                   | 内容流（专家系统建模）——智能怎么实现 | 机制讨论 → 四选一收敛                                  | `docs/design/` 机制文档 + ADR          | 收敛为 机制文档/ADR/spec/story 四选一 |

**接缝关系**（三者怎么咬合，这是关键）：

- **spec 是 DDD 战术设计的落点**：不碰边界 → spec 本身就是战术设计（在一个已有限界上下文里设计单个聚合/话题怎么做）；碰边界（新限界上下文、新通用语言、改上下文关系）→ 先做战略设计（更新 `docs/ddd/` + UL），再写 spec。
- **plan 是故事级时间轴**：它和 sprint-plan 是同一个轴的两个刻度——plan 排一个故事怎么实现，sprint-plan 排一周的故事。二者不是竞争关系，是不同粒度。
- **story 是 Scrum ↔ spec-driven 的接缝**：故事从 backlog 来，规格从 spec 来。sprint 选故事（Scrum），故事被认领后走 spec-driven 流程。

> **引擎机制不是节奏层**——它是"我们在设计什么"（引擎的智能机制，即专家系统建模），不是"我们怎么工作"（DDD/Scrum/spec-driven 三条工作方式）。它进 `docs/design/` 存放，与地图层的领域建模、设计哲学混居；层归属见 [README 索引](README.md)。讨论纪律见第 8 节。

## 3. 最佳实践过程

一次典型工作的端到端走法（单人 + AI）：

1. **判断需求流**：一个需求冒出来，先分两类——
   - **应用级**（不碰引擎能力，站在具体咨询域视角）→ 直接 YAML scripts + templates 实现，无需新机制；
   - **引擎级**（需要引擎新能力，站在引擎产品视角）→ 走引擎机制流（第 8 节）。
2. **新领域/新边界 → 事件风暴 → 战略设计**：引擎级需求若涉及新咨询域或新边界，先做一次 AI 辅助事件风暴，产出 context map + UL，落 `docs/ddd/` + `docs/design/`。
3. **拆 story**：设计成型后切成 story，每个 story = 一个可见增量 + DoD，进 `docs/scrum/backlog.md`，sprint 时选入 `sprint-plan.md`。
4. **每个 story → spec-driven**：认领 story 后走 头脑风暴 → spec → plan → TDD → review（第 7 节）。
5. **引擎机制讨论 → 四选一收敛**：机制讨论随时开，但必须收敛为 机制文档/ADR/spec/backlog 故事（第 8 节）。

> 这五步不是瀑布——第 2 步的"边界"是草稿，允许反悔（贵的东西晚拍板）；第 4、5 步常常交织。

## 4. 人机协同协议

单人 + AI 协同开发的核心问题：**什么时候找 AI 讨论、讨论后生成什么、哪些必须由人审核**。

| 阶段              | 何时与 AI 讨论                         | 产出物                                    | 需要人审核                                       |
| ----------------- | -------------------------------------- | ----------------------------------------- | ------------------------------------------------ |
| 需求判断          | 一个需求冒出来，分不清应用级还是引擎级 | 需求流归类 + backlog 故事草稿             | **是**：确认归类与用户价值                       |
| 事件风暴          | 遇到新咨询域 / 新边界                  | 领域事件/命令/聚合草图 → context map + UL | **是**：边界和术语必须由你（领域专家）定         |
| 战略设计          | 边界画完，要定上下文关系               | `docs/ddd/` 战略文档 / UL 更新            | **是**：这是咨询智慧的封装                       |
| 拆 story          | 设计成型，要切交付                     | backlog 故事 + DoD                        | **是**：确认增量可见、DoD 合理                   |
| spec-driven       | 认领 story 后                          | brainstorm → spec                         | **是**：spec 是否忠实于你的意图                  |
| plan + TDD + 代码 | spec 通过后                            | plan → 代码 → 测试                        | **否**：正确性由测试验证，只在测试挡不住时才介入 |
| 引擎机制讨论      | 讨论"智能怎么实现"                     | 机制文档 / ADR / spec / story             | **是**：机制是否真捕获了咨询智慧                 |

**核心原则**：审核门落在**"人类咨询智慧被建模"的地方**，不落在"代码能不能跑"的地方。代码能不能跑由测试验证；人要审的是 AI 无法自己验证的领域判断——边界画对没、术语是不是咨询师真用的词、机制是否真捕获了咨询智慧、spec 是否忠实于意图。**你是咨询智慧的来源，所以审的是"建模是否忠实"，不是"实现是否可行"。**

## 5. 时钟：轻量 Scrum

**节奏**：每周一个 sprint。**仪式**：仅 sprint 计划（定目标 → 从 backlog 选故事 → 定每故事 DoD）。不设 review/retro 仪式。

**载体**：

- `docs/scrum/backlog.md` — 产品待办。所有候选故事，含三类：`[feature]` / `[design]` / `[intelligence]`。每项：标题、类型、状态（`backlog/ready/in-progress/done`）、关联文档。
- `docs/scrum/sprint-plan.md` — 当前 sprint。sprint 目标、选中的故事清单（含 DoD）、状态。每次 sprint 覆盖，旧计划留在 git 历史。

**故事级 DoD**（Definition of Done）：

| 故事类型         | DoD                                                                    |
| ---------------- | ---------------------------------------------------------------------- |
| `[feature]`      | 测试通过 + lint/typecheck 通过 + commit + push + sprint-plan 标记 done |
| `[design]`       | 文档达到 `decision-recorded`（必要时追加 ADR）+ commit + push          |
| `[intelligence]` | 收敛出 机制文档 / ADR / spec / backlog 故事（四选一）+ commit + push   |

**故事粒度规则**：一个故事应在 1–2 个会话内完成。若某工作"需要先写一篇大设计"，它本质是战略设计议题，先走第 3 节流程，产出决策后再拆成小故事。

## 6. 地图：DDD（战略设计 / 战术设计 / 事件风暴）

**事件风暴是战略设计的发现手段**：遇到新咨询域 / 新边界时，用 AI 辅助枚举「领域事件 → 命令 → 聚合 → 限界上下文」，产出 context map + UL。它回答"领域里发生了什么、边界画在哪"。

**战略 vs 战术的分界 = 可逆性**：战略（限界上下文、上下文映射、通用语言）改起来贵——一旦代码和团队围着边界建起来，重画边界极贵；战术（聚合、实体、值对象、领域服务）改起来便宜——单个聚合内部重构不动边界。**贵的晚拍板、便宜的随手做。**

**载体**：战略设计 → `docs/ddd/`（strategic-design、context-map）；领域建模 → `docs/design/`（topic-unit-modeling、ubiquitous-language）。ADR 落 `docs/design/decisions/`。

> 注意：`docs/design/` 是**混层目录**——机制文档（引擎机制）与领域建模（地图层）并存。层归属以 [README 索引](README.md) 的「层」列为准，暂不物理拆分。

**状态语义**（每篇文档顶部 frontmatter 的 `status`）：

| 状态                | 含义                                                          |
| ------------------- | ------------------------------------------------------------- |
| `draft`             | 尚未验证，正在成形                                            |
| `active`            | 正在被实现/使用的活文档                                       |
| `decision-recorded` | 关键决策已记录（ADR），封板；仅当实现或新证据与之矛盾时才修订 |
| `superseded`        | 被其他文档取代                                                |

**封板规则**：设计文档在关键决策落入 ADR 后，从 `active` → `decision-recorded`，停止积累。修订是**证据驱动**的：实现碰壁、e2e 暴露问题、或领域理解深化时才打开修订，改完重新封板。

**索引**：`docs/design/README.md` 维护状态总表，作为地图的"一页视图"。

## 7. 施工队：spec-driven（superpowers）

每个故事按既有 superpowers 流程执行：**头脑风暴（brainstorm）→ spec → plan → TDD → code review**。

- spec 落 `docs/superpowers/specs/`，plan 落 `docs/superpowers/plans/`（已有 11 spec + 13 plan 先例）。
- **spec 的归属**：不碰边界 → spec 就是战术设计；碰边界 → 先更新 `docs/ddd/` 战略 + UL，再写 spec（见第 2 节接缝）。
- **plan 是故事级时间轴**：排这一个故事怎么一步步实现，与 sprint-plan（周粒度）同轴不同刻度。
- **接缝**：故事从 backlog 来，规格从 spec 来。backlog 里的故事被认领后，若需要规格先写 spec，再按 plan 实施。

## 8. 引擎机制：专家系统建模

**HeartRule 的本质**：把人类咨询智慧（咨询师怎么问、怎么觉察、怎么调整议程）建模成 LLM + 脚本能执行的机制。所以开发过程会不断讨论**具体智能模拟的实现方式**——记忆怎么调取、意识怎么触发、话题队列怎么动态调整。

**为什么单列一节**：这类机制设计**不适合 DDD 事件风暴，也不适合 spec-driven 头脑风暴**。事件风暴和头脑风暴假设你在"探索业务领域 / 发现需求"；而机制设计是在"设计智能的实现方式"——一个是对领域的发现，一个是对智能的技术建模。二者对象不同，需要单独的位置与纪律。

**可追溯性闸门**：每个机制文档开头必须写清它服务的**引擎级业务需求**（一句话用户价值）——"这个机制让谁在什么场景得到什么价值"。写不出来说明没有需求锚点，是技术自嗨，不写。业务需求分两流：

- **应用级**——站在最终用户/具体咨询域的视角，用 YAML scripts + templates 实现，不需要新机制；
- **引擎级**——站在引擎作为产品的用户价值视角（"咨询师会谈中能觉察信号并调整议程"），需要引擎新能力时由机制承载。

机制文档回答"怎么做"，锚定的业务需求回答"要什么"；二者靠**可追溯性**连接。

**载体**：机制文档 → `docs/design/`（memory-framework、consciousness-system、ai-ask-memory-recall 等）；决策 → `docs/design/decisions/`（ADR）；探索 → backlog「智能设计议题」。

**规则（产出物驱动）**：机制讨论**事件驱动**——遇到了就讨论，不必等排期；但每次讨论必须收敛为以下四选一：

1. **机制设计文档** —— 思路是引擎实现机制（如记忆调取、意识触发、队列调整），更新 `docs/design/` 对应文档（锚定引擎级业务需求）；
2. **ADR** —— 关键决策已定，记录进 `docs/design/decisions/`；
3. **spec** —— 思路已成型、可交付实现，写进 `docs/superpowers/specs/`；
4. **backlog 故事** —— 思路还需实施，沉淀为 `[intelligence]` 故事进 backlog。

若一次讨论无法收敛，明确标记为 backlog「智能设计议题」下的**探索项**（exploration item），注明未决问题，下次继续——不允许"无产出地聊到哪算哪"。

**机制的归宿**：机制文档成熟后，拆成 `[intelligence]` / `[feature]` 故事流入时钟层（backlog → sprint），每个故事面向脚本作者/引擎可观察的增量 + DoD。机制设计不是终点——流入 backlog 才是。

## 9. 每会话开工约定

Claude Code 在 HeartRule 仓库启动会话时：

1. **先看 `docs/scrum/sprint-plan.md`** —— 知道当前 sprint 做什么、哪些故事 in-progress。
2. **若涉及设计**，查 `docs/design/README.md` 确认相关文档状态，遵守封板规则（第 6 节）。
3. **若涉及引擎机制**，按第 8 节收敛规则执行，产出物必须落地。
4. **人机分工**：参照第 4 节协议——AI 生成，人审关键建模决策。

人类侧同样：开工前扫一眼 sprint-plan，确认本周目标；做完一个故事主动触发 DoD 检查；AI 生成的 spec/机制文档在落库前由人审核。

## 10. 演进规则

本文档自身按**渐进规则化**（Progressive Rulification）演进：

- 让流程先宽松运行，在**反复出问题的地方**加一条明确规则；
- 规则被证明多余时删掉；
- 每季度回顾一次本节奏系统是否还适配（co-evolutionary，反馈通道）。
