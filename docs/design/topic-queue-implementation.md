## 1. 议程是什么

议程是会谈准备（个案化）的输出——一份按顺序排列的话题执行清单。它的核心特征：

- **可变**。脚本是静态模板，议程是动态实例。意识层可以随时插入、取消、重排条目。
- **独立于脚本**。议程一旦生成就与脚本解耦。脚本被编辑不影响正在进行的会谈。
- **跨请求持久**。议程存于 `sessions.metadata` JSONB，每次 HTTP 请求加载→执行→更新→存回。

每个议程条目（AgendaEntry）的关键属性：

| 属性                | 说明                                                                                     |
| ------------------- | ---------------------------------------------------------------------------------------- |
| `topicId`           | 来源话题，关联回脚本                                                                     |
| `status`            | pending → active → completed / frozen / cancelled                                        |
| `estimatedDuration` | 预估时长（分钟），脚本声明，默认 5 分钟                                                  |
| `urgency`           | 动态紧急度，决定执行顺序（值越高越靠前）。来源：脚本声明，意识层可通过 `setUrgency` 调整 |
| `importance`        | 话题重要性（low / medium / high），决定时间压力下的取舍策略。来源：脚本声明              |
| `depth`             | quick / standard / deep，影响动作执行参数                                                |
| `expandBy`          | 列表展开配置（见 §3）                                                                    |

议程附有一个 `phasePlan`（阶段时间预算），独立于条目。每个阶段有 `plannedDuration`、`accumulatedTime`、可选的 `minDuration`。

## 2. 个案化：脚本 → 议程

会谈开始时，`AgendaPreparer` 遍历脚本的每个阶段（Phase）下的每个话题（Topic），为每个话题创建一个议程条目。

**变量代换**是这个过程的核心。脚本中的 `{{variable_name}}` 被来访者的具体信息替换——通用的 "询问症状触发模式" 变成 "询问 34 岁男性互联网从业者的焦虑触发模式"。

**时间预估**也在这一步完成。每个话题的 `estimatedDuration` 按以下优先级取值：

1. 脚本声明的 `estimatedDuration`（刚性话题必须声明）
2. 该话题的群体统计值（同 scheme 下所有来访者已完成该话题的实际耗时移动平均，见 §4.6）
3. 系统默认值（刚性 5 分钟，弹性 10 分钟）

阶段级 `accumulatedTime` 按 Phase 顺序累加。**会谈准备时不调用 LLM 评估时间**——没有执行数据时 LLM 的推测和默认值无本质区别，真正准的时间来自群体执行数据。

**话题时间预估的首要用途是议程规划**：在会谈开始前判断哪些话题能放进本次会谈。大话题和小话题的区分依赖群体统计——新来访者没有任何个人历史，但系统仍需要知道某个话题通常耗时多久，才能做出 "大话题 + 小话题" 的合理组合。

```
阶段"开始欢迎"(5min) → 阶段"咨询评估"(15min, accumulated=20)
→ 阶段"咨询干预"(25min, accumulated=45) → 阶段"结束收尾"(10min, accumulated=55)
```

**动作 ID** 在个案化时自动生成（`topic_id.action_index`），无需咨询师手工命名。

### 2.1 脚本如何声明时间与深度

咨询师在 YAML 脚本中可以声明阶段级和话题级的时间与深度配置。

**阶段级**：

```yaml
phases:
  - id: closing
    time:
      planned_duration: 10 # 分钟数；也支持 ratio: 0.2（占总时间比例），分钟数优先
      min_duration: 10 # 至少需要多久，不可压缩
```

不填 `time` 的阶段由引擎按剩余时间均分。

**话题级**——刚性 vs 弹性：

```yaml
topics:
  - id: confirm_scope
    time:
      type: rigid # 刚性话题：流程固定，时间可预估
      estimated_duration: 5

  - id: explore_trauma
    time:
      type: flexible # 弹性话题：时间取决于来访者
      min_duration: 10 # 最少需要多久，但总时间可变

  - id: psychoeducation
    # 不声明 time → 默认 flexible，estimatedDuration=5
```

|              | rigid                                        | flexible                                                                 |
| ------------ | -------------------------------------------- | ------------------------------------------------------------------------ |
| 时间预估来源 | 脚本声明的 `estimatedDuration`，执行后不修正 | 群体统计值 > 默认值（10min），每次会谈后用实际耗时修正（反哺回群体统计） |
| 适用场景     | 流程固定的短期话题                           | 时间取决于来访者状态的话题                                               |

**深度预设**（可选）：

```yaml
topics:
  - id: quick_checkin
    depth: quick # 该话题默认为 quick 版，意识层可在执行中覆盖
```

## 3. 列表展开（expand_by）

### 3.1 问题

有些话题需要针对列表中的每个元素各执行一次。比如 "了解来访者与抚养者的关系"，抚养者是谁取决于来访者——可能是 ["妈妈", "爸爸"]，也可能是 ["妈妈", "爸爸", "奶奶"]。列表在脚本编写时不确定，列表可能在会谈中增长。

### 3.2 机制

脚本用 `expand_by` 声明这个话题需要按列表展开，`item_variable` 指定每个元素的变量名：

```yaml
topics:
  - topic_id: explore_caregiver
    expand_by: '{{caregivers}}'
    item_variable: caregiver
    actions:
      - action_type: ai_ask
        content: '你和{{caregiver.name}}的关系是怎样的？'
```

**两阶段展开**：

| 时机       | 条件                                         | 动作                                                        |
| ---------- | -------------------------------------------- | ----------------------------------------------------------- |
| 会谈准备时 | 列表变量已有值（如从全局变量、上次会谈继承） | 立即展开为 N 个具体条目，替换 `{{caregiver.name}}` 等占位符 |
| 会谈准备时 | 列表变量尚无值（等前面的话题收集）           | 创建 `pending_expand` 占位条目，actions 为空                |
| 会谈进行中 | 列表变量被更新（如新增成员）                 | 对比 `expandedItems` 与新列表，追加新条目、取消移除的条目   |

**动态追加示例**：原列表 ["妈妈", "爸爸"]，执行"探索与妈妈的关系"时来访者提到奶奶也一起住 → 变量更新为 ["妈妈", "爸爸", "奶奶"] → 议程自动追加 `explore_caregiver::奶奶` 条目 → 插在同组展开条目的最后。意识层可通过 urgency + reorder 调整优先级。

**执行引擎遇到 `pending_expand`**：跳过。说明前面的话题未能收集到列表变量。此时由意识层决定是取消还是继续等。

## 4. 时间管理

时间是参谋，不是军令。引擎不做到点就停、不做分钟级精确调度、不做前台实时计时显示。时间数据用于辅助意识层做判断。

### 4.1 两级时间预算

| 层级 | 字段                | 来源                         | 什么含义                           |
| ---- | ------------------- | ---------------------------- | ---------------------------------- |
| 阶段 | `plannedDuration`   | 脚本声明                     | 该阶段计划用多少分钟               |
| 阶段 | `accumulatedTime`   | 议程生成时自动累加           | 从会谈开始到该阶段结束的累计时间点 |
| 阶段 | `minDuration`       | 脚本声明（可选）             | 该阶段至少需要多久，不可压缩       |
| 话题 | `estimatedDuration` | 脚本声明 / 历史学习 / 默认值 | 这个话题预估要多久                 |

话题分刚性（`type: rigid`）和弹性（`type: flexible`），声明格式见 §2.1。刚性话题的预估不随执行修正，弹性话题每次会谈后用实际耗时修正。

### 4.2 时间判断的承担者

时间判断不是独立意识，而是 `process_quality` 内置意识（见 [意识系统设计](consciousness-system.md) §2.5）的一个判断维度。`process_quality` 始终运行、每轮评估。

三层运算，各走各的路径：

| 层           | 频率                  | 做什么                               | 调 LLM？                  |
| ------------ | --------------------- | ------------------------------------ | ------------------------- |
| 计算         | 每轮                  | 话题已用时间、阶段剩余时间、偏差比例 | 否，算术运算              |
| 判断         | 每轮                  | 偏差超过阈值 → 触发对应级别干预      | 否，规则判断              |
| 生成干预文本 | 触发时，cooldown≥2 轮 | 生成上下文相关的收束提示词           | 是，复用意识管线 LLM 调用 |

计算和判断不含 LLM——每轮只是做除法和比较。只有生成"怎么说"时才调 LLM，且受 cooldown 约束避免频繁重复。

**阈值按领域可配**（放在 `_system/config/custom/{scheme}/` 下的意识配置中）：

```
topic_pressure_threshold: 1.5    # 实际/预估 > 1.5 → 话题级压力
stage_pressure_threshold: 0.8    # 阶段剩余/计划 < 0.8 → 阶段级压力
intervention_cooldown: 2         # 提示词注入至少间隔 2 轮
```

### 4.3 两级压力，分级响应

| 压力层级 | 判断条件                                                      | 触发动作                    | 走什么通道                            |
| -------- | ------------------------------------------------------------- | --------------------------- | ------------------------------------- |
| 话题级   | 当前话题实际耗时 > 预估 × 1.5                                 | 生成上下文相关的收束提示词  | 轻量干预 → `suggestedIntervention`    |
| 阶段级   | 阶段剩余时间 < 后续阶段 `minDuration` 或无法覆盖 pending 话题 | cancel / setDepth / reorder | 重量干预 → 直接调用 `IAgendaModifier` |

话题级管"当前这个话题怎么收"，阶段级管"整个阶段还能塞多少"。两级独立判断，按更严重的行动。例：

```
阶段"咨询评估" plannedDuration=20min，当前第 18 分钟
话题 A(active): 预估 8min，实际已 14min → 话题级压力（超 75%）
阶段 pending: B(预估 6min), C(预估 5min)，剩余 2min 无法覆盖

→ 话题级：A 注入"1-2 轮内收束"
→ 阶段级：B cancel(carryover), C cancel(时间不够)
```

**异常检测**：话题实际耗时不仅用于节奏控制，也是信号源。同一话题在同一 scheme 下的群体统计形成稳定基线（移动平均和标准差）。当某来访者本次耗时显著偏离群体基线（如超过 2 个标准差）时，不是时间管理问题——是来访者状态问题（情绪变化、阻抗、重要事件、或该来访者本身节奏偏快/偏慢）。这个信号上报意识层，由意识层判断是否需要干预。个体偏离的方向和幅度同时反哺来访者节奏因子（见 §4.6）。

### 4.4 取舍逻辑

取什么，弃什么，延什么——按以下顺序：

1. **保障结束收尾**。`minDuration` 的阶段不可取消、不可压缩。从此向前倒推时间边界。
2. **按重要性三分**。同阶段内根据话题 `importance` 做不同处理：
   - **低重要性** → cancel，自动收集为 carryover，下次再聊。
   - **中重要性** → `setDepth('quick')`，压缩执行（减轮数、跳过 Think、加速提示词）。聊到了，但不展开。
   - **高重要性** → 不压缩、不取消。移到下次会谈（carryover），保留完整时间。重要话题值得认真对待，不应 quick。
3. **连续 carryover 提权**。同一话题连续两次被 carryover 时 `urgency` 自动提升，下次会谈准备时优先入队。

### 4.5 深度切换

深度切换（`setDepth`）是 quick / standard / deep 之间的切换。quick 和 deep 是系统在 standard（脚本写的标准版）基础上做参数调整，**不要求咨询师编写多个版本**。

**三层叠加实现**，各管各的，互不冲突：

| 层       | 机制                   | quick 做什么                             | 调 LLM？           |
| -------- | ---------------------- | ---------------------------------------- | ------------------ |
| 参数层   | 调整 `max_rounds` 数值 | 缩为标准版的 1/3（deep 扩为 1.5 倍）     | 否                 |
| 动作层   | 执行引擎检查当前深度   | 跳过 Think 动作（直接标记 completed）    | 否                 |
| 提示词层 | 注入深度相关的行为指导 | "请保持简洁直接，抓住核心，不必展开细节" | 是，由模板系统管理 |

**两条注入通道**：

| 作用范围               | 通道                                                                         | 时机           |
| ---------------------- | ---------------------------------------------------------------------------- | -------------- |
| `all_pending` / `full` | 引擎层：深度写在 `AgendaEntry.depth` → Action 构建时读取并注入               | Action 创建时  |
| `current_remaining`    | 意识反馈通道：`process_quality` → `suggestedIntervention` → 下一轮主线提示词 | 每轮意识分析后 |

`current_remaining` 只影响当前话题的剩余动作（已执行的不重跑）。`all_pending` 影响所有尚未开始的条目。两种范围可同时生效。

### 4.6 记时与学习

**记时**：议程执行引擎在话题开始/完成时记录时间戳，差值写入 `AgendaEntry.metadata.actualDuration`。

#### 群体统计（主力）

每个话题的实际耗时在会谈结束后**反哺回群体统计**，按 `scheme × topicId × depth` 三维聚合：

```
TopicDurationStats {
  scheme: string           // 哪个咨询方案
  topicId: string          // 哪个话题
  depth: "quick" | "standard" | "deep"
  movingAverage: number    // 跨所有来访者的移动平均
  stddev: number           // 标准差，用于异常检测
  sampleCount: number      // 样本量（置信度参考）
}
```

群体统计是话题时间预估的主力来源。它的核心价值在**议程规划阶段**：系统需要知道每个话题的典型耗时，才能判断大话题和小话题如何组合放进一次会谈。新来访者没有任何个人历史，但群体数据已经可用。

**为什么不是个体历史？** 咨询场景下，大部分实质性话题只出现一次——"探索童年创伤" 聊完就过了，不会重复。按个体存话题历史意味着绝大部分记录永远不会被二次读取。真正的冷启动问题出在来访者首次会谈，而不是同一个话题的第二次出现。

#### 来访者节奏因子（辅助修正）

在群体统计基础上，每个来访者维护一个**全局节奏乘数**：

```
clientPaceFactor = 该来访者所有已完成话题的实际耗时总和 / 预估耗时总和
```

这是一个粗糙但普适的修正。张三话多，所有话题都偏长 30% → 乘数 1.3。李四简练 → 乘数 0.8。一场会谈跑完 5-8 个话题就有初步乘数，几场会谈后稳定。

叠加方式：

```
estimatedDuration(client, topic, depth) =
  groupStats(topic, depth).movingAverage   // 群体统计
  × clientPaceFactor(client)               // 来访者节奏修正（有数据后启用）
```

节奏因子对**议程规划的帮助有限**（规划更需要话题间的相对大小，而不是绝对分钟数），但对会谈进行中的**阶段剩余时间判断**有价值——同样是 10 分钟剩余，话多的来访者实际上只能塞进一个 7 分钟的话题。

#### 个体话题历史（窄场景）

仅对**真正会重复的话题**保留个体历史：

- 仪式性话题（开场 check-in、结束收尾）——每次会谈都执行
- carryover 话题——上次被取消，下次补上

这些话题的个体历史比群体统计更精确，因为同一个来访者的仪式性话题耗时高度稳定。存储维度同群体统计（`来访者 × topicId × depth`），查询时优先命中个体历史，未命中时回退到群体统计。

#### 冷启动与收敛路径

```
新来访者 + 新话题 → 群体统计值（或默认值）
                   → 话题完成后反哺群体统计
                   → 同时更新来访者节奏因子

老来访者 + 新话题 → 群体统计 × 来访者节奏因子
                   → 话题完成后同上

老来访者 + 重复话题 → 个体历史 > 群体统计 × 来访者节奏因子
```

初始无历史数据时用默认值。群体统计在几场会谈后收敛，来访者节奏因子更快（一场会谈内就有初步值）。

## 5. 议程的持久化与恢复

议程生成后存入 `sessions.metadata.agenda`（JSONB），不需要改数据库 schema。

**每次 HTTP 请求**的议程生命周期：

```
创建会谈：  脚本个案化 → 议程生成 → 存入 metadata
请求到达：  从 metadata 加载议程 → 从 headIndex 继续执行 → 议程修改写回 metadata
```

会谈中断后恢复时，加载的是同一份议程实例，`headIndex` 指向当前或下一个待执行条目。不再重新解析脚本。

**向后兼容**：旧测试不经过会谈准备流程，没有 agenda → `ScriptExecutor` 检测到 agenda 不存在时走旧的三层索引迭代路径。旧代码标注 `@deprecated`，待测试迁移完成后移除。

## 6. 意识层对议程的修改

六种操作，意识层是唯一调用者（编译期通过 `IAgendaReader` / `IAgendaModifier` 接口隔离保证）：

| 操作           | 场景                                             | 效果                                                                      |
| -------------- | ------------------------------------------------ | ------------------------------------------------------------------------- |
| **insert**     | 检测到阻抗，需要插入安抚话题；expand_by 动态追加 | 在指定位置后插入新条目                                                    |
| **interrupt**  | 来访者说"我想自杀"                               | 当前条目冻结（保存动作进度），紧急条目插到队首。完成后 LIFO 恢复          |
| **cancel**     | 时间不够；来访者父亲已去世，取消相关话题         | 标记 cancelled，自动收集为 carryover                                      |
| **reorder**    | 时间压力下让高紧急度话题先执行                   | 调整 pending 条目的顺序                                                   |
| **setDepth**   | 时间不够但话题仍需保留                           | 三层叠加：参数层减轮数 + 动作层跳过 Think + 提示词层加速指导（详见 §4.5） |
| **setUrgency** | 发现新线索，某话题需要提前处理                   | 调整紧急度，影响执行顺序                                                  |

**中断（interrupt）的机制**：当前条目冻结（保存 `actionIndex` 和动作状态），紧急条目插入。若紧急条目执行中再次触发中断，当前紧急条目也被冻结，新紧急条目插入其后。所有冻结的条目都在同一份议程中排队，不是"嵌套调用-返回"，而是"大家排好队，一个一个来"。
