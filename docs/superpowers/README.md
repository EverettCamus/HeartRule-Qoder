# 过程记录（spec / plan / domain-check）

> 单个故事走六步时留下的**过程记录**（落点由[开发节奏系统](../process/development-rhythm.md) §7 规定）。**不作为设计依据**——设计问题查 [`docs/design/`](../design/README.md) 与 [ADR 注册表](../design/README.md#adr-注册表)。

## 三个子目录

| 目录             | 放什么                                     | 何时退场                         |
| ---------------- | ------------------------------------------ | -------------------------------- |
| `specs/`         | 第 3 步「写 Spec」：验收标准、领域模型片段 | 故事 done 后转为历史，失效则归档 |
| `plans/`         | 第 4 步「写 Plan」：实现步骤与测试计划     | 同上                             |
| `domain-checks/` | 第 1 步「领域概念检查」的草稿纸            | **定期清理**，不进长期留存       |

## 怎么用这些文档

- **想知道某段代码为什么长这样** → 找同名 spec/plan，它记录了当时的约束与取舍。
- **想知道现在该怎么做** → **不要**用这里。过程记录反映的是写下时的判断，之后可能被 ADR 推翻。典型：`2026-04-28-global-variables` 引入了全局变量系统，而 [ADR 007](../design/decisions/007-variable-document-boundary.md) 已把它取消。
- **想知道某个决策的现行结论** → ADR 注册表，或设计文档；只活在某份 plan 里的决策应当补成 ADR 或设计文档。

## 命名与配对

文件名形如 `YYYY-MM-DD-<slug>.md`，spec 与 plan 用同一 slug 配对。**目前不严格一一对应**（部分 plan 无同名 spec，`ai-ask-exit-decision` 是两个 spec 对一个 plan）——配对关系以文件内的相互引用为准。
