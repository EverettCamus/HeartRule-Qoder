# AI_Ask退出判断机制优化设计

> **日期**: 2026-03-18
> **版本**: v1.4（简化架构：移除require字段，progress前置，规则层仅保留max_rounds）
> **状态**: 已实施

## 1. 背景与目标

### 1.1 现有问题分析

当前AI_Ask退出判断机制存在4个核心痛点：

1. **对话轮次过多但信息仍未收集完整** - AI陷入循环追问却无法获得所需变量
2. **用户明显不愿继续但AI仍追问** - 阻抗检测不够灵敏
3. **退出条件不够灵活** - 难以适应不同咨询场景的个性化需求
4. **偏题识别不足** - 用户偏离主题时无法智能引导或退出

### 1.2 设计目标

- **极简架构**：规则层只做 `max_rounds` 兜底，语义判断完全交给LLM
- **因果链清晰**：assessment → progress → exit（先评估用户状态，再评估信息进度，最后判断退出）
- **配置简化**：信息收集程度通过 `define` 描述表达，不需要额外的 `require` 字段

## 2. 架构设计

### 2.1 决策流程

```
用户输入 → LLM生成(assessment + progress + exit + content) → 代码层检查max_rounds → 综合决策
```

**流程说明**：

1. 每轮对话后，LLM生成结构化评估（assessment + progress）
2. LLM基于评估结果判断是否退出（exit + exit_reason）
3. LLM生成回复内容（content）
4. 代码层检查 `max_rounds` 是否达到（安全网兜底）
5. 综合LLM建议和规则引擎结果，得出最终退出决策

### 2.2 退出条件分类

#### 规则控制类（代码实现）

| 字段         | 说明                                      |
| ------------ | ----------------------------------------- |
| `max_rounds` | 最大轮次限制（安全网，防止LLM陷入死循环） |

**已移除**：

- `custom_conditions`（功能与 `exit_condition` 文本描述重叠）
- `required_variables`（信息收集完整性判断交给LLM）

#### LLM控制类（语义理解）

所有语义判断（阻抗、偏题、理解度、信息完整性等）都通过 `assessment` 和 `progress` 字段表达，**不再需要独立的阈值配置字段**。

**已移除的阈值字段**：

- `impedance_threshold`
- `topic_drift_threshold`
- `understanding_threshold`
- `has_questions`
- `min_variable_completeness`

## 3. LLM输出格式设计

### 3.1 JSON输出结构（因果链顺序）

```json
{
  "assessment": "## 阻抗分析\n阻抗程度：低(20分)\n主要表现：配合度高\n\n## 风险识别\n无明显安全风险\n\n## 用户理解\n用户理解程度良好",
  "progress": "## 进度评估\n- [x] 症状描述：已收集，描述详细充分\n- [ ] 持续时间：未收集，用户回避此话题\n- [x] 姓名：已收集",
  "exit": "false",
  "exit_reason": "信息不足",
  "content": "能具体说一下这个症状持续多久了吗？",
  "brief": "追问持续时间",
  "safety_check": {
    "passed": true,
    "concern": null
  },
  "crisis_detected": false
}
```

### 3.2 字段说明

| 字段              | 类型    | 说明                                                     |
| ----------------- | ------- | -------------------------------------------------------- |
| `assessment`      | string  | 语义评估（markdown），包含：阻抗分析、风险识别、用户理解 |
| `progress`        | string  | 进度评估（markdown），包含：变量收集状态、信息充分度评价 |
| `exit`            | string  | 退出标志（"true" 或 "false"）                            |
| `exit_reason`     | string  | 退出/继续的关键字理由（8个枚举值）                       |
| `content`         | string  | AI生成的提问内容（展示给用户）                           |
| `brief`           | string  | content摘要（20字以内，用于对话历史压缩）                |
| `safety_check`    | object  | 安全自查结果：passed（boolean）、concern（string或null） |
| `crisis_detected` | boolean | **仅明显危机**时为true，触发同步危机处理流程             |

### 3.3 assessment字段内容

- **阻抗分析**：用户回避、困惑、记忆缺失等程度评估
- **风险识别**：安全边界遵守情况、隐蔽危机信号（不明显危机）
- **用户理解**：用户对问题的理解程度

### 3.4 progress字段内容

- **进度评估**：使用任务列表格式说明每个变量的收集状态
  - `- [x] 变量名：已收集，信息充分度评价` 表示已完成
  - `- [ ] 变量名：未收集，原因说明` 表示未完成
- **信息充分度**：已收集的变量是否达到期望的详细程度（由 `define` 描述引导）

**示例**：

```markdown
## 进度评估

- [x] 症状描述：已收集，描述详细充分，包括具体表现和影响范围
- [ ] 持续时间：未收集，用户回避此话题
- [x] 姓名：已收集
```

**注意**：轮次信息（当前轮次/最大轮次）**不在** JSON 中输出，由代码层在模板中提供（`{{current_round}}/{{max_rounds}}`），代码层更准确。

### 3.5 exit_reason 枚举值

| 关键字         | 说明                         |
| -------------- | ---------------------------- |
| `信息已完整`   | 正常完成，任务目标达成       |
| `信息不足`     | 用户未提供足够信息，需要继续 |
| `用户阻抗`     | 用户回避/抗拒，建议退出      |
| `达到最大轮次` | 安全网触发，强制退出         |
| `用户理解困难` | 用户困惑，无法继续           |
| `话题偏离`     | 偏题严重，建议退出           |
| `危机信号`     | 检测到危机，需要处理         |
| `继续收集`     | 正常继续收集信息             |

### 3.6 危机检测分层机制

采用**分层危机检测**策略，区分明显危机与隐蔽危机：

| 危机类型     | 触发条件                           | 处理方式                                    |
| ------------ | ---------------------------------- | ------------------------------------------- |
| **明显危机** | `crisis_detected: true`            | 主线程同步启动危机处理LLM，评估是否修订回复 |
| **隐蔽危机** | assessment中风险识别部分有细微信号 | 另一线程的ai_ask监控LLM异步分析             |

**设计原则**：

- `crisis_detected` 仅用于**明显、紧急**的危机信号
- 明显危机包括：明确的自杀意念、自伤计划、他伤倾向等
- 隐蔽危机嵌入在assessment的markdown描述中，由监控流程处理

## 4. YAML配置格式

### 4.1 基本结构

```yaml
action:
  type: ai_ask
  content: '请问你最近感觉怎么样？'
  max_rounds: 100 # 安全网，默认100，通常无需修改
  exit_condition: '已完整收集必要信息，用户理解充分，无阻抗'
  output:
    - get: '症状描述'
      define: '来访者描述的影响日常生活、工作、健康的客观表现，请尽量详细，包括具体表现、频率、影响范围'
    - get: '持续时间'
      define: '有这个症状大致的时间长度描述'
    - get: '姓名'
      define: '来访者的姓名或称呼'
```

### 4.2 字段说明

| 字段              | 类型   | 必填 | 说明                                       |
| ----------------- | ------ | ---- | ------------------------------------------ |
| `content`         | string | 是   | 提问内容模板                               |
| `max_rounds`      | number | 否   | 最大轮数（安全网，默认100）                |
| `exit_condition`  | string | 否   | 退出条件的文本描述（给LLM的语义提示）      |
| `output`          | array  | 否   | 输出变量配置                               |
| `output[].get`    | string | 是   | 提取的变量名                               |
| `output[].define` | string | 否   | 变量定义说明，可包含收集期望的详细程度描述 |

### 4.3 信息收集程度表达

**不需要**单独的 `require` 字段。信息收集的期望程度通过 `define` 描述自然表达：

```yaml
output:
  # 需要详细收集的信息
  - get: '症状描述'
    define: '请尽量详细描述，包括具体表现、频率、对日常生活的影响'

  # 基本信息，收集即可
  - get: '姓名'
    define: '来访者的姓名或称呼'

  # 可选信息，有则记录
  - get: '家族病史'
    define: '家族中是否有类似心理问题（如有则记录，不必强求）'
```

LLM 基于 `define` 中的描述自然理解收集期望，并在 `progress` 字段中评价信息充分度。

### 4.4 兼容性策略

采用**一次性升级**策略：

- 重命名 `exit` 字段为 `exit_condition`（避免与LLM输出字段混淆）
- 移除 `metrics` 和 `progress_suggestion` 字段
- 移除 `custom_conditions` 字段（语义判断交给LLM）
- 移除 `required_variables` 字段（信息完整性判断交给LLM）
- 移除 `require` 字段（收集程度通过 `define` 表达）
- 新增 `assessment` 和 `progress` 字段
- 设置 `max_rounds` 默认值为100（安全网，通常无需修改）

## 9. 设计决策说明

### 9.1 为何移除 `min_rounds`

**移除原因**：在大多数咨询场景中无实际意义。

**分析**：

- 如果用户第一轮就提供了完整信息，强制继续N轮会损害用户体验
- 无意义的追问会降低咨询质量
- 如有特殊场景需要，可通过 `exit_condition` 文本描述引导LLM判断

### 9.2 为何移除 `custom_conditions`

**移除原因**：功能与 `exit_condition` 文本描述重叠，语义判断应交给LLM。

**分析**：

1. **职责重叠**：`custom_conditions` 和 `exit_condition` 都用于控制退出时机
2. **语义判断交给LLM**：`custom_conditions` 的变量比较本质上是语义理解
3. **简化架构**：移除后退出决策更清晰
   - 规则层：只做 `max_rounds` 兜底
   - LLM层：处理所有语义判断（阻抗、理解度、话题偏离等）
   - 脚本工程师：通过 `exit_condition` 文本描述引导LLM

### 9.3 为何移除 `max_tokens` 和 `max_cost`

**移除原因**：成本控制应在系统层而非Action层实现。

**分析**：

1. **追踪成本高**：需要累计token、维护价格表、跨会话持久化
2. **实际意义有限**：单次AI_Ask成本约$0.01-0.05，需要10-50轮才触发，此时 `max_rounds` 早已生效
3. **职责混淆**：成本控制应属于：
   - 系统级：用户配额、订阅限制（API层）
   - 监控层：成本预警（运营层）
   - 不应混入Action的退出条件

### 9.4 `max_rounds` 的正确理解

**定位**：安全网（Safety Net），而非目标值。

| 角色            | 应作为                          |
| --------------- | ------------------------------- |
| `max_rounds`    | 防止LLM陷入死循环的最后一道防线 |
| LLM `exit` 字段 | 主要退出决策者（语义层面判断）  |

**退出优先级**：

```
1. max_rounds 触发 → 强制退出（安全网）
2. LLM exit=true → 语义层面的退出判断（含阻抗检测、信息完整性评估）
```

### 9.5 为何移除 `required_variables`

**移除原因**：信息收集完整性判断应交给LLM的语义评估。

**分析**：

1. **硬检查不准确**：变量存在≠信息充分（用户可能只说了一个字）
2. **LLM更擅长判断**：LLM可以理解用户回复的详细程度和相关性
3. **progress字段替代**：LLM在 `progress` 中明确标记每个变量的收集状态和充分度

### 9.6 为何移除 `require` 字段

**移除原因**：信息收集程度通过 `define` 描述表达更自然。

**分析**：

1. **配置简化**：少一个字段，少一种验证逻辑
2. **表达更灵活**：`define` 中可以详细描述期望的详细程度
3. **LLM自然理解**：LLM基于 `define` 描述判断收集是否充分

### 9.7 为何移除 `max_silence_rounds` 和 `min_response_length`

**移除原因**：字符长度判断不准确，且与LLM阻抗检测功能重复。

**分析**：

1. **简单字符长度无法代表用户意图**：
   - 用户可能表达简洁但内容充实（"很难受，三个月了"仅7字）
   - 用户可能回复冗长但实质回避（"这个嘛...怎么说呢...其实也没什么..."）
2. **与LLM阻抗检测重复**：
   - LLM的 `assessment` 字段已包含阻抗分析
   - LLM可以根据上下文、语义、情绪综合判断
   - 规则层无法理解"我不知道"与"我不想说"的区别

3. **相信LLM的能力**：
   - 阻抗检测本质是语义理解任务
   - LLM比规则层更适合做这类判断
   - `max_rounds` 已经作为最后的规则层安全网

### 9.8 为何 `progress` 在 `exit` 之前

**因果链**：assessment（用户状态分析）→ progress（信息收集进度）→ exit（退出判断）

**理由**：

1. **逻辑顺序**：LLM需要先评估信息收集进度，才能判断是否应该退出
2. **决策依据**：`exit` 的判断依赖于 `progress` 中的变量收集状态
3. **监控需要**：`progress` 字段可被监控层用于追踪收集进度
