# AI_Ask退出判断机制优化设计

> **日期**: 2026-03-18
> **版本**: v1.3（移除custom_conditions，添加require紧迫度等级）
> **状态**: 已实施

## 1. 背景与目标

### 1.1 现有问题分析

当前AI_Ask退出判断机制存在4个核心痛点：

1. **对话轮次过多但信息仍未收集完整** - AI陷入循环追问却无法获得所需变量
2. **用户明显不愿继续但AI仍追问** - 阻抗检测不够灵敏
3. **退出条件不够灵活** - 难以适应不同咨询场景的个性化需求
4. **偏题识别不足** - 用户偏离主题时无法智能引导或退出

### 1.2 设计目标

- 建立清晰的退出条件分类体系（规则控制 vs LLM控制）
- 简化LLM评估字段结构，使用markdown格式表达复杂语义
- 保持向后兼容性，逐步升级现有代码

## 2. 架构设计

### 2.1 决策流程

```
用户输入 → LLM生成(回复+评估) → 规则引擎检查 → 综合决策
         (统一JSON输出)      (硬性条件)
```

**流程说明**：

1. 每轮对话后，LLM生成回复并输出结构化评估
2. 规则引擎检查硬性条件（轮次、沉默轮次等）
3. 综合LLM建议和规则引擎结果，得出最终退出决策

### 2.2 退出条件分类

#### 规则控制类（代码实现）

适用于所有咨询领域，通过计数、比较、存在性检查等纯代码逻辑实现：

| 字段                 | 说明                                      |
| -------------------- | ----------------------------------------- |
| `max_rounds`         | 最大轮次限制（安全网，防止LLM陷入死循环） |
| `required_variables` | 必须收集的变量列表（确保任务完成）        |

**已移除**: `custom_conditions`（功能与 `exit_condition` 文本描述重叠，语义判断交给LLM）

#### LLM控制类（语义理解）

需要理解用户回答的语义、情感和相关性：

| 字段                        | 说明                   |
| --------------------------- | ---------------------- |
| `impedance_threshold`       | 阻抗检测阈值           |
| `topic_drift_threshold`     | 偏题识别阈值           |
| `understanding_threshold`   | 理解度阈值             |
| `has_questions`             | 是否允许有疑问时退出   |
| `min_variable_completeness` | 变量完整度阈值（混合） |

## 3. LLM输出格式设计

### 3.1 简化JSON输出结构

```json
{
  "content": "您能再具体说一下这个症状持续多久了吗？",
  "assessment": "## 阻抗分析\n阻抗程度：中等(65分)\n主要表现：回避倾向，回答简短\n\n## 风险识别\n无明显安全风险\n\n## 用户理解\n用户理解程度良好",
  "progress": "## 进度评估\n- [x] 症状描述：已收集详细描述\n- [ ] 持续时间：用户未明确说明\n- [x] 严重程度：已确认中度\n\n## 成本与轮次\n当前轮次：3/5\n建议轮次：还需1-2轮",
  "exit": "false",
  "brief": "信息不足，需要继续收集持续时间",
  "crisis_detected": false
}
```

### 3.2 字段说明

| 字段              | 类型    | 说明                                                       |
| ----------------- | ------- | ---------------------------------------------------------- |
| `content`         | string  | AI生成的提问内容（展示给用户）                             |
| `assessment`      | string  | 综合评估（markdown格式），包含阻抗分析、风险识别、用户理解 |
| `progress`        | string  | 任务进度说明（markdown格式），包含变量收集状态、成本与轮次 |
| `exit`            | string  | 退出标志（"true" 或 "false"）                              |
| `brief`           | string  | 退出/继续的简短理由（不超过15个字）                        |
| `crisis_detected` | boolean | **仅明显危机**时为true，触发同步危机处理流程               |

### 3.3 assessment字段内容

- **阻抗分析**：用户回避、困惑、记忆缺失等程度评估
- **风险识别**：安全边界遵守情况、隐蔽危机信号（不明显危机）
- **用户理解**：用户对问题的理解程度

### 3.4 progress字段内容

- **进度评估**：使用任务列表格式说明每个变量的收集状态
  - `- [x] 变量名：状态描述` 表示已完成
  - `- [ ] 变量名：状态描述` 表示未完成
- **成本与轮次**：当前轮次、建议轮次、效率评估

### 3.5 危机检测分层机制

采用**分层危机检测**策略，区分明显危机与隐蔽危机：

| 危机类型     | 触发条件                           | 处理方式                                    |
| ------------ | ---------------------------------- | ------------------------------------------- |
| **明显危机** | `crisis_detected: true`            | 主线程同步启动危机处理LLM，评估是否修订回复 |
| **隐蔽危机** | assessment中风险识别部分有细微信号 | 另一线程的ai_ask监控LLM异步分析             |

**危机处理流程（明显危机）**：

```
crisis_detected: true
  → 主线程同步启动危机处理LLM
  → 综合评估：用户输入 + AI生成的回复 + 危机内容
  → 决策：是否修订回复
  → 如需修订：重新生成安全的回复
  → 返回处理后的回复
```

**设计原则**：

- `crisis_detected` 仅用于**明显、紧急**的危机信号
- 明显危机包括：明确的自杀意念、自伤计划、他伤倾向等
- 隐蔽危机嵌入在assessment的markdown描述中，由监控流程处理

## 4. 向后兼容性设计

### 4.1 YAML配置格式

保持现有`output`字段结构，添加`require`字段标识信息收集紧迫度：

```yaml
output:
  - get: '症状描述'
    define: '来访者描述的影响日常生活，工作，健康的客观表现'
    require: '即时' # 即时|本次对话内|可推迟|持续跟踪，默认"可推迟"
  - get: '持续时间'
    define: '有这个症状大致的时间长度描述'
    require: '本次对话内'
```

**紧迫度等级说明**：

| 等级         | 说明         | 处理策略                                   |
| ------------ | ------------ | ------------------------------------------ |
| `即时`       | 必须立刻获得 | 用户不答则反复追问，仍拒绝则终止或转人工   |
| `本次对话内` | 优先本次获取 | 暂时跳过则结束前补问一次，仍缺失则标注假设 |
| `可推迟`     | 本次完全跳过 | 结尾提示下次可聊，用户主动提及才顺势收集   |
| `持续跟踪`   | 不主动提问   | 仅记录用户自发报告，用于长期跟踪           |

### 4.2 兼容性策略

采用**一次性升级**策略：

- 重命名`exit`字段为`exit_condition`（避免与LLM输出字段混淆）
- 移除`metrics`和`progress_suggestion`字段
- 移除`custom_conditions`字段（语义判断交给LLM）
- 新增`assessment`和`progress`字段
- 更新所有依赖现有字段的代码
- 现有YAML脚本添加`require`字段（可选，默认"可推迟"）
- 设置`max_rounds`默认值为100（安全网，通常无需修改）

## 9. 设计决策说明

### 9.1 为何移除 `min_rounds`

**移除原因**：在大多数咨询场景中无实际意义。

**分析**：

- 如果用户第一轮就提供了完整信息，强制继续N轮会损害用户体验
- 无意义的追问会降低咨询质量
- 如有特殊场景需要，可通过 `exit_condition` 文本描述引导LLM判断

### 9.2 为何移除 `custom_conditions`

**移除原因**：功能与 `exit_condition` 文本描述重叠，语义判断应交给LLM。

**分析**：

1. **职责重叠**：`custom_conditions` 和 `exit_condition` 都用于控制退出时机
2. **语义判断交给LLM**：`custom_conditions` 的变量比较本质上是语义理解
3. **简化架构**：移除后退出决策更清晰
   - 规则层：只做 `max_rounds` 兜底
   - LLM层：处理所有语义判断（阻抗、理解度、话题偏离等）
   - 脚本工程师：通过 `exit_condition` 文本描述引导LLM

### 9.3 为何移除 `max_tokens` 和 `max_cost`

**移除原因**：成本控制应在系统层而非Action层实现。

**分析**：

1. **追踪成本高**：需要累计token、维护价格表、跨会话持久化
2. **实际意义有限**：单次AI_Ask成本约$0.01-0.05，需要10-50轮才触发，此时 `max_rounds` 早已生效
3. **职责混淆**：成本控制应属于：
   - 系统级：用户配额、订阅限制（API层）
   - 监控层：成本预警（运营层）
   - 不应混入Action的退出条件

### 9.4 `max_rounds` 的正确理解

**定位**：安全网（Safety Net），而非目标值。

| 角色            | 应作为                          |
| --------------- | ------------------------------- |
| `max_rounds`    | 防止LLM陷入死循环的最后一道防线 |
| LLM `EXIT` 字段 | 主要退出决策者（语义层面判断）  |

**退出优先级**：

```
1. max_rounds 触发 → 强制退出（安全网）
2. LLM EXIT=true → 语义层面的退出判断（含阻抗检测）
3. required_variables 全部收集 → 任务完成退出
```

### 9.5 为何移除 `max_silence_rounds` 和 `min_response_length`

**移除原因**：字符长度判断不准确，且与LLM阻抗检测功能重复。

**分析**：

1. **简单字符长度无法代表用户意图**：
   - 用户可能表达简洁但内容充实（"很难受，三个月了"仅7字）
   - 用户可能回复冗长但实质回避（"这个嘛...怎么说呢...其实也没什么..."）
2. **与LLM阻抗检测重复**：
   - LLM的 `assessment` 字段已包含阻抗分析
   - LLM可以根据上下文、语义、情绪综合判断
   - 规则层无法理解"我不知道"与"我不想说"的区别

3. **相信LLM的能力**：
   - 阻抗检测本质是语义理解任务
   - LLM比规则层更适合做这类判断
   - `max_rounds` 已经作为最后的规则层安全网

**如果未来需要兜底机制**：

- 可以考虑增加 `impedance_score` 字段让LLM输出阻抗评分
- 规则层累计阻抗评分做触发判断
- 目前不需要，优先相信LLM
