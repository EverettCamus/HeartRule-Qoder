# 领域概念检查（开发节奏系统 §7 第 1 步）

**核心原则**：每个 story 头脑风暴前先过概念关——概念叫什么、登记了没、属哪个限界上下文、关系定义了没。节奏依据：`docs/design/development-rhythm.md` §7 第 1 步。

## 何时用

- story-flow 第 ① 步调用（头脑风暴前）
- 用户单独要求"做 domain-check"
- 怀疑代码里的命名与 UL/本体不一致时

**何时不用**：咨询知识概念的建模本身（转 `heartrule-mechanism-flow` 补本体）；封板/治理动作（`heartrule-design-docs`）。

## 步骤

1. **列概念清单**：列出本 story 涉及的领域概念（类名、字段、枚举、新术语、新关系）。
2. **对照检查**，逐个回答：
   - 叫什么——与 UL（`docs/design/ubiquitous-language.md`）或本体（`docs/design/ontology.md`）一致的名称？
   - 在不在——代码概念是否已登记 UL；咨询知识概念是否已在本体（任务/领域/推理三层）？
   - 属哪个限界上下文、与谁的关系是否已定义？
3. **缺口按归属补齐**：
   - **代码概念**（类名/枚举/字段/端口）→ 补 UL。注意 UL 各节表格列数不同：一~五节、七节是 `| 术语 | 英文 | 定义 |`；六节多一列「所属上下文」；八节是缩写表。追加后更新文末「版本历史」表。
   - **咨询知识概念** → 转 `heartrule-mechanism-flow` 补本体（ontology.md），遵守任务锚纪律。
   - **本体概念变成代码类名/枚举/字段时** → 在 UL 登记一行、指向 ontology.md（**UL 登记的单一出处**，§8）；登记后同步 ontology.md §4「桥接现状」的「已在 UL 登记/待登记」两份清单。
   - **边界或上下文关系变化** → 触发战略设计（事件风暴按需 → `docs/ddd/` + UL），**先于 spec**。
4. **产出 domain-check 笔记**，落 `docs/superpowers/domain-checks/`（命名 `YYYY-MM-DD-<slug>.md`；草稿纸级，定期清理）。内容：概念清单 + 检查结论 + 补登记摘要。

## 人审门（停止点）

补齐定义后停下：人确认概念准确、缺失定义已补对。

## 产出物规则（§4 住所）

domain-check 笔记的**下一个读者是写 spec 的 AI 与人**（§7 第 2-3 步回看），住所 = `docs/superpowers/domain-checks/`。

## 常见违规

| 违规                            | 纠正                                                     |
| ------------------------------- | -------------------------------------------------------- |
| 发现概念缺失就地在代码里造新词  | 先补 UL/本体登记，再允许代码使用                         |
| 咨询知识概念直接塞进 UL         | UL 管代码术语；咨询知识概念进本体（ontology.md），两条账 |
| 碰了限界上下文边界却继续写 spec | 先做战略设计（docs/ddd/ + UL），再回 spec                |

## Red Flags

- 概念清单跳过、直接开写
- 补了 UL 没更新「版本历史」
- 本体概念进了代码但 UL 没有对应行
