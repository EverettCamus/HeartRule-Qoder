# 开工节奏（开发节奏系统 §9）

**核心原则**：开工先看节奏——先知道 sprint 在做什么，再主动提计划，人批准后才动手。节奏依据：`docs/design/development-rhythm.md` §9（每会话开工约定）与 §3 路由表。

## 何时用

- 本会话刚开始（SessionStart hook 会指向本技能）
- 用户直接调用 `/heartrule-session-start`
- 会话中途用户抛出新方向，需要重新对齐"这次做什么"

**何时不用**：已批准计划执行途中（不必重复开工仪式）；机制讨论（转 `heartrule-mechanism-flow`）。

## 步骤

1. **读节奏现状**：读 `docs/scrum/sprint-plan.md`（当前 sprint 目标 + 各故事状态）和 `docs/scrum/backlog.md`（意图区 + 各 epic 就绪故事）。
2. **对照用户意图**：
   - 用户带明确任务 → 对照 sprint-plan：属于哪个 in-progress / ready 故事？
   - 用户带新意图（backlog 里没有）→ **不急着拆**：按 §5 意图区规则，一句话 + 价值登记进 backlog 意图区（转 `heartrule-intent-to-epic`），想清楚了再拆 epic。
3. **主动提出本会话工作计划草案**：做什么（对应哪些故事/意图）、按什么顺序、预计产出。**停下来，等人批准。**
4. **人批准后开工**，并按涉及面转交：
   - 涉及设计文档 → 查 `docs/design/README.md` 确认相关文档状态，守封板规则（`heartrule-design-docs`）；
   - 涉及引擎机制 → 按 §8 收敛规则（`heartrule-mechanism-flow`）；
   - 认领 story → `heartrule-story-flow`。

## 人审门（停止点）

工作计划草案必须经人批准——批准前不读代码、不改文件、不做任何实现。

## 产出物规则（§4 住所）

计划草案的**下一个读者是人**（拍板是否照此干），**住所是本会话**——不落盘、不写进任何文档。

## 常见违规（rationalization 表）

| 违规想法                       | 现实                                                                  |
| ------------------------------ | --------------------------------------------------------------------- |
| "用户已经说了要做什么，直接干" | 仍需确认做什么、按什么顺序、预计产出——用户说目标 ≠ 用户批准了执行计划 |
| "先看看代码再提计划"           | 节奏要求先提计划后动手；看代码是批准后的事                            |
| "这个小改动不用走开工仪式"     | 会话开头对节奏的第一次确认是 §9 约定，不因改动大小豁免                |

## Red Flags

- 未读 sprint-plan / backlog 就开始执行
- 提出计划后未等人批准就继续动手
- 遇到新意图直接开干而不是先进 backlog 意图区
