# 意图登记与拆解（开发节奏系统 §3 路由表 + §5 意图区）

**核心原则**：意图随时可提、不急着拆——先登记进意图区（一句话 + 价值），想清楚了再拆成 epic。节奏依据：`docs/design/development-rhythm.md` §3 路由表前两行、§5 意图区。

## 何时用

- 会话中新意图/新想法/需求冒出（含开工时用户带来的新方向）
- 分不清一个需求该归哪类时

**何时不用**：意图已登记、正在执行的 story 内部改动（走 `heartrule-story-flow`）。

## 步骤

### 第一段：意图登记

1. 把意图写成**一句话 + 价值**，登记进 `docs/scrum/backlog.md` 顶部**意图区**（表格式：`| 状态 | 意图（一句话） | 价值 | 来源 | 关联 epic |`）。
   - 拆不出 epic 的模糊意图 → 状态 `未拆`，先登记，想清楚再拆；
   - 连一句话都写不出的才留在对话里。
   - 来源：`回溯补录` / 会话日期 / 领域来源，照实标注。
2. **停下等人确认意图与价值**。

### 第二段：拆解（人确认后）

1. **需求流三分类**（§3 单一出处）：
   - 平台级 · 咨询内容类 → 直接 YAML scripts + templates 实现，无需新机制；
   - 平台级 · 功能类 → 常规 DDD 开发；
   - 引擎级 → 转 `heartrule-mechanism-flow`。
2. **epic 拆解**：组名 + 一句话，按**内聚**分组不按进度（§12 借入规则）；同一条主线上的故事放一组。
3. 写 backlog epic 分组：`### Epic X · 主线名 —— 一句话`，分组内标注 `> 来源意图：意图区「…」`；把意图区该行状态改「已拆成 epic」、回填关联 epic 列。
4. **停下等人确认 epic 划分与归类**（内聚、不重不漏）。

### 故事行格式（拆故事时用，不新造列）

`| 状态 | 类型 | 故事 | 关联 |`——状态 backlog/ready/in-progress/done；类型 `[feature]`/`[design]`/`[intelligence]`；关联列用相对链接、`·` 分隔。

## 人审门（停止点）

第一段停一次（确认意图与价值）、第二段停一次（确认 epic 划分与归类）。

## 产出物规则（§4 住所）

意图的**下一个读者是 sprint 计划**（sprint 计划从「活跃」意图选目标），住所 = backlog 意图区。

## 常见违规

| 违规                          | 纠正                                                 |
| ----------------------------- | ---------------------------------------------------- |
| 意图刚冒出就直接拆 story 开干 | 先登记意图区，人确认后再拆——"不急着拆"是 §3 的约定   |
| 把模糊意图留在对话里不登记    | 只有"连一句话都写不出"的才留对话里；写得出就进意图区 |
| 按进度分组而不是按内聚        | §12 借入规则：同一条智能主线上的故事天然一组         |

## Red Flags

- 意图区没有对应行就开始动手
- epic 分组没标注来源意图
- 意图区状态没从「未拆」改成「已拆成 epic」
